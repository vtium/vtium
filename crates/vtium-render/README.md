# vtium-render

vtium's renderer: frames from `vtium-term` in, display pixels out. This crate holds the CPU compositor (vtium/vtium#16), which ADR-1300 decides: a drawn-glyph cache, decorations as sprites, the cursor's shapes, the pointer, four orientations, damage handed to the display as clips, and the render timer. It forbids unsafe code and denies the determinism lints. It draws into anything that takes a run of pixels (`Target`), never reads it, and opens no device: the display backends are vtium/vtium#18, and the GPU path, behind a feature, is vtium/vtium#33.

## Behaviour

The C reference is the floor: its `bbulk.c`, `deco.c`, `drm2d_render.c` and `render_timer.c`. vtium keeps their flow and their per-pixel arithmetic, so that tier 2's bitmap-font goldens (vtium/vtium#17) judge it unchanged; `tests/reference.rs` and `src/deco.rs` hold it to digests of whole cells and of every sprite at 1,152 cell sizes, taken from the C reference's own code (`tests/reference/README.md`), but for the doubles and curls the quarter-cell departure below redraws. ADR-1300 records the six ways the cache and composition differ from the C reference's, none of which moves a pixel but the blank cells of the first departure below.

`draw` follows the frame contract with the displays (vtium/vtium#18): it takes the buffer the display lends and the buffer's age, 1 when it holds the last frame drawn with damage, n when it holds the frame n back, 0 when its contents are unknown. Each cell carries the serial of the frame that last changed what it shows, its cursor (place, shape and color), blink phase and wide pairing included, and a buffer at age n gets the cells that changed in the last n frames. At age 0, or at an age past the renderer's history, the buffer gets the whole picture and the border, and every other buffer's history stays as it was. Nothing assumes the buffers take turns or counts them, so a swap that failed, a third buffer and a buffer the display lost each get exactly what they lack. The frame is read since the checkpoint taken after the renderer's previous `draw`, whatever buffer that drew into.

Dim text (SGR 2) draws its foreground halfway to its background, each channel the sum of the two halved, as the C reference drew it. Dim mixes the colors reverse video left, and the cursor draws over the result: a block swaps the mix with the background. An underline or strike in the foreground's color takes the mix; SGR 58's underline color is exact. Test: `tests/dim.rs`.

Blinking text (SGR 5 and 6) draws in the text blink's off phase as `Config::blink` says, which the binary sets from `blink-text` and `blink-decorations`. `Full`, the default, draws the cell without its glyph; `Partial` draws the glyph halfway to its background with SGR 2's arithmetic, over a glyph SGR 2 already dimmed too; `Off` draws it steady, and a phase change redraws nothing. With `decorations`, the underline and strike hide with the glyph under `Full` and dim with it under `Partial`, SGR 58's color and a configured color included; without, they stay as the on phase draws them. The cell under the cursor shows in either phase. Tests: `tests/blink.rs` and `every_frame_matches_a_whole_draw_under_each_blink_option`.

The renderer draws the pointer only when `DrawState::pointer` is set, which the owner does on a display without a cursor plane; where the display drives a cursor plane, the plane shows the same arrow (`Renderer::arrow`) at the place `Renderer::pointer_at` gives, and moving the pointer involves no draw. The arrow is a cell tall, kept between 8 and `POINTER_SIDE_MAX` pixels, white on a dark outline with its hotspot at the tip, and turns with the display (`src/arrow.rs`). With `Config::pointer` naming a character (`pointer-char`), the pointer is that character's glyph from the font, one cell wide, white on the same outline, its top left on the corner of the cell under the pointer wherever in the cell the pointer is; a character the font lacks, which would draw as a fallback such as U+FFFD, and a blank one, whose glyph covers nothing, keep the arrow, and over cells so tall that the outlined glyph passes `POINTER_SIDE_MAX`, the cursor plane refuses it and the renderer draws it. Tests: `a_glyph_pointer_sits_on_the_cell_under_the_pointer`, `a_glyph_pointer_the_font_cannot_show_keeps_the_arrow`. It is blended over each run of pixels written beneath it, cells and border alike, so the cells show around it and nothing is read back. It changes the cells it covers only when it appears, moves or hides, and a cell under it that changes is drawn alone, with the arrow over it. A frame that changes nothing, pointer shown or not, writes nothing and returns no damage; the owner does not swap it, and it does not count as a frame. A change of grid size or of the default background changes every cell and the border.

## Departures

- **A full cache draws the glyph uncached.** A glyph that would evict one the frame draws, or that alone passes its pool's byte ceiling, is drawn from the font without being cached. The C reference drew such a cell blank and drew it again on the next frame (bbulk.c:1426-1432), and its GPU renderer drew blank past its hard stop (gltex.c:860-930). No specification covers a cache. The reason: a blank cell makes the cache change pixels (ADR-1300 D3). Test: `tests/cache.rs`, every frame at a cache of 1 and 7 glyphs against a cache of none.
- **A wide glyph cut at the margin shows its left half in every orientation.** On a display turned left or upside down, the C reference showed the glyph's right half in a wide cell's first column when the display held no second (aaronsb/kmscon#44, not fixed in the C fork). No specification covers turned displays. The reason: a turned display draws the unturned picture turned. That holds for the grid, not for the border around it: an odd remainder is split rounding down in the display's own coordinates in every orientation, as the C reference's goldens do, so with 5 pixels to spare a display turned upside down leaves 3 at the text's left where an unturned one leaves 2. Tests: `every_orientation_draws_the_same_picture_turned` and `a_wide_glyph_cut_at_the_margin_shows_its_left_half`.
- **A full redraw reaches each buffer once.** After a full redraw the C reference drew every cell a third time, and reported it as damage (aaronsb/kmscon#81, not fixed in the C fork). The reason: each buffer gets what its age says it lacks, and a buffer drawn whole lacks nothing. Tests: `a_full_redraw_reaches_each_buffer_once` and `buffers_at_age_0_are_each_drawn_whole_once`.
- **The pointer is an arrow over the cells.** The C reference drew the font's I in the default colors, in a cell's box centred on the pointer that hid the cells beneath it (bbulk.c:1669-1700), and marked the two by two cells its centre fell among, so at an odd cell size its moves left pixels behind (bbulk.c:1583-1613); its hardware cursor was an I-beam (terminal.c:220-301). No specification covers a pointer's shape. vtium draws an arrow, the operator's decision on vtium/vtium#92, the same in software as on the cursor plane, with its tip on the pointer's pixel kept inside the grid; its damage is every cell it covers and, where it reaches past the grid, its area clipped to the display, in which only the border is filled again; the history keeps the last 16 such areas, and a buffer older than those redraws the whole border. Tests: `the_pointer_is_an_arrow_over_the_cells`, `the_pointer_turns_with_the_display`, `the_pointer_leaves_nothing_behind_at_odd_cell_sizes`, `a_move_in_the_bottom_row_damages_only_its_cells_and_the_arrow`.
- **A keystroke damages only the cells it changes.** At 7680x2160 the C reference redrew about 70% of the screen at 20-28 flips a second while a prompt waited for typing, from a cause never found (aaronsb/kmscon#156, not fixed in the C fork). vtium's damage is the cells it draws, and a keystroke draws the cell it wrote and the cells the cursor left and entered. Test: `a_keystroke_damages_only_the_cells_it_changes`.
- **An underline takes at most a quarter of the cell.** The C reference moved a double or curly underline up into the cell as far as its band needed (deco.c's `fit`), so in an 8-pixel cell, whose letters stand on row 6, both reached rows 5 to 7 (vtium/vtium#119). No specification covers an underline's shape. vtium gives an underline at most a quarter of the cell's rows, the most the C reference let a line's thickness take (font.c:370-408). The single, dotted and dashed lines are the font's line, which a face with no metrics of its own puts in the cell's bottom rows, one row below the letters at 8 pixels. A curl lowers its wave to fit, down to the C reference's 2 rows peak to peak. A double, or a curl that still does not fit, draws as the single line. A cell 12 rows tall or more keeps the C reference's double, and its curl when at most half as wide as tall; both hold for the lines `for_height` gives, and a face with lines of its own meets the same quarter at the sizes its own thickness sets. The reason: an underline drawn over the letters hides their lower rows, and at 8 pixels the double and curl took three of the cell's eight. A strike vtium-font scales by a whole factor brings the lines of the cell it draws (vtium/vtium#124): `for_height` of the scaled height when its own lines were `for_height` of its height, and its own lines scaled otherwise. The room is the drawn cell's, so an 8-pixel strike drawn at 16 pixels draws a 16-pixel cell's double. One whose own lines scale with it, two rows thick from row 14, draws its double as the 8-pixel single line scaled, and its curl as a wave 2 rows peak to peak in rows 12 to 15, which the 8-pixel cell had no room for. The C reference's sprite digests (`tests/reference/cells.tsv`) judge every sprite but 616, which the rule redraws: the double at every width from 1 to 24 at heights 2 to 11 (240), and the curl at every width at heights 1 to 11, at widths 12 to 24 at heights 12 to 15, 16 to 24 at 16 to 19, 20 to 24 at 20 to 23, and 24 at 24 to 27 (376). At each of those, `sprites_match_the_c_reference` checks that the sprite differs from the C reference's and is the fallback: the single line, or a curl lowered to the cell's bottom quarter, as wavy, when 2 rows peak to peak and the line fit there. Tests: `every_underline_at_8_pixels_lies_in_the_bottom_row`, `no_underline_takes_more_than_a_quarter_of_the_cell`, `a_double_or_curl_with_no_room_draws_as_the_single_line`, `a_curl_lowers_its_wave_to_fit_before_it_flattens`, `a_scaled_strike_takes_the_room_of_the_cell_it_draws` and `sprites_match_the_c_reference`.

## Beyond the C reference

- **The cursor takes OSC 12's color.** A block cursor's background, and an underline or bar cursor's line, take the color OSC 12 set, and the character under a block keeps the cell's background as its color; with none set, the cell is drawn inverted as the C reference drew it, which did not parse OSC 12 (aaronsb/libtsm#22). Test: `a_colored_block_takes_its_color`.
- **The selection takes OSC 17's and 19's colors.** The frame resolves them (`vtium-term`'s README), and a selected cell draws in them; the C reference always drew the selection inverted. Test: `the_selection_draws_in_its_colors`.
- **A wide half whose partner is missing draws as one cell.** The C reference's frame always paired them; vtium's frame does not promise it, so a leading half without its trailing half, or the reverse, draws in its own cell and no frame leaves a cell undrawn.
- **The text blink has options.** `Partial`, `Off` and blinking decorations are the operator's decision on vtium/vtium#81; the C reference hid the glyph and kept the decorations (bbulk.c:1521), which the default keeps. Tests: `tests/blink.rs`.
- **A decoration color may name a palette index.** `DecoColor::Indexed` resolves through each frame's palette, as the C reference resolved its configured decoration colors on every frame (`kmscon_conf_resolve_deco`), so a program's OSC 4 recolors the decorations. Test: `a_palette_decoration_color_follows_the_palette`.
- **A 1-bit display draws in black and white** (vtium/vtium#135). With `Config::depth` at `Depth::One`, which the binary sets from `display-depth` or from what the display reports, every pixel the renderer writes is `0x000000` or `0xffffff`. Colors map to lit or unlit by cell, never by brightness, the operator's decision (2026-10-28): the default background is unlit; a cell whose background differs from it, reverse video and the selection included, is lit; its foreground and decorations are the background's opposite, and the background's own state where they equal it, so a foreground equal to its background stays invisible. Colors compare by value. Each pixel's coverage, the glyph's or a sprite's, is lit at 128 and above, the threshold the kernel's `drm_fb_xrgb8888_to_mono` gives a DRM mono panel, so a frame drawn here passes that conversion unchanged. Where #135 left the rule open, vtium chooses: a light default background is unlit too, so a light theme draws light text on black; the border is unlit; dim text (SGR 2) draws as plain text, since its half-way color is not the background; `blink-text=partial` hides the glyph in the off phase as `full` does, since the half-way glyph would never blink; a color glyph draws as its silhouette, its alpha cut at half in the cell's foreground, since its own colors would light by brightness; the pointer is drawn white with a black outline as it is in color, the outline cut to black. The C reference drew no 1-bit display. Tests: `tests/mono.rs` and `src/mono.rs`'s. The curly underline, sampled at 8 by 8 a pixel, is cut at half like any coverage: drawing vtium's own sprites as 1-bit where the cut breaks them waits on vtium/vtium#135's sprite step.
- **The two profiles, 1-bit and scale-1 storage, and the row scratch** are ADR-1300's D2, D4 and D5: memory and composition, with no pixel changed. Every run of a row's drawn cells is composed in the scratch and reaches the display a pixel line at a time, where D5 writes a cell of one layer straight, a call for each line of each cell: at 1366x768 a full frame's writes take 0.05 ms where the cell's took 0.48 ms (vtium/vtium#78).

## Not yet

- **Conceal and overline are not drawn.** A concealed cell shows its text, and an overline draws nothing. Both are vtium/vtium#37's: a concealed cell draws as its background, and an overline as a decoration beside the underline.
- **Rapid blink (SGR 6) blinks at SGR 5's rate.** ADR-1000's `sgr.rapid-blink` asks for a faster phase, which is vtium/vtium#37's; `tests/blink.rs` pins the shared phase until then.
- **`Frame::palette()` is owed.** The frame does not expose its palette, so the owner passes the default foreground and background in `DrawState`. The frame types the renderers read are vtium/vtium#10's.
- **A full frame takes about 0.5 ms.** At 1366x768 a full redraw with a warm cache measures 0.49 ms in a release build and in the minspec build alike, on one pinned core (`tests/figures.rs`), against the 0.33 ms ADR-1300 measured for its draw kernel alone over the same screen in cached memory. That kernel, the 1-bit glyph loop and its writes, takes 0.18 ms of the release figure. The rest lies outside it: reading the frame a row at a time about 0.035 ms (derived: the 0.07 ms a cell at a time took, less the 0.037 ms the whole frame dropped when the frame was read a row at a time; a 170x48 frame read alone, outside the renderer, took 0.053 ms a cell at a time and 0.027 ms a row at a time), each cell's history 0.04 ms, building the cells' jobs 0.12 ms, the glyph cache's lookups 0.04 ms, setting up each cell's composition 0.05 ms and collecting the damage 0.03 ms. The minspec build builds this crate at `opt-level = 3` (the operator's decision on vtium/vtium#78): at the profile's `opt-level = "z"` it measured 0.93 ms, the composition and the writes taking twice as long, and the binary is 6,232 B larger for it. Reaching ADR-1300's figure, or the operator revising it, is vtium/vtium#78's.

## Bounds

The frame comes from a program, the font from a file and the cell size from the configuration. Every glyph is bounded by the font's `CELL_SIDE_MAX`, a cluster by `vtium-term`'s `CLUSTER_MAX`, the cache by its budgets and the row scratch by its size.
