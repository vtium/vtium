# vtium-term

vtium's terminal state: the screen, its cells and lines, the scrollback, the modes, SGR, the character sets and the replies, applied from the actions `vtium-parse` produces; what keys, the pointer, focus and pastes send the program; and the frames a renderer reads. It forbids unsafe code and has no dependency outside the workspace. The cell, line and frame model (vtium/vtium#10, ADR-1001), the screen, scrollback, selection and Unicode tables (vtium/vtium#11), the modes, SGR, the replies and the input encoding (vtium/vtium#12), the character sets (vtium/vtium#13), OSC 52's copy-out (vtium/vtium#39), the colors a program sets, queries and resets (vtium/vtium#38), OSC 8's links and OSC 133's prompt marks (vtium/vtium#40, ADR-1002), and OSC 50's font requests (vtium/vtium#126, ADR-1200) are in place.

## Behaviour

The C reference is the floor: vtium does everything it does, and where it departs from a protocol specification, vtium follows the specification. Each departure is listed below with its reason, and with the specification it follows where one covers it. The test of each is named with it.

Text is cut into cells by UAX #29's extended grapheme clusters at the Unicode version the tables carry, or by codepoint width with mode 2027 reset. A codepoint takes no cell when its General_Category is Mn, Me, Cf or Cc (but U+00AD and Prepend characters), or it is a Hangul medial vowel or final consonant; two when its East_Asian_Width is W or F or it has Emoji_Presentation; one otherwise. A VS16 makes an emoji-style base two cells. These are the C reference's rules and tables, so tier 1's goldens judge them unchanged.

The rectangular areas, DECERA, DECSERA, DECFRA, DECCRA, DECCARA and DECRARA with DECSACE, follow xterm's ctlseqs and DEC STD 070; the C reference had none. A rectangle's corners count from the top margin in origin mode and clip to the screen, or the region, and DECCRA's page numbers name the one page. vtium differs from xterm in eight places. DECERA and DECSERA erase as ED does, to empty cells in the pen's background, where xterm wrote spaces in the pen's attributes for DECERA and kept each cell's attributes for DECSERA: the reason is that a rectangle erase and ED leave the same cell. DECCARA in the rectangle extent gives an empty cell the attributes and leaves it empty, where xterm wrote a space into it; the two draw the same, and a selection copies no space the program never wrote. DECCARA takes every SGR parameter as SGR applies it to the pen, kitty's extension (`deccara`), so its 0 also returns the colors to their defaults, where xterm's 0 resets bold, underline, blink and inverse; an omitted attribute parameter of DECCARA or DECRARA is 0, as an omitted SGR parameter is, where xterm ignores it. DECFRA refuses a character two cells wide, which xterm writes into each cell. A wide character a rectangle's edge cuts goes whole, as one an edit cuts does, which xterm also does for DECFRA, DECERA and DECSERA, clearing both halves; DECCARA and DECRARA change it whole, and DECCRA's source edge brings an empty cell in its style, where xterm changed or copied half of it. In the stream extent DECCARA and DECRARA skip every empty cell, those ECH, EL 1 or DECERA emptied in the middle of a line among them, where xterm marks an erased cell as drawn and changes it; vtium's cell keeps no drawn mark apart from its content. DECERA, DECSERA, DECFRA and DECCRA end wraps where xterm's keep them, as the wrap rules below list. DECRQSS reports DECSACE's stream as 0, whatever value other than 2 selected it, where xterm reports the value as set. Tests: `tests/rect.rs`, and `decrqss_reports_decsca_and_decsace`.

The modes and controls ADR-1000 adds beyond the C reference (vtium/vtium#54), which the C reference lacked, follow xterm's ctlseqs and xterm's own code, and each row's spec column in `docs/modes.md` gives its rule. Mode 45 reverse-wraps BS and CUB only into a row that printing wrapped from, as xterm's `CursorBack` does, and never past the screen's first row. Mode 66, DECNKM, holds the state DECKPAM and DECKPNM set. Mode 1007 starts set, as foot and Ghostty start it, where xterm starts it reset. Mode 1015 is one of the three encodings, one set at a time as xterm keeps them. Modes 1034 and 1036 choose what Alt sends as xterm's `Input` does, both starting set, so Alt puts ESC before a key as the C reference sent it. Mode 1035 starts set, as xterm's `numLock` resource does, and changes only how NumLock reads, since vtium has one Alt modifier. Mode 1042 is xterm's bellIsUrgent, and vtium has no window to mark urgent, so while the mode is set a BEL reaches the host, and while it is reset vtium ignores BEL; it starts set, so BEL rings as the C reference rang it. XTSAVE and XTRESTORE keep one saved state for each group of modes that share a state, as xterm's `savemodes` does: tracking modes 1000 to 1003 share one and mode 9 has its own, the encodings share one, and the alternate screen modes share one. An empty list saves and restores every mode free of side effects, as kitty's misc-protocol has it and the maintainer ruled: every supported DEC private mode but DECOM, the alternate screen modes 47, 1047 and 1049, 1048 and 2026, and no ANSI mode, so its restore never moves the cursor or switches the screen. XTRESTORE of a mode nothing was saved for leaves the mode as it is, where xterm restores from a saved value that starts at zero. DECSTR keeps what XTSAVE saved and XTSHIFTESCAPE, as xterm and Ghostty do; RIS clears both, listed under Departures. DECALN follows xterm's `CASE_DECALN`: origin mode off, the margins the whole screen, every line single size, every cell an E in the default style, the cursor home, and the pen keeping its colors and DECSCA's protection, as xterm's `resetRendition` keeps them, and losing its other attributes and its underline color, which xterm does not have and Ghostty drops. Tests: the mode rows' tests in `tests/modes.rs`, `xtrestore_restores_each_mode_xtsave_saved`, `xtsave_keeps_one_state_for_modes_that_share_one`, `the_empty_list_saves_and_restores_every_mode`, `the_empty_list_leaves_the_cursor_and_the_screen_alone`, `xtshiftescape_says_whether_shift_reaches_the_mouse_reports`, `decaln_fills_the_screen_with_e_and_resets_the_margins_and_cursor`, `decaln_returns_a_double_width_line_to_single_size`.

The `images` feature carries the image pipeline (ADR-1100); the default build, minspec, carries no image code: its input call, dispatch and screen events hold no image hook. With it, the screen holds one image store (`vtium-image`) for its main and alternate screens, tells it of every write, erase, rectangle operation, ICH and DCH, scroll, IL and DL, line the scrollback drops, ED 2 and ED 3, alternate screen switch, RIS and rewrap, with the `LineId` of each line as the store's key, and marks the cells under each box the store reports changed (ADR-1001). The frame carries the view's placements in draw order, each with its image's pixels shared. The terminal routes DCS `q`, APC strings starting with `G` and a complete OSC `1337;File=` to the handler installed for each, while its protocol is switched on; no handler is installed by default, and vtium-image's sixel handler and the kitty graphics handler (vtium/vtium#49) are installed by the host. Sixel is offered while it is switched on, its handler is installed and the budget is above 0: then DA1 reports attribute 4, the mode table's rows 80 (DECSDM), 1070 (private sixel color registers) and 8452 (sixel cursor to the right) report their state, and XTSMGRAPHICS (`CSI ? Pi ; Pa ; Pv S`) reads, sets and resets the color register count and reads the geometry, `max-graphic-size`. While sixel is not offered, the three rows report their fixed state and XTSMGRAPHICS answers status 1 for every item; a build without images has no row for them, so DECRQM answers 0, and answers XTSMGRAPHICS status 1 too (ADR-1100, D10). Tests: `tests/sixel.rs`. While a handler's request to the image helper is out, the input call takes nothing, so a later string cannot land before an earlier image, and an input call stops once its image work reaches `INPUT_WORK_MAX`, right after the byte that passed the bound: a handler takes only as much of a run of DCS data as the work left allows (vtium-parse's `Consumer::dcs_put_run`, vtium-image's `Handler::feed_some`), and the rest of the run comes in the next call. While a handler holds an upload in chunks open between its strings (vtium-image's `Handler::upload_open`), any other output the terminal takes, text, a control, or another escape sequence or string, makes the handler drop it (`Handler::interrupt`); the terminator that ends a string, `ESC \` or an 8-bit ST, is no other output. `Terminal::session_ended`, which the host calls when the program in the console exits, drops it too, and so does RIS. vtium-image's README lists this as a departure from kitty, which keeps the upload open. Tests: `tests/kitty.rs`. The image replies are written under one query, which the reply rule's test sends hostile text through with a stand-in kitty handler. Tests: `tests/images.rs`, and the store's own in `vtium-image`.

**Notes for the log.** With the `images` feature, a handler that drops or ignores what a program sent says why in a fixed phrase through vtium-image's `Context::note`, with a `Cause` that says who can act on it. `Cause::Program` marks a string that breaks its protocol, such as an iTerm2 picture without `inline=1`, a sixel picture with no size, or a kitty upload's data past the pixels `s` and `v` call for, which the kitty handler ignores and answers OK; only the program's author can act on these. `Cause::Console` marks a picture the program sent as its protocol asks that the console refused: a setting, one of vtium's bounds, the image budget, memory, or the image helper, missing or failing. Such a picture never draws, and the operator can act on why, so the kitty handler notes these refusals even when the program asked for no answer with `q=2` or no id. When the program that made a request has gone, the host drops the request with `Terminal::abandon_image_request`: the handler that asked is cancelled, and nothing is answered or noted, since the helper did not fail. The terminal counts each protocol, cause and reason, and keeps a note (`ImageNote`: the protocol, the cause, the reason and the count so far) the first time one comes and again each time its count reaches 10, 100, 1,000 and so on. The host takes the notes with `Terminal::take_image_notes` and writes them to its log; vtium writes a program's note at debug level and a console's at info level, which it shows by default. A program that sends the same bad picture every frame therefore costs the log seven lines in its first million pictures. RIS keeps the counts, so a program cannot start them again. The terminal counts at most `IMAGE_NOTE_REASONS_MAX` reasons and keeps at most `IMAGE_NOTE_BYTES_MAX` bytes of each. The C reference logged each sixel picture it did not store or place, and each kitty upload's bytes past `s` and `v`, at debug level every time (libtsm `eeaf293`, `src/tsm/tsm-vte-image.c:161-171`, `src/tsm/tsm-kitty.c:806-826`), so an operator whose pictures never drew found nothing in the default log. Tests: `a_handlers_note_reaches_the_host_once_with_its_protocol`, `a_reason_that_repeats_reaches_the_host_at_each_power_of_ten`, `each_protocol_and_reason_is_counted_on_its_own`, `the_notes_hold_a_bounded_count_of_reasons_and_bytes`, `a_dropped_picture_is_noted_for_the_log` and `a_picture_the_store_refuses_a_place_is_noted_for_the_log` (`tests/sixel.rs`), and `data_past_the_pixels_is_noted_for_the_log_and_answered_ok`, `a_picture_the_budget_refuses_is_noted_even_unanswered`, `a_failing_helper_is_noted_and_an_abandoned_request_is_not` and `a_picture_past_vtiums_bounds_is_noted` (`tests/kitty.rs`).

The C reference's cluster table took a hash seed from the system's entropy, and logged nothing when it fell back (aaronsb/libtsm#41). vtium keeps each line's clusters in the line's own arena (ADR-1001), so there is no shared table, no hash and no seed: the item has no counterpart.

### Kitty's Unicode placeholders

With the `images` feature, vtium-term reads kitty's Unicode placeholder cells (ADR-1100, D13). A placeholder cell is a cell whose text is U+10EEEE followed by up to three marks from the kitty spec's list of 297 row and column diacritics: the first mark's place in the list is the cell's row in the picture, the second its column, and the third the top byte of the image id. The cell's foreground color gives the image id's low 24 bits, a palette index or a direct color's 24-bit value, and its underline color gives the placement id the same way; the default foreground, or an image id of 0, names no image, and the default underline color names no placement. A cell that leaves marks out takes them from the placeholder cell to its left, when that cell has the same foreground and underline colors: with no mark, its row, its column plus one and its top byte; with only a row, on the same picture row, its column plus one and its top byte; with a row and a column, on the same picture row and in the column before, its top byte. A value no rule gives is 0. A mark that is not one of the 297 ends the cell's marks, and a third mark past 255 gives no top byte.

vtium-term groups the placeholder cells of each row into runs: side-by-side cells that name the same image id and placement id, lie on the same picture row and show consecutive picture columns. A run is the line's key, its first column, its cell count, the 32-bit image id, the placement id and the picture row and column of its first cell (vtium-image's `PlaceholderRun`, which vtium-term re-exports). vtium-term keeps no runs: `Screen::placeholder_runs` reads them from the rows the view shows, for a frame; `Screen::screen_placeholder_runs` from the screen's own lines of a buffer, for a store decision that needs a virtual placement's position; and `Screen::mark_placeholders` marks changed the placeholder cells of one image on the screen's own lines, for damage. The last two count the cells they read as input work. A write, an erase, a scroll or a rewrap moves the cells as text, and the next read finds them where they are, so a picture row that a rewrap splits over two rows is two runs. A cell that leaves its marks out inherits from the last cell of the row before when that row soft-wrapped into its own, so the second piece of a split picture row keeps counting columns from the first; a hard line break restarts the count. A read that starts at the top of the screen or of the view first walks back through the rows above it that soft-wrapped and end in a placeholder cell, at most as many as a picture row of 297 cells fills, so a row that wrapped down from the scrollback keeps its columns; `screen_placeholder_runs` counts those cells as work too.

A frame resolves a placeholder cell's colors with the default foreground and no underline color, since those colors name its image and its placement. Under SGR 7, DECSCNM or a selection drawn by swapping, the cell therefore takes the colors a space with the same background and attributes takes, and never the color that encodes its image id. The cell keeps its glyph, by which vtium-render draws no text, underline or strike-through there. A build without images resolves U+10EEEE's colors as any private-use character's.

vtium-term hands the image store the runs at three times. `Screen::placements` builds the frame with the runs on the rows the view shows (`Store::frame_with_runs`), so a virtual placement draws its slice of picture under each run, and the picture moves with its cells; it reads them only while the shown buffer holds a virtual placement (`Store::has_virtual`). For the store's decisions, vtium-term reads the runs from the screen lines of each buffer that holds a child of a virtual placement (`Store::has_virtual_children`), and only then. It reads them for every call that reaches the store through `Screen::with_images`: every kitty command and every picture a protocol handler stores, and `Screen::add_image` and `Screen::place_image`. The store then holds them through the call (`Store::with_runs`), and the decisions that take such a child by the cells it draws on use them: a kitty delete by cell, row or column or of every placement, and a reservation that may evict. vtium-term cannot tell those calls from the others, such as a transmission that evicts nothing, because a handler reaches the store through one call, so it reads the runs for each. ED 2 reads only the screen in use, before its erase removes the cells, and runs its rule inside `Store::with_runs` the same way. After each store call, vtium-term marks the placeholder cells of every image whose virtual placement the store reports changed (`Store::take_changed_virtual`), through one read of the screen.

Tests: `tests/placeholders.rs`, `tests/placeholder_pictures.rs`, `a_placeholder_cell_takes_a_blank_cells_colors_under_reverse_video`, `every_diacritic_is_an_above_mark_in_the_pinned_ucd` and `the_table_is_ghosttys_list_entry_for_entry`.

## Departures

- **DL at the screen's first row clips the placements on the lines it deletes.** In a build with images, the lines DL deletes go, and so does what is anchored on them, as at any other row. The C reference took a DL at the first row of a screen with a scrollback for a scroll into the scrollback, so a placement on a deleted line moved with that line, which it reused, to the region's bottom. No specification covers it; the kitty spec has a placement wholly inside a scrolled band clipped at its edges. Test: `dl_at_the_first_row_clips_what_it_deletes`.

- **Cells past a line's end read in the line's fill, never the pen.** A scrollback line narrower than the screen is padded, when drawn, with empty cells in its fill: the default style, unless the program erased the line's end in a color (ADR-1003). The C reference drew them with the current pen, so an SGR under BCE recolored them with no change age moving (aaronsb/libtsm#47). No specification covers padding. The reason: padding is not text the program wrote, so the pen has no claim on it, and a pen change that moved no age left a display drawing stale colors. Tests: `cells_past_the_end_read_blank_in_the_default_style` and `trim_keeps_the_fill_as_the_style_past_the_end` (the line), `a_pen_change_while_scrolled_back_leaves_the_padding_alone` (the screen).
- **A width change rewraps the main screen and its scrollback (ADR-1003, vtium/vtium#41).** Rows a wrap joined become one logical line and wrap at the new width; a line the program ended with a newline, or placed by moving the cursor, joins nothing. A wide character that no longer fits moves whole to the next row and leaves a pad, and on a screen one column wide becomes an empty cell. The cursor, the main screen's saved cursor, the selection and the view keep their place in the text, and the rows below the cursor keep their number less what the text above it grew, as Ghostty keeps them. The C reference rewrapped nothing: it grew every line to the wider width, never shrank one, and clamped the cursor's column (aaronsb/libtsm#28). Spec: contour's line reflow mode, mode 2028, whose rows printed while it is reset are cut instead. Tests: `tests/reflow.rs`, among them `a_wrapped_line_rejoins_when_the_screen_widens` (the probe `reflow`), `the_cursor_keeps_its_place_in_the_text` and the three property tests.
- **No row keeps a cell past the right margin.** The alternate screen, rows printed with mode 2028 reset and rows of double size are cut at a narrower width and never rewrapped; the main screen wraps its text onto extra rows instead. The C reference kept every cell past a narrower margin, so a widening showed stale text again (aaronsb/libtsm#19). No specification covers a resize's cells; the reason: a hidden cell reappearing is text the screen no longer shows, and a full-screen program redraws on SIGWINCH. With no parameters, or one omitted, the pop restores every part of the pen SGR sets; each parameter otherwise names a part by its SGR code, 1 bold, 2 faint, 3 italic, 4 underlined, 5 blink, 7 inverse, 8 invisible, 9 crossed-out, 21 doubly underlined, 30 the foreground and 31 the background, with xterm's older 10 and 11 for 30 and 31, and a code it does not list names nothing, as in xterm 412 (`charproc.c`, `CASE_XTERM_PUSH_SGR`). vtium holds the underline's style and color (SGR 58) as one part, which 4 and 21 both name; blink takes rapid blink with it, as SGR 25 clears both; the overline and the script, which the list does not name, return only with every part; DECSCA's protection is not SGR's and stays, as with SGR 0. The stack keeps `SGR_STACK_MAX` pens; a push past it keeps nothing and is counted, and the pop that pairs with it restores nothing, as xterm's `xtermPushSGR` and `xtermPopSGR` do (`misc.c`). A pop of an empty stack does nothing. Tests: `tests/stacks.rs`, `a_pop_leaves_the_protection`, `the_parts_xterm_does_not_list_return_with_every_part`.
- **XTPUSHCOLORS, XTPOPCOLORS and XTREPORTCOLORS keep palettes on a stack, which kitty's OSC 30001 and 30101 push and pop.** The C reference ignored the three CSI functions and dropped both OSC strings. Spec: ctlseqs, XTPUSHCOLORS, XTPOPCOLORS and XTREPORTCOLORS; kitty's `color-stack`. An entry holds all of `Terminal::palette()`: the 256 colors, the defaults, and the cursor's, pointer's and selection's colors. `CSI # P` stores the palette in the entry after the current one and `CSI # Q` restores it from the current one; a parameter of 1 to `COLOR_STACK_MAX` stores into or restores from that entry, which becomes the current one or, for a pop, the one after it; 0 pushes and pops, as ctlseqs says, where xterm 412 stored an explicit 0 and then made the stack empty (`xtermPushColors`, `misc.c`); several parameters act in turn. A push with the stack full, a parameter past the bound, a pop of an empty stack and a pop of an entry never stored do nothing, as in xterm. A pop that changes a color marks every cell changed. `CSI # R` answers `CSI ? Pc ; Ps # Q`, the current entry and the entries stored, the highest that holds a palette, as ctlseqs words it and foot answers (foot's `csi.c` at `152487e`, MIT); xterm 412 answered with the most entries a push without a parameter had reached, so an entry stored by number was left out. OSC 30001 and 30101, each with nothing after the number, push and pop the same stack as `CSI # P` and `CSI # Q`: kitty takes xterm's functions too and documents neither a depth nor two stacks. Tests: `tests/stacks.rs`, `no_reply_carries_the_requests_bytes`.
- **A color push with the stack full keeps nothing, where kitty drops the oldest entry.** kitty 0.49.2, run as a program and driven through its pty, kept the newest 10 of 11 pushes, by XTPUSHCOLORS and OSC 30001 alike, so its tenth pop restored the second push's palette; it reported `CSI ? 9 ; 10 # Q` after the pushes and `CSI ? 0 ; 0 # Q` once the pops emptied it. vtium keeps the first 10, as xterm 412 does (`xtermPushColors`, `misc.c`), so its tenth pop restores the first push's palette, the stack reports `CSI ? 10 ; 10 # Q` and then `CSI ? 0 ; 10 # Q`, and the pops still pair with the pushes the stack kept. kitty's `color-stack` documents neither. Test: `a_push_past_the_color_bound_keeps_nothing`.
- **RIS empties the SGR and color stacks, and DECSTR keeps them.** xterm 412 kept both stacks through RIS and DECSTR (`ReallyReset`, `charproc.c`); foot empties its color stack on RIS and keeps it on DECSTR (`term_reset` in foot's `terminal.c` at `152487e`). RIS returns the terminal to its initial state, which holds no pushed pens or palettes. Test: `ris_empties_the_stacks_and_decstr_keeps_them`.
- **OSC 52 sets the selection, and its query gets no reply.** The C reference dropped OSC 52 (`kmscon/src/terminal.c`, `osc_event`). A set reaches the host through `Terminal::take_clipboard_write`, decoded, and the query is refused (ADR-1000, osc.52.read): the operator's decisions in vtium/vtium#39. Spec: ctlseqs, OSC 52, with three differences. Data that is not base64 is dropped where ctlseqs clears the selection, as RFC 4648, 3.3 has a decoder "reject the encoded data"; the decoding is strict but for the padding, which may be left off, as Ghostty takes it. `c`, `p`, `s` and the empty list, ctlseqs's `s 0`, set vtium's one selection, and `q` and the cut buffers `0` to `7`, which name none of vtium's, set nothing; xterm sets each it has. A set past `CLIPBOARD_MAX`, or one the parser truncated, is dropped whole. Tests: `tests/clipboard.rs`, and `a_truncated_osc_52_sets_nothing` in `src/terminal/clipboard.rs`.
- **OSC 50 asks for a font set, and its query names the one in use.** The C reference had no OSC 50. A name reaches the host through `Terminal::take_font_request`, and the query, `OSC 50 ; ?`, is answered `OSC 50 ; NAME`, ended as it was asked, with the set the host named with `set_font_name`, never the name asked for; until the host turns them on with `set_font_ops`, both are ignored (ADR-1200 D5). The input call returns after a set asked for, so the host switches before a query that follows is answered. Spec: ctlseqs, OSC 50, and xterm's `allowFontOps`, with three differences. A Pt starting with `#`, xterm's font menu, absolute, relative and its query, is ignored: vtium has no menu. The query is answered only while font operations are on, as the set is. Tests: `tests/font.rs`.
- **OSC 8 links the cells printed while a link is open, and the link store holds each distinct link once.** The C reference dropped OSC 8: libtsm kept at most 127 bytes of an OSC string and kmscon's host took only its own two (`kmscon/src/terminal.c`, `osc_event`). Spec: Egmont Koblinger's "Hyperlinks in terminal emulators", with ADR-1002's bounds and one difference. A URI is 1 to 2,083 bytes and an id 1 to 250, VTE's and iTerm2's limits; a URI past its bound, with a byte outside 0x21 to 0x7E or with no RFC 3986 scheme closes the open link, and an id past its bound is ignored. The specification allows the space, 0x20, which vtium refuses, as a URI percent-encodes it: with every byte printable ASCII, the overlay that shows a URI shows what a copy carries. A link with the same id and URI takes the store's entry again; past `LINKS_BYTES_MAX` the store sweeps (Bounds). RIS and a switch of screens end the open link, as VTE ends it, and erased cells take none. Tests: `tests/links.rs`.
- **OSC 133 marks a prompt, its input and its output on their lines.** The C reference dropped OSC 133 (`kmscon/src/terminal.c`, `osc_event`). Spec: the semantic prompts proposal (FinalTerm's sequences). A and N do a fresh line, a carriage return and a line feed when the cursor is not in the first column, and mark the cursor's line a prompt; L does the fresh line alone; B and I mark the input, C the output; P, D and the options are taken and change nothing, and D's exit status is not kept. kitty and foot mark A where the cursor is, with no fresh line. ED 2, ED 3 and RIS clear the marks of the lines they erase, and EL and the partial erases keep them, since shells redraw a prompt with them. A rewrap gives a rejoined line the marks of all its rows (ADR-1003). Tests: `tests/marks.rs`.
- **DECSCA sets the protection DECSED, DECSEL and DECSERA leave.** The C reference honoured a protect flag in DECSED and DECSEL that nothing set, and ignored `CSI Ps " q`. Spec: ctlseqs, DECSCA: 1 protects, 0, 2 and the default do not; SGR 0 keeps it, DECSTR and RIS end it, as in xterm. Test: `decsca_protects_printed_cells_from_decsed_and_decsel`.
- **A key's character in 7-bit input is `?` past 0x7F.** The C reference tested bit 7 alone, so U+0100 sent NUL. Spec: none covers it; the reason: a 7-bit program cannot read the character, and NUL is not what was typed. Test: `decscl_resets_and_sets_the_input`.
- **Mode 2031 reports a change between dark and light, and nothing as it is set.** contour's color palette update notifications send `CSI ? 997 ; Ps n` on each update of the palette. vtium sends it only when the default background crosses between dark and light, by OSC 11, 111 or 21, a color stack pop or the configured palette, since the report carries only that; a palette color, the foreground or a background of the same scheme sends nothing. Dark is a luma below half, Y = 0.299 R + 0.587 G + 0.114 B (ITU-R BT.601), the rule neovim applies to OSC 11's answer; contour's spec and foot(7) give none. The C reference had no mode 2031. Tests: `mode_2031_reports_a_change_of_scheme`, `a_color_stack_pop_reports_a_change_of_scheme`, `the_scheme_query_answers_by_the_backgrounds_luma`.
- **The Linux console's blank sequences reach the host.** `CSI 9 ; n ]` hands the host a blank timeout of n minutes, at most 60 as the Linux console caps it, with 0 or none turning blanking off, and a wake, as the Linux console woke the screen as it set the timeout; `CSI 13 ]` hands it a wake, and RIS the host's own timeout again (`Terminal::take_blank_request`). `CSI 14 ; n ]`, the VESA powerdown interval, is ignored, since vtium has one DPMS step (the operator's decision on vtium/vtium#79). The C reference parsed the three and did nothing. Spec: console_codes(4). Tests: `tests/blank.rs`.
- **The scrollback holds at most `sb-memory` bytes as well as `sb-size` lines,** and drops its oldest lines past either. Each line costs its struct and its heap, waiting or rewrapped; a line that alone passes the budget does not enter. The C reference capped it by lines alone (`libtsm/src/tsm/tsm-screen.c:291`, `kmscon/src/config.c:1371`). No specification covers a scrollback's size. The reason: the program sizes the lines, so a count of them bounds no memory. A row whose every cell has its own style, link and cluster, concentrated by a rewrap, costs up to 7,560 bytes at 170 columns, and up to 10,450 in a build with images, where a kitty placeholder cluster of 17 bytes may fill each cell its budget leaves; 1,000 of them pass the minspec peak. When the configuration does not set `sb-memory`, the budget follows the grid: it is what the 16 MiB minspec peak leaves after the rest of the process (`MINSPEC_REST`), the two screens with every row at its worst (`screens_bytes_max`, each row at `Line::bytes_max`) and a full link store, rounded down to 64 KiB (`sb_memory_default`), and each resize works it out again from the rows the screens hold, dropping the oldest lines past it. A grid larger than the 170 by 48 minspec grid keeps that grid's value, 5,242,880 bytes, or 4,653,056 in a build with images, and never less: its console uses more memory than the minspec peak by design, and the default does not grow with the display or the machine, so a user on a capable machine who wants a deeper scrollback raises `sb-memory`. At the minspec grid the default holds about 693 such rows (445 with images) while 1,000 full-width shell lines take about 29% of it (33% with images), and at 80 by 30 and smaller it holds 1,000 of the worst rows. `sb-memory` sets a fixed budget, fenced from `SB_MEMORY_MIN` to the lesser of `SB_MEMORY_MAX` and a quarter of the machine's memory (`sb_memory`), and `sb-size` can only lower what it allows. Tests: `the_scrollback_drops_its_oldest_lines_past_its_byte_budget`, `the_byte_budget_drops_hostile_lines_and_keeps_a_thousand_plain_ones` (`tests/flood.rs`), `the_byte_budget_holds_through_resizes_and_its_count_is_exact` (`tests/reflow.rs`) and `the_worst_default_scrollback_fits_the_minspec_peak` and `the_scrollback_budget_follows_the_grid` (`tests/memory.rs`).

- **RIS clears what XTSAVE saved and returns XTSHIFTESCAPE to 0, and DECSTR keeps both.** The C reference had neither control. xterm keeps both through RIS and DECSTR (`ReallyReset` in xterm's `charproc.c` touches neither); vtium splits them as Ghostty does, the maintainer's ruling recorded in ADR-1000. The reason: RIS returns the terminal to its initial state, which holds no saved modes. Tests: `decstr_keeps_what_xtsave_saved_and_ris_clears_it`, `xtshiftescape_says_whether_shift_reaches_the_mouse_reports`.
- **A line keeps 6 bytes of clusters a cell (ADR-1001's cluster budget),** so on a screen one column wide a heart and VS16, 7 bytes with its length byte, keep the heart; the C reference kept both. This moves the golden of the conformance case `insert-wide-one-column`. A row cut to fewer cells, or landing on a screen narrower than the width its clusters were written at, keeps the clusters that printing it at the narrower width keeps, so a family emoji of five codepoints narrowed from 5 columns to 3 keeps its first four. A row that lands on a screen as wide or wider, where a widening has gathered onto it the clusters of parts of three source rows, keeps with the same cut the clusters that fit twice its budget, its arena's limit; the scrollback keeps every cluster of each row that rewraps. The C reference kept every cluster through a resize, since its lines only grew and its clusters lived in one table for the screen (`libtsm/src/tsm/tsm-screen.c:238-260`). No specification bounds a cluster; the reason: a program cannot grow a line's memory past its budget. In a build with images, the departure does not cover a kitty placeholder cluster, which keeps its first three marks outside the budget, as the C reference kept them (ADR-1001, "Placeholder cells"). Tests: `the_cluster_budget_cuts_a_cluster_on_a_one_column_line`, `a_placeholder_keeps_three_marks_whatever_the_budget`, `a_row_narrowed_past_its_budget_keeps_what_printing_there_keeps`, `a_screen_narrowed_from_a_wide_grid_holds_its_rows_to_their_bound`, `a_screen_widened_by_a_fraction_holds_its_rows_to_their_bound`.

## Bounds

The byte stream comes from an untrusted program, so nothing it sends grows memory without a bound. A screen is at most `COLUMNS_MAX` by `ROWS_MAX`, and its size comes from the display and the font. Every path that writes, moves or erases cells gives back the cluster bytes it drops through the line, so a line's arena keeps its budget on each of them (`tests/flood.rs`). A rectangle operation is linear in the rectangle's cells, and DECCRA holds one source line at a time. REP prints at most `PARAM_VALUE_CAP` copies (vtium-parse), as printed text does. The replies and input reports waiting for the host take at most `REPLIES_PENDING_MAX` bytes, and the replies of the byte that reaches the bound, before the input call returns for the host to take them; at the bound the input call takes nothing. An OSC 4 list, which one string at vtium-parse's `OSC_MAX` can hold a quarter of a million queries in, skips its queries past the bound and still applies its sets, so what a string sets does not depend on when the host took the replies; OSC 21's one reply skips the queries past the bound the same way. A color specification is read at most four hex digits a channel, into a color of 3 bytes. XTVERSION's text is at most `VERSION_MAX` bytes; XTGETTCAP's table holds at most `TERMCAP_ENTRIES_MAX` names of `TERMCAP_NAME_MAX` bytes and values of `TERMCAP_VALUE_MAX`, and one request is answered for `XTGETTCAP_NAMES` names in a reply of at most `XTGETTCAP_REPLY_MAX` bytes. DECRQSS keeps the request's first two bytes, as long as any it answers, and a longer one gets the error form. A line's style and link tables hold at most twice its cells before they compact, so a program that writes a new style or link into every cell, over and over, never grows them past that. A grapheme cluster keeps at most `CLUSTER_MAX` codepoints, and the clusters a line's cells name take at most `CLUSTER_BYTES_PER_CELL` bytes a cell of the width the line was written at, with the arena compacting at twice that; a line trimmed for the scrollback keeps what its cells name. In a build with images, a cluster that starts with U+10EEEE, the kitty graphics protocol's Unicode placeholder, sits outside that budget: it keeps the placeholder and its first `PLACEHOLDER_MARKS` codepoints, at most 17 bytes, wherever it starts in its line, and the line counts the cells that name one and compacts its arena at twice its budget and 17 bytes for each of them (ADR-1001, "Placeholder cells"), so a row that `write` fills holds at most `Line::bytes_max`, 128 + 90 bytes a cell: 15,428 bytes at 170 columns, where a build without images holds 128 + 56, 9,648 bytes. A rewrap moves each cluster with its cell, so a rewrapped row may name more than its own cells' budget: a logical line of `n` rows names at most the budget of `2n + 1` rows of the widest screen, and the scrollback and the screen together at most twice the widest screen's budget a row and what a last row's few cells hold past 6 bytes each, `CLUSTER_MAX` bounding a cell: 3,012 bytes a row at 170 columns, 2.95 times the 1,020 ADR-1001 took, and with images placeholder clusters add up to 17 bytes for each cell of the widest screen, 5,902 bytes a row in all. ADR-1001's worst case grows to 7,560 bytes a row, 10,450 with images: 7.21 MiB at 1,000 rows and 720.98 MiB at 100,000 rows, 9.97 MiB and 996.59 MiB with images (`tests/flood.rs` derives each figure and holds the scrollback to it; its shapes reach about 1.4 times the budget a row on average). Damage tracks at most `COLUMNS_MAX` by `ROWS_MAX` positions, and the scrollback keeps at most `sb-size` rows at the current width, a narrowing past it dropping the oldest for good, capped by default by the machine's memory or by a configured cap, at most `SB_SIZE_MAX`: the screen is made with the cap `sb_size_cap` gives, and clamps `sb-size` to it. It keeps at most `sb-memory` bytes too, `SB_MEMORY_DEFAULT` unless the configuration sets it inside its fence (Departures); a rewrap that the view or a drop reaches, whose rows may cost more than they did waiting, drops the oldest past it as a new line does. The selection an OSC 52 sets waits for the host at most `CLIPBOARD_MAX` bytes, decoded, one set at a time, and a set past it is checked by its length before anything is decoded or allocated. XTPUSHSGR keeps at most `SGR_STACK_MAX` pens and counts the pushes past it, and the color stack at most `COLOR_STACK_MAX` palettes (`tests/stacks.rs` floods both). The link store holds each distinct OSC 8 link once, charged its id and URI bytes and 64, at most `LINKS_BYTES_MAX` in all, and its heap stays at or under its charge (`the_stores_heap_stays_at_or_under_its_charge`). An open that would pass the bound sweeps it: every line's link table on both screens and in the scrollback, and the hovered link, are read once, and the links no line names are freed. With less than a quarter of the bound then free, the scrollback's oldest lines lose their links until a quarter is; when the screens alone hold the bound, the open is refused and the text prints unlinked. A sweep is linear in the lines held and runs at most once per quarter of the bound of links opened, added or refused, so an open that comes sooner and does not fit is refused unswept (`refused_opens_sweep_once_per_quarter_of_the_bound`); it runs only on a byte from the stream, so the store follows the bytes, fed whole or in pieces (`tests/links.rs`). With the store full, the two screens at their worst and every scrollback row at 7,560 bytes, the worst default scrollback at the minspec grid comes to 16,776,192 bytes (16.00 MiB) against the 16 MiB minspec peak, the byte budget keeping 693 of the 1,000 lines; with images, at 10,450 bytes a row, it comes to 16,741,248 bytes (15.97 MiB), keeping 445 (`the_worst_default_scrollback_fits_the_minspec_peak`).

## Reflow cost

A resize that changes the width rewraps at once the screen, the main screen's rows below it, the newest scrollback rows that could reach the screen, and every row from the view's top or the selection's start down to the screen. Of a logical line with no wide character, which breaks at multiples of the width, it takes only the newest rows it needs, and the line's head waits. It counts the rest of the scrollback at the new width from each line's length, since each line keeps a mark that it may hold a wide character, laying out cell by cell only a long line with one. The rest waits and rewraps when the view, a drop past `sb-size`, a taller screen or the newest line's wrap reaches it, or `Screen::rewrap_scrollback`; a drop cuts a long line with no wide character by length, unrewrapped. The result equals rewrapping everything at each resize, which `reflow_is_the_same_chunked_and_lazy_or_eager` holds over random streams, resizes, view moves and selections. In a build with images, a waiting logical line that an image placement is anchored on never waits at an older width: each resize rewraps it at once and carries its anchors, and a placement that a drop moves onto a waiting line has that line rewrapped first. A rewrap keeps an anchor past a row's text inside the row, so carrying it through each width in turn can land it in another column than carrying it once; this way it lands where rewrapping at each resize puts it. The rewrapping a resize does for anchors costs the anchored lines, not the scrollback's depth, but the resize still walks every waiting row to count the rows it takes at the new width. `tests/images_reflow.rs` holds it against an eager terminal and one that takes the whole scrollback at each resize. Past `sb-memory` the lines dropped follow what the rows cost as held, waiting or rewrapped, so there a lazy rewrap and an eager one may keep a different number of the oldest lines; the byte count stays exact and inside the budget either way (`the_byte_budget_holds_through_resizes_and_its_count_is_exact`). A resize to one column, where a wide character becomes an empty cell, rewraps the whole scrollback at once, and a waiting row that never rewraps is cut at each narrowing, so a row that waited loses what one rewrapped at each resize loses. A rewrap consumes each row as it builds the new ones, so it holds a row or two beyond its result.

Measured by `reflow_cost` (`cargo test --release -p vtium-term --test reflow reflow_cost -- --ignored --nocapture`) on the development machine, a Ryzen 9 9950X3D, 2026-10-28, with 100,000 scrollback rows (10,000 for a style a cell) behind a screen of 170 by 48, resizing to 169, back to 170 and to 100 columns:

| Scrollback | The resize | The rest of the scrollback | In all, a cell | Heap before and after |
|---|---|---|---|---|
| Full rows wrapped in pairs | 2.0-3.1 ms | 51-56 ms | 3.1-5.2 ns | 136 MB, 68 MB |
| One logical line spanning it | 1.8-2.5 ms | 41-69 ms | 2.6-4.2 ns | 136 MB, 80 MB |
| A shell's lines of 40 cells | 0.6-1.1 ms | 2.5 ms | 0.2 ns | 32 MB, 32 MB |
| Wrapped pairs, the view at the top | 55-85 ms | none | 3.4-5.0 ns | 136 MB, 68 MB |
| A style a cell, 10,000 rows | 0.2-0.7 ms | 4.7-6.0 ms | 2.9-5.2 ns | 14.5 MB, 7.8 MB |

The resize's own time is mostly the count, except with the view scrolled back, where every row below the view rewraps at once; keeping that to the rows the view shows needs a second stretch of waiting rows, which the operator decides on (ADR-1003's note on Cost). The rest is paid only when something reaches it. The minspec board's figures, the gate vtium/vtium#41 names, are not measured yet: no board is at hand, and tier 3's VM runs on a host core, so it measures memory, not a board's speed. ADR-1003 takes the board as ten times slower.

## Selection

The screen holds the selection (`src/screen/selection.rs`): from one cell to another (`select_start`, `select_to`), a word, the run of cells between spaces (`select_word`), or a whole line (`select_line`), held by line identity as the screen scrolls. `selection_text` copies it, at most the text of the scrollback and the screen. The host drives it from the pointer and keeps the selection buffer; vtium's README describes how.

- **A line selection takes the whole line, and its copy ends with a line end.** The C reference had no line selection. Spec: xterm's `line` unit, with `cutNewline`, on by default, ending the copy with a line end; xterm leaves it off on the screen's last row, and vtium does not. Test: `a_line_selection_copies_the_row_and_its_end`.
- **A wrapped line is one line to the selection.** A word goes on across the wrap, a line selection takes each row of the line, and the copy has no line end where it wrapped. The C reference's lines kept no wrap flag: its word selection stopped at the row's end and its copy ended every row with a line end. Spec: xterm, which tests `LINEWRAPPED` to extend a word or line selection across rows (`button.c`, `ComputeSelect`) and to leave out the line end (`SaveText`'s `eol`). The alternate screen's first row never continues the scrollback, which holds the main screen's lines. Test: `a_selection_follows_a_wrapped_line`.
- **A wide character is one character of a word.** The C reference ended a word at a wide character's second column, which held no codepoint, so a double click on the `a` of `a中b` took `a中`. No specification covers word selection; the reason: the second column is part of the character. Test: `a_word_selection_takes_a_wide_character_whole`.

A line records that printing wrapped it at the right margin (`LineFlags::WRAPPED`), which the selection and reflow (ADR-1003) read. An edit that clears the row's last column ends the wrap, as xterm's does: EL 0, ECH, DCH, ED on the cursor's row from the cursor (`ClearRight`, `ScrnDeleteChar`), and ED on each row it clears whole (`ClearBufRows`). EL 2 ends it too, as Ghostty's `eraseLine` does, where xterm keeps it. DECSED ends it on each row it clears whole, and a row where it leaves a protected cell keeps it; xterm keeps every row's wrap under DECSED once DECSCA has protected a cell, and ends it as ED does otherwise (`do_erase_display`). EL 1, ICH and the cursor's row under ED 1 keep it. A line feed's scroll, and SU, move lines with their flags, into the scrollback too, and bring in unflagged lines. Tests: `an_edit_that_clears_the_last_column_ends_the_wrap`, `a_wrap_ends_where_its_next_row_is_gone`.

Four rules depart from xterm, which joins a line to text that merely took the place of its next row. IL, DL and SD (and RI at the top margin) end the wrap of each row they shift and of the row above them, as Ghostty's `insertLines` and `deleteLines` do in a region as wide as the screen, and a scroll ends the wrap of the row above the region; xterm moves the flags, so DL at a wrapped line's second row joins its first row to an unrelated one. An erase that clears the main screen's first row whole (ED 2, ED 1 below it, RIS, or any erase of that whole row), and IL, DL, SD or RI that replace that row, end the wrap of the scrollback's newest line, whose next row it was; xterm keeps it, so a line wrapped before a clear joins the prompt printed after it. The alternate screen's rows are no line's next row. A line that a scroll region starting below the first row pushes into the scrollback enters it unwrapped, since its next row stays in the region; xterm keeps the scrollback only for a region at the screen's top. DECERA, DECSERA, DECFRA and DECCRA end the wrap of each row whose last column they reach, as EL 0 does, and one that clears or writes the main screen's first row whole ends the scrollback's newest line's; xterm's rectangle operations never touch the wrap (`ScrnFillRectangle`, `ScrnWipeRectangle`, `ScrnCopyRectangle`). Tests: `a_wrap_ends_where_its_next_row_is_gone`, `a_rectangle_over_the_last_column_ends_the_wrap`.
