# vtium-image

vtium-image handles inline images. It is the one pipeline that sixel, the kitty graphics protocol and iTerm2's pictures all feed (ADR-1100, ADR-1103). The crate holds these parts:

- each console's image store;
- the protocol tag and its rules;
- the handler trait that the protocol front ends implement;
- the decode request and reply types that the image helper answers;
- the crate's bounds.

The crate forbids unsafe code. It denies the arithmetic, cast and indexing lints that `docs/architecture.md` lists, and it uses no `HashMap`. It depends on `vtium-parse` alone. It names a line by an opaque 64-bit key, so it never depends on `vtium-term`. vtium-term takes this crate behind its `images` feature. The minspec build, vtium's default and smallest build, carries none of it.

## How the store works

A store has a main buffer and an alternate buffer. Each buffer has its own images, kitty ids and placements. One budget and one use clock cover both buffers. The binary gives each console a store of its own, so each console has its own budget and its own clock. The store keeps images and placements in ordered maps by key. It counts each key up, and it never reuses a key. A placement is anchored to a column and to the line that holds its top row. When an event needs it, the terminal tells the store which line holds each screen row. The terminal names the screen's rows, and the newest scrollback rows above them, as many as the tallest placement reaches.

An image reserves its whole cost before the store keeps it. That cost is its pixels at 4 bytes each, and 512 bytes beside them. Each placement of an image past its first costs 256 bytes more. The store refuses a reservation that cannot fit even once everything that may go has gone, and it then evicts nothing. Otherwise images go in this eviction order:

- images with no placement, transient ones first, then least recently used first;
- images placed only in the scrollback, least recently used first;
- images whose rules allow eviction while they are placed on the screen's own lines, oldest transmission first.

A sixel placed on the screen's own lines is never evicted. The use clock moves only on stream events. These are storing an image, placing one, and a command that names an existing image, such as a kitty put or query by id or number. Drawing a frame moves no clock, so the eviction order never depends on which frames were drawn. Test: `drawing_a_frame_moves_no_clock`.

A handler reserves an image's bytes as its payload arrives, before it allocates them. A reservation for a kitty id already in the buffer holds that image. So nothing evicts the old image before its replacement is stored. The store keeps a ledger of the reservations it granted and has not yet seen spent. So it spends each reservation once. A copy of a reservation already spent gives back no bytes, and it releases no hold. An image stored with such a copy reserves its whole cost, and a growth of such a copy is refused. Tests: `a_reservation_given_back_twice_gives_its_bytes_and_its_hold_back_once`, `a_reservation_an_image_spent_pays_for_no_second_image`.

A screen event can cut placements into pieces. The store settles the charges of those pieces when the event ends. So which pieces the budget refuses never depends on how the input was split into reads. The smallest pieces go first. Tests: `pieces_the_budget_refuses_go_smallest_first`, and vtium-term's `the_charges_of_cut_pieces_settle_per_event_however_the_input_is_cut`.

A new sixel can be placed over older sixels. Under every cell that the new sixel covers fully with opaque pixels, it removes the older sixels' parts, as text written there would. Under a cell it covers only partly, at its edge or where it has a clear pixel, the older parts stay and show through. Each older sixel under its box that then draws nothing goes too. That is an older sixel with no pixel set left, or one whose every set pixel lies under an opaque pixel of the new picture.

chafa pads its frames with clear cells, and mpv's frames end inside a cell. Either way, each frame replaces the one before it. The second kind of piece shows nowhere, so removing it changes no drawn pixel. `hidden_pieces_change_no_composite_pixel` composes 3,000 seeded random stacks of pictures, with the rule and without it, and finds no pixel that differs. Without the rule, two opaque pictures of the same size whose edge ends inside a cell leave the older picture's pieces in the edge cells. A stream of mpv's frames then stacked 471 placements before the budget refused the next. The store never takes a picture drawn scaled, or made in another cell size, for hidden. It reads at most as many pixels as the new picture has, and it leaves in place a piece it did not check. The maintainer accepted this reading on 2026-11-02. Test: `opaque_frames_that_end_inside_a_cell_leave_one_picture`.

A sixel placed again over its own placement keeps its image. The store holds the image being placed through the cut that removes its older placements, and it never frees a held image. So the new placement shows the image, and the charge that the placement first took is given back. Test: `an_opaque_sixel_placed_twice_over_itself_keeps_its_image`.

The store keeps the pixel buffer that a handler filled as it is, with nothing copied, and the frame shares that buffer. The store also keeps the buffer of the image it freed last. That spare buffer stays charged to the budget, and the store frees it before any image when a reservation needs room. `Edit::take_spare` gives the spare buffer to a handler that asks for one of its size, once no frame holds the buffer. The buffer's charge becomes the handler's reservation. So frame after frame of one size reuses one allocation, even under a budget that fits only the frame shown and the next. A handler may know whether its picture is opaque. The sixel decoder knows this for every picture but one with P2 of 1. Such a handler says so in `NewImage::opaque`, and the store reads the pixels only when it does not know. A build with debug assertions checks the value given.

Two kinds of kitty placement have no line of their own: relative placements and virtual placements (ADR-1100, D13).

A relative placement, made by a put with `P`, follows another placement, its parent. Its box's top left is its parent's origin plus `H` columns and `V` rows. A placement's origin is the cell that held its box's top left when it was placed. The store keeps only the link and the offset. It works the box out from the parent whenever an event, a delete or a frame needs it. So whatever moves the parent moves its children: a scroll, the scrollback, a rewrap, a region scroll, and a replacement by a put with the same image and placement id. A region scroll or a dropped scrollback line can cut off a parent's top. Such a parent keeps its origin, so its children stay where they were against its picture. A relative placement goes when its parent goes, and its own children go with it. An image left with no placement that way goes too, as the kitty spec asks.

As the kitty spec also asks, a put whose parent does not exist answers ENOPARENT, and one that would follow itself answers ECYCLE. A chain past `RELATIVE_DEPTH_MAX` answers ETOODEEP, and `U=1` with a parent answers EINVAL. Tests: `a_relative_placement_draws_at_its_parents_origin_plus_its_offset`, `a_relative_placement_follows_its_parent_through_a_scroll_and_the_scrollback`, `a_relative_placement_moves_with_its_parent_in_a_region_scroll`, `a_relative_placement_follows_its_parent_when_the_parent_is_replaced`, `deleting_a_parent_takes_its_children_and_images_left_without_placements`, `a_parent_that_does_not_exist_is_enoparent`, `a_placement_that_would_follow_itself_is_ecycle`, `a_chain_deeper_than_eight_relative_placements_is_etoodeep`, `a_virtual_placement_is_stored_on_no_line_and_only_a_delete_by_image_takes_it`.

A virtual placement, made by a put with `U=1`, lies on no line, so no screen event reaches it. Only these remove it: a delete by image (`d=i`, `d=n`, `d=r`), its image's eviction or replacement, RIS, and the alternate buffer's emptying. A virtual placement draws only where placeholder cells show it. vtium-term reads those cells, as the next section describes.

When a placement's box changes, the store tells vtium-term which cells to redraw. It names a line, how many rows from that line the box starts, and how many rows and columns the box covers. A placement on a line names its own line, and its box starts there. A relative placement has no line of its own. So the store names the line of the nearest placement up its chain of parents that has a line. `Region::row` says how many rows below that line the relative placement's box starts. That number is negative when the box starts above the line. A frame may be drawn while the view is scrolled back into the scrollback. That frame also needs the lines below the view, as many as `Store::reach_below` says (`Store::frame_with_below`). Then a relative placement drawn above a parent that has moved out below the view still shows. For eviction, an image that a virtual placement shows ranks with the kitty images on the screen's own lines.

The placements at one layer and z form a stack, which the store keeps in order as placements arrive. A later picture goes on top, with one exception. A picture whose image has a kitty id slides in directly beneath the first placement, counted from the bottom, whose image has a higher id. So nothing already shown moves. A sixel and a kitty picture at equal z therefore draw in the order they arrived. Tests: `kitty_two_a_sixel_then_kitty_one_draw_one_two_sixel`, `a_later_picture_goes_on_top_whatever_its_protocol`. A kitty picture whose image has no id goes on top as it arrives, as a sixel does. A later kitty picture that looks for the first higher id passes over it. Test: `a_kitty_picture_with_no_id_stacks_like_a_sixel`. A kitty placement that replaces one with the same image and placement id arrives anew in its stack. Test: `a_replacement_is_a_new_arrival_in_its_stack`. A cut or a scroll may split a placement. Its pieces then stay together at its place in the stack, in the order they were made. That order is above, left, right and below for a cut, and top to bottom for a scroll.

## How placeholder cells draw a virtual placement

A program shows a virtual placement by writing kitty's placeholder character, U+10EEEE, into the text. Each placeholder cell names the image, the placement, and the cell's row and column in the picture (ADR-1100, D13). vtium-term owns the cells, so vtium-term reads them and groups them into *runs*. A run is a set of side-by-side placeholder cells on one row that name the same image and placement. The cells of a run lie on one row of the picture, and they show consecutive columns of it. A `PlaceholderRun` holds the run's line and first column, its cell count, the image id, the placement id or none, and the picture row and column of its first cell. The store never sees a cell. It takes runs at two times, and it keeps none.

- **For a frame,** vtium-term hands `Store::frame_with_runs` the runs on the rows the view shows. For each run, the store finds the virtual placement that the run names, in the buffer in use. It finds the placement by image id and placement id. For a run with no placement id, it takes that image's virtual placement made last. It takes the placement's picture as the picture was fitted to its grid of cells when it was placed, with its aspect kept and centered. It makes an entry for the part of the picture under the run's cells, anchored at the run's line and first column. Some cells of a run lie outside the grid or the screen, or the fitted picture does not reach them. Those cells draw nothing. A run whose image or placement is not found makes no entry. The entries take their virtual placement's place in the draw order, row by row, then column by column. Each entry has a key of its own among the frame's entries, counted from 2^63. So a renderer that keys what it last drew on an entry's key tells the entries apart. A relative placement whose parent is virtual draws from its parent's *origin*. That origin is the least row and the least column over the parent's runs, each run's own picture row and column taken off first. When no run of the parent is handed over, the child draws nothing.
- **For a decision,** vtium-term reads the runs on the screen's own lines, and it runs the decision inside `Store::with_runs`. A decision is a kitty delete by cell, row or column, a delete of every placement on the screen (`d=a`), ED 2, or a reservation that may evict. So a virtual parent's children are deleted and ranked by where they draw there, and never by what a frame showed. A child whose virtual parent has no run there counts as lying on the screen's own lines. vtium-term reads these runs only while `Store::has_virtual_children` says that a buffer holds such a child.

The store takes at most one run for each cell of the rows it is given, and it leaves the rest. Each run costs one lookup in an index of the buffer's virtual placements, which the call builds once. The runs that a decision takes count as input work. The store notes the buffer and the image id when a virtual placement is made, replaced or deleted, or when its image is sent again. `Store::take_changed_virtual` hands those notes to vtium-term, which marks that image's placeholder cells changed. The store does the same when a kitty frame edit changes the frame that a virtual placement may show.

A relative placement that follows a virtual placement has no box of its own. Such a placement may be placed, deleted or moved, or its image's frame on show may change. The store then notes where the placement draws relative to the virtual placement's runs. The note holds that virtual placement's image id and placement id, and whether it is its image's virtual placement made last. It also holds the box's offset and size in cells. `Store::take_changed_floating` hands these notes to vtium-term. vtium-term finds the origin from the shown screen's runs, and it marks the box's cells. The store keeps at most twice `PLACEMENTS_PER_BUFFER` of these notes. Past that, it reports the buffer as changed whole.

## How a kitty upload in chunks works

A kitty program can send one picture in several commands, its *chunks*. Every chunk but the last carries `m=1`, and the first chunk's keys decide what the upload is. The kitty spec asks a program to finish an upload before it sends another graphics command, and to send nothing else between its chunks. The spec says that a delete ends an unfinished upload. Where the spec leaves the rest open, vtium follows kitty 0.49.2. The parts of kitty it follows are `grman_handle_command`, `handle_add_command`, `handle_animation_frame_load_command` and `handle_delete_command`, in its `graphics.c`. vtium departs from kitty 0.49.2 where a program that left an upload unfinished could spoil the next program's picture.

- **A command between the chunks.** A transmission or a frame sent directly is the upload's next chunk, whatever else it names, unless it names another image. Such a command is `a=t`, `a=T`, `a=q`, `a=f` or no `a`, with `t=d` or no `t`. The handler reads only its `m` and `q`. kitty-doom relies on this, because its later chunks repeat `a=f,r=1,q=2`. A chunk with a key that cannot be read, such as `f=99`, fails the upload. The upload then answers EINVAL once, at its last chunk. kitty's parser drops such a chunk instead, and the upload, short of its data, fails at its end. The same command sent from a file, a temporary file or shared memory ends the upload, and it runs as a command of its own. So does a delete. A put (`a=p`) and a composition (`a=c`) run on their own and leave the upload open. Tests: `a_chunk_that_repeats_the_first_chunks_keys_still_continues_the_upload` and the `inside_an_upload_` tests in `src/protocol/kitty/tests.rs`, and `another_command_ends_an_upload_and_gives_back_its_reservation` for the delete.
- **An animation control between the chunks.** An `a=a` leaves the upload open. During a frame's upload (`a=f`), the control acts on the image the frame belongs to, as kitty's does. During a picture's own upload, the control reaches the image of that id or number already stored, if there is one. Otherwise it answers ENOENT. vtium reserves the picture's bytes at the first chunk, but it stores the image only when its last chunk arrives. So no other command, and no frame, ever sees a picture whose pixels are half there. The upload's last chunk then replaces that image. So the control is answered OK, but it has no effect on the picture that stays. kitty 0.49.2 makes the image at the first chunk, so there the control acts on the picture being uploaded. During an `a=q`, whose picture is never stored, the control names no image and answers nothing. Tests: `inside_a_pictures_upload_an_animation_control_reaches_the_image_already_stored`, `inside_a_querys_upload_an_animation_control_names_no_image`, `inside_an_upload_an_animation_control_acts_on_the_image_being_loaded`.
- **A chunk that names another image.** A transmission or frame sent directly may name an image by `i` or `I` other than the one the first chunk named. That chunk ends the upload. The upload gives back what it reserved and answers nothing, and the new command runs on its own. Three kinds of chunk continue the upload. The first names no image, and the second names the upload's own image. The third names `i=0` or `I=0`, which kitty reads as naming none. kitty 0.49.2 loads a chunk that names another image into the open upload (its `graphics.c`, `handle_add_command`). So a program that left an upload unfinished makes the next program's first picture land in the wrong image. That picture has mixed pixels, and its answer carries the wrong id. kitty-doom's later chunks name no image, so kitty-doom meets none of this. Tests: `inside_an_upload_a_chunk_naming_another_image_ends_it_and_starts_its_own`, `inside_an_upload_a_chunk_with_i_0_or_capital_i_0_continues_it`.
- **Anything else between the chunks, RIS and the end of the session.** While an upload is open, vtium-term tells the kitty handler about any output that is not a kitty string. That output is text, a control, or another escape sequence, an OSC, a DCS or another APC string among them. The handler then drops the upload, gives back what it reserved and answers nothing. So the upload's next chunk starts a new command. RIS drops the upload too. So does the end of the session the output came from, when the program in the console exits. kitty 0.49.2 keeps the upload open through all of these. vtium ends the upload because a program that dies part way through an upload must not leave its unfinished picture open. That open picture would swallow the next program's first picture command. A program that sends its chunks back to back, as kitty-doom does, meets none of this. A multiplexer such as tmux forwards each chunk separately, and it can put its own output between them. So vtium may drop a picture sent through a multiplexer where kitty keeps it. vtium makes no exception for a multiplexer. Tests: `output_between_chunks_ends_an_upload_and_the_next_command_starts_fresh`, `an_8_bit_st_ending_each_chunk_leaves_the_upload_open`, `ris_ends_an_upload` and `the_session_ending_ends_an_upload` in vtium-term's `tests/kitty.rs`, and `the_childs_exit_ends_a_kitty_upload_it_left_open` in the binary's `src/term.rs`.
- **A cancelled string.** CAN, SUB or another control can cut off a kitty string. A kitty handler can also be cancelled because kitty graphics went off. Either one gives back the reservation of an upload in chunks, and drops a request out. The handler's one `cancel` serves both. So a cancelled string whose keys passed `KEYS_MAX` also ends the upload. The upload's next chunk then starts a new command. A program sending chunks never meets this, since every chunk's keys are short. Test: `a_cancelled_string_whose_keys_passed_1_kib_still_ends_an_upload`.

## How kitty animation works

Kitty animation (ADR-1102) gives an image more frames. The image's own pixels are its first frame, the *root frame*. A program sends a later frame with `a=f`. The frame is a rectangle of pixels laid on a *canvas*. The canvas is a color or an earlier frame. The color is transparent black when the program names none. The store keeps a frame in one of two kinds. A *whole frame* holds every pixel of the image. A *change frame* holds only its base and its *layers*. The base is the color or the earlier frame. The layers are the rectangles the program sent, each with its offset and whether it blends over the canvas or replaces it.

When a frame's command arrives, the store may compose the frame into a whole frame. It does so if the image is at most `FRAME_WHOLE_MAX` bytes, or if the frame's layers cover at least half of the image. It also does so if composing the frame would apply more than `FRAME_CHAIN_MAX` layers. Two commands change a frame that change frames may be laid on: an edit (`a=f` with `r`) and a composition (`a=c`). Before such a command, the store composes each of those change frames into a whole frame. So a frame never changes when another frame does.

Frames past the root are charged to the console's *frame allowance*, which is five times its image budget. They are never charged to the image budget, so frames never evict a still picture. A whole frame costs its pixels at 4 bytes each, and `FRAME_OVERHEAD` beside them. A change frame costs the same for each of its layers. An image that holds a change frame is also charged for its cache at the cache's full bound, `FRAME_CACHE_FRAMES` whole frames, whatever the cache holds. The handler reserves a frame's data before it allocates the data. The store reserves the rest of the command's cost before it composes anything. When the cost does not fit, the store frees whole animations of other images, least recently used first. It never frees the image's own frames or any root frame. When even that cannot make room, it frees nothing, and the command answers ENOSPC. An image holds at most `FRAMES_MAX` frames. An animation command that names an image that does not exist answers ENOENT, as a put does. Tests: `animation_commands_are_answered_as_a_put_is`, `a_frame_in_chunks_holds_one_reservation_and_answers_once`, `d_f_deletes_every_frame_but_the_root_and_needs_an_image`, `a_frame_from_the_helper_is_reserved_of_the_allowance_and_stored`, and the frame code's tests in `src/store/anim/tests.rs`.

The store records what the commands set: each frame's gap, the run state (`s`), the loops (`v`), and the current frame (`c`). It also records two stamps, which tell the binary's animation clock what a command changed. The frame stamp moves when a command makes a frame current. The run stamp moves when a command sets the run state or the loops. `d=f`, `d=F` and frames freed for the allowance move both stamps. They leave the root frame current and the animation stopped. The store never records which frame is on the screen. A frame entry shows the image's current frame, as the commands set it. The binary's snapshot asks `Store::frame_pixels` for the frame its clock chose, and it puts that frame on the entry with `FramePlacement::show`. A change frame composed for a snapshot goes into the image's cache. No comparison, reply or decision of the store reads that cache. The image's key, the frame's number and its pixel revision name the pixels. The renderers key what they keep on all three.

## How sixel works

The sixel handler takes a DCS `q` string while sixel is offered. The string's data goes to the decoder as the parser hands it over. So a picture costs its pixels, and never the text that drew it. For example, a 7680×2160 frame from `mpv --vo=sixel` is up to 29 MB of text and 65 MB of pixels. The decoder draws each dot in its register's color as the dot arrives. So a register defined again later changes only what is drawn after it. The decoder reserves the picture's pixels of the console's budget before it allocates them. Raster attributes reserve the whole picture before any sixel, so a picture that cannot fit is refused before it is decoded. A picture without raster attributes reserves as it grows, each side by at least a quarter. While the rows move across, it holds both buffers. A string that ends with its terminator stores the picture, with that reservation and the 512 bytes beside it, and places the picture. A cancelled string, or one that ends while sixel is not offered, gives everything back.

With mode 80 (DECSDM) reset, the picture's top left is the cursor's cell. A pending wrap counts as the last column. When the picture would pass the bottom margin, the scroll region first scrolls up as far as it can. So a picture that fits the region moves whole. A picture scrolls the region only while the picture's left column is between the left and right margins. Then the cursor goes down one row fewer than the picture's rows, as that many line feeds do. The cursor ends on the row of the picture's last pixel row, at its left column. With mode 8452, the cursor ends instead in the column after the picture's right edge, and at most in the column where CUF stops. That column is the right margin when the picture's left column is not past it, and the last column otherwise.

With mode 80 set, the picture sits at the screen's top left, cut to the screen, and the cursor stays where it is.

With mode 1070 set, as `private-color-registers` starts it, each picture starts from the default registers. The defaults are the VT340's sixteen colors and black. With mode 1070 reset, the pictures share one set of registers. That set goes back to the defaults on RIS, and on each change of the register count in force. It also goes back when the host switches sixel off, or changes `max-graphic-size`, `num-color-registers` or `private-color-registers`. The three modes reset only on RIS. While sixel is not offered, DECRQM reports each mode's fixed state, and SM and RM still store it.

The decoder counts as input work every byte it reads, and every pixel it writes, allocates or copies (D5). So a short string that draws many pixels, such as `!10000~`, stops the input call once the call's work passes its bound. The handler takes a run of string data through `Handler::feed_some`, with the work the call has left. The decoder stops right after the byte that passes that bound. So a call does at most its bound and one band's work.

A sixel dot is one square pixel, whatever pixel aspect the string's first parameter or the raster attributes' Pan;Pad ask for. xterm, WezTerm and mlterm draw a sixel dot the same way. DEC's VT340 manual draws a dot twice as tall as it is wide, unless the picture says otherwise. The maintainer chose square dots on 2026-11-01 (ADR-1100, D3). Test: `raster_attributes_size_the_picture_and_reserve_it_first`.

The decoder computes HLS colors exactly, in integers. It rounds up a channel whose exact value lies halfway between two 8-bit levels. Floating point rounds those halves up in some colors and down in others, by how the decimal fractions are stored. Of the 3.7 million HLS colors, 2,747 have such a half. Test: `hls_in_integers_matches_floating_point_but_at_exact_halves`.

## How iTerm2's pictures work

vtium-term's router hands the iTerm2 handler a complete OSC 1337 string while the iTerm2 switch is on (ADR-1103, D1). The string's text starts `File=`, `MultipartFile=` or `FilePart=`, or is `FileEnd`. A `File=` string carries its keys up to the first `:`, and the base64 file after it. A `MultipartFile=` string carries the keys of a *transfer in parts*. The file then comes in `FilePart=` strings of any length, and it ends with `FileEnd`. The handler decodes the base64 into a buffer. It reserves the buffer under the console's image budget as the buffer grows, up to `ITERM2_FILE_MAX` bytes of file and `ITERM2_PARTS_MAX` parts. The handler drops a string without `inline=1`, and a `File=` string without its `:`. These abandon a transfer and give its reservation back: a new `File=` or `MultipartFile=`, RIS, a bound, and base64 that does not decode. So do a budget refusal, the switch going off, and an OSC 1337 string that vtium drops. Nothing is ever answered. The context's `note` receives why a picture was dropped.

Once the file is whole, the handler sends it to the image helper as inline bytes, with the any-image flag. The helper decodes the file as PNG, JPEG or GIF by its first bytes (ADR-1101, D6). The handler stores the decoded picture under the sixel tag, so every rule of the sixel column applies to it. The handler places the picture at the cursor with sixel scrolling on, through the placement that the sixel handler uses too. Modes 80 and 8452 are sixel's, and they do not apply. An iTerm2 picture always scrolls, and the cursor ends on the picture's last row at its left column. `width` and `height` size the picture in cells, in pixels, in percent of the screen, or at its own size. `preserveAspectRatio` keeps the picture's shape unless it is 0 (D3). The store draws the picture at exactly that size from its box's top left, and the box covers the cells the picture reaches. ADR-1103's "Where vtium departs" lists where vtium's handling differs from iTerm2's own. Tests: `a_picture_in_one_string_goes_to_the_helper_and_is_placed_under_the_sixel_tag`, `a_transfer_in_parts_gathers_its_file_across_parts_of_any_length`.

An animated GIF plays through kitty animation's frames (ADR-1102). The handler asks the helper for every frame, up to `FRAMES_MAX`. It asks for as many bytes as the frame allowance could hold, counting the frames of other animations it could free. The helper composes each frame whole, by the disposal method of the frame before it. Before a byte of the frames is copied, the handler reserves the first frame under the image budget, and the rest under the frame allowance, ahead of the image (`src/store/iterm2.rs`). When the allowance refuses, the handler copies the first frame alone, and the picture is still. The handler stores the frames past the first as whole frames, each with its gap. A gap is 10 ms for each hundredth of a second, and 100 ms for a delay of 0 or 1. The handler sets the loops from the GIF's loop count. No loop count plays the frames once, 0 loops forever, and L plays them L + 1 times. The handler leaves the animation running from its first frame, so the binary's animation clock plays it. The picture keeps the sixel tag (D4). The store reads every frame of it for the cell-by-cell rules. The picture covers a cell fully only where every frame does, and it draws nothing in a place only where every frame draws nothing.

## Readings of the record

These follow ADR-1100 where its literal text leaves room.

- **ED 2 keeps the part of a sixel that lies in the scrollback.** ED 2 removes every placement whose rules say that the clear screen code removes it, as kitty's rules do. It removes such a placement when the placement has a row on the screen's own lines. A sixel loses the cells that the erase clears, as D3 says text and erases cut it. So a sixel that reaches up into the scrollback keeps its part there. D8 says that ED 2 removes every placement on the screen's own lines. vtium reads that as the placements' parts on those lines.

## Readings of the kitty spec

These follow the kitty spec where it leaves a choice open. Each stays vtium's reading until a black-box run of kitty confirms or corrects it (ADR-1100, D14).

- **A relative placement without `Q` follows the parent image's placement made last that has no placement id.** D13 decides this. With no such placement, the put answers ENOPARENT.
- **`P=0` names no parent.** An id of 0 names no image anywhere in the protocol. So the put is an ordinary one, and `Q`, `H` and `V` do nothing.
- **A change "covers half the picture" when its layers' areas add up to half the image's or more** (ADR-1102, D1, the second rule). Layers that overlap count twice. So a frame can only be composed whole earlier than its covered pixels alone would make it, and never later.
- **`z` on any `a=f` sets the gap of the frame the command makes or edits.** That includes the root frame's gap. `z=0` keeps the gap the frame has, and a new frame's gap is 40.
- **`a=a` sets a gap only with both `r` and `z`.** With `z` and no `r` it sets no gap, since `r=0` names no frame.
- **`a=c` without `c` answers kitty's text for a missing destination frame,** `ENOENT:No destination frame number 0 exists in image id: I`, since frame 0 does not exist. An `s` past 3 in `a=a` is not answered, as kitty answers no control whose image exists.
- **A refusal kitty was not seen to give keeps vtium's own fixed text,** such as `ENOENT:image not found` for a composition's missing source frame; ADR-1100 D15 lists the texts taken from kitty.
- **`d=f` and `d=F` with neither `i` nor `I` delete nothing,** since the spec asks every animation command for one of them (ADR-1102, D5).
- **The text after ECYCLE is vtium's own.** kitty answers a placement that names itself as its parent with its own EINVAL text, and a longer cycle was not seen, so `ECYCLE:relative placement would make a cycle` stays vtium's.

## How kitty's palette formats work

Kitty's `f=8` and `f=16` send each pixel as an index into the terminal's palette. `f=16` adds an alpha byte after each index (ADR-1100, D15). When the upload's first chunk arrives, the kitty handler asks the terminal for its colors through `Context::colors`. It resolves all 256 indices to colors once. It turns each pixel into a premultiplied color as the pixel's bytes arrive, so the store keeps its one pixel format. vtium-term answers with the palette its frames draw through. The handler refuses a frame in either format with kitty's own reply. It also refuses a frame or a composition on a picture that arrived as palette indices. The specification supports no animation for these pictures, and kitty 0.50.0 refuses it (`frames_on_palette_index_pictures_are_refused_as_kitty_refuses_them`). A host whose context gives no colors gets both formats refused with EINVAL. So does the graphics query `a=q` with `f=8`, which programs use to find out whether the terminal takes these formats. Tests: `palette_index_pictures_store_the_colors_their_indices_give`, `a_palette_change_after_the_first_chunk_leaves_the_picture_as_it_arrived`, `palette_index_pictures_are_refused_where_vtium_cannot_take_them`, and `palette_indices_take_their_tables_colors_in_any_pieces` in `src/decode/raw.rs`.

A raw upload or frame that leaves out `s` or `v` is answered `EINVAL:Zero width/height not allowed`, as kitty answers it (`a_raw_upload_without_s_or_v_is_refused_as_kitty_refuses_it`). Raw data may be sent directly and uncompressed, with fewer bytes than its picture's width and height need. In every raw format, that data is answered `ENODATA:Insufficient image data: GOT < WANT`, with the bytes that came and the bytes needed. kitty 0.49.2 answers it the same way (`raw_data_short_of_its_picture_is_enodata_in_every_raw_format`). A frame's data short of its rectangle is answered the same way too (ADR-1102, D2). Raw data that the image helper inflates short answers EINVAL, as kitty answers it.

## Where vtium reads kitty's specification its own way

- **A raw frame without `s` or `v` is refused** with `EINVAL:Zero width/height not allowed`, as kitty 0.49.2 and 0.50.0 refuse it. The spec says instead that a frame's rectangle is the whole image where `x`, `y`, `s` and `v` are left out (ADR-1102, D2). A PNG frame takes its size from the picture.
- **A palette-index picture keeps the colors it arrived with.** Kitty's specification redraws an `f=8` or `f=16` picture whenever the terminal's colors change. vtium turns the indices into colors once, as the picture arrives. So a later palette change leaves the picture as it was (the maintainer, 2026-11-06).
- **`f=8` and `f=16` are taken only sent directly and uncompressed.** From a file, a temporary file or shared memory, or with `o=z`, they answer EINVAL, because the image helper's pixel description has no layout for palette indices.

## Bounds

The kitty handler's two bounds live in `src/protocol/kitty.rs`, and they are not yet in this table. `KEYS_MAX` is 1024 bytes of control keys, past which the handler ignores the whole string. `NAME_MAX` is 4095 bytes of a decoded file or shared-memory name, past which the command answers EBADF. `KEYS_MAX` bounds what the handler holds before it parses a command. `NAME_MAX` is the image helper's name bound: the kernel's `PATH_MAX`, less its terminating NUL.
