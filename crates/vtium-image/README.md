# vtium-image

Inline images: the one pipeline sixel and the kitty graphics protocol feed (ADR-1100). It holds each console's image store, the protocol tag and its rules, the handler trait the protocol front ends implement, the decode request and reply types the image helper answers, and its bounds. It forbids unsafe code, denies the arithmetic, cast and indexing lints `docs/architecture.md` lists, and uses no `HashMap`. It depends on `vtium-parse` alone and names a line by an opaque 64-bit key, so it never depends on `vtium-term`; vtium-term takes it behind its `images` feature, and the minspec build carries none of it.

## How the store works

A store has a main and an alternate buffer, each with its own images, kitty ids and placements, and one budget and one use clock over both. Images and placements are kept in ordered maps by key, each key counted up and never reused. A placement is anchored to the line holding its top row and a column; the terminal tells the store which line holds each screen row when an event needs it, the screen's rows and the newest scrollback rows above them, as many as the tallest placement reaches.

An image reserves its whole cost, its pixels at 4 bytes each and 512 bytes beside them, before it is stored; each placement of an image past its first costs 256 bytes more. A reservation that cannot fit once everything that may go has gone evicts nothing and is refused. Otherwise images go in the eviction order: images with no placement, transient ones first, then images placed only in the scrollback, each least recently used first, then images whose rules allow eviction while placed on the screen's own lines, oldest transmission first. A sixel placed on the screen's own lines is never evicted. The use clock moves only on stream events: storing an image, placing one, and a command that names an existing image, such as a kitty put or query by id or number. A handler reserves an image's bytes before it allocates them, as its payload arrives, and a reservation for a kitty id already in the buffer holds that image so nothing evicts it before its replacement is stored. The store keeps a ledger of the reservations it granted and has not seen spent, so it spends each reservation once: a copy of a reservation already spent gives back no bytes and releases no hold, an image stored with one reserves its whole cost, and a growth of one is refused.

A sixel placed over older sixels removes their parts under every cell it covers fully with opaque pixels, as text written there would; under a cell it covers only partly, at its edge or where it has a clear pixel, they stay and show through. Each older sixel under its box that then draws nothing goes too: one with no pixel set left, or one whose every set pixel lies under an opaque pixel of the new picture. chafa pads its frames with clear cells, and mpv's frames end inside a cell, and either way each frame replaces the one before it.

The store keeps the pixel buffer a handler filled as it is, with nothing copied, and the frame shares it. It keeps the buffer of the image it freed last, charged to the budget and freed before any image when a reservation needs room, and `Edit::take_spare` gives it to a handler that asks for one of its size once no frame holds it, with its charge as the handler's reservation, so frame after frame of one size reuses one allocation even under a budget that fits only the frame shown and the next. A handler that knows whether its picture is opaque, as the sixel decoder does for every picture but one with P2 of 1, says so in `NewImage::opaque`, and the store reads the pixels only when it does not know; a build with debug assertions checks the value given.

Two kinds of kitty placement have no line of their own (ADR-1100, D13). A relative placement, made by a put with `P`, follows another placement, its parent: its box's top left is its parent's origin plus `H` columns and `V` rows, where a placement's origin is the cell that held its box's top left as it was placed. The store keeps only the link and the offset, and works the box out from the parent whenever an event, a delete or a frame needs it, so whatever moves the parent moves its children: a scroll, the scrollback, a rewrap, a region scroll and a replacement by a put with the same image and placement id. A parent whose top a region scroll or a dropped scrollback line cut off keeps its origin, so its children stay where they were against its picture. A relative placement goes with its parent, and its own children with it, and an image left with no placement that way goes too, as the kitty spec asks. A virtual placement, made by a put with `U=1`, lies on no line, so no screen event reaches it; only a delete by image (`d=i`, `d=n`, `d=r`), its image's eviction or replacement, RIS and the alternate buffer's emptying remove it. A virtual placement draws only where placeholder cells show it, which vtium-term reads (below). When a placement's box changes, the store tells vtium-term which cells to redraw by naming a line, how many rows from that line the box starts, and how many rows and columns it covers. A placement on a line names its own line, and its box starts there. A relative placement has no line of its own, so the store names the line of the nearest placement up its chain of parents that has one, and `Region::row` says how many rows below that line the relative placement's box starts, a negative number when the box starts above it. A frame drawn while the view is scrolled back into the scrollback also needs the lines below the view, as many as `Store::reach_below` says, so that a relative placement drawn above a parent that has moved out below the view still shows (`Store::frame_with_below`). For eviction, an image a virtual placement shows ranks with the kitty images on the screen's own lines.

The placements at one layer and z form a stack, kept as placements arrive: a later picture goes on top, except that a picture whose image has a kitty id slides in directly beneath the first placement from the bottom whose image has a higher id, so nothing already shown moves. A cut or a scroll that splits a placement keeps its pieces together at its place, in the order they were made: above, left, right and below for a cut, top to bottom for a scroll.

## How placeholder cells draw a virtual placement

A program shows a virtual placement by writing kitty's placeholder character, U+10EEEE, into the text, each cell naming the image, the placement and its row and column in the picture (ADR-1100, D13). vtium-term owns the cells, so it reads them and groups them into *runs*: side-by-side placeholder cells on one row that name the same image and placement, lie on one row of the picture and show consecutive columns of it. A `PlaceholderRun` is the run's line and first column, its cell count, the image id, the placement id or none, and the picture row and column of its first cell. The store never sees a cell; it takes runs at two times, and keeps none.

- **For a frame,** vtium-term hands `Store::frame_with_runs` the runs on the rows the view shows. For each run, the store finds the virtual placement of the buffer in use that the run names: by image id and placement id, or for a run with no placement id, that image's virtual placement made last. It takes the placement's picture as it was fitted to its grid of cells when it was placed, with its aspect kept and centered, and makes an entry for the part of it under the run's cells, anchored at the run's line and first column. Cells of a run that lie outside the grid or the screen, or that the fitted picture does not reach, draw nothing, and a run whose image or placement is not found makes no entry. The entries take their virtual placement's place in the draw order, row by row, then column by column, and each has a key of its own among the frame's entries, counted from 2^63, so a renderer that keys what it last drew on an entry's key tells them apart. A relative placement whose parent is virtual draws from its parent's *origin*: the least row and the least column over the parent's runs, each run's own picture row and column taken off first. When no run of the parent is handed, the child draws nothing.
- **For a decision,** a kitty delete by cell, row or column or a reservation that may evict, vtium-term reads the runs on the screen's own lines and runs the decision inside `Store::with_runs`, so a virtual parent's children are deleted and ranked by where they draw there, and never by what a frame showed. A child whose virtual parent has no run there counts as lying on the screen's own lines. vtium-term reads these runs only while `Store::has_virtual_children` says a buffer holds such a child.

The store takes at most one run for each cell of the rows it is given, and leaves the rest. Each run costs one lookup in an index of the buffer's virtual placements that the call builds once, and the runs a decision takes count as input work. When a virtual placement is made, replaced or deleted, or its image is sent again, the store notes the buffer and the image id, and `Store::take_changed_virtual` hands them to vtium-term, which marks that image's placeholder cells changed.

## How kitty animation works

Kitty animation (ADR-1102) gives an image more frames. The image's own pixels are its first frame, the *root frame*. A program sends a later frame with `a=f`, as a rectangle of pixels laid on a *canvas*: a color, transparent black when the program names none, or an earlier frame. The store keeps a frame in one of two kinds. A *whole frame* holds every pixel of the image. A *change frame* holds only its base, the color or the earlier frame, and its *layers*, the rectangles the program sent, each with its offset and whether it blends over the canvas or replaces it. The store composes a frame into a whole frame when its command arrives if the image is at most `FRAME_WHOLE_MAX` bytes, if the frame's layers cover at least half of the image, or if composing it would apply more than `FRAME_CHAIN_MAX` layers. Before a command changes a frame that change frames are laid on, an edit (`a=f` with `r`) or a composition (`a=c`), the store composes each of those frames into a whole frame, so a frame never changes when another frame does.

Frames past the root are charged to the console's *frame allowance*, five times its image budget, and never to the image budget, so frames never evict a still picture. A whole frame costs its pixels at 4 bytes each and `FRAME_OVERHEAD` beside them, and a change frame costs the same for each of its layers. An image that holds a change frame is also charged for its cache at its full bound, `FRAME_CACHE_FRAMES` whole frames, whatever the cache holds. The handler reserves a frame's data before it allocates it, and the store reserves the rest of the command's cost before it composes anything. When the cost does not fit, the store frees whole animations of other images, least recently used first, and never the image's own frames or any root frame; when even that cannot make room, it frees nothing and the command answers ENOSPC. An image holds at most `FRAMES_MAX` frames.

The store records what the commands set: each frame's gap, the run state (`s`), the loops (`v`), the current frame (`c`), and two stamps that tell the binary's animation clock what a command changed. The frame stamp moves when a command makes a frame current, and the run stamp when a command sets the run state or the loops; `d=f`, `d=F` and frames freed for the allowance move both and leave the root frame current and the animation stopped. The store never records which frame is on the screen. A frame entry shows the image's current frame, as the commands set it; the binary's snapshot asks `Store::frame_pixels` for the frame its clock chose, and puts it on the entry with `FramePlacement::show`. A change frame composed for a snapshot goes into the image's cache, which no comparison, reply or decision of the store reads. The image's key, the frame's number and its pixel revision name the pixels, and the renderers key what they keep on all three.

## How sixel works

The sixel handler takes a DCS `q` string while sixel is offered. Its data goes to the decoder as the parser hands it over, so a picture costs its pixels and never the text that drew it: a 7680 by 2160 frame from `mpv --vo=sixel` is up to 29 MB of text and 65 MB of pixels. The decoder draws each dot in its register's color as the dot arrives, so a register defined again later changes only what is drawn after. It reserves the picture's pixels of the console's budget before it allocates them: raster attributes reserve the whole picture before any sixel, so a picture that cannot fit is refused before it is decoded, and a picture without them reserves as it grows, each side by at least a quarter, holding both buffers while the rows move across. A string that ends with its terminator stores the picture, with that reservation and the 512 bytes beside it, and places it; a cancelled string, or one that ends while sixel is not offered, gives everything back.

With mode 80 (DECSDM) reset, the picture's top left is the cursor's cell, a pending wrap counting as the last column. When the picture would pass the bottom margin, the scroll region scrolls up first, as far as it can, so a picture that fits the region moves whole; then the cursor goes down a row fewer than the picture's rows, as that many line feeds do. The cursor ends on the row of the picture's last pixel row, at its left column, or with mode 8452 in the column after its right edge, at most the last column. With mode 80 set, the picture sits at the screen's top left, cut to the screen, and the cursor stays where it is. With mode 1070 set, as `private-color-registers` starts it, each picture starts from the default registers, the VT340's sixteen colors and black; reset, the pictures share one set, which go back to the defaults on RIS, on each change of the register count in force, and when the host switches sixel off or changes `max-graphic-size`, `num-color-registers` or `private-color-registers`, as the C reference dropped them. The three modes reset only on RIS. While sixel is not offered, DECRQM reports each one's fixed state, and SM and RM still store it.

The decoder counts every byte it reads and every pixel it writes, allocates or copies as input work (D5), so a short string that draws many pixels, such as `!10000~`, stops the input call once the call's work passes its bound. The handler takes a run of string data through `Handler::feed_some` with the work the call has left, and the decoder stops right after the byte that passes it, as the C reference's `tsm_sixel_feed_some` did, so a call does at most its bound and one band's work.

## Departures

- **An opaque sixel placed again over its own placement keeps its image.** The image being placed is held through the cut that removes its older placements, and a held image is never freed, so the new placement shows it and the charge that placement first took is given back. The C reference's `screen_image_place` freed the image in that cut and then placed it, a use after free. Test: `an_opaque_sixel_placed_twice_over_itself_keeps_its_image`.

- **A copy of a reservation already spent gives back nothing.** The store keeps a ledger of the reservations it granted and has not seen spent, and spending one takes it out, so a handler that gives one reservation back twice, or stores an image with a copy of one already spent, gets its bytes and its hold back once and pays for no second image. The C reference's `screen_kitty_unreserve` zeroed only the struct it was given, so a copy of that struct gave its bytes back a second time and the budget then counted less than the images held. Tests: `a_reservation_given_back_twice_gives_its_bytes_and_its_hold_back_once`, `a_reservation_an_image_spent_pays_for_no_second_image`.
- **The use clock is each store's own and moves only on stream events.** The C reference renewed every drawn image's use on each frame, on one clock for the whole process, so its eviction order depended on which frames were drawn (ADR-1100, D5). Test: `drawing_a_frame_moves_no_clock`.
- **Each console has its own budget.** The C reference had one budget for the whole process (ADR-1100, D5). The store holds its own limit, and the binary gives each console one.
- **At equal z, a sixel and a kitty picture draw in the order they arrived,** with a newly arrived kitty picture slid beneath the first higher kitty id. The C reference drew every sixel above every kitty picture at equal z (ADR-1100, D4). Tests: `kitty_two_a_sixel_then_kitty_one_draw_one_two_sixel`, `a_later_picture_goes_on_top_whatever_its_protocol`.
- **A kitty picture whose image has no id goes on top of its stack as it arrives,** as a sixel does, and a later kitty picture looking for the first higher id passes over it. The C reference drew kitty pictures by image id and counted an image without one as id 0, below every other (ADR-1100, D4). `kit-transmit` shows it: its picture sent with neither `i` nor `I` is the last of the three at row 0 in vtium's draw order and the first in the golden's; the pictures do not overlap, so no pixel differs. Test: `a_kitty_picture_with_no_id_stacks_like_a_sixel`.
- **A kitty placement that replaces one with the same image and placement id is a new arrival** in its stack, where the C reference kept the replaced placement's place (ADR-1100, D4). Test: `a_replacement_is_a_new_arrival_in_its_stack`.
- **The charges of the pieces a screen event cuts are settled when the event ends.** The C reference settled them at the end of an input call, or before the next reservation, so when the budget refused them, which pieces went depended on how the input was chunked. Tests: `pieces_the_budget_refuses_go_smallest_first`, and vtium-term's `the_charges_of_cut_pieces_settle_per_event_however_the_input_is_cut`.
- **A placement's change marks the cells under its old and new boxes,** which vtium-term does from the regions the store reports, where the C reference left each renderer to damage placement rectangles itself (ADR-1001).
- **A cancelled kitty string ends an upload in chunks, whatever it held.** A string cut off by CAN, SUB or another control, or a kitty handler cancelled because kitty graphics went off, gives back the reservation of an upload in chunks and drops a request out. The handler's one `cancel` serves both, so a cancelled string whose keys passed 1 KiB also ends the upload, where the C reference kept the upload open for a cancelled string it was already ignoring. The upload's next chunk then starts a new command, which a program sending chunks never meets, since every chunk's keys are short. Test: `a_cancelled_string_whose_keys_passed_1_kib_still_ends_an_upload`.
- **A new sixel also removes an older one it hides entirely.** The rule the operator chose for the C reference (its image record's row "A new sixel placed over cells") removes the parts of older sixels under every cell a new sixel covers fully with opaque pixels, and then an older piece left with no pixel set. vtium also removes an older piece under the new picture's box whose every set pixel lies under an opaque pixel of the new picture. That piece shows nowhere, so removing it changes no drawn pixel: the test `hidden_pieces_change_no_composite_pixel` composes 3,000 seeded random stacks of pictures with the rule and without it and finds no pixel that differs. Without it, two opaque pictures of the same size whose edge ends inside a cell, as most of mpv's frames do, leave the older one's pieces in the edge cells, and each frame keeps an image until the budget refuses the next. A picture drawn scaled, or made in another cell size, is never taken for hidden, and the check reads at most as many pixels as the new picture has, leaving an unchecked piece in place. The maintainer accepted this reading on 2026-11-02, since it changes no drawn pixel and, without it, a stream of mpv's frames stacked 471 placements. Tests: `opaque_frames_that_end_inside_a_cell_leave_one_picture`, `hidden_pieces_change_no_composite_pixel`.
- **Relative placements and virtual placements are built.** The C reference answered `P`, `Q`, `H`, `V` and `U` with EINVAL and left them to a later step of its image record (ADR-1100, D13). vtium makes both, answers a missing parent ENOPARENT, a placement that would follow itself ECYCLE and a chain past `RELATIVE_DEPTH_MAX` ETOODEEP, and refuses `U=1` with a parent with EINVAL, as the kitty spec asks. Tests: `a_relative_placement_draws_at_its_parents_origin_plus_its_offset`, `a_relative_placement_follows_its_parent_through_a_scroll_and_the_scrollback`, `a_relative_placement_moves_with_its_parent_in_a_region_scroll`, `a_relative_placement_follows_its_parent_when_the_parent_is_replaced`, `deleting_a_parent_takes_its_children_and_images_left_without_placements`, `a_parent_that_does_not_exist_is_enoparent`, `a_placement_that_would_follow_itself_is_ecycle`, `a_chain_deeper_than_eight_relative_placements_is_etoodeep`, `a_virtual_placement_is_stored_on_no_line_and_only_a_delete_by_image_takes_it`.
- **Kitty animation is built.** The C reference answered `a=f`, `a=a` and `a=c` with EINVAL before reading any data, and `d=f` and `d=F` deleted nothing (ADR-1102). vtium stores the frames, composes them, records the animation's state for the binary's clock, and deletes the frames with `d=f` and `d=F`. A command that names an image that does not exist therefore answers ENOENT where the C reference answered EINVAL: the first three replies of `kit-refused`, the reply to `i=11` in `kit-host-requests`, and the two replies to `a=a` in `kit-host-icat-gif`, each in its `-nohook` twin too. Tests: `animation_commands_are_answered_as_a_put_is`, `a_frame_in_chunks_holds_one_reservation_and_answers_once`, `d_f_deletes_every_frame_but_the_root_and_needs_an_image`, `a_frame_from_the_helper_is_reserved_of_the_allowance_and_stored`, and the frame code's tests in `src/store/anim/tests.rs`.
- **A sixel dot is one square pixel,** whatever pixel aspect the string's first parameter or raster attributes' Pan;Pad ask for, as the C reference, xterm, WezTerm and mlterm draw it; DEC's VT340 manual draws a dot twice as tall as it is wide unless the picture says otherwise (ADR-1100, D3), so this is a departure from the specification. Test: `raster_attributes_size_the_picture_and_reserve_it_first`.
- **HLS colors are computed exactly, in integers.** The C reference computed them in floating point, so where a channel's exact value lies halfway between two 8-bit levels, 2,747 of the 3.7 million HLS colors, its decimal fractions rounded the half down in some colors and up in others; vtium rounds each half up. No golden draws one of those colors. Test: `hls_in_integers_is_the_c_references_but_at_exact_halves`.

## Readings of the record

These follow ADR-1100 where its literal text leaves room, and each is the C reference's flow.

- **ED 2 keeps the part of a sixel that lies in the scrollback.** ED 2 removes every placement whose rules say the clear screen code removes it, kitty's, with a row on the screen's own lines. A sixel loses the cells the erase clears, as D3 says text and erases cut it, so a sixel reaching up into the scrollback keeps its part there. D8 says ED 2 removes every placement on the screen's own lines; vtium reads that as their parts on those lines.

## Readings of the kitty spec

These follow the kitty spec where it leaves a choice open. Each stays vtium's reading until a black-box run of kitty confirms or corrects it (ADR-1100, D14).

- **A relative placement without `Q` follows the parent image's placement made last that has no placement id,** as D13 decides; with no such placement the put answers ENOPARENT.
- **`P=0` names no parent,** as an id of 0 names no image anywhere in the protocol, so the put is an ordinary one, and `Q`, `H` and `V` do nothing.
- **A raw frame without `s` or `v` reaches the image's right or bottom edge** from `x` or `y`. The spec says only that a frame's rectangle is the whole image where `x`, `y`, `s` and `v` are left out.
- **A change "covers half the picture" when its layers' areas add up to half the image's or more** (ADR-1102, D1, the second rule). Layers that overlap count twice, so a frame can only be composed whole earlier than its covered pixels alone would make it, never later.
- **`z` on any `a=f` sets the gap of the frame the command makes or edits,** the root frame's included; `z=0` keeps the gap the frame has, and a new frame's is 40.
- **`a=a` sets a gap only with both `r` and `z`.** With `z` and no `r` it sets no gap, since `r=0` names no frame.
- **`a=c` without `r` or `c` answers ENOENT,** as a composition whose source or destination does not exist does, since frame 0 does not exist. An `s` past 3 in `a=a` answers EINVAL.
- **A missing frame answers `ENOENT:image not found`,** the message a missing image gets, so the handler's replies stay a closed set of fixed messages.
- **`d=f` and `d=F` with neither `i` nor `I` delete nothing,** since the spec asks every animation command for one of them (ADR-1102, D5).
- **The text after ENOPARENT, ECYCLE and ETOODEEP is vtium's own.** The spec names the three codes and no message, so each reply is a fixed message of vtium's: `ENOPARENT:parent placement not found`, `ECYCLE:relative placement would make a cycle` and `ETOODEEP:chain of relative placements is too deep`.

## Bounds

The kitty handler's two bounds live in `src/protocol/kitty.rs`, not yet in this table: `KEYS_MAX`, 1024 bytes of control keys, past which the whole string is ignored, and `NAME_MAX`, 4095 bytes of a decoded file or shared-memory name, past which the command answers EBADF. They are the C reference's `KITTY_KEYS_MAX` and `KITTY_NAME_MAX`.
