# vtium-image

Inline images: the one pipeline sixel, the kitty graphics protocol and iTerm2's pictures feed (ADR-1100, ADR-1103). It holds each console's image store, the protocol tag and its rules, the handler trait the protocol front ends implement, the decode request and reply types the image helper answers, and its bounds. It forbids unsafe code, denies the arithmetic, cast and indexing lints `docs/architecture.md` lists, and uses no `HashMap`. It depends on `vtium-parse` alone and names a line by an opaque 64-bit key, so it never depends on `vtium-term`; vtium-term takes it behind its `images` feature, and the minspec build carries none of it.

## How the store works

A store has a main and an alternate buffer, each with its own images, kitty ids and placements, and one budget and one use clock over both. The binary gives each console a store of its own, so each console has its own budget and its own clock. Images and placements are kept in ordered maps by key, each key counted up and never reused. A placement is anchored to the line holding its top row and a column; the terminal tells the store which line holds each screen row when an event needs it, the screen's rows and the newest scrollback rows above them, as many as the tallest placement reaches.

An image reserves its whole cost, its pixels at 4 bytes each and 512 bytes beside them, before it is stored; each placement of an image past its first costs 256 bytes more. A reservation that cannot fit once everything that may go has gone evicts nothing and is refused. Otherwise images go in the eviction order: images with no placement, transient ones first, then images placed only in the scrollback, each least recently used first, then images whose rules allow eviction while placed on the screen's own lines, oldest transmission first. A sixel placed on the screen's own lines is never evicted. The use clock moves only on stream events: storing an image, placing one, and a command that names an existing image, such as a kitty put or query by id or number. Drawing a frame moves no clock, so the eviction order never depends on which frames were drawn (test: `drawing_a_frame_moves_no_clock`). A handler reserves an image's bytes before it allocates them, as its payload arrives, and a reservation for a kitty id already in the buffer holds that image so nothing evicts it before its replacement is stored. The store keeps a ledger of the reservations it granted and has not seen spent, so it spends each reservation once: a copy of a reservation already spent gives back no bytes and releases no hold, an image stored with one reserves its whole cost, and a growth of one is refused (tests: `a_reservation_given_back_twice_gives_its_bytes_and_its_hold_back_once`, `a_reservation_an_image_spent_pays_for_no_second_image`). The store settles the charges of the pieces a screen event cuts when that event ends, so which pieces the budget refuses never depends on how the input was split into reads; the smallest pieces go first (tests: `pieces_the_budget_refuses_go_smallest_first`, and vtium-term's `the_charges_of_cut_pieces_settle_per_event_however_the_input_is_cut`).

A sixel placed over older sixels removes their parts under every cell it covers fully with opaque pixels, as text written there would; under a cell it covers only partly, at its edge or where it has a clear pixel, they stay and show through. Each older sixel under its box that then draws nothing goes too: one with no pixel set left, or one whose every set pixel lies under an opaque pixel of the new picture. chafa pads its frames with clear cells, and mpv's frames end inside a cell, and either way each frame replaces the one before it. The second kind of piece shows nowhere, so removing it changes no drawn pixel: `hidden_pieces_change_no_composite_pixel` composes 3,000 seeded random stacks of pictures with the rule and without it and finds no pixel that differs. Without it, two opaque pictures of the same size whose edge ends inside a cell leave the older one's pieces in the edge cells, and a stream of mpv's frames stacked 471 placements before the budget refused the next. The store never takes a picture drawn scaled, or made in another cell size, for hidden, and it reads at most as many pixels as the new picture has, leaving a piece it did not check in place. The maintainer accepted this reading on 2026-11-02 (test: `opaque_frames_that_end_inside_a_cell_leave_one_picture`). A sixel placed again over its own placement keeps its image: the store holds the image being placed through the cut that removes its older placements and never frees a held image, so the new placement shows it, and the charge that placement first took is given back (test: `an_opaque_sixel_placed_twice_over_itself_keeps_its_image`).

The store keeps the pixel buffer a handler filled as it is, with nothing copied, and the frame shares it. It keeps the buffer of the image it freed last, charged to the budget and freed before any image when a reservation needs room, and `Edit::take_spare` gives it to a handler that asks for one of its size once no frame holds it, with its charge as the handler's reservation, so frame after frame of one size reuses one allocation even under a budget that fits only the frame shown and the next. A handler that knows whether its picture is opaque, as the sixel decoder does for every picture but one with P2 of 1, says so in `NewImage::opaque`, and the store reads the pixels only when it does not know; a build with debug assertions checks the value given.

Two kinds of kitty placement have no line of their own (ADR-1100, D13). A relative placement, made by a put with `P`, follows another placement, its parent: its box's top left is its parent's origin plus `H` columns and `V` rows, where a placement's origin is the cell that held its box's top left as it was placed. The store keeps only the link and the offset, and works the box out from the parent whenever an event, a delete or a frame needs it, so whatever moves the parent moves its children: a scroll, the scrollback, a rewrap, a region scroll and a replacement by a put with the same image and placement id. A parent whose top a region scroll or a dropped scrollback line cut off keeps its origin, so its children stay where they were against its picture. A relative placement goes with its parent, and its own children with it, and an image left with no placement that way goes too, as the kitty spec asks. A put whose parent does not exist answers ENOPARENT, one that would follow itself ECYCLE, a chain past `RELATIVE_DEPTH_MAX` ETOODEEP, and `U=1` with a parent EINVAL, as the kitty spec asks (tests: `a_relative_placement_draws_at_its_parents_origin_plus_its_offset`, `a_relative_placement_follows_its_parent_through_a_scroll_and_the_scrollback`, `a_relative_placement_moves_with_its_parent_in_a_region_scroll`, `a_relative_placement_follows_its_parent_when_the_parent_is_replaced`, `deleting_a_parent_takes_its_children_and_images_left_without_placements`, `a_parent_that_does_not_exist_is_enoparent`, `a_placement_that_would_follow_itself_is_ecycle`, `a_chain_deeper_than_eight_relative_placements_is_etoodeep`, `a_virtual_placement_is_stored_on_no_line_and_only_a_delete_by_image_takes_it`). A virtual placement, made by a put with `U=1`, lies on no line, so no screen event reaches it; only a delete by image (`d=i`, `d=n`, `d=r`), its image's eviction or replacement, RIS and the alternate buffer's emptying remove it. A virtual placement draws only where placeholder cells show it, which vtium-term reads (below). When a placement's box changes, the store tells vtium-term which cells to redraw by naming a line, how many rows from that line the box starts, and how many rows and columns it covers. A placement on a line names its own line, and its box starts there. A relative placement has no line of its own, so the store names the line of the nearest placement up its chain of parents that has one, and `Region::row` says how many rows below that line the relative placement's box starts, a negative number when the box starts above it. A frame drawn while the view is scrolled back into the scrollback also needs the lines below the view, as many as `Store::reach_below` says, so that a relative placement drawn above a parent that has moved out below the view still shows (`Store::frame_with_below`). For eviction, an image a virtual placement shows ranks with the kitty images on the screen's own lines.

The placements at one layer and z form a stack, kept as placements arrive: a later picture goes on top, except that a picture whose image has a kitty id slides in directly beneath the first placement from the bottom whose image has a higher id, so nothing already shown moves. A sixel and a kitty picture at equal z therefore draw in the order they arrived (tests: `kitty_two_a_sixel_then_kitty_one_draw_one_two_sixel`, `a_later_picture_goes_on_top_whatever_its_protocol`). A kitty picture whose image has no id goes on top as it arrives, as a sixel does, and a later kitty picture looking for the first higher id passes over it (test: `a_kitty_picture_with_no_id_stacks_like_a_sixel`). A kitty placement that replaces one with the same image and placement id arrives anew in its stack (test: `a_replacement_is_a_new_arrival_in_its_stack`). A cut or a scroll that splits a placement keeps its pieces together at its place, in the order they were made: above, left, right and below for a cut, top to bottom for a scroll.

## How placeholder cells draw a virtual placement

A program shows a virtual placement by writing kitty's placeholder character, U+10EEEE, into the text, each cell naming the image, the placement and its row and column in the picture (ADR-1100, D13). vtium-term owns the cells, so it reads them and groups them into *runs*: side-by-side placeholder cells on one row that name the same image and placement, lie on one row of the picture and show consecutive columns of it. A `PlaceholderRun` is the run's line and first column, its cell count, the image id, the placement id or none, and the picture row and column of its first cell. The store never sees a cell; it takes runs at two times, and keeps none.

- **For a frame,** vtium-term hands `Store::frame_with_runs` the runs on the rows the view shows. For each run, the store finds the virtual placement of the buffer in use that the run names: by image id and placement id, or for a run with no placement id, that image's virtual placement made last. It takes the placement's picture as it was fitted to its grid of cells when it was placed, with its aspect kept and centered, and makes an entry for the part of it under the run's cells, anchored at the run's line and first column. Cells of a run that lie outside the grid or the screen, or that the fitted picture does not reach, draw nothing, and a run whose image or placement is not found makes no entry. The entries take their virtual placement's place in the draw order, row by row, then column by column, and each has a key of its own among the frame's entries, counted from 2^63, so a renderer that keys what it last drew on an entry's key tells them apart. A relative placement whose parent is virtual draws from its parent's *origin*: the least row and the least column over the parent's runs, each run's own picture row and column taken off first. When no run of the parent is handed, the child draws nothing.
- **For a decision,** a kitty delete by cell, row or column or of every placement on the screen (`d=a`), ED 2, or a reservation that may evict, vtium-term reads the runs on the screen's own lines and runs the decision inside `Store::with_runs`, so a virtual parent's children are deleted and ranked by where they draw there, and never by what a frame showed. A child whose virtual parent has no run there counts as lying on the screen's own lines. vtium-term reads these runs only while `Store::has_virtual_children` says a buffer holds such a child.

The store takes at most one run for each cell of the rows it is given, and leaves the rest. Each run costs one lookup in an index of the buffer's virtual placements that the call builds once, and the runs a decision takes count as input work. When a virtual placement is made, replaced or deleted, or its image is sent again, the store notes the buffer and the image id, and `Store::take_changed_virtual` hands them to vtium-term, which marks that image's placeholder cells changed. It does the same when a kitty frame edit changes the frame a virtual placement may show. A relative placement that follows a virtual placement has no box of its own, so when one is placed, deleted or moved, or its image's frame on show changes, the store notes where it draws relative to the virtual placement's runs: that placement's image id and placement id, whether it is its image's virtual placement made last, and the box's offset and size in cells. `Store::take_changed_floating` hands these notes to vtium-term, which finds the origin from the shown screen's runs and marks the box's cells. The store keeps at most twice `PLACEMENTS_PER_BUFFER` of these notes, and past that it reports the buffer as changed whole.

## How a kitty upload in chunks works

A kitty program can send one picture in several commands, its *chunks*: every chunk but the last carries `m=1`, and the first chunk's keys decide what the upload is. The kitty spec asks a program to finish an upload before it sends another graphics command, and to send nothing else between its chunks; it says that a delete ends an unfinished upload. Where the spec leaves the rest open, vtium follows kitty 0.49.2 (its `graphics.c`, `grman_handle_command`, `handle_add_command`, `handle_animation_frame_load_command` and `handle_delete_command`), except where a program that left an upload unfinished could spoil the next program's picture.

- **A command between the chunks.** A transmission or a frame sent directly (`a=t`, `a=T`, `a=q`, `a=f` or no `a`, with `t=d` or no `t`) is the upload's next chunk, whatever else it names but another image: the handler reads only its `m` and `q`. kitty-doom relies on this, since its later chunks repeat `a=f,r=1,q=2`. A chunk with a key that cannot be read, such as `f=99`, fails the upload, which then answers EINVAL once, at its last chunk; kitty's parser drops such a chunk instead, and the upload, short of its data, fails at its end. The same command from a file, a temporary file or shared memory ends the upload and runs as a command of its own, and so does a delete. A put (`a=p`) and a composition (`a=c`) run on their own and leave the upload open. Tests: `a_chunk_that_repeats_the_first_chunks_keys_still_continues_the_upload` and the `inside_an_upload_` tests in `src/protocol/kitty/tests.rs`, and `another_command_ends_an_upload_and_gives_back_its_reservation` for the delete.
- **An animation control between the chunks.** An `a=a` leaves the upload open. During a frame's upload (`a=f`) it acts on the image the frame belongs to, as kitty's does. During a picture's own upload it reaches the image of that id or number already stored, if there is one, and otherwise answers ENOENT: vtium reserves the picture's bytes at the first chunk but stores the image only when its last chunk arrives, so that no other command, and no frame, ever sees a picture whose pixels are half there. The upload's last chunk then replaces that image, so the control, though answered OK, has no effect on the picture that stays. kitty 0.49.2 makes the image at the first chunk, so there the control acts on the picture being uploaded. During an `a=q`, whose picture is never stored, the control names no image and answers nothing. Tests: `inside_a_pictures_upload_an_animation_control_reaches_the_image_already_stored`, `inside_a_querys_upload_an_animation_control_names_no_image`, `inside_an_upload_an_animation_control_acts_on_the_image_being_loaded`.
- **A chunk that names another image.** A transmission or frame sent directly that names an image by `i` or `I` other than the one the first chunk named ends the upload, which gives back what it reserved and answers nothing, and the new command runs on its own. A chunk that names no image, names `i=0` or `I=0`, which kitty reads as naming none, or names the upload's own image continues the upload. kitty 0.49.2 loads such a chunk into the open upload (its `graphics.c`, `handle_add_command`), so a program that left an upload unfinished makes the next program's first picture land in the wrong image, with mixed pixels, answered with the wrong id. kitty-doom's later chunks name no image, so it meets none of this. Tests: `inside_an_upload_a_chunk_naming_another_image_ends_it_and_starts_its_own`, `inside_an_upload_a_chunk_with_i_0_or_capital_i_0_continues_it`.
- **Anything else between the chunks, RIS and the end of the session.** While an upload is open, vtium-term tells the kitty handler about any output that is not a kitty string: text, a control, or another escape sequence, an OSC, a DCS or another APC string among them. The handler then drops the upload, gives back what it reserved and answers nothing, so the upload's next chunk starts a new command. RIS drops it too, and so does the end of the session the output came from, when the program in the console exits. kitty 0.49.2 keeps the upload open through all of these. vtium ends it because a program that dies part way through an upload must not leave its unfinished picture open to swallow the next program's first picture command. A program that sends its chunks back to back, as kitty-doom does, meets none of this. A multiplexer such as tmux forwards each chunk separately and can put its own output between them, so vtium may drop a picture sent through one where kitty keeps it; vtium makes no exception for a multiplexer. Tests: `output_between_chunks_ends_an_upload_and_the_next_command_starts_fresh`, `an_8_bit_st_ending_each_chunk_leaves_the_upload_open`, `ris_ends_an_upload` and `the_session_ending_ends_an_upload` in vtium-term's `tests/kitty.rs`, and `the_childs_exit_ends_a_kitty_upload_it_left_open` in the binary's `src/term.rs`.
- **A cancelled string.** A kitty string cut off by CAN, SUB or another control, or a kitty handler cancelled because kitty graphics went off, gives back the reservation of an upload in chunks and drops a request out. The handler's one `cancel` serves both, so a cancelled string whose keys passed `KEYS_MAX` also ends the upload. The upload's next chunk then starts a new command, which a program sending chunks never meets, since every chunk's keys are short. Test: `a_cancelled_string_whose_keys_passed_1_kib_still_ends_an_upload`.

## How kitty animation works

Kitty animation (ADR-1102) gives an image more frames. The image's own pixels are its first frame, the *root frame*. A program sends a later frame with `a=f`, as a rectangle of pixels laid on a *canvas*: a color, transparent black when the program names none, or an earlier frame. The store keeps a frame in one of two kinds. A *whole frame* holds every pixel of the image. A *change frame* holds only its base, the color or the earlier frame, and its *layers*, the rectangles the program sent, each with its offset and whether it blends over the canvas or replaces it. The store composes a frame into a whole frame when its command arrives if the image is at most `FRAME_WHOLE_MAX` bytes, if the frame's layers cover at least half of the image, or if composing it would apply more than `FRAME_CHAIN_MAX` layers. Before a command changes a frame that change frames are laid on, an edit (`a=f` with `r`) or a composition (`a=c`), the store composes each of those frames into a whole frame, so a frame never changes when another frame does.

Frames past the root are charged to the console's *frame allowance*, five times its image budget, and never to the image budget, so frames never evict a still picture. A whole frame costs its pixels at 4 bytes each and `FRAME_OVERHEAD` beside them, and a change frame costs the same for each of its layers. An image that holds a change frame is also charged for its cache at its full bound, `FRAME_CACHE_FRAMES` whole frames, whatever the cache holds. The handler reserves a frame's data before it allocates it, and the store reserves the rest of the command's cost before it composes anything. When the cost does not fit, the store frees whole animations of other images, least recently used first, and never the image's own frames or any root frame; when even that cannot make room, it frees nothing and the command answers ENOSPC. An image holds at most `FRAMES_MAX` frames. An animation command that names an image that does not exist answers ENOENT, as a put does (tests: `animation_commands_are_answered_as_a_put_is`, `a_frame_in_chunks_holds_one_reservation_and_answers_once`, `d_f_deletes_every_frame_but_the_root_and_needs_an_image`, `a_frame_from_the_helper_is_reserved_of_the_allowance_and_stored`, and the frame code's tests in `src/store/anim/tests.rs`).

The store records what the commands set: each frame's gap, the run state (`s`), the loops (`v`), the current frame (`c`), and two stamps that tell the binary's animation clock what a command changed. The frame stamp moves when a command makes a frame current, and the run stamp when a command sets the run state or the loops; `d=f`, `d=F` and frames freed for the allowance move both and leave the root frame current and the animation stopped. The store never records which frame is on the screen. A frame entry shows the image's current frame, as the commands set it; the binary's snapshot asks `Store::frame_pixels` for the frame its clock chose, and puts it on the entry with `FramePlacement::show`. A change frame composed for a snapshot goes into the image's cache, which no comparison, reply or decision of the store reads. The image's key, the frame's number and its pixel revision name the pixels, and the renderers key what they keep on all three.

## How sixel works

The sixel handler takes a DCS `q` string while sixel is offered. Its data goes to the decoder as the parser hands it over, so a picture costs its pixels and never the text that drew it: a 7680 by 2160 frame from `mpv --vo=sixel` is up to 29 MB of text and 65 MB of pixels. The decoder draws each dot in its register's color as the dot arrives, so a register defined again later changes only what is drawn after. It reserves the picture's pixels of the console's budget before it allocates them: raster attributes reserve the whole picture before any sixel, so a picture that cannot fit is refused before it is decoded, and a picture without them reserves as it grows, each side by at least a quarter, holding both buffers while the rows move across. A string that ends with its terminator stores the picture, with that reservation and the 512 bytes beside it, and places it; a cancelled string, or one that ends while sixel is not offered, gives everything back.

With mode 80 (DECSDM) reset, the picture's top left is the cursor's cell, a pending wrap counting as the last column. When the picture would pass the bottom margin, the scroll region scrolls up first, as far as it can, so a picture that fits the region moves whole; then the cursor goes down a row fewer than the picture's rows, as that many line feeds do. The cursor ends on the row of the picture's last pixel row, at its left column, or with mode 8452 in the column after its right edge, at most the last column. With mode 80 set, the picture sits at the screen's top left, cut to the screen, and the cursor stays where it is. With mode 1070 set, as `private-color-registers` starts it, each picture starts from the default registers, the VT340's sixteen colors and black; reset, the pictures share one set, which go back to the defaults on RIS, on each change of the register count in force, and when the host switches sixel off or changes `max-graphic-size`, `num-color-registers` or `private-color-registers`. The three modes reset only on RIS. While sixel is not offered, DECRQM reports each one's fixed state, and SM and RM still store it.

The decoder counts every byte it reads and every pixel it writes, allocates or copies as input work (D5), so a short string that draws many pixels, such as `!10000~`, stops the input call once the call's work passes its bound. The handler takes a run of string data through `Handler::feed_some` with the work the call has left, and the decoder stops right after the byte that passes it, so a call does at most its bound and one band's work.

A sixel dot is one square pixel, whatever pixel aspect the string's first parameter or the raster attributes' Pan;Pad ask for, as xterm, WezTerm and mlterm draw it. DEC's VT340 manual draws a dot twice as tall as it is wide unless the picture says otherwise; the maintainer chose square dots on 2026-11-01 (ADR-1100, D3). Test: `raster_attributes_size_the_picture_and_reserve_it_first`.

The decoder computes HLS colors exactly, in integers, and rounds a channel whose exact value lies halfway between two 8-bit levels up. Floating point rounds those halves up in some colors and down in others, by how the decimal fractions are stored; 2,747 of the 3.7 million HLS colors have such a half. Test: `hls_in_integers_matches_floating_point_but_at_exact_halves`.

## How iTerm2's pictures work

vtium-term's router hands the iTerm2 handler a complete OSC 1337 string whose text starts `File=`, `MultipartFile=` or `FilePart=`, or is `FileEnd`, while the iTerm2 switch is on (ADR-1103, D1). A `File=` string carries its keys up to the first `:` and the base64 file after it; a `MultipartFile=` string carries the keys of a *transfer in parts*, whose file then comes in `FilePart=` strings of any length and ends with `FileEnd`. The handler decodes the base64 into a buffer it reserves under the console's image budget as the buffer grows, up to `ITERM2_FILE_MAX` bytes of file and `ITERM2_PARTS_MAX` parts. A string without `inline=1` or a `File=` string without its `:` is dropped, and a new `File=` or `MultipartFile=`, RIS, a bound, base64 that does not decode, a budget refusal, the switch going off and an OSC 1337 string vtium drops each abandon a transfer and give its reservation back. Nothing is ever answered; the context's `note` receives why a picture was dropped.

Once the file is whole, the handler sends it to the image helper as inline bytes with the any-image flag, and the helper decodes it as PNG, JPEG or GIF by its first bytes (ADR-1101, D6). The handler stores the decoded picture under the sixel tag, so every rule of the sixel column applies to it, and places it at the cursor with sixel scrolling on, through the placement the sixel handler uses too. Modes 80 and 8452 are sixel's and do not apply: an iTerm2 picture always scrolls, and the cursor ends on its last row at its left column. `width` and `height` size the picture in cells, pixels, percent of the screen or at its own size, and `preserveAspectRatio` keeps its shape unless it is 0 (D3); the store draws it at exactly that size from its box's top left, and the box covers the cells it reaches. ADR-1103's "Where vtium departs" lists where vtium's handling differs from iTerm2's own. Tests: `a_picture_in_one_string_goes_to_the_helper_and_is_placed_under_the_sixel_tag`, `a_transfer_in_parts_gathers_its_file_across_parts_of_any_length`.

An animated GIF plays through kitty animation's frames (ADR-1102). The handler asks the helper for every frame, up to `FRAMES_MAX` and as many bytes as the frame allowance could hold, counting the frames of other animations it could free; the helper composes each frame whole, by the disposal method of the frame before it. Before a byte of the frames is copied, the handler reserves the first frame under the image budget and the rest under the frame allowance, ahead of the image (`src/store/iterm2.rs`); when the allowance refuses, it copies the first frame alone and the picture is still. It stores the frames past the first as whole frames, each with its gap, 10 ms a hundredth of a second and 100 ms for a delay of 0 or 1, sets the loops from the GIF's loop count (none plays the frames once, 0 loops forever, L plays them L + 1 times), and leaves the animation running from its first frame, so the binary's animation clock plays it. The picture keeps the sixel tag (D4), and the store reads every frame of it for the cell-by-cell rules: it covers a cell fully only where every frame does, and draws nothing in a place only where every frame draws nothing.

## Readings of the record

These follow ADR-1100 where its literal text leaves room.

- **ED 2 keeps the part of a sixel that lies in the scrollback.** ED 2 removes every placement whose rules say the clear screen code removes it, kitty's, with a row on the screen's own lines. A sixel loses the cells the erase clears, as D3 says text and erases cut it, so a sixel reaching up into the scrollback keeps its part there. D8 says ED 2 removes every placement on the screen's own lines; vtium reads that as their parts on those lines.

## Readings of the kitty spec

These follow the kitty spec where it leaves a choice open. Each stays vtium's reading until a black-box run of kitty confirms or corrects it (ADR-1100, D14).

- **A relative placement without `Q` follows the parent image's placement made last that has no placement id,** as D13 decides; with no such placement the put answers ENOPARENT.
- **`P=0` names no parent,** as an id of 0 names no image anywhere in the protocol, so the put is an ordinary one, and `Q`, `H` and `V` do nothing.
- **A raw frame without `s` or `v` reaches the image's right or bottom edge** from `x` or `y`. The spec says only that a frame's rectangle is the whole image where `x`, `y`, `s` and `v` are left out.
- **A change "covers half the picture" when its layers' areas add up to half the image's or more** (ADR-1102, D1, the second rule). Layers that overlap count twice, so a frame can only be composed whole earlier than its covered pixels alone would make it, never later.
- **`z` on any `a=f` sets the gap of the frame the command makes or edits,** the root frame's included; `z=0` keeps the gap the frame has, and a new frame's is 40.
- **`a=a` sets a gap only with both `r` and `z`.** With `z` and no `r` it sets no gap, since `r=0` names no frame.
- **`a=c` without `r` or `c` answers ENOENT,** as a composition whose source or destination does not exist does, since frame 0 does not exist. An `s` past 3 in `a=a` answers EINVAL.
- **A missing frame answers `ENOENT:image not found`,** the message a missing image gets, so the handler's replies stay a closed set of fixed messages.
- **`d=f` and `d=F` with neither `i` nor `I` delete nothing,** since the spec asks every animation command for one of them (ADR-1102, D5).
- **The text after ENOPARENT, ECYCLE and ETOODEEP is vtium's own.** The spec names the three codes and no message, so each reply is a fixed message of vtium's: `ENOPARENT:parent placement not found`, `ECYCLE:relative placement would make a cycle` and `ETOODEEP:chain of relative placements is too deep`.

## How kitty's palette formats work

Kitty's `f=8` and `f=16` send each pixel as an index into the terminal's palette, and `f=16` adds an alpha byte after each index (ADR-1100, D15). The kitty handler asks the terminal for its colors through `Context::colors` when the upload's first chunk arrives, resolves all 256 indices to colors once, and turns each pixel into a premultiplied color as its bytes arrive, so the store keeps its one pixel format. vtium-term answers with the palette its frames draw through. A host whose context gives no colors gets both formats refused with EINVAL, and so does the graphics query `a=q` with `f=8`, which programs use to find out whether the terminal takes them. Tests: `palette_index_pictures_store_the_colors_their_indices_give`, `a_palette_change_after_the_first_chunk_leaves_the_picture_as_it_arrived`, `palette_index_pictures_are_refused_where_vtium_cannot_take_them`, and `palette_indices_take_their_tables_colors_in_any_pieces` in `src/decode/raw.rs`.

Raw data sent directly and uncompressed that holds fewer bytes than its picture's width and height need is answered `ENODATA:Insufficient image data: GOT < WANT` in every raw format, with the bytes that came and the bytes needed, as kitty 0.49.2 answers it (`raw_data_short_of_its_picture_is_enodata_in_every_raw_format`). Raw data the image helper inflates short answers EINVAL, and a frame's data short of its rectangle answers EINVAL, as ADR-1102 decides.

## Departures from the kitty spec

- **A palette-index picture keeps the colors it arrived with.** Kitty's specification redraws an `f=8` or `f=16` picture whenever the terminal's colors change. vtium turns the indices into colors once, as the picture arrives, so a later palette change leaves it as it was (the maintainer, 2026-11-06).
- **`f=8` and `f=16` are taken only sent directly and uncompressed.** From a file, a temporary file or shared memory, or with `o=z`, they answer EINVAL, because the image helper's pixel description has no layout for palette indices.
- **A picture that arrived as palette indices takes frames.** The specification supports no animation for pictures in these formats. vtium refuses a frame sent as `f=8` or `f=16`, but stores the picture as colors, so frames in the other formats can be added to it.

## Bounds
