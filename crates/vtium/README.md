# vtium

The binary: the configuration and command line, the terminfo entry and the XTGETTCAP table generated from it, the session's command and environment, the respawn policy, the rules the terminal follows, and the seat and its heads wired to them through vtium-platform's loop. The rules are functions of what they are given, time included, so their tests need no VT, display or pty. The seat takes the time from the loop too: `tests/boot.rs` boots it with the fake VT, a video device in memory and a real child on a real pty.

## Setting it up

The vtium package (ADR-1500) installs `/usr/bin/vtium`, its glyph helper and the unit `vtium@.service`, and enables nothing. A build with images also installs the image helper, `/usr/bin/vtium-image`, and the sysusers file `vtium-image.conf`, from which `systemd-sysusers` creates the account the helper runs as at the login prompt (ADR-1101 D2). `vtium console` gives vtium a VT, or every VT, and takes them back (ADR-1500 D7). `enable` and `disable` need root, and as any other user they change nothing and say so; `status` runs as any user:

```sh
vtium console status                      # per VT: what systemd starts at boot, what logind starts when you switch to it, what runs now
sudo vtium console enable 3               # VT 3 is vtium's from its next start, and its getty is disabled
sudo systemctl start vtium@tty3.service   # start vtium on VT 3 now, which ends every session there
sudo vtium console disable 3              # VT 3 goes back to what it had from its next start
sudo vtium console enable --all           # every VT is vtium's, on a machine whose autovt@.service link does not name kmscon
sudo vtium console disable --all          # every VT goes back as vtium console found it
```

`enable --all` links `autovt@.service`, the unit logind starts on a VT when you switch to it and nothing runs there, to vtium, enables vtium at boot on VT 1, where logind never starts a console itself, and disables the gettys on VTs 2 to 6, so vtium starts on each the first time you switch to it. VT 6 is logind's reserved VT, where logind starts a console at every switch, even while the VT is in use, so `enable --all` and `enable 6` refuse while someone is logged in on VT 6 anywhere but inside a vtium running there, and `enable --all` also refuses while kmscon, the development install or a masked `vtium@tty6` is there without a link of VT 6's own, and says what to free first. A getty waiting at its login prompt on VT 6 holds no session: both verbs go ahead, and the next switch to VT 6 stops that getty, which ends nothing.

vtium console follows common convention: while a display manager is enabled, VT 1 stays the display manager's and its getty's, whatever VT the display manager uses now, and vtium takes other VTs. It never takes a VT that the system's intended configuration gives to another program: a unit enabled at boot that claims it, or an enabled display manager (linked as `display-manager.service`, or a display manager vtium knows by name enabled at boot), VT 1 and any VT its configuration names. What runs now adds to that and never frees a VT. A VT is held now when a graphical session or greeter is on it, which vtium asks logind for with `loginctl`, or when another console runs there as a unit named `PREFIX@ttyN.service`. A VT is held from the next boot when a unit that starts at boot names its getty in `Conflicts=`, as Arch's sddm.service names `getty@tty1.service`, or runs on it: an instance such as `cage@tty3.service`, or a unit with `TTYPath=/dev/tty3`. The display manager's own configuration adds the VT its greeter starts on: LightDM's `minimum-vt` (7 by default), greetd's `vt` or `--vt`, and SDDM's `MinimumVT`. Nothing frees a VT, neither a configuration file nor a greeter running on another VT. `enable N` refuses a held VT and says which signal it read, `enable --all` passes it by and says so, and `status` marks it and gives the reason under its table.

When vtium fails on a VT, its unit's fallback, `vtium-getty@.service`, runs `vtium console fallback ttyN`, which starts the VT's getty so that you have a login again. It starts nothing when the getty's start would stop another program: a unit that runs, waits to start or is enabled, and that conflicts with the getty, as a display manager conflicts with `getty@tty1`. Then the VT is left without a console, and the journal of `vtium-getty@ttyN` says why. It also starts nothing when it cannot ask systemd. Under a closed policy in vtium.conf the fallback skips itself (ADR-1401 D9).

Under a closed policy vtium writes `/run/vtium/ttyN.closed` at start, and removes it under an open policy, and `vtium-getty@.service`, generated from `install/vtium-getty@.service`, skips the getty while the file exists, so no failure of vtium starts a getty on its VT (ADR-1401 D9). Tests: `a_closed_file_writes_the_marker_of_its_vt`, `a_later_open_run_removes_an_earlier_closed_runs_marker`. `vtium@.service`, generated from `install/vtium@.service`, has `Restart=on-failure` with systemd's defaults, so a one-off failure brings vtium back after 100 ms, and past 5 starts in 10 s the unit stays failed with `start-limit-hit`; under a closed policy no getty then takes the VT. The unit also has `After=getty@%i.service` beside its `Conflicts=getty@%i.service`, since `Conflicts=` alone orders nothing (systemd.unit(5)) and the getty's stop, which hangs up and resets the VT (`TTYVHangup=`, `TTYVTDisallocate=`), would otherwise run at the same time as vtium's start. Tests: `test_install_writes_the_binary_the_units_and_the_manifest_and_swaps_the_getty` in `tools/vt/tests/test_vt.py`, and tier 3's `getty-fallback` and `start-limit` in `heads-closed-broken`.

Neither verb starts or stops vtium. Each prints the `systemctl start` or `stop` that does, and that command ends every session on the VT. Before `enable` changes a VT or moves `autovt@.service`, it records what was there in `/var/lib/vtium/console/`, the unit file each getty linked to included, and `disable` puts back exactly that. `vtium console` refuses a VT that kmscon holds (see "Sharing VTs with kmscon"). On a host that was not booted with systemd it changes nothing and says so, and there an inittab line or an init script runs `vtium --vt=ttyN --no-switchvt` on the VT ([docs/systemd.md](../../docs/systemd.md)).

### Sharing VTs with kmscon

kmscon, another console that draws a VT through DRM/KMS, and vtium can run on one machine, each on VTs of its own. When you switch to a VT that no console runs on, logind starts the unit `autovt@ttyN.service` there, N being the VT's number. systemd looks first for a link of that exact name, `/etc/systemd/system/autovt@ttyN.service`, which gives one VT a console of its own. Every VT without one falls back to the single template link, `/etc/systemd/system/autovt@.service`, so whichever console that link names gets all of those VTs. `sudo vtium console enable --all` points it at vtium. On Arch it points at the getty from the start, because systemd's package enables `getty@.service` when it installs; kmscon's own `sudo systemctl enable kmsconvt@` then fails on that link (it still enables kmscon at boot on VT 1), and only `systemctl enable --force kmsconvt@.service` points the link at kmscon. `vtium console status` says on its first line which console the link names.

**vtium holds the template link, and you want kmscon on one VT.** Give that VT a link of its own to kmscon. For VT 3:

```sh
sudo systemctl disable getty@tty3.service    # only where VT 3's getty is enabled at boot
sudo ln -s /usr/lib/systemd/system/kmsconvt@.service /etc/systemd/system/autovt@tty3.service
sudo systemctl daemon-reload
```

Nothing starts kmscon at boot or at once. logind starts it the next time you switch to VT 3 while no console runs there. `vtium console` sees the link and leaves VT 3 to kmscon: `enable 3` refuses it, `enable --all` names it and passes it by, and `disable` never touches it. The way back:

```sh
sudo systemctl stop kmsconvt@tty3.service    # ends every session on VT 3
sudo rm /etc/systemd/system/autovt@tty3.service
sudo systemctl daemon-reload
sudo systemctl add-wants getty.target getty@tty3.service    # only if you disabled VT 3's getty above
```

Use `add-wants` rather than `systemctl enable getty@tty3.service` there. `enable` also links `autovt@tty3.service` to the getty, and `vtium console enable 3` then refuses VT 3 until that link is gone.

`sudo systemctl enable --now kmsconvt@tty3.service`, run after the same `systemctl disable getty@tty3.service`, makes the same link and also starts kmscon on VT 3 at boot and at once. Without the getty's disable, systemd would start both kmscon and the getty on VT 3 at boot, and the two conflict. The way back:

```sh
sudo systemctl disable --now kmsconvt@tty3.service    # stops kmscon, which ends every session on VT 3, and takes it off boot
sudo rm /etc/systemd/system/autovt@tty3.service      # the link that disable leaves
sudo systemctl daemon-reload
sudo systemctl add-wants getty.target getty@tty3.service    # only if you disabled VT 3's getty
```

The guide prefers the hand-made link because two consoles started at boot both open the display card, and the second cannot draw while the first holds it. Do not run kmscon's own `systemctl enable kmsconvt@` while vtium holds the template link either. It fails on that link, and it still enables kmscon at boot on VT 1, beside vtium there.

**`/etc/systemd/system/autovt@.service` links to `kmsconvt@.service`**, as on a machine set up to run kmscon on every VT. `sudo vtium console enable N` gives vtium one VT at a time, and `sudo vtium console enable --all` refuses until kmscon lets go of the template.

**Moving from kmscon to vtium entirely:**

```sh
sudo systemctl disable kmsconvt@.service      # removes the template link and every VT's kmscon link
systemctl list-units 'kmsconvt@*'             # the VTs where kmscon still runs
sudo systemctl stop kmsconvt@tty2.service     # for each VT listed; ends every session there
sudo vtium console enable --all               # every VT is vtium's from its next start; it prints the command that starts vtium on VT 1 now
sudo pacman -R kmscon                         # if you want: removes kmscon itself
```

`systemctl disable` stops nothing, and logging out of a VT leaves its kmscon running. `vtium console enable --all` passes by every VT where kmscon still runs, names each one, and leaves its getty as it is, so that VT keeps its getty after a reboot. Stop kmscon there first, as above, or run `sudo vtium console enable N` for that VT once kmscon has stopped.

`pacman -R kmscon` leaves the `kmscon-terminfo` package, which holds the terminfo entry named `kmscon`. vtium sets `TERM=xterm-vtium`, whose entry the `vtium-terminfo` package installs, so vtium itself needs no `kmscon` entry. Keep `kmscon-terminfo` while anything still uses `TERM=kmscon`: a vtium run with `--term=kmscon` or `term=kmscon` in its configuration, `make vt-login` on a machine without the `xterm-vtium` entry, which then runs vtium with `--term=kmscon`, and an ssh login to this machine from a kmscon console elsewhere, which arrives with `TERM=kmscon`. Once nothing does, you may remove it with `sudo pacman -R kmscon-terminfo`.

### ssh from vtium

vtium sets `TERM=xterm-vtium` in its session, `TERM=vtium` when it runs with `--term=vtium` (another name of the same entry), or `TERM=kmscon` when it runs with `--term=kmscon`. ssh passes `TERM` on to the remote host, and most hosts have no terminfo entry by any of these names, so the programs there cannot look up how to drive the terminal, and the remote shell misbehaves: zsh, for one, echoes every keystroke.

The fix the maintainer uses is to wrap ssh in the shell's rc file on the machine that runs vtium, so that a plain `ssh` from vtium presents the remote host with `xterm-256color`, an entry nearly every host has. In `~/.zshrc`:

```zsh
if [[ $TERM == (xterm-vtium|vtium|kmscon) ]]; then
  ssh() { TERM=xterm-256color command ssh "$@" }
fi
```

In `~/.bashrc`:

```bash
case $TERM in
xterm-vtium | vtium | kmscon) ssh() { TERM=xterm-256color command ssh "$@"; } ;;
esac
```

Remote programs then use only what `xterm-256color` describes, and none of vtium's own capabilities that the entry lacks. On a host you own you can install vtium's entry instead, from a machine that has it (the `vtium-terminfo` package installs it):

```sh
infocmp -x xterm-vtium | ssh host tic -x -
```

`tic` run as a user other than root compiles the entry into that user's `~/.terminfo` on the host. With the wrapper in place, `command ssh host` skips it, so that host gets `xterm-vtium`.

## Reading the configuration

vtium reads `vtium.conf` and then its command line through the key table, `src/config/keys.rs`, and treats both as untrusted input (see "Bounds").

- **One file.** vtium reads `vtium.conf` in `/etc/vtium`, or in the directory `--configdir` names, and never `/etc/kmscon/kmscon.conf`, the file the released `kmscon` reads. They are separate programs, so on a machine that runs both, a change to one program's configuration never changes the other's (ADR-1500 D4). vtium takes the keys `kmscon` takes, and [docs/config.md](../../docs/config.md) says how to move a file from kmscon. vtium reads no seat file such as `seat0.seat.conf`: a seat's flow goes into `vtium.conf` with the rest (ADR-1403 D2). `configdir` is set on the command line only, since a file cannot name the directory it is read from. Tests: `vtium_conf_is_the_one_file_read`, `a_seat_file_beside_vtium_conf_is_not_read`, `configdir_names_the_file_read`.
- **Only a file that root owns is read,** or that the account vtium runs as owns when that is not root, and only when neither its group nor others can write it or a directory above it. vtium reads none of a file that fails, runs its compiled-in configuration, and says which path fails and the command that mends it, `chown root:root PATH` or `chmod go-w PATH`, because the file places keyboards and its `login` names the command vtium starts as root (ADR-1403 D3). Tests: `a_file_others_can_write_applies_nothing_and_says_how_to_mend_it`, `a_directory_others_can_write_refuses_the_file_below_it`.
- **Only a regular file is read,** opened without blocking and with `O_NOCTTY`, so that a tty never becomes the controlling one, and read whole up to `FILE_MAX`. A FIFO, a device or a directory at the path is reported and skipped, so a FIFO with no writer cannot hold the start. Test: `only_a_regular_file_is_read`.
- **A value that cannot be read is reported, and the rest of the file is read.** The key keeps the value a lower source set. A number is digits only, so `font-size=12px`, `sb-size=abc` and `sb-size=-1` are each reported, and a number past its key's bound is clamped to the bound and reported. Test: `a_number_out_of_bounds_is_clamped_and_reported`.
- **An unknown `palette` name is reported,** and the value a lower source set stands. Test: `a_palette_vtium_does_not_hold_is_reported_and_leaves_the_value_below`.
- **A `#` glued to a value stays in it.** By vtium.conf's one comment rule, which its sections share, a comment starts only at the start of a line or after a blank, so `sb-size=10#comment` is the value `10#comment`, which vtium reports it cannot read, keeping the key's default (ADR-1403 D4). Test: `comments_blanks_and_colors`.
- **`no-` turns off a switch only,** so `no-font-size=12` is not read as `font-size=12`.
- **A mode line is read whole:** a size is digits, each side 1 to 65535, and a card's or connector's name at most 63 bytes; anything else is reported. Test: `a_mode_that_does_not_read_is_reported`.
- **An option name is matched whole,** so `--lo` is not `--login`.
- **A command-line word that is not an option refuses the start,** with `--login` too: the word does not join the command, which comes only after `--`. `--login` with no command after `--` refuses the start as well. `check-config` is the one such word vtium takes, wherever it stands before `--`. The words after `--` are passed as given, bytes that are not UTF-8 included. Tests: `a_stray_argument_or_a_login_without_its_command_refuses_the_start`, `a_command_word_that_is_not_utf8_is_passed_as_given`.
- **vtium logs information messages and above by default, and `debug` adds debug messages.** There is no `verbose` or `silent`: a file or command line that sets either is reported as setting an unknown key.
- **A build without images reads the image keys and says nothing of them.** That build never offers sixel or kitty graphics, so vtium logs nothing about them.

## Heads

The seat runs what the sections of `/etc/vtium/vtium.conf` resolve to at the three levels of ADR-1401 D7, and never writes the file (ADR-1403 D3). With no file, or one with no section, it runs the compiled-in configuration's one `console` head, silently. A file that root does not own, that its group or others can write, or that cannot be read as a file is never read: the shipped rules run, and every head shows `vtium.conf not used: running the built-in configuration.` A trusted file runs under its policy, each error logged with its line and dropping what it takes: a valid file runs as written; a partly broken one runs what survives, with `vtium.conf has errors: running the parts without errors.` on every head; and a broken one runs the shipped rules with `vtium.conf not used: running the built-in configuration.` under open, and nothing under closed, where the boot display shows `vtium.conf has errors and counts as closed: all input is off.` and no input is delivered. Each console line is followed by its next step from vtium-settings's catalog, such as `To see why, run vtium check-config /etc/vtium/vtium.conf.` A head is a terminal of its own: its session's pty, screen and scrollback, its grid, laid out over its displays by the scaled rule (see "The font"), its density, zoom and rotation, and its font: the keys its look's section and its own section set, laid over the top level's, the look's `font-name` naming its frit (ADR-1403 D5). Each display walks the rules alone when it comes and joins the head the first match names; a display a rule sends `off`, or that no rule claims, is set off and logged, the latter with the rule that would give it the first head ready to paste. A DRM card sets such a display off before it announces it, a frame another master left included; a framebuffer's is set off after each wake-up and unblank. A head whose displays never appear starts no session, under `display-wait=forever` too. Each input device walks the rules alone when it comes: one a rule sends to a head delivers to that head alone, and one sent to `roaming`, or that no rule claims under the open policy, delivers to the active head; under the closed policy one that no rule claims is ignored. One sent to `ignore` is never opened, but under the open policy a keyboard, opened for the rescue key alone. Under vtium.conf's `mouse` off, the shipped rules send each pointer class to `ignore`, their tail that a partly broken open file's inputs walk included, so no pointer opens, one whose node also has udev's key class included. The active head starts on the head of the boot display, the connector lit at start, else the first connected one on the boot card, then the other cards, in the kernel's order, else the first head in the file with a display, and starts again as each display lights until the first key reaching a head or the first roaming chord, over every display lit since the start, one that left included, so a boot display lighting a turn late takes it and a display leaving never moves it; after, only the roaming chord and the anti-lockout guard move it: Ctrl-Super-Up to the next lit head that is not isolated, Ctrl-Super-Down to the previous, matched after the power keys and before the terminal's grabs, once a press. Only a roaming keyboard takes the roaming chord; pressed on a keyboard a rule sends to a head, it moves nothing and reaches that head's session as a key. The VT's keys switch the VT only from a keyboard that asks a head that is not isolated, its rule's head or, for a roaming keyboard, the active head; from an isolated head's keyboard they reach its session as keys, and from a roaming keyboard while no head is active they do nothing. Under the closed policy an event from a device the seat has no route for, as one queued before its device went, delivers nothing; under open it roams. A pointer moves within the grid of the head it delivers to, with the modifiers of the keyboards delivering there. The terminal of each head a keyboard delivers to has mode 1004's focus, so several hold it at once. The blank, the selection buffer and the power keys are the seat's. Each head holds consoles, a session each, one shown on every display of the head: it starts the `consoles` its section in vtium.conf gives as its first display lights, at most `head-consoles-max`, 4 by default, and every head together at most `consoles-max`, 8 by default, each head keeping its first and the others opening in the file's order, so the share does not depend on which display comes first. Ctrl-Super-Right and Ctrl-Super-Left show the next and the previous console of the head the keyboard delivers to, wrapping. Under the closed policy a head keeps the consoles it started with for as long as it runs: vtium takes Ctrl-Super-Return and Ctrl-Super-Backspace and does nothing with them, so neither reaches a session. Under the open policy Ctrl-Super-Return opens a console just after the one the head shows, starts the head's login in it on the grid the layout gives it, and shows it. Where the head has `head-consoles-max` consoles, or every head together has `consoles-max`, nothing opens: vtium logs a line naming the cap and shows a brief line at the top of the head, such as `No more consoles: desk has 4, its most.`, for `osd-timeout`, or 3 s under `never`, in place of the on-screen display's full line, and under `osd = off` only the log line. The new console's session starts while the console is still hidden, and the head shows it once the session runs. A session the chord cannot start leaves the run alive: vtium logs a line, the console leaves without being shown, so the console shown before is told nothing, its id stays given, and the head shows the notice `Console not opened: login could not start.`, a notice of a problem, which shows whatever `osd` says and goes as the guards' notices go. A session that cannot start at a head's start, or when a console's program starts again, ends vtium with status 1, so the unit's getty fallback takes the VT (see "The session"). Ctrl-Super-Backspace closes the console the head shows: its pty closes, so its programs get SIGHUP, and the head shows the console after it, or the first when it was the last; the closing console gets no focus-out and the console shown next gains the focus. On a head's last console it does nothing. Neither chord reaches a session, and from a roaming keyboard with no active head neither does anything. Each console keeps its own grid and zoom, and the head draws whole when the shown console changes. The font and the displays are the head's, so a hidden console's OSC 50 and blank sequences wait until it is shown, and its output after an OSC 50 waits with them; each console's OSC 52 selection is taken at once. A head's consoles run its section's `login`, else the `login` at vtium.conf's top level. Each console's session has `VTIUM_HEAD`, its head's name, and `VTIUM_CONSOLE`, the console's id, in its environment; a head gives its consoles ids from 1 as it opens them at its start, a console the chord opens takes the next id the head has not given, so no id is given twice in a run, and a console keeps its id when its session starts again. A console whose program exits keeps its place and follows the respawn policy, each console counting its own quick exits: under respawn its login comes back in the same console, from a hard reset, and no other console is touched; under `oneshot` the console ends and shows the notice that its session ended, the head ends once every one of its consoles has, and vtium exits with status 0 once every head has ended, a head whose display never lit counting as ended, since it has nothing to run. Quick exits past the limit, on any console of any head, end the run (ADR-1401 D1): every head's sessions hang up, and the log names the head. Under the open policy vtium then exits with status 1, so the unit's getty takes the VT, with no notice drawn. Under the closed policy it holds its VT, since a getty's login would take any keyboard: every head's display goes dark, no session starts again, no input is delivered, and the boot display shows that a session kept ending as soon as it started, for as long as vtium runs. Heads drawing one frit share its helper and its store, and a head drawing another frit has its own. The memory of every console and frit together is bounded (ADR-1401 D10; "Bounds"): each console's scrollback takes `sb-memory`, at most the most `sb-memory` may be on the machine, a quarter of its memory, divided by `consoles-max`, or by the heads when vtium.conf declares more, since each head keeps its first console, so every console's together stay within that quarter; on a 512 MiB machine that is 128 MiB, 16 MiB a console for `consoles-max`'s 8, and 2,684,354 bytes each for 50 consoles. Left unset, `sb-memory` follows each console's grid inside that share: on minspec's grids it is what the 16 MiB minspec peak leaves after the console's two screens at their worst, 5,242,880 bytes at 170 by 48 and more on a smaller display, and a larger display keeps 5,242,880 bytes, worked out again whenever the console's grid changes; a user who wants a deeper scrollback sets `sb-memory`, up to the share (ADR-1001, "Memory"). Each frit's glyph store takes the machine's store limit, 16 MiB below 2 GiB, divided by the heads, since a head draws one frit at a time, so every frit's store together stays within that limit: 16 MiB with one head, 1 MiB each with 16.

vtium draws its own over a head's frames, outside the terminal's cells, so no pty, scrollback or reply sees it (ADR-1401 D5, D7), with vtium-render's `Notice` and `Mark` in the built-in fonts, fitted to the head's cell. On a head drawing a frit, the overlay takes them from the frit's face's `Face::builtins`, so every character of a notice or the mark comes from the built-in fonts on one baseline, whatever the helper sent for the characters the terminal shows. A notice is a box of vtium's lines across the top of each of the head's displays: the start's console line for sections of vtium.conf it skipped or partly ran, on every head, naming no error, since the log holds the errors, no keyboard found by the start's scan on every head, the anti-lockout guard's on the active head, the rescue key's on the active head or, with no active head, on every head, and a console's notice that its session ended for good under `oneshot`, shown while that console is. Each says in plain words what happened. A head shows each notice once and the newest four (`NOTICES_MAX`), a repeat changing nothing. A notice ends on any key reaching its head, or 30 s after it is first drawn, but an ended console's, which stays and keeps no time; the frame beneath is drawn whole once it goes. The on-screen display, the OSD (`src/osd.rs`, ADR-1401 D5, vtium/vtium#169), draws each head's status in the box across the top of each of its displays and in its top-right cell. Under `osd = minimal`, the default, it is a `Mark` in the head's top-right cell, filled on the active head and hollow on the others, shown on every head with a lit display when the roaming chord or the anti-lockout guard moves the active head, and never in normal use. A head that loses its last display drops what it showed, and a head starting its sessions shows nothing. Under `osd = full` it is a line at the top of the box, such as `● desk · console 2 of 3`, shown on every lit head at those moves and on one head when it shows another console or its display returns after it had none. The box is drawn in the notice's colors while a notice is in it, and in the on-screen display's colors while the line is alone, and the dot is drawn in the on-screen display's colors. vtium.conf's `notice-foreground`, `notice-background` and `notice-border` set the notice's colors, and its `osd-foreground`, `osd-background` and `osd-border` set the on-screen display's; unset, they are vtium-render's `Colors::NOTICE`, dark on pale red, and `Colors::STATUS`, light on dark. Under `off` nothing of the status is drawn, and every notice still shows. Under `render-timer = osd` or `both`, the console measures each display's frames and, once a second, puts that display's render timer line, `Report::osd`'s frames a second, median time a frame and share of the screen drawn, in the box under the status line, whatever `osd` says, and draws the display again to show it. That redraw counts in the next second's figures, so the figures include the cost of showing them. The OSD stays for `osd-timeout`, 3 s by default, or always under `never`. `focus-mark` is read as the older name of the two keys, where they are unset, with a line in the log naming them.

The guards run after every display and input added or removed, and after a rescue (ADR-1401 D9), the anti-lockout guard and the rescue key on under the open policy and off under the closed one, and the display guard always on. Under open the display guard lights the boot display in the first head while the rules light no display, a `console` head where the file declares none, and lets it go dark once the rules light another. Under closed it lights the boot display for a notice alone, on a screen with no session that no input reaches, which stays until a head lights: `No head has a connected display.`, or the start's console line; a closed file with no heads stays dark; a DRM card announces a display the rules leave dark while vtium has none lit, so the guard can light it, and one the card set off at its bind while another was lit, never announced, the guard lets go for the card to scan again and announce once that one goes. A display the guard lit goes dark again by its power state. The anti-lockout guard, with a keyboard-class device present, makes every keyboard roam, opening an ignored one to deliver, while no keyboard reaches a head with a lit display, and makes the boot display's head the active head when lit, else the first lit head, with a notice and the on-screen display; each keyboard goes back to its rule once one reaches a lit head. `Ctrl-Alt-F<n>` for vtium's own VT, pressed on any keyboard, the ignored ones included, makes that keyboard roam for the rest of the boot, through an unplug for the newest 16 devices (`RESCUED_MAX`), with a notice naming the head the keyboard then types into, on that head, or saying that no head is active, on every head, under the open policy, unless the head its rule names is isolated; nothing is written. A keyboard the rescue key moved reaches a lit head while the active head is lit.

Each head composes its frames on a render thread of its own (ADR-1401 D2), so one head's redraw delays neither another head's frames nor the loop, which keeps the input, the ptys, the hotplug, the VT's switches and the devices: their buffers, cursor planes, blanking and flips. A frame is the head's screen, taken by the loop with the buffer token its display lends (vtium-platform's frame contract). The thread composes the frame straight into the token's buffer, writing only, drawing the cells that buffer lacks at its age, and the loop gives the token back with the frame's damage, so the display presents the buffer the frame was drawn into. No view keeps a copy of its display's frame, and nothing copies a frame between buffers: a display at 1920x1080 holds no 8,294,400-byte copy beside its own buffers. When vtium's notice box or the on-screen display changes, the renderer draws again the cells and the border under what it covered, so no buffer keeps it whatever its age, and a view whose display lost its picture draws its next frame whole. A display has one frame on its way at a time; a draw asked for meanwhile is taken from the screen as it is when the frame comes back, so no frame queues behind another. A frame that comes back once the VT is released or the displays blanked is dropped by its display, which draws whole at the next acquire, and a job the thread cannot take gives its token back unused. Its thread starts when the head's first display is set up. The thread's stack is 128 KiB, or 8 MiB when `hwaccel` asks for the GPU path (see the next paragraph), and when its head is dropped, at a new reading of vtium.conf and at the exit, the loop joins it. A thread that `hwaccel` gave a GPU is waited for at most `LET_GO_MS` (see "Bounds"), since a driver can hang destroying its GL context; past it the thread is left to end alone, and the log says the GPU driver did not let go. vtium keeps each thread it left, and joins it at the first drop of a head after it ends, as at a reload of vtium.conf, or at the exit, which frees the thread's stack. A thread that still runs at the exit may be inside the GPU driver, and the exit handlers of libEGL and Mesa would tear EGL down under it, which corrupts the heap or aborts, so vtium then flushes its output and ends at once without running its exit handlers, and the log says how many threads still ran. A test that leaves a thread on purpose joins it before it returns, and the GPU tests' seat joins every thread its app left as it drops. A reload of vtium.conf and the exit tell every head's thread to end first and wait for all of them against one deadline, so heads on a driver that hangs hold vtium `LET_GO_MS` in all. At debug level, under the `render` target, each head logs once a second while it draws its frames the time each took to compose, mean and largest.

A head whose `hwaccel` is on, in a build with the `gpu` feature, draws on the GPU path (ADR-1303 D9). Its render thread makes the head's GL context on the render node of the card that drives the head's first display before it takes a frame. The loop does not wait for that set-up: it takes the thread's answer at the turn the thread wakes it and logs each of the head's display lines then, and meanwhile it takes the input, reads the ptys and draws the other heads, while the head's frames wait in its queue. The first frame sent while the set-up is not known makes the log say once that the head waits for the GPU driver; a head whose set-up never returns draws nothing until vtium restarts. Tests: `start_returns_while_the_gpu_set_up_hangs_and_its_frames_wait_for_it` and `a_head_whose_gpu_set_up_hangs_holds_neither_the_loop_nor_another_head`, on a test GPU whose set-up waits until the test lets it go, `dropping_a_painter_whose_driver_hangs_letting_go_does_not_wait_for_it`, `letting_go_of_two_heads_whose_driver_hangs_waits_one_bound_in_all` and `heads_whose_driver_hangs_letting_go_hold_the_exit_one_bound_in_all`, which also checks each head's line saying the driver did not let go. The thread keeps a pipeline for each display, and draws each frame through it into a frame of the display's size kept in GL. The part of that frame the display's buffer lacks at its age is then read back into the buffer, which the display lends in memory as it does on the CPU path: that read is the staging copy (ADR-1401 D2), which every display takes until displays lend their buffers as dma-bufs. The notice box and the on-screen display go over the buffer afterwards, as on the CPU path. A set-up that fails at any step, a card with no render node such as a framebuffer, or a build without `gpu`, leaves the head on the CPU path, and the log says why. Each display's line names the path that draws it, `text renderer [cpu]` or `text renderer [gpu]` (ADR-1303 D10). During a run the GPU path sorts its failures by their kind (ADR-1303 D9): a frame a GL error fails, at any step up to the read back into the display's buffer, is drawn on the CPU path whole once the renderer forgets its history, so no buffer keeps part of the failed frame, and the next frame on the GPU path draws whole too; a GL error in two of one display's frames in a row or in three of its last 60 frames, an out-of-memory error, or a lost context, which a fence the GPU does not pass within `GPU_FENCE_WAIT_MS` counts as, leaves the head on the CPU path until vtium restarts. The loop then logs once why, and each of the head's displays' lines again, naming `cpu`. The loop logs a display's first frame the GPU path failed, naming the display's connector, and none of its later ones. The GPU path counts the errors in frames, never in time, so a fault that fails every other frame ends the path at its third failure, and a lone error ages out of the 60 frames before the next one comes. `crates/vtium/src/gpu/flap.rs` holds both rules of the window, and the cap on trips back below, in two small types with no GL in them, with table tests that drive each one through a sequence of frames. Tests: `a_gl_error_drops_one_frame_and_the_head_stays_on_the_gpu_path`, `a_gl_error_in_every_other_frame_ends_the_gpu_path_at_the_third`, `a_lone_gl_error_every_100_frames_never_ends_the_gpu_path`, `a_frame_whose_read_back_fails_leaves_no_ghost_in_the_other_buffer` (on a display that lends two buffers in turn), `a_displays_failed_gpu_frames_are_logged_once_by_its_connector` and `a_second_error_running_out_of_memory_or_a_lost_context_leave_the_gpu_path_once`, on a test GPU that fails the frames they queue a fault for, counted in frames. A display that leaves the head, unplugged, moved to another head or gone dark, is sent to the render thread after the frames sent before it, at the loop's next turn that finds room in the queue, and the GPU path frees its pipeline, with its upright frame and glyph pools, and its staging frame; a display whose mode changed takes new ones at its next frame. Tests: `a_display_that_leaves_frees_what_the_gpu_path_kept_for_it`, which counts the displays the GPU path keeps, and `a_display_that_leaves_while_the_queue_is_full_goes_once_the_queue_has_room`. When the head's VT is released, the render thread, after the frames sent before, gives back each display's glyph and picture textures, its upright frame and its staging frame, and keeps the GL context and its compiled programs, so a head in the background holds no textures; the first frame after the VT comes back makes them again and draws whole, and sets no display up again. The loop logs the GPU path's notes, such as glyph textures at their ceiling, naming the head. Tests: `a_release_gives_back_every_texture_and_keeps_the_programs`, `a_release_on_the_cpu_path_sends_nothing` and `a_head_on_the_gpu_path_gives_back_its_textures_while_the_vt_is_away`. A display's set-up on the GPU path is sorted the same way: out of memory or a lost context leaves the head on the CPU path until vtium restarts, and a GL error counts as one of the display's failed frames, so the next frame sets the display up again. A display is past the GPU's limits when its buffer is wider or taller than the GPU's largest renderbuffer or its largest viewport; the head checks that before it makes anything for the display, when the display appears and at each change of its size, and the log line names both limits. While every display takes the staging copy, the frame it reads back from is a texture, so a display past the GPU's largest texture is refused too. A set-up that fails for any other reason, such as a size past the GPU's limits or a shader that does not compile, puts the whole head on the CPU path while that display keeps its size, and the GPU path does not try the set-up again at each frame. The log says so once, naming the display's connector and its size, and gives each of the head's display lines again, naming `cpu`. The head keeps its GL context and each other display's pipeline meanwhile, and goes back to the GPU path when the display takes a size the GPU path sets up or leaves the head; the log then gives each display line again, naming `gpu`. A display whose next size meets out of memory or a lost context ends the head's GPU path instead, and the log does not say the head is back. A head goes back to the GPU path at most three times in a run: the fourth hold keeps it on the CPU path until vtium restarts, so a display that keeps re-plugging at a size the GPU cannot set up does not move the head between the paths at each plug, and the log says so once, as it does for any end of the GPU path. The hold clears every display's window of GL errors, since the CPU path draws the frames in between. Tests: `a_failed_set_up_is_sorted_by_its_kind`, on a test GPU that fails the set-ups a test queues a fault for; `a_display_the_gpu_cannot_set_up_holds_its_whole_head_on_the_cpu_path_until_it_leaves`; `a_hold_on_the_cpu_path_breaks_a_displays_row_of_gl_errors`; `a_display_the_gpu_cannot_set_up_holds_its_head_on_the_cpu_path_while_its_size_lasts`, which also checks that only the display that held the head is set up again, `a_head_held_on_the_cpu_path_goes_back_to_the_gpu_when_the_display_leaves`, `a_head_held_on_the_cpu_path_a_fourth_time_stays_there_until_vtium_restarts`, `a_refused_display_whose_next_set_up_loses_the_gpu_does_not_bring_its_head_back` and `a_display_refused_again_at_its_next_size_keeps_its_head_on_the_cpu_path`, on two displays of one head, one of which takes new modes, on a test GPU whose largest renderbuffer the test sets; `a_display_past_the_gpus_largest_renderbuffer_is_refused_before_its_set_up` and `a_let_go_and_a_refusal_in_the_same_frame_count_no_trip_back`, which takes a display refused at one size to another size refused too, four times, and counts no trip back; `a_mode_past_the_gpus_largest_renderbuffer_holds_only_its_own_head_on_the_cpu_path`, on two heads; `a_display_the_gpu_cannot_set_up_logs_once_and_its_line_names_cpu`; and `a_gl_error_in_two_of_a_displays_frames_in_a_row_ends_the_gpu_path`. The render thread's stack is 8 MiB whenever `hwaccel` asks for the GPU path and the card has a render node, also when the GPU path's set-up then fails, since the driver compiles its shaders on the calling thread, and Mesa's llvmpipe does so through LLVM. ## The session

- **`TERM` is `xterm-vtium` by default,** vtium's own entry, which the `vtium-terminfo` package installs. A program that does not read terminfo and guesses from the name treats a name that starts with `xterm-` as xterm-like, so mc, for one, turns its mouse on, and the entry reports the mouse in SGR form, which has no column limit; the X10 form stops at column 223. `--term=kmscon` names the entry for the released `kmscon`'s name; the entry the kmscon-terminfo package installs under that name reports the mouse in X10 form. Spec: ADR-1000, "The terminfo entry and TERM". Tests: `the_default_is_login_with_the_environment_reset`, `the_entry_reads`.
- **XTGETTCAP answers from the entry the session's `TERM` names, and only under that name:** from `install/xterm-vtium.ti` under `xterm-vtium` and `vtium`, from `install/kmscon.ti` under `kmscon`, and under any other `TERM` every name is unknown. vtium's entry holds every name and value of kmscon.ti, with `TN` and `name` naming `xterm-vtium` and with `sgr` leaving out SGR 8, concealed text, which vtium-term does not do yet (vtium/vtium#37), and adds `Su`, `blink`, `it`, `smam` and `rmam`, `smir` and `rmir`, `ccc`, `initc` and `oc`, `Cs` and `Cr`, `XR` and `RV`, and the cursor keys and Page Up and Page Down with modifiers. Both entries have `Ms` for OSC 52. The kmscon-terminfo package installs a different entry under the name `kmscon`: it lacks `Ms`, `Smulx`, `Setulc`, `Sync`, `XM`, `XF`, `E3`, `BD`, `BE`, `PS`, `PE`, `fe`, `fd`, `kxIN`, `kxOUT`, `smxx`, `rmxx`, `sitm`, `ritm` and `dim`, reports the mouse with `kmous=\E[M` where kmscon.ti has `\E[<`, and ends `setrgbf` and `setrgbb` with `;m`. A program that reads the installed entry sees fewer of vtium's abilities than vtium has, and one that asks vtium with XTGETTCAP gets kmscon.ti's answers, which tier 1's `xtgettcap` probe checks. Spec: ADR-1000, "The terminfo entry and TERM". Tests: `the_table_and_the_entry_agree`, `each_capability_does_what_it_names`, `each_entrys_name_gets_its_own_table`, `tools/conformance/tests/termcap.rs`.
- **Each session is told the terminal's name and version, and its head and console:** `TERM_PROGRAM=vtium` and `TERM_PROGRAM_VERSION`, over any the environment held, so a program can tell the terminal whatever `TERM` names, and `VTIUM_HEAD`, the head's name, and `VTIUM_CONSOLE`, the console's id (ADR-1401 D5). vtium sets no `KMS_START_SCRIPT`, a variable that names a script for starting a graphical session from the console, since vtium installs no such script (the operator's decision on vtium/vtium#21). A `login` word that is `$NAME` becomes that variable of the session's environment, after the environment is reset. Tests: `without_reset_env_login_keeps_vtiums_environment`, `each_console_is_told_its_head_and_its_own_id_through_a_restart`.
- **The session's command starts once vtium's VT is shown,** so under `--no-switchvt` it waits until the VT is switched to, and it starts at the end of the turn that sets the displays up, on the grid of every display set up by then (see "No display"), so it sees no SIGWINCH as it starts. A display set up a turn later, as one udev brings, still resizes the session (the operator's decision on vtium/vtium#99). A command started again starts on the grid the session runs on. Test: `the_child_starts_on_the_grid_of_every_display_at_the_start`.
- **A child's exit closes its pty after the output it left is read** (vtium-platform's README, "Behaviour"), and the next child starts from a hard reset (RIS).
- **The respawn limit times each start from that start, on the monotonic clock,** so after one slow restart a command that fails at once still meets the limit, and a slow exit after quick restarts starts the command again with the count reset. Quick exits past the limit, on any console of any head, end the run with status 1 under the open policy, so that the unit's `OnFailure=`, which does not count a status of 0 as a failure, starts the getty fallback (ADR-1401 D1, the operator's decision of 2026-10-31). Tests: `a_head_restarting_too_fast_ends_vtium_and_hangs_up_every_head`, `a_hidden_consoles_crash_loop_ends_the_run`.
- **A session outlives a restart of vtium** (ADR-1401 D13). vtium gives a copy of each session's pty master to a keeper: systemd's file-descriptor store, where the unit enables it, or else, when vtium runs as root on a VT, its holder, `vtium hold`, which listens on `/run/vtium/ttyN/hold`. Each copy is kept under the name `pty.<console>.<head>`, and vtium tells the keeper which masters run at the end of each turn, so it drops one whose session ended or whose console closed. While a copy stays open, the kernel does not hang up the pty, so a restart or a crash costs the session only its screen and scrollback. The vtium that starts next takes the masters back: when a head starts, it opens exactly the consoles it has kept masters for, within the caps, shows the one with the lowest id and opens no fresh console; each adopts its pty in place of starting a new session, sets it to the console's size, and sends SIGWINCH so the program redraws. A head with no kept master opens its consoles as it always does. vtium watches the process that leads the pty's session then, since it cannot wait for a process it did not start, and logs that session's end with no exit status. A session whose program ended meanwhile counts as the console's program exiting at the start, with no quick exit counted. A master whose head is gone from vtium.conf, for which the caps leave no room, or kept second for one console, is hung up. A keeper that fails, such as a holder that died, is given up with one warning, and a session the keeper has no room for is logged once and left unkept. As vtium leaves, it lets go of the sessions its keeper holds without SIGHUP; systemd's stop then closes them, or the next vtium takes them. No session inherits the variables systemd sets for vtium's own service: `LISTEN_FDS`, `LISTEN_PID`, `LISTEN_FDNAMES`, `NOTIFY_SOCKET`, `FDSTORE`, `INVOCATION_ID`, `JOURNAL_STREAM`, `SYSTEMD_EXEC_PID` and the `MEMORY_PRESSURE_` ones. docs/systemd.md says what the unit and systemd do. ADR-1401 D13 records how each of these was decided. Tests: `a_kept_session_goes_back_to_its_console_at_its_size`, `a_head_with_kept_sessions_opens_exactly_those_consoles`, `a_second_master_for_one_console_is_hung_up_and_the_first_kept`, `no_session_inherits_systemds_variables`, `a_kept_session_that_ended_meanwhile_counts_as_an_exit`, `a_kept_session_with_no_head_is_hung_up`, `a_held_session_outlives_the_vtium_that_started_it`, the store's and the holder's in `src/survive/tests.rs`, vtium-platform's `a_released_pty_leaves_its_session_to_the_pty_that_adopts_it`, and tier 3's `heads-survive`.
- **vtium never keeps a console with no session.** A console the open chord adds whose session cannot start leaves the head, which goes on showing the console it showed. A session that cannot start at a head's start, or when a console's program starts again, ends vtium with status 1 (`Exit::Spawn`), so the unit's getty fallback takes the VT instead of leaving a console that takes keys and runs nothing (ADR-1401 D1, D5). Tests: `a_console_the_open_chord_cannot_start_leaves_and_the_run_goes_on`, `a_failed_open_tells_the_console_shown_nothing`, `a_failed_open_mid_ring_keeps_the_order_and_uses_up_its_id`.

## The blank

After `dpms-timeout` with no activity every display powers down, and the next activity powers it up. Activity is the user's input: a key press, a pointer's move, a button or the wheel, and the wake-up after the user switches back to vtium's VT. A key release, a key with no keysym, a press partway through a compose sequence (a dead key's among them), the end of a pointer frame and the pointer's hide neither wake the displays nor restart the countdown, since none of them sends the session anything or moves the pointer: a release follows a press that already counted, a compose sequence counts at the press that ends it, and the end of a frame and the hide are vtium's own events. The Linux console woke on any keyboard event, releases included (`kbd_event` in the kernel's drivers/tty/vt/keyboard.c). A change in which displays are attached counts too, for now: the last display going ends a blank in force and resets the idle clock, and the blank does not run while none is attached; the first display, and each that comes after none, starts the countdown afresh. A display coming or going among others does not count, nor does a re-take: a re-take sets the displays up again and keeps the blank and its timer as they were, and while blanked its set-up waits for the input that ends the blank (the operator's decision on vtium/vtium#21). While the VT is another's, as a released fake VT is, the countdown blanks no display and the user's input is no activity, since the displays are the other session's; the acquire starts the countdown afresh and ends a blank in force. The idle lock (vtium/vtium#87) will count the user's input alone.

A program commands the blank with the Linux console's sequences while `program-blank` is on, as it is by default (the operator's decisions on vtium/vtium#79). `CSI 9 ; n ]` sets the timeout to n minutes, at most 60, and 0 turns the blank off; it also wakes the displays, as on the Linux console. `CSI 13 ]` wakes them as a key does. The program's timeout lasts until a program changes it, and RIS returns it to `dpms-timeout`; a change restarts the countdown and leaves a blank in force. Output alone never wakes the displays, so a clock redrawing every second does not keep them lit. `setterm --blank N` writes `CSI 9` only under `TERM=linux`; under vtium's own `TERM` it refuses. A program cannot blank the displays at once: the Linux console's only way, the `TIOCLINUX` ioctl, has no counterpart on a pty.

From outside the session, `SIGRTMIN+1` blanks every display at once and `SIGRTMIN+2` wakes them as a key does, so a script or a power daemon acts without writing to the session's terminal (the operator's decisions on vtium/vtium#79). The blank is the timer's, and input, a program's `CSI 13 ]` or `SIGRTMIN+2` ends it; while the VT is another's, a blank sent is dropped, since its displays are not vtium's to blank. Neither `dpms-timeout=0` nor `no-program-blank` holds the signals back. `vtium blank --vt N` and `vtium wake --vt N` find the vtium on VT N, the process named `vtium` holding VT N's device (major 4, minor N) on a descriptor past its stdin, stdout and stderr, which may be the VT it was started from; they hold it by its pidfd, look again that it is still that vtium, and send it the signal through the pidfd, so a process that took its pid in between is never signalled; they exit 1 when none is found or the signal fails, and 2 for an argument they cannot take. Under systemd, `systemctl kill --kill-whom=main -s SIGRTMIN+1 vtium@ttyN` sends it too; without `--kill-whom=main` the signal also reaches the login session, whose programs a real-time signal ends by default. Reading a process's descriptors and signalling it take the same right, so root and the user vtium runs as may send these, and a program on the terminal running as another user may not; a vtium started as root takes them from root alone. vtium's other signals are SIGTERM, SIGINT and SIGPIPE, and SIGUSR1 and SIGUSR2 for the VT's switches; the `SIGRTMIN+4` it sends PID 1 for `grab-power-off` is systemd's, never one vtium takes.

## No display

At start vtium waits `display-wait` (10 s by default) for a frame on a display's screen, counted from when its VT is shown, and with none by then it exits with status 1, so the unit's getty fallback takes the VT. The wait runs only while the VT is vtium's. When another program takes the VT before vtium's first frame is on screen, as X starting on another VT does at boot (#270), vtium waits for the VT to come back, as it does for a switch away later in its run. When the VT comes back, the wait starts again from the full `display-wait`. Under a closed policy it never gives up: it holds its VT and waits however long it takes, as under `forever` (ADR-1401 D8). A device whose displays are never set up, as when the modeset fails, counts as none, as does a display announced whose every frame fails to show. `display-wait=0` exits at once without one; `forever` waits for the first display however long it takes, for a machine whose only display is a USB adapter (DisplayLink, `udl`) plugged in at any time after boot. A frame reaches the screen at its flip, which the turn after its draw reads at the earliest, so the wait runs out at the end of a turn after its due time, and while a frame is on its way to a screen it waits up to 1 s more for the flip (`wait::FLIP_WAIT`), so that vtium does not exit just before a frame it has already sent shows; under `display-wait=0` a display set up when the VT is shown is drawn, and its flip read, before the wait decides.

A head's command starts once one of its displays is set up, on the grid of every display of the head set up by then, so it sees no SIGWINCH as it starts. While the wait runs with none, the command waits, and if vtium exits it never starts. Under `forever` with none, it waits for the head's first display however long that takes.

Once a display has come, vtium never exits for want of one. When a head's last goes, it logs it and does what the head's `when-display-lost` in vtium.conf says for that head (ADR-1401 D8); a mirrored head keeps its sessions while one of its displays remains. Under `keep`, the default, every head's and the compiled-in `console` head's, the head's sessions run on: the grid keeps the last display's size, so the program sees no SIGWINCH; the keys of the devices reaching the head still type into it, as the kernel console's tty takes them through an unplugged monitor; and the blank does not run (see "The blank"). Under `hangup` the head's sessions are hung up at once, as a serial line losing its carrier: every console's pty closes, its programs get SIGHUP, and each console follows the respawn policy, its session starting again in the same console, with its id, under respawn and ending under `oneshot`; a hang-up is vtium's, so it counts as no quick exit, and an exit read in its turn is the hung-up session's. Under `hangup DURATION`, such as `hangup 30s`, they are hung up the same way once the time runs out with no display back, each head keeping its own timer, which wakes the loop. A head comes back only on a display its rules match, logged and drawn whole, and the grid takes its size where that differs, one SIGWINCH (the operator's decisions on vtium/vtium#21). A head whose display never lit receives no key, even from a keyboard its rule claims; and the active head never moves because a head's display left or came back, but by the anti-lockout guard (see "Heads").

## Displays and frames

- **A frame its display cannot take yet is drawn once the display can.** A display takes no frame while a flip, a vblank or a modeset waits, while it is powered down, or while its card sleeps. A frame that meets one of these waits stays pending, and the loop draws it at the first turn the display takes frames again, with no timer, so an idle session never goes on showing an older frame; a display that keeps taking none does not wake the loop for it (vtium/vtium#174). Tests: `a_frame_that_found_no_canvas_is_drawn_once_the_display_lends_again`, `a_display_lending_no_canvas_does_not_spin_the_loop`, vtium-platform's `a_display_lends_a_canvas_exactly_while_it_is_ready_for_a_frame` and `the_display_is_ready_for_a_frame_while_awake_on_and_not_flipping`.
- **A display whose mode changes in place is laid out again at its new size.** A modeset can give a display that is already online a new mode on the same connector: when its test commit fails, every display falls back to its default mode, and a framebuffer wakes at whatever geometry another program set while the VT was away. The display then asks for a redraw, and vtium reads its size again, gives its view a new renderer at that size, sets the head's grid and its pty from the new layout, and draws the next frame whole. At every redraw vtium also reads the display's refresh rate again, whatever its size, so a mode that changes only the refresh rate paces the display's frames at the new rate (vtium/vtium#208, vtium/vtium#216). Tests: `a_display_whose_mode_changes_in_place_draws_whole_at_its_new_size`, `a_frame_composing_across_a_mode_change_is_dropped`, `a_mode_smaller_than_a_cell_and_back_draws_at_the_new_size`, `a_display_whose_refresh_rate_changes_in_place_paces_at_its_new_rate`, vtium-platform's `a_mode_changed_in_place_asks_for_a_redraw_at_the_new_size`, `a_geometry_changed_while_away_asks_for_a_redraw_at_the_new_size` and `a_refresh_rate_changed_in_place_asks_for_a_redraw`.
- **A renderer set that fails keeps the display's renderer, and the pointer on its cursor plane:** an arrow made from the failed set would have no font to size it by, and the pointer would show nowhere.

## Selection, copy and paste

The pointer drives vtium-term's selection, and the seat keeps one selection buffer: what the user copied last, or what a program set last with OSC 52 while `clipboard-write` is on. The console has no system clipboard. The middle button and the keys `grab-paste` binds, Shift+Insert by default, paste the buffer through vtium-term's `Terminal::paste`, filtered, and bracketed while the program asks with mode 2004. The buffer holds at most the text of the scrollback and the screen, or vtium-term's `CLIPBOARD_MAX` bytes from one OSC 52.

The pointer also drives OSC 8 links and OSC 133 prompt marks, as ADR-1002 decides. vtium tells the shown console's screen which cell the pointer is over and whether Ctrl is held, at each pointer event and each key press, so the frame names the link under the pointer and, while Ctrl is held, carries its URI for the overlay row. Letting go of Ctrl sends no key, so vtium also reads which modifiers a head's own keyboards hold, the keyboards that deliver to it, whenever a keyboard's modifiers change, a keyboard goes, the focus moves, the anti-lockout guard moves a keyboard or the VT comes back, when the keyboards start afresh: letting go of Ctrl or unplugging the keyboard that holds it ends the overlay. The overlay is the focus's. The head that loses the focus shows none unless one of its own keyboards holds Ctrl, though it still underlines the link under its pointer and still draws its pointer, and the head that takes it shows the overlay of the link under its own pointer at once while the keyboard that follows the focus holds Ctrl. A pointer that hides, or that is in the strip a display leaves past the grid, is over no cell, so it hovers no link; a click in that strip still selects at the grid's nearest cell. The pointer is over the shown console alone: a console chord leaves the console it hides hovering nothing, and the console it shows hovers the link under the pointer at once, with the Ctrl the chord holds. Ctrl+click on a link copies its URI into the selection buffer and clears the selection; nothing is opened and nothing reaches the program until the user pastes. Ctrl+right-click on a line of a command's output selects that output as whole lines and copies it. While a program tracks the pointer, both take Shift as well, as selection does. On the main screen Ctrl+Shift+Up moves the view to the nearest marked prompt above its top row and Ctrl+Shift+Down to the nearest below, or back to the live screen; on the alternate screen both keys reach the program.

- **With no mouse tracking, or with Shift,** the left button's drag selects and its release copies, a double click selects and copies a word, a triple click selects and copies a line, as xterm's `on3Clicks` default, `line`, does, and a fourth click starts again; the right button clears the selection, where xterm's extends it. A click with no drag, or a double click on a space, leaves the selection buffer as it was, as xterm's `SelectSet` takes a selection only when it is not empty. A key, the pointer hiding while the VT is vtium's, blanked or not, and a change of mouse tracking clear the selection. vtium-term's README says how the line is copied. Test: `a_double_click_selects_a_word_and_a_triple_click_a_line`.
- **A drag ends when the left button is no longer held, and at the VT's release,** since motion with no button held is not a drag. Test: `a_drag_ends_without_its_button_and_at_a_vt_release`.
- **The middle button pastes at its release,** by xterm's translation `~Ctrl ~Meta <Btn2Up>: insert-selection(SELECT, CUT_BUFFER0)`. **A key pastes too, once a press:** `grab-paste`, Shift+Insert by default, by xterm's translation `Shift <KeyPress> Insert: insert-selection(SELECT, CUT_BUFFER0)`. A repeat of the held key pastes nothing more, and the bound chords are matched before the fixed grabs. Tests: `grab_paste_binds_the_paste`, `a_hostile_selection_is_pasted_filtered_once_a_press`.
- **Shift selects, pastes and scrolls back while the program tracks the pointer.** Spec: xterm's `ShiftOverride` in `button.c`, with `shiftEscape` false, its default: a button, the wheel included, or motion with Shift held is not reported, and Shift and the wheel scroll the scrollback. vtium decides a button at its press, and the button selects or pastes, or is reported, until its release whatever Shift does meanwhile; xterm decides each event by the Shift held then. A program that asks with XTSHIFTESCAPE 1 (`CSI > 1 s`) that Shift reach it gets Shift in its reports, and then Shift selects, pastes and scrolls nothing, as xterm's `shiftEscape` true does. Tests: `shift_selects_and_pastes_while_the_program_tracks_the_pointer`, `shift_and_the_wheel_scroll_back_while_the_program_tracks_the_pointer`, `shift_pressed_during_a_reported_drag_changes_nothing`, `a_program_that_asks_for_shift_gets_it_in_its_reports`.
- **A wheel event is one report while the program tracks the pointer, else a zoom with Ctrl, else three lines of scrollback,** whatever its number of steps. On the alternate screen, while mode 1007 is set, as it is at start, a wheel step vtium does not report goes to the program as three cursor-up or cursor-down keys, one a line, as DECCKM encodes them; reset, the wheel scrolls the view as elsewhere. Spec: ctlseqs' alternate scroll, as vtium-term's mode table states it. Test: `the_wheel_sends_cursor_keys_on_the_alternate_screen_under_mode_1007`.
- **Natural scrolling** reverses the wheel's report and its scroll, and with them the cursor keys mode 1007 sends, and leaves Ctrl's zoom as the wheel turns. `natural-scrolling` is off by default, and vtium.conf or the command line sets it at the start (vtium/vtium#203). Tests: `natural_scrolling_reverses_the_wheel_but_not_its_zoom`, `natural_scrolling_turns_the_report_and_the_scroll_but_not_the_zoom`, `natural_scrolling_comes_from_the_file_and_the_command_line`.
- **The pointer hides after 20 seconds with no pointer event by default,** and not when a key is typed. `pointer-hide-timeout` sets the time, 0 never hiding it, `pointer-hide-while-typing` hides it at each key sent to the program, and `pointer-char` draws a character's glyph in place of the arrow (the operator's decisions on vtium/vtium#102). `soft-cursor`, off by default, has the renderer draw the pointer on every display and sets no cursor plane up. Tests: `typing_hides_the_pointer_under_pointer_hide_while_typing`, `soft_cursor_draws_the_pointer_in_software`.

## The power keys

The power keys are the seat's, second in the key order (`src/power.rs`).

- **A power key acts once a press.** A repeat of a held chord asks nothing more, since a held key asks once, and systemd takes seven Ctrl+Alt+Del in two seconds as a reboot that stops no service (`CtrlAltDelBurstAction=reboot-force`). Test: `a_bound_chord_acts_once_a_press`.
- **`grab-reboot`** is unbound by default. Bound, it is matched after the VT's keys and before the terminal's grabs, only while the VT is vtium's, and leaves the selection. It asks init with `SIGINT` while `/proc/sys/kernel/ctrl-alt-del` is 0 or cannot be read, as the kernel itself does for Ctrl+Alt+Del, and otherwise calls `sync()` and `reboot(RB_AUTOBOOT)`.
- **`grab-power-off` and `grab-suspend` power the machine off and suspend it.** Spec: systemd(1)'s `SIGRTMIN+4`, which starts `poweroff.target`; logind's `Suspend` method (org.freedesktop.login1(5)) in a build with `logind`, and where logind is not on the system bus or not built in, `mem` written to `/sys/power/state` (the kernel's `Documentation/admin-guide/pm/sleep-states.rst`) by a shell vtium starts, so the loop still serves the VT's switch to the kernel's suspend console. The operator's decision on vtium/vtium#21. Neither calls `reboot(2)`. A minspec build on a host running logind suspends through sysfs too, so it passes logind's inhibitors by and skips its `PrepareForSleep` signal: no other session's lock-on-suspend runs. Tests: `power_off_asks_init_and_suspend_asks_the_host`, `a_suspend_waits_for_the_last_one_to_wake`, vtium-platform's `no_logind_on_the_bus_is_told_from_a_refusal` and `the_sysfs_child_is_reaped_from_the_loop`, and tier 3's power variants.
- **`grab-power-off` warns where PID 1 does not take its signal.** At start and in `check-config`, vtium warns when the key is bound and PID 1 neither catches `SIGRTMIN+4` with a handler nor blocks it, by the `SigCgt` and `SigBlk` masks in `/proc/1/status`, or when the file does not answer. The kernel drops a signal sent to PID 1 that PID 1 neither catches nor blocks, so the key would power nothing off. sysvinit catches the signal with a handler. systemd blocks it and reads it from a signalfd, so its bit is in `SigBlk` and not in `SigCgt`. busybox init does neither. Tests: `grab_power_off_is_silent_where_init_takes_the_signal`, `grab_power_off_warns_where_init_neither_catches_nor_blocks_it`, `grab_power_off_names_why_an_unreadable_status_does_not_answer`, and tier 3's `power-off` and `power-off-sysvinit`.

## A fake VT

A fake VT is the VT vtium runs on when the seat has no kernel VTs. On it vtium holds the seat's keyboards and pointers open for as long as it runs, so that after Ctrl+Super+F12 releases the VT the same chord can take it back. While that VT is released, vtium still sees every key typed into the other session and drops each one but the chord. A pointer's move, button or wheel reaches no program and selects, pastes or zooms nothing, and no key or pointer action wakes a display, since the displays are the other session's. The mouse moving in the other session still arms the pointer's hide, and that hide hides the arrow and leaves the selection for the user's return. At the return the arrow stays hidden until the pointer moves, since vtium's input keeps adding up the moves made in the other session (vtium-platform's `src/input/pointer.rs`), so an arrow drawn at its old place would jump at the next move. A program on vtium's console can still set the keyboards' LEDs with DECLL. A held key's repeat timer still runs, and vtium drops its repeats. vtium takes no exclusive grab of a device (`EVIOCGRAB`), so the other session still gets all of its input. A kernel VT's release closes the devices instead. Tests: `a_released_fake_vt_keeps_the_keyboards_open_to_take_it_back`, `input_on_a_released_fake_vt_wakes_no_display`, `a_released_fake_vt_reports_no_pointer_action_to_the_program`, `a_pointer_hide_on_a_released_vt_keeps_the_selection`.

## Pictures

The `images` feature (ADR-1100 D10) builds vtium-term with its image store and router, vtium-render with the compositor's pictures, and vtium-image with the sixel and kitty graphics handlers. The minspec build, which leaves the feature out, carries none of that code. Every build reads the six image keys, `image-storage-limit`, `max-graphic-size`, `num-color-registers`, `private-color-registers`, `sixel` and `kitty-graphics` (ADR-1100 D11), and a build without images then draws no picture.

In a build with images, each console's terminal gets the sixel and kitty handlers, with `max-graphic-size` and the color registers' keys as their limits. At every turn of the loop, between two input calls, each head gives each of its consoles three host events (ADR-1100 D5), each only when it changed:

- **The budget**: `image-storage-limit`, or under `auto` four frames of the head's displays in RGBA, from 16 MiB to 192 MiB, worked out again when a display joins or leaves the head or changes size. A smaller budget evicts nothing at once; the store's next reservation evicts down to it.
- **What it offers**: sixel and kitty graphics, each while its key is on, the budget is above 0 and every display of the head draws pictures, which the CPU compositor does in this build. A head with no display yet offers them. A console that offers sixel reports DA1's attribute 4.
- **The cell size** its pictures are placed in: the head's cell for the console shown, the console's own for a hidden one. A picture keeps the cell it was made in, so a zoom draws it scaled.

The head's snapshot carries the frame's pictures to its render thread, each sharing its image's pixels (ADR-1100 D9). A renderer keeps scaled copies and its damage history under the image keys of one console's store, and every console's store numbers its keys from zero, so a console switch makes each display of the head a new renderer, as a font change does.

Kitty animations, and animated GIFs, which the store keeps the same way, play through each console's animation clock (ADR-1102 D3). The image store records only what the program's commands set: the frames, their gaps, whether the animation runs, its loops and the frame a command made current. At each turn of the loop the clock answers the commands that changed an animation, and moves each running animation on by its frames' gaps, passing over gapless frames, which have a negative gap and never show, its timer firing at most once every `ANIMATION_FLOOR_MS`. When a head takes its snapshot, the clock puts the frame it chose on every placement of an animated picture, asking the store for that frame's pixels once for each picture, and a turn that moves a frame draws the head again. `v=n` plays the frames `n` − 1 times and then stops on the last frame, and `v=1` plays them forever; a run started past the first frame plays to the last frame before its first time through (ADR-1102 D4). The clock arms no timer while nothing plays, while its console is hidden, or while another program holds the VT or the displays are blanked. When its console shows again, the clock works out from the time where each animation has got to and shows that frame at once, without playing the frames it missed.

A handler that needs the image helper (ADR-1101), for a file, shared memory, PNG or zlib, leaves a request, and its terminal takes no input until the reply. The helper is its own program, `vtium-image`, which reads what a program names and decodes it as the session's user, so the console, which runs as root, does neither. vtium opens the program `image-helper` names, by default the path vtium was built with (`VTIUM_IMAGE`), once at start, and refuses it by the glyph helper's rules, logging why. Each console has one image helper host from vtium-platform for as long as the console lives, and the host starts that console's helper from the opened program at the console's first request that needs it. At the turn that finds a request, the head hands it to the console's host with the console's session: the login child's pid and the owner of the pty, which vtium reads again for each request by reopening the pty's slave from its master (ADR-1101 D2). The host either answers at once, and the answer goes straight back to the terminal with the pty never paused, or sends the request: the head then pauses the console's pty, puts the host's socket in the loop so that the loop wakes when the reply arrives, and holds the reply timer, `head::images::REPLY_TIMEOUT`, 2,000 ms. The reply, or `FAILED` once the timer fires, goes back to the terminal, the replies the handler writes go to the program, the socket leaves the loop, and the pty resumes. The binary checks a reply's sizes against its request again before it hands it back. A failed reply, as from a lost socket or a reply that fails the host's checks, means the host has stopped its helper and counted a crash; when the timer fires, the head tells the host to stop its helper, and no crash is counted. The console's next request starts another helper. After three crashes in one session (`IMAGE_CRASHES_MAX`) the host starts no more helpers for that console, and the head tells that console's terminal that no helper runs, so the kitty handler answers such a request at once with the reply ADR-1100 D7 gives for "no helper": `EBADF` for a file, a temporary file or shared memory, and `EINVAL` for PNG and zlib. Every console answers the same way when vtium has no program to start. A session that ends drops its request out with no reply, so the reset that starts the next session takes, and the host stops its helper and clears its crash count. Other consoles, drawing and keys carry on while one console waits, and a console past its crash limit leaves the other consoles' helpers alone. A temporary file may lie in vtium's own `TMPDIR`, which reaches the helper when it is an absolute path. `App::set_image_helpers` puts a test's stand-in hosts in place of the real ones.

## The font

vtium draws frits, generated at run time by the helper (ADR-1200, ADR-1301 D2), and its built-in fonts, and parses no font file: vtium-font's PSF loader is behind a feature the binary leaves out.

- **At start** the font is `font-name` when a file or the command line sets it, else vconsole's (`vconsole.font=` on the kernel command line over `FONT=` in `/etc/vconsole.conf`), else none, and the built-ins draw with no line; `font-engine=unifont` or `8x16` draws the built-ins too (ADR-1200 D9). A head's look, its `[look NAME]` section's `font-name`, wins over these (see "Heads"). A name is the frit `NAME.vtfrit` in `/etc/vtium/fonts`; a name no frit bears becomes a one-source frit made on the fly, `source=file:PATH` for a path, as `font-engine=psf` gives one, `source=font:FAMILY` for an outline family, as `font-engine=freetype` or `pango` gives one, `source=vconsole` for vconsole's font, `source=kbd:NAME` for another name, which the helper is handed as text with no file, under the name it was given when that is a frit's name and as `generated` when it is not, as for a path or a family, since the helper refuses a request naming anything else (D1). A frit whose `cell=` or `size=` vtium cannot read draws the built-ins with one line naming the font and why. A source the helper cannot read gives the helper's own line, and the built-ins go on drawing.
- **A frit** is generated in the cell it states with `cell=WIDTHxHEIGHT`, in pixels, read as text before the first frame; else the cell its first source gives (#145). That cell is the helper's to tell, since the console parses no font: the console asks for it at the height it draws at, a configured `font-size` in points, else an outline frit's `size=` at the density, else the automatic rule, and waits at most 100 ms (`OWN_CELL_MS`), the one wait on the helper. It asks before the first frame, at an OSC 50 switch, and at each zoom of an outline frit; it asks again at a height only after a zoom, and every head drawing the frit shares each answer. A bitmap first source answers with its own cell, when every later bitmap source's cell fits in it, and with no `font-size` configured the console takes that cell at the largest whole multiple not over the display's automatic height, at least once, so a bitmap font keeps its own pixels whole (the operator's decision on #145, 2026-10-28). An outline first source answers with the cell the W rule gives at the height asked, which the console takes at that height alone (the maintainer, 2026-11-01). The answer, and not the frit's text, says which kind the first source is: a `font:` source that resolves to a bitmap font zooms as a bitmap frit, and when a bitmap first source is missing on the machine and an outline source answers, the frit zooms as an outline frit. A refusal, no answer in time, or an outline cell of another height, which gives the helper up, leaves the display's cell for a bitmap frit and the built-in font's width for an outline frit, with one line saying why. An answer that comes after the wait is kept (ADR-1200 D17, the maintainer, 2026-11-03): from the next frame each head drawing the frit that takes a cell from it draws in that cell, its grid laid out again, with one line, and a refusal that comes late holds as one in time does. A late answer is dropped where the frit already holds an answer that came in time: at the height asked for an outline frit, and at any height for a bitmap frit, whose answer holds at every height. An outline frit's `size=` is the size of its glyphs in the cell; a bitmap frit's is left aside. A configured `font-size` wins over the frit's cell and size (ADR-1200 D16); `font-size=0` does not. A head's look that sets `cell` gives the font the head draws that cell, over the frit's `cell=` and `size=` and over the top level's `font-size`, since the look is the more specific level; the look's own `font-size`, other than 0, wins over its `cell` (ADR-1403 D5). The built-in fonts take the look's `cell` too, so a head whose frit fails keeps the cell its look asked for. A head draws them alone when nothing names a font, when `font-engine` is `unifont` or `8x16`, when its look names `unifont` or `unscii-8`, when the frit named cannot be read, or after an OSC 50 switch to a built-in font. A built-in font that is named keeps its own strike in the cell: `unscii-8` draws its 8x8 glyphs at the largest whole factor that fits, centered, so a 12x24 cell draws them at their own size, since at twice that size they are 16 pixels wide, wider than the cell, and `unifont` in a cell smaller than its 8x16 is cut to the cell. A cell vtium picks a height for, from `size=`, `font-size` or the display, is as wide as the built-in font at that height (D17); the display's height is `font-size=0`'s automatic rule (see `font-size` below): 8x8 at 320x240, 8x16 at 640x480, 8x19 at 1366x768. The built-ins draw in the cell from the first frame: unifont at the largest whole factor that fits, else Unscii-8, centered in a larger cell and cropped to a smaller one. The helper generates for that cell and never moves it, so the grid resizes only at a zoom or, while the cell is the display's, a display hotplug. The frit's `glyph-source=` and `glyph-source-<range>=` lines are the font's sprite policy, and the configuration's keys override them (D1). The console starts `vtium-config serve` on the first need, as `nobody` when vtium is root, under the operator's fill model (2026-10-28): the characters the screen shows, or newly shows, are asked for and answered first; while nothing is asked the helper fills each display cell's coverage, the screen's characters, then printable Latin and box drawing, then the rest, a waiting ask answered before its next batch. Each answer is checked for bounds and dimensions and for being what was asked, kept in memory for the boot, and redraws only the cells that show its characters; a character the frit lacks draws in the built-in font (vtium/vtium#141). The frits' stores together hold 16 MiB below 2 GiB of memory, 64 MiB from 2 GiB and 128 MiB from 4 GiB, each frit's that limit divided by the heads (see "Heads"): a fill stops at its store's limit, and an ask past it evicts the sets least recently on the screen, which are asked for again when the screen shows them. A helper that answers what is not a frame or not asked, or fails, is given up for the boot and logged once, and the built-ins go on drawing; one that crashes, reaches its CPU limit, gives no answer for 10 s (`ANSWER_MS`), leaves an ask unanswered for 60 s (`REQUEST_MS`) or exits with work outstanding is started again, at most 3 times a boot (`RESTARTS_MAX`). The console reads the kernel's font from its VT once at start, before the VT turns graphical, and hands it to the helper with each request for a frit's `console:` source (D8).
- **Bold and italic** come from the helper by ask (ADR-1200 D21). The console keys each glyph by its text and its style, bold, italic, both or neither, and asks for each style the screen shows in a request of its own that names the style; the helper draws it from the frit's face for that style, or synthesises it (vtium-config's README, "Styles"), and the console refuses an answer whose strikes are of another style than the one it asked for. The fill brings regular glyphs alone. Until a styled glyph arrives, and where the helper gives none, the built-in font draws it in its own synthetic style: widened for bold and sheared for italic, a pixel row at a time about its baseline (ADR-1302 D4). Tests: `an_italic_ask_names_its_style_and_its_glyphs_are_held_as_italic`, `a_strike_in_a_style_not_asked_for_gives_the_helper_up`, `a_style_draws_its_own_glyph_else_the_built_in_fonts_in_that_style`, `italic_and_bold_text_is_asked_for_in_its_style`.
- **The built-ins** are Unscii-8 for cells under 16 pixels and unifont from 16, but in a zh, ja or ko locale, whose characters Unscii-8 lacks, unifont at every size (D7). The locale is the first of `LC_ALL`, `LC_CTYPE` and `LANG` vtium starts with.
- **Sizes are points,** 1/72 inch (the operator's decision on #145, 2026-10-28): `font-size` and an outline frit's `size=` draw at points × DPI ÷ 72 pixels, to the nearest pixel, a half away from zero (`font::points_to_pixels`), at most vtium-font's `CELL_SIDE_MAX`. The density is `display-dpi`, with no line logged; else each display's, measured from the physical size it reports (vtium-platform's `Density`), down its rows as vtium draws it; else 96 DPI, with one warning for each display that reports none. Where displays differ, the lowest density converts, and a larger display draws larger by the layout rule; the team lead accepted this reading for the operator to confirm (2026-10-28). A configured `font-size` follows the displays' density until a zoom. `vtium check-config` opens no display, so it notes the density's source on standard output, outside its exit status, and the start logs each display's. Points do not apply to bitmap fonts: an all-bitmap frit takes its stated `cell=` or its fonts' own cell, and the built-ins step by their strikes. A `cell=` stays in pixels, an exact override.
- **Line spacing** (ADR-1302 D13): `font-line-spacing`, at the top level or in a look, else the frit's `line-spacing=`, adds a whole percentage of the text's height to each row, split evenly above and below the text band with the odd pixel above, so the grid has fewer rows. The cell a look or a frit states, `cell` or `cell=`, is exact and takes none; the cell vtium works out takes it, the cell a configured `font-size` gives in place of a frit's `cell=` included. The text's height stays the height asked for, so zoom and `font-size` step as before. The console tells the helper the rows added with each ask and fill, and the helper places its glyphs in the taller cell. The console asks for, and holds, a frit's glyphs by the cell and its rows added, since two heads can draw one cell size with different spacing. The built-in font's glyphs are placed by their default fit: line and block characters stretch by repeating their top and bottom rows, and the rest keep their size with blank rows above and below. The sprites draw at the whole cell, so they join from row to row, and the underline and strike-through move down with the text band. A session's end reads `font-line-spacing` again with the other font keys (ADR-1201 D11), so the next login draws with the spacing vtium.conf names then, and the font is drawn again when it changed.
- **`font-size`** picks the built-in's strike of its height in pixels, else the tallest under it scaled by the largest whole factor that fits. `font-size=0` picks it from the smallest display: the height that gives at most 120 columns, taking a cell as half as wide as it is high, and at least 40 rows, and never under 16; but where 16-pixel cells would leave fewer than 80 by 25 cells, the font's smallest height, so 320x240 draws 40 by 30 cells of 8x8 (vtium/vtium#118). The fallback is tried once: when no font is in use yet and the lookup fails at the size asked, vtium tries `FALLBACK_SIZE`, 16, and a second failure is the error; with a font in use, as at a zoom, a failure leaves that font. Tests: `a_small_display_takes_the_fonts_own_height`, `a_320x240_display_draws_40_by_30_cells_of_8x8`.
- **Zoom** steps through the font's sizes (D17): a frit whose first source is an outline font, by 1 point, to the next whole point whose pixels at the density differ, each height in the helper's cell for that height, else as wide as the built-in font there, but its stated cell's, down to the built-in's smallest; a bitmap frit by its stated or own cell's whole multiples, and the built-ins in a look's `cell` by that cell's; the built-ins in their own cell, and a bitmap frit with no cell, stated or own, through Unscii-8's 8 and unifont's 16, 32 and on. Below the smallest it stops with one line naming the font and its height, and a zoom in from a height above 150 pixels (`ZOOM_IN_MAX`) does nothing. Tests: `zoom_steps_through_the_strikes_and_their_multiples`, `zoom_steps_through_the_built_ins_and_stops_at_the_smallest`, `an_outline_frit_zooms_by_one_point`, `a_zoom_steps_an_outline_frit_by_one_point`.
- **The helper** is the program `font-helper` names, and the frits are in the directory `font-frits` names, each by default the path vtium was built with (`VTIUM_FONT_HELPER` and `VTIUM_FONT_FRITS`). vtium opens the program once at start and starts every helper from that open file, so a running console keeps the helper it started with across a package upgrade; it refuses a path that is not absolute, a file that is not a regular file, a setuid or setgid file, a file owned by an account other than root or the account vtium runs as, and a file its group or others may write, and logs why (ADR-1200 D15). The opened file is close-on-exec, so neither the helper nor the session holds it. The helper starts through `/proc/self/fd`, which the kernel lets a process read as any account, so vtium needs `/proc` mounted to start it.
- **OSC 50,** under `allow-font-ops`, on by default, switches the live console to a frit in `font-frits`'s directory or a built-in the name names, on a new grid with a pty resize, as a zoom does; a frit gets the helper and the store every head drawing it shares, and the built-ins draw what the helper has not yet sent. Anything else, a path, a name no frit bears or a frit whose cell cannot be read, leaves the font with one line saying why. Its query names the frit or built-in in use, a frit made on the fly by the name it was given. The output after a font asked for waits for the turn that switches, so a query written with it, as `vtium-config set` writes it, names the new font. A switch lasts for the session it came from. A session ends when its program exits, when vtium hangs it up under `when-display-lost = hangup`, or when the close chord closes its console. When that session ends, or the session in the head's only console, vtium reads vtium.conf's `font-name`, `font-size`, `font-engine` and `font-line-spacing` again with the reader it starts with and returns the head to the font they give, at their size and spacing, before the console's next session starts; a zoom made in the session that ended is undone with it (ADR-1201 D11). A session ending in another console of the same head leaves the font. Where the `font-size` read again turns a configured size on or off, the frit the head draws is rebuilt to drop or take its own cell. An OSC 50 request that a hidden console still holds goes with its session. A font key that does not read is reported and dropped, as at the start; every other key, and its reports, wait for the next start.

- **A cluster draws its own glyph, keyed by its whole text** (#144, ADR-1200 D20 to D22). The console asks the helper for each cluster the screen shows, the helper shapes it with HarfRust and draws it whole, and the store keys it by its text. Until it lands, and where the helper gives none, a cluster draws its NFC form's glyph where that is one codepoint the store holds, else its base's glyph with its marks, leaving out the default ignorables and the rest of an emoji sequence. Where the helper is unavailable, every cluster draws so, and the one line that says so names it. The arrival of a cluster's glyph redraws each cell showing any of its characters. Tests: `a_cluster_draws_its_own_generated_glyph`, `a_cluster_draws_its_precomposed_form_from_the_store`, `a_base_draws_with_its_marks_overstruck`, `a_cluster_the_screen_shows_is_asked_for_whole`.
- **The part of a cluster the font draws, in a build with the bidi feature** (ADR-1200 D22 step 3): where the font set has no glyph for some marks of a cluster, as no shipped font draws the superscript alef over lam with shadda and fatha, the helper sends the cluster without those marks under its own key, and the console takes it though the ask named only the whole cluster. Such a console asks with the request kind that takes parts; the minspec build asks with the plain kind, gets no part, and draws the cluster from its base and marks as before, so it carries none of this. The lookup draws that part as the font shapes it and lays the missing marks over it, from the store or from the built-in font. Tests: `the_part_of_a_cluster_the_font_draws_is_taken`, `a_joined_letter_draws_the_part_of_it_the_store_holds`.
- **Joined letters, in a build with the bidi feature** (ADR-1004 D6). The console asks the helper for each letter of a joining script keyed with U+200D on each side it joins, for lam followed by alef as their ligature, and for the Arabic presentation form each of those draws where no font holds the joined form, reading what each display shows through `deferred::read_shown`, which tier 2 and the specimens read through too. The lookup tries the key first. Where the store does not hold it, a letter draws the presentation form of its joined form, from the store where the frit holds that codepoint, else from the built-in font while the store holds nothing for the letter, so a letter the frit draws never takes a joined form from another font; and else its own glyph, unjoined. Lam-alef draws its ligature's presentation form the same way, else lam's joined form in the right cell and alef's final form in the left. `gen-lookup` generates the presentation-form tables from UnicodeData.txt. The built-in font draws through the same lookup in such a build, with a store that stays empty, so GNU Unifont joins Arabic by its presentation forms. The arrival of a presentation form's glyph redraws the cells that show the letters it presents. Tests: `a_row_of_arabic_asks_for_its_joined_forms`, `the_built_in_font_draws_a_joined_letter_by_its_presentation_form`, `a_joined_letter_draws_from_the_store_before_any_presentation_form`, `lam_and_alef_draw_their_ligature_or_their_two_forms`, `an_arrived_presentation_form_redraws_its_letters`.
- **A cluster drawn from its parts** (ADR-1302 D14): the base's glyph takes each nonspacing mark's glyph over it. A spacing mark (General_Category Mc), such as a Devanagari vowel sign, stands beside its letter instead: after it, or before it where its Indic_Positional_Category is Left, Top_And_Left, Bottom_And_Left or Top_And_Bottom_And_Left. A two-part vowel sign is drawn as its canonical parts. Where a letter and its spacing marks need more room than the letter's cells, they scale sideways together to fill them. A mark the font already draws in place keeps the font's placement: GNU Unifont draws every Devanagari, Bengali, Tamil and Malayalam vowel sign beside its letter, in a box as wide as the letter's, and Myanmar's medial ra as a bracket round its consonant. Tests: `a_spacing_mark_stands_after_its_letter`, `a_pre_base_spacing_mark_stands_before_its_letter`, `a_letter_and_spacing_marks_wider_than_the_cells_scale_to_fit`, `a_spacing_mark_the_font_draws_beside_its_letter_stays_there`, `a_pre_base_mark_drawn_after_its_letter_moves_before_it`, `a_mark_drawn_before_its_letter_moves_after_it`, `a_spacing_mark_the_font_draws_round_its_letter_stays_there`, `a_mark_in_a_box_wider_than_its_letters_stands_beside_it`.
- **A frit's glyphs arrive while the console runs, and their arrival damages only the cells that show them** (#145, #149, the operator's decision, 2026-10-28). Arrival is a damage source on the same path as program output: the answers that land between frames merge into one set per cell, the next frame draws it once, the cells drawn are read from the view each buffer shows, scrollback and clusters included, a fill of characters no buffer shows draws no frame, and an eviction at the store's limit damages nothing. A character the frit lacks draws in the built-in font, unifont from 16 pixels and Unscii-8 under 16, before the replacement glyph (vtium/vtium#141, ADR-1200 D7 and D22). Test: `a_character_the_frit_lacks_draws_in_the_built_in_font`.

## Bounds

A configuration file is untrusted input. The bounds of each key's value are in `docs/config.md`.

| Bound | Value | Past it |
|---|---|---|
| `FILE_MAX` | 65,536 bytes of a file | The rest is not read, and the file is reported |
| `LINE_MAX` | 8,192 bytes of a line | The line is ignored and reported |
| `TEXT_MAX` | 4,095 bytes of a text value or a `login` command, `PATH_MAX` less its NUL | The value is ignored and reported |
| `REPORTS_MAX` | 64 reports | The rest are counted in one report |
| A head's render thread | a stack of 128 KiB, or 8 MiB when `hwaccel` asks for the GPU path, 16 frames each way, a frame on its way per display | A frame the full queue refuses goes back to its display, which draws at the next turn; the thread waits while the loop has not taken what it composed |
| `LET_GO_MS` | 3,000 ms the drop of a head waits for a render thread that `hwaccel` gave a GPU to end, and a reload of vtium.conf or the exit for every head's together: its frame's fence wait, at most `GPU_FENCE_WAIT_MS` (vtium-platform's bounds), and the driver destroying the head's GL context (ADR-1303 D9) | The thread is left to end alone, and the log says the GPU driver did not let go; an exit while it still runs skips the exit handlers |
| `head-consoles-max` | 4 consoles a head by default, 1 to 50 | A head's `consoles` past it opens this many, with a warning |
| `consoles-max` | 8 consoles every head together by default, 1 to 50 | Each head keeps its first; the others past it, in the file's order, do not open, with a warning |
| `HEADS_MAX` | 16 heads vtium.conf declares (vtium-settings's bounds) | The file is invalid, and the shipped rules run |
| A console's scrollback | `sb-memory`, at most a quarter of the machine's memory divided by `consoles-max` or by the heads, whichever is more | Its oldest lines go, as past `sb-memory` |
| `REPLY_TIMEOUT` | 2,000 ms a request to the image helper is out, in a build with images (ADR-1100 D7) | The request fails, the helper is stopped with no crash counted, and the console's pty resumes |
| `ANIMATION_FLOOR_MS` | 10 ms between two firings of the animation clock's timer, in a build with images (ADR-1102 D3) | A frame whose gap is shorter shows at the next firing, or is passed over when its time has gone |
| A frit's glyph store | the machine's store limit (16 MiB below 2 GiB, 64 MiB from 2 GiB, 128 MiB from 4 GiB) divided by the heads | A fill stops at it, as at the store's limit |
| The helper client's record of a cell in one style | four bitsets of every codepoint, held, lacked, asked for and brought by the fill, 136 KiB each, made only when a bit is first set; a style other than regular never fills, so at most 544 KiB for the regular record and 408 KiB for each other style's, 1.73 MiB for a cell the screen shows in all four styles (`helper.rs`, `Bits`) | Nothing past it: one record a cell and style the displays draw at, dropped with its cell |

## Limitations

A vtium not running as root refuses every image request while the session's program holds its terminal exclusive with TIOCEXCL, unless logind names the session's user: the kernel refuses to reopen an exclusive pty's slave for an unprivileged process, so vtium cannot read the pty's owner.

## Not yet built

Some keys that a `kmscon` configuration file may hold are not in the key table yet, and vtium reports each as a key it does not know: `multi-monitor`, whose `clone` and `largest` wait for their own change (vtium lays several displays out as `scaled`, the operator's choice on vtium/vtium#21), `screen`, and `kmscon`'s grab keys other than `grab-reboot`.

vtium takes `font-hinting`, checks its value and warns when it is set, but nothing reads it yet: the font helper hints as the frit says.

Two parts of ADR-1002 wait outside this crate. vtium-render does not draw the overlay row, though the frame vtium hands it carries the row. vtium-platform sends no event when a key is let go, so releasing Ctrl with the pointer still leaves the overlay until the next pointer event or key press.

## Left to tier 3

Each needs a real VT or display, which the boot tests stand in for:

- The panic hook under `panic=abort` on a real VT: the VT back in text mode with its keyboard before the message prints.
- The 100 ms the loop is served at exit for SIGUSR2 on a real switch back.
- A release a real flip in flight delays, acknowledged once the device reports asleep.
- A card udev raises during `display-wait`, the getty fallback starting when no display comes under an open policy, and its skipping the getty after a failure under a closed one.
- Whether fbdev stays lit when a re-take while blanked defers its set-up to the input that ends the blank; on drm2d the displays stay dark.
- What each power key asks of the machine: tier 3's power variants press each on the console and see the guest reboot both ways, power off with its services stopped and its filesystems unmounted, and suspend and resume.
