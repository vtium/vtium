# vtium

This crate builds the vtium binary. It holds these parts:

- The configuration and the command line.
- The terminfo entry, and the XTGETTCAP table generated from that entry.
- The session's command and environment.
- The respawn policy.
- The rules the terminal follows.
- The seat and its heads, which vtium-platform's loop wires to those rules. The seat handles the VT's events, the devices, and the keys. A head is a terminal for one or more displays.

The rules are functions of what they are given, the time included. So their tests need no VT, display, or pty. The seat takes the time from the loop too. `tests/boot.rs` boots the seat with the fake VT, a video device in memory, and a real child on a real pty.

## Setting it up

The vtium package (ADR-1500) installs `/usr/bin/vtium`, its glyph helper, and the unit `vtium@.service`. A build with `libseat` and `logind` also installs seat mode's unit, `vtium-seat@.service`, and the PAM file `/etc/pam.d/vtium`. The package's install script turns vtium on with `vtium console enable --direct --all`. A build with images also installs the image helper, `/usr/bin/vtium-image`, and the sysusers file `vtium-image.conf`. From that file, `systemd-sysusers` creates the account that the image helper runs as at the login prompt (ADR-1101 D2).

`vtium console` gives vtium a VT, or every VT, and takes them back (ADR-1500 D7). `enable` and `disable` need root. Run as any other user, they change nothing and say so. `status` runs as any user:

```sh
vtium console status                         # per VT: what systemd starts at boot, what logind starts when you switch to it, what runs now
vtium console enable                         # changes nothing: what vtium finds on this machine, the mode it recommends, and the command
sudo vtium console enable --direct 3         # VT 3 is vtium's from its next start, in direct mode, and its getty is disabled
sudo systemctl start vtium@tty3.service      # start vtium on VT 3 now, which ends every session there
sudo vtium console enable --seat 3           # VT 3 moves to seat mode, vtium-seat@tty3.service, from its next start
sudo vtium console disable 3                 # VT 3 goes back to what it had from its next start, whichever mode it had
sudo vtium console enable --direct --all     # every VT is vtium's, on a machine whose autovt@.service link does not name kmscon
sudo vtium console disable --all             # every VT goes back as vtium console found it
```

vtium runs on a VT in one of two modes (ADR-1400 D3).

- **Direct mode.** `vtium@.service` runs vtium. vtium opens the screen and the keyboards itself. Where seatd runs and the build has `libseat`, vtium takes them from seatd instead. Each login gets an active logind session on seat0, as it does at a getty.
- **Seat mode.** `vtium-seat@.service` runs vtium. vtium takes the screen, the keyboards, and VT switching from logind, through libseat. Each login gets a logind session with no seat. polkit treats that session as inactive, and udev gives it no devices, such as sound cards. Seat mode needs a build with `libseat` and `logind`. The install of such a build ships `vtium-seat@.service`.

The two units conflict, so a VT runs one mode at a time. `enable` in one mode moves a VT that runs the other mode. `enable` with no mode turns nothing on, and it recommends direct mode (ADR-1500 D7).

`autovt@.service` is the unit that logind starts on a VT when you switch to that VT and nothing runs there. `enable --all` links `autovt@.service` to vtium. It also runs `enable N` on each free VT from 1 to 6. So systemd starts vtium on each of those VTs at boot, in place of the getty that `enable` disables. vtium then holds each of those VTs open from boot. Some display managers put a new desktop session on the first VT that nobody holds open, as SDDM 0.20 and later does. Such a display manager then passes those VTs by (ADR-1500 D7). Each claimed VT runs one idle vtium from boot. Each idle vtium takes about 6 MiB of resident memory on tier 3's minspec machine. The minspec build is vtium's default, smallest build.

A machine may have been claimed before vtium started at boot on every VT it claims. On such a machine, `status` names each VT from 2 to 5 that nothing holds open at boot, under its table. Running `sudo vtium console enable --direct --all` again starts vtium at boot on those VTs.

VT 6 is logind's reserved VT. logind starts a console there at every switch, even while the VT is in use. So `enable --all` and `enable 6` refuse while someone is logged in on VT 6, unless that login is inside a vtium running there. `enable --all` also refuses while one of these is on VT 6 without a link of VT 6's own: kmscon, the development install, or a masked `vtium@tty6`. It then says what to free first. A getty waiting at its login prompt on VT 6 holds no session. So both verbs go ahead, and the next switch to VT 6 stops that getty. Stopping that getty ends nothing.

`vtium console` follows common convention. While a display manager is enabled, VT 1 stays with the display manager and its getty, whatever VT the display manager uses now. vtium takes other VTs.

`vtium console` never takes a VT that the system's intended configuration gives to another program. These hold VTs that way:

- A unit enabled at boot that claims the VT.
- An enabled display manager, which holds VT 1 and any VT its configuration names. A display manager counts as enabled when it is linked as `display-manager.service`. It also counts when vtium knows it by name and it is enabled at boot.

What runs now adds to that list, and it never frees a VT. A VT is held now in each of these cases:

- A graphical session or a greeter is on the VT. vtium asks logind for these with `loginctl`.
- Another console runs on the VT as a unit named `PREFIX@ttyN.service`.
- The VT is the controlling terminal of a program running now, with or without a logind session. For example, SDDM's X11 greeter runs the X server on VT 2.

vtium reads each process's controlling terminal from `/proc/PID/stat`, and the process's unit from `/proc/PID/cgroup`. vtium leaves two kinds of process to the rules for consoles and sessions. One is a process in a unit on the same VT, such as `getty@ttyN.service`. The other is a process in the scope of a logind session on the same VT (`src/console/process.rs`, ADR-1500 D7).

A VT is held from the next boot in two cases. In the first, a unit that starts at boot names the VT's getty in `Conflicts=`, as Arch's sddm.service names `getty@tty1.service`. In the second, a unit that starts at boot runs on the VT. Such a unit is an instance, such as `cage@tty3.service`, or a unit with `TTYPath=/dev/tty3`. The display manager's own configuration adds the VT that its greeter starts on. vtium reads LightDM's `minimum-vt` (7 by default), greetd's `vt` or `--vt`, and SDDM's `MinimumVT`.

Nothing frees a VT: neither a configuration file nor a greeter running on another VT. `enable N` refuses a held VT, and it says which signal it read. `enable --all` passes a held VT by, and it says so. `status` marks a held VT, and it gives the reason under its table.

When vtium fails on a VT, its unit's fallback, `vtium-getty@.service`, runs `vtium console fallback ttyN`. That command starts the VT's getty, so that you have a login prompt again. The fallback starts nothing when the getty's start would stop another program. Such a program is a unit that conflicts with the getty and that runs, waits to start, or is enabled. For example, a display manager conflicts with `getty@tty1`. The VT is then left without a console, and the journal of `vtium-getty@ttyN` says why. The fallback also starts nothing when it cannot ask systemd. Under a closed policy in vtium.conf, the fallback skips itself (ADR-1401 D9). A closed policy is the line `policy = closed` in vtium.conf. Under it, vtium ignores any input that no rule names.

Under a closed policy, vtium writes `/run/vtium/ttyN.closed` at start. Under an open policy, vtium removes that file. `vtium-getty@.service`, generated from `install/vtium-getty@.service`, skips the getty while the file exists. So no failure of vtium starts a getty on its VT (ADR-1401 D9). Tests: `a_closed_file_writes_the_marker_of_its_vt`, `a_later_open_run_removes_an_earlier_closed_runs_marker`.

`vtium@.service`, generated from `install/vtium@.service`, has `Restart=on-failure` with systemd's defaults. So after a one-off failure, systemd brings vtium back after 100 ms. Past 5 starts in 10 s, the unit stays failed with `start-limit-hit`. Under a closed policy, no getty then takes the VT.

The unit also has `After=getty@%i.service` beside its `Conflicts=getty@%i.service`, because `Conflicts=` alone orders nothing (systemd.unit(5)). The getty's stop hangs up and resets the VT (`TTYVHangup=`, `TTYVTDisallocate=`). Without that ordering, the getty's stop would run at the same time as vtium's start. Tests: `test_install_writes_the_binary_the_units_and_the_manifest_and_swaps_the_getty` in `tools/vt/tests/test_vt.py`, and tier 3's `getty-fallback` and `start-limit` in `heads-closed-broken`.

Neither verb starts or stops vtium. Each verb prints the `systemctl start` or `stop` command that does. That command ends every session on the VT. Before `enable` changes a VT or moves `autovt@.service`, it records what was there in `/var/lib/vtium/console/`. The record includes the unit file that each getty linked to. `disable` puts back exactly what the record holds. `vtium console` refuses a VT that kmscon holds. See "Sharing VTs with kmscon" for details. On a host that was not booted with systemd, `vtium console` changes nothing and says so. On such a host, an inittab line or an init script runs `vtium --vt=ttyN --no-switchvt` on the VT. See [docs/systemd.md](../../docs/systemd.md).

### Sharing VTs with kmscon

kmscon is another console that draws a VT through DRM/KMS. kmscon and vtium can run on one machine, each on VTs of its own. When you switch to a VT that no console runs on, logind starts the unit `autovt@ttyN.service` there. N is the VT's number. systemd looks first for a link of that exact name, `/etc/systemd/system/autovt@ttyN.service`. Such a link gives one VT a console of its own. Every VT without such a link falls back to the single template link, `/etc/systemd/system/autovt@.service`. So whichever console the template link names gets all of those VTs. `sudo vtium console enable --direct --all` points the template link at vtium.

On Arch, the template link points at the getty from the start, because systemd's package enables `getty@.service` when it installs. kmscon's own `sudo systemctl enable kmsconvt@` then fails on that link. That command still enables kmscon at boot on VT 1. Only `systemctl enable --force kmsconvt@.service` points the link at kmscon. `vtium console status` says on its first line which console the template link names.

**vtium holds the template link, and you want kmscon on one VT.** Take that VT back from vtium. Then give the VT a link of its own to kmscon. For VT 3:

```sh
sudo vtium console disable 3                 # enable --all starts vtium at boot on VT 3; this takes VT 3 back and gives it the getty it had
sudo systemctl disable getty@tty3.service    # only where vtium console status now shows a getty at boot on VT 3
sudo ln -s /usr/lib/systemd/system/kmsconvt@.service /etc/systemd/system/autovt@tty3.service
sudo systemctl daemon-reload
```

Nothing starts kmscon at boot or at once. logind starts kmscon the next time you switch to VT 3 while no console runs there. Until then, nothing holds VT 3 open. So a display manager that puts a desktop session on the first free VT can take VT 3. `vtium console` sees the link and leaves VT 3 to kmscon. `enable 3` refuses VT 3. `enable --all` names VT 3 and passes it by. `disable` never touches VT 3. The way back:

```sh
sudo systemctl stop kmsconvt@tty3.service    # ends every session on VT 3
sudo rm /etc/systemd/system/autovt@tty3.service
sudo systemctl daemon-reload
sudo vtium console enable --direct 3        # VT 3 is vtium's again from its next start
```

To give VT 3 its getty instead, run `sudo systemctl add-wants getty.target getty@tty3.service` in place of the last line. Use `add-wants` rather than `systemctl enable getty@tty3.service` there. That `enable` also links `autovt@tty3.service` to the getty. `vtium console enable --direct 3` then refuses VT 3 until that link is gone.

You can also run `sudo systemctl enable --now kmsconvt@tty3.service`, after the same `vtium console disable 3` and `systemctl disable getty@tty3.service`. That command makes the same link. It also starts kmscon on VT 3 at boot, and at once. Without the getty's disable, systemd would start both kmscon and the getty on VT 3 at boot, and the two conflict. The way back:

```sh
sudo systemctl disable --now kmsconvt@tty3.service    # stops kmscon, which ends every session on VT 3, and takes it off boot
sudo rm /etc/systemd/system/autovt@tty3.service      # the link that disable leaves
sudo systemctl daemon-reload
sudo systemctl add-wants getty.target getty@tty3.service    # only if you disabled VT 3's getty
```

Several vtiums started at boot can each draw. A vtium that opens the display card on a VT that is not shown lets go of the card's DRM master at once. DRM master is the right to set what the card shows. So the vtium on the VT that is shown draws (ADR-1500 D7). vtium's tests do not check whether kmscon does the same when it starts at boot on a VT that is not shown. A console that keeps the card's master stops the vtium on the shown VT from drawing. So this guide prefers the hand-made link, which starts kmscon only when you switch to VT 3. Also, do not run kmscon's own `systemctl enable kmsconvt@` while vtium holds the template link. That command fails on that link. It still enables kmscon at boot on VT 1, beside vtium there.

**`/etc/systemd/system/autovt@.service` links to `kmsconvt@.service`**, as on a machine set up to run kmscon on every VT. `sudo vtium console enable --direct N` gives vtium one VT at a time. `sudo vtium console enable --direct --all` refuses until kmscon lets go of the template link.

**Moving from kmscon to vtium entirely:**

```sh
sudo systemctl disable kmsconvt@.service      # removes the template link and every VT's kmscon link
systemctl list-units 'kmsconvt@*'             # the VTs where kmscon still runs
sudo systemctl stop kmsconvt@tty2.service     # for each VT listed; ends every session there
sudo vtium console enable --direct --all               # every free VT is vtium's from its next start; it prints the command that starts vtium on a VT now
sudo pacman -R kmscon                         # if you want: removes kmscon itself
```

`systemctl disable` stops nothing. Logging out of a VT leaves its kmscon running. `vtium console enable --direct --all` passes by every VT where kmscon still runs, and it names each one. It leaves each such VT's getty as it is, so that VT keeps its getty after a reboot. Stop kmscon on such a VT first, as above. Or run `sudo vtium console enable --direct N` for that VT once kmscon has stopped.

`pacman -R kmscon` leaves the `kmscon-terminfo` package, which holds the terminfo entry named `kmscon`. vtium sets `TERM=xterm-vtium`, and the `vtium-terminfo` package installs that entry. So vtium itself needs no `kmscon` entry. Keep `kmscon-terminfo` while anything still uses `TERM=kmscon`. These use it:

- A vtium run with `--term=kmscon`, or with `term=kmscon` in its configuration.
- `make vt-login` on a machine without the `xterm-vtium` entry, because `make vt-login` then runs vtium with `--term=kmscon`.
- An ssh login to this machine from a kmscon console elsewhere, which arrives with `TERM=kmscon`.

Once nothing uses `TERM=kmscon`, you may remove the package with `sudo pacman -R kmscon-terminfo`.

### ssh from vtium

vtium sets `TERM=xterm-vtium` in its session. It sets `TERM=vtium` when it runs with `--term=vtium`, which is another name of the same entry. It sets `TERM=kmscon` when it runs with `--term=kmscon`. ssh passes `TERM` on to the remote host. Most hosts have no terminfo entry by any of these names. So the programs there cannot look up how to drive the terminal, and the remote shell misbehaves. zsh, for one, echoes every keystroke.

The maintainer's fix is to wrap ssh in the shell's rc file on the machine that runs vtium. A plain `ssh` from vtium then presents the remote host with `xterm-256color`, an entry nearly every host has. In `~/.zshrc`:

```zsh
if [[ $TERM == (xterm-vtium|vtium|kmscon) ]]; then
  ssh() { TERM=xterm-256color command ssh "$@" }
fi
```

In `~/.bashrc`:

```bash
case $TERM in
xterm-vtium | vtium | kmscon) ssh() { TERM=xterm-256color command ssh "$@"; } ;;
esac
```

Remote programs then use only what `xterm-256color` describes. They use none of vtium's own capabilities that the entry lacks. On a host you own, you can install vtium's entry instead, from a machine that has the entry. The `vtium-terminfo` package installs the entry on that machine:

```sh
infocmp -x xterm-vtium | ssh host tic -x -
```

When `tic` runs as a user other than root, it compiles the entry into that user's `~/.terminfo` on the host. With the wrapper in place, `command ssh host` skips the wrapper, so that host gets `xterm-vtium`.

## Reading the configuration

vtium reads `vtium.conf`, and then its command line, through the key table in `src/config/keys.rs`. vtium treats both as untrusted input. See "Bounds" for details.

- **One file.** vtium reads `vtium.conf` in `/etc/vtium`, or in the directory that `--configdir` names. vtium never reads `/etc/kmscon/kmscon.conf`, the file that the released `kmscon` reads. They are separate programs. So on a machine that runs both, a change to one program's configuration never changes the other's (ADR-1500 D4). vtium takes the keys that `kmscon` takes. [docs/config.md](../../docs/config.md) says how to move a file from kmscon. vtium reads no seat file, such as `seat0.seat.conf`. A seat's flow goes into `vtium.conf` with the rest (ADR-1403 D2). The flow is the part of vtium.conf that decides where each display and input goes. `configdir` is set on the command line only, because a file cannot name the directory it is read from. Tests: `vtium_conf_is_the_one_file_read`, `a_seat_file_beside_vtium_conf_is_not_read`, `configdir_names_the_file_read`.
- **Only a file that root owns is read.** When vtium runs as an account other than root, a file that account owns is read too. vtium reads the file only when neither its group nor others can write it, or any directory above it. vtium reads none of a file that fails this check, and it runs its compiled-in configuration instead. It says which path fails, and the command that mends that path: `chown root:root PATH` or `chmod go-w PATH`. The check is strict because the file places keyboards, and its `login` names the command that vtium starts as root (ADR-1403 D3). Tests: `a_file_others_can_write_applies_nothing_and_says_how_to_mend_it`, `a_directory_others_can_write_refuses_the_file_below_it`.
- **Only a regular file is read.** vtium opens the file without blocking, and with `O_NOCTTY` so that a tty never becomes its controlling terminal. vtium reads the file whole, up to `FILE_MAX`. A FIFO, a device, or a directory at the path is reported and skipped. So a FIFO with no writer cannot hold up the start. Test: `only_a_regular_file_is_read`.
- **A value that cannot be read is reported, and the rest of the file is read.** The key keeps the value that a lower source set, such as the default. A number is digits only. So `font-size=12px`, `sb-size=abc`, and `sb-size=-1` are each reported. A number past its key's bound is clamped to the bound, and reported. Test: `a_number_out_of_bounds_is_clamped_and_reported`.
- **An unknown `palette` name is reported,** and the value a lower source set stands. Test: `a_palette_vtium_does_not_hold_is_reported_and_leaves_the_value_below`.
- **A `#` glued to a value stays in it.** vtium.conf has one comment rule, and its sections share that rule. A comment starts only at the start of a line or after a blank. So `sb-size=10#comment` is the value `10#comment`. vtium reports that it cannot read that value, and the key keeps its default (ADR-1403 D4). Test: `comments_blanks_and_colors`.
- **`no-` turns off a switch only,** so `no-font-size=12` is not read as `font-size=12`.
- **A mode line is read whole.** A size is digits, and each side is 1 to 65535. A card's or connector's name is at most 63 bytes. vtium reports anything else. Test: `a_mode_that_does_not_read_is_reported`.
- **An option name is matched whole,** so `--lo` is not `--login`.
- **A command-line word that is not an option refuses the start.** This holds with `--login` too. The word does not join the command, which comes only after `--`. `--login` with no command after `--` refuses the start as well. `check-config` is the one such word that vtium takes, wherever it stands before `--`. vtium passes the words after `--` as given, bytes that are not UTF-8 included. Tests: `a_stray_argument_or_a_login_without_its_command_refuses_the_start`, `a_command_word_that_is_not_utf8_is_passed_as_given`.
- **vtium logs information messages and above by default, and `debug` adds debug messages.** There is no `verbose` or `silent` key. vtium reports a file or command line that sets either one as setting an unknown key.
- **A build without images reads the image keys and says nothing of them.** That build never offers sixel or kitty graphics, so vtium logs nothing about them.

## Heads

The seat runs what the sections of `/etc/vtium/vtium.conf` resolve to, at the three levels of ADR-1401 D7. The seat never writes the file (ADR-1403 D3).

- With no file, or with a file that has no section, the seat runs the compiled-in configuration's one `console` head, silently.
- Some files are never read. These are a file that root does not own, a file that its group or others can write, and a file that cannot be read as a file. For such a file, the shipped rules run. The shipped rules are the rules of the compiled-in configuration. Every head shows `vtium.conf not used: running the built-in configuration.`
- A trusted file runs under its policy. vtium logs each error with its line, and each error drops what it takes:
  - A valid file runs as written.
  - A partly broken file runs what survives. Every head shows `vtium.conf has errors: running the parts without errors.`
  - A broken file under the open policy runs the shipped rules, with `vtium.conf not used: running the built-in configuration.`
  - A broken file under the closed policy runs nothing. The boot display shows `vtium.conf has errors and counts as closed: all input is off.`, and no input is delivered.

Each console line is followed by its next step from vtium-settings's catalog, such as `To see why, run vtium check-config /etc/vtium/vtium.conf.`

A head is a terminal of its own. Each head has these parts:

- Its session's pty, screen, and scrollback.
- Its grid. The scaled rule lays the grid out over the head's displays. See "The font" for the scaled rule.
- Its density, zoom, and rotation.
- Its font. A look is the font and the font settings that a head draws with. The head's font comes from the keys that its look's section and its own section set, laid over the top level's keys. The look's `font-name` names its frit, the font set file that the head draws (ADR-1403 D5).

Each display walks the rules on its own when it comes. The display joins the head that the first matching rule names. vtium sets off and logs a display that a rule sends to `off`, or that no rule claims. For a display that no rule claims, the log line gives a rule, ready to paste, that would give the display the first head. A DRM card sets such a display off before the card announces it, even when another master left a frame on it. A framebuffer's display is set off after each wake-up and unblank. A head whose displays never appear starts no session, under `display-wait=forever` too.

Each input device walks the rules on its own when it comes:

- A device that a rule sends to a head delivers to that head alone.
- A device sent to `roaming` delivers to the active head. Under the open policy, so does a device that no rule claims. The active head is the head that roaming input types into.
- Under the closed policy, vtium ignores a device that no rule claims.
- vtium never opens a device sent to `ignore`, with one exception. Under the open policy, vtium opens such a keyboard for the VT keys alone. The rescue key is among the VT keys.

When vtium.conf turns `mouse` off, the shipped rules send each pointer class to `ignore`. That includes the tail of the shipped rules, which the inputs of a partly broken open file walk. So no pointer opens, not even one whose device node also has udev's key class.

The active head starts on the head of the boot display. The boot display is the connector lit at start. Without one, it is the first connected connector on the boot card, and then on the other cards, in the kernel's order. Without a boot display, the active head starts on the first head in the file that has a display. Until the first key reaches a head, or until the first roaming chord, vtium chooses the active head again as each display lights. Each time, it chooses over every display lit since the start, including one that has left. So a boot display that lights a turn late takes the active head, and a display that leaves never moves it.

After that, only the roaming chord and the anti-lockout guard move the active head. The anti-lockout guard acts when no keyboard reaches a lit head. See the guards below for details. Ctrl-Super-Up moves the active head to the next lit head that is not isolated, and Ctrl-Super-Down moves it to the previous one. An isolated head is a head that can never be the active head. vtium matches the roaming chord after the power keys and before the terminal's grabs, once a press. Only a roaming keyboard takes the roaming chord. Pressed on a keyboard that a rule sends to a head, the chord moves nothing, and it reaches that head's session as a key.

The VT's keys switch the VT only from a keyboard whose head is not isolated. A keyboard's head is its rule's head, or the active head for a roaming keyboard. From an isolated head's keyboard, the VT's keys reach that head's session as keys. From a roaming keyboard while no head is active, the VT's keys do nothing.

Sometimes the seat has no route for a device's event, for example for an event queued before its device went away. Under the closed policy, such an event delivers nothing. Under open, it roams. A pointer moves within the grid of the head it delivers to. It carries the modifiers of the keyboards that deliver to that head. The terminal of each head that a keyboard delivers to has mode 1004's focus, so several terminals can hold the focus at once. The blank, the selection buffer, and the power keys belong to the seat.

Each head holds consoles, and each console runs one session. The head shows one console on every display of the head. As a head's first display lights, the head starts the number of consoles that `consoles` gives in the head's section of vtium.conf. A head starts at most `head-consoles-max` consoles, 4 by default. Every head together starts at most `consoles-max`, 8 by default. Each head keeps its first console, and the other consoles open in the file's order. So the share does not depend on which display comes first.

Ctrl-Super-Right shows the next console of the head that the keyboard delivers to, and Ctrl-Super-Left shows the previous one. Both wrap around. Under the closed policy, a head keeps the consoles it started with for as long as it runs. vtium takes Ctrl-Super-Return and Ctrl-Super-Backspace and does nothing with them, so neither reaches a session.

Under the open policy, Ctrl-Super-Return opens a console just after the one that the head shows. vtium starts the head's login in the new console, on the grid that the layout gives the console, and shows the console. Nothing opens when the head has `head-consoles-max` consoles, or when every head together has `consoles-max`. vtium then logs a line that names the cap. It also shows a brief line at the top of the head, such as `No more consoles: desk has 4, its most.` The brief line takes the place of the on-screen display's full line. It shows for `osd-timeout`, or for 3 s under `never`. Under `osd = off`, vtium writes only the log line.

The new console's session starts while the console is still hidden. The head shows the console once the session runs. When the chord cannot start a session, the run stays alive. vtium logs a line, and the new console leaves without being shown. So the console shown before is told nothing. The new console's id stays given. The head shows the notice `Console not opened: login could not start.` This is a notice of a problem. It shows whatever `osd` says, and it goes away the way the guards' notices go. A session may also fail to start at a head's start, or when a console's program starts again. That failure ends vtium with status 1, so the unit's getty fallback takes the VT. See "The session" for details.

Ctrl-Super-Backspace closes the console that the head shows. The console's pty closes, so its programs get SIGHUP. The head then shows the console after it, or the first console when the closed one was the last. The closing console gets no focus-out, and the console shown next gains the focus. On a head's last console, Ctrl-Super-Backspace does nothing. Neither chord reaches a session. From a roaming keyboard with no active head, neither chord does anything.

Each console keeps its own grid and zoom. The head draws the whole screen when the shown console changes. The font and the displays belong to the head. So a hidden console's OSC 50 font request and blank sequences wait until the console is shown. The console's output after an OSC 50 request waits with them. A hidden console's OSC 50 query is answered at once, with the name of the font that the head draws. A console that the head opens later answers the query with that name too. Each console's OSC 52 selection is taken at once.

A head's consoles run the `login` of the head's section. Without one, they run the `login` at vtium.conf's top level. Each console's session has two variables in its environment: `VTIUM_HEAD`, its head's name, and `VTIUM_CONSOLE`, the console's id. A head gives its consoles ids from 1 as it opens them at its start. A console that the chord opens takes the next id that the head has not given. So no id is given twice in a run. A console keeps its id when its session starts again.

A console whose program exits keeps its place, and it follows the respawn policy. Each console counts its own quick exits.

- Under respawn, the console's login comes back in the same console, from a hard reset. No other console is touched.
- Under `oneshot`, the console ends and shows the notice that its session ended. The head ends once every one of its consoles has ended. vtium exits with status 0 once every head has ended. A head whose display never lit counts as ended, because it has nothing to run.

Quick exits past the limit, on any console of any head, end the run (ADR-1401 D1). Every head's sessions hang up, and the log names the head. Under the open policy, vtium then exits with status 1, so the unit's getty takes the VT. vtium draws no notice. Under the closed policy, vtium holds its VT, because a getty's login would take any keyboard. Every head's display goes dark, no session starts again, and no input is delivered. For as long as vtium runs, the boot display shows that a session kept ending as soon as it started.

Heads that draw one frit share its helper and its store. A head that draws another frit has its own helper and store. The memory of every console and frit together is bounded (ADR-1401 D10). See "Bounds" for details.

Each console's scrollback takes `sb-memory`. The most that `sb-memory` may be on a machine is a quarter of the machine's memory, divided by `consoles-max`. When vtium.conf declares more heads than that, vtium divides by the number of heads instead, because each head keeps its first console. So every console's scrollback together stays within that quarter. On a 512 MiB machine, the quarter is 128 MiB. That gives 16 MiB a console for `consoles-max`'s 8, and 2,684,354 bytes each for 50 consoles.

Left unset, `sb-memory` follows each console's grid, inside that share. The minspec build is vtium's default, smallest build. On minspec's grids, `sb-memory` is what the 16 MiB minspec peak leaves after the console's two screens at their worst. That is 5,242,880 bytes at 170 by 48, and more on a smaller display. A larger display keeps 5,242,880 bytes. vtium works the value out again whenever the console's grid changes. A user who wants a deeper scrollback sets `sb-memory`, up to the share (ADR-1001, "Memory").

Each frit's glyph store takes the machine's store limit, divided by the number of heads. The store limit is 16 MiB below 2 GiB of memory. vtium divides by the heads because a head draws one frit at a time. So every frit's store together stays within that limit: 16 MiB with one head, and 1 MiB each with 16.

vtium draws its own notices and status over a head's frames, outside the terminal's cells. So no pty, scrollback, or reply sees them (ADR-1401 D5, D7). vtium draws them with vtium-render's `Notice` and `Mark`, in the built-in fonts, fitted to the head's cell. On a head that draws a frit, the overlay takes the built-in fonts from the frit's face's `Face::builtins`. So every character of a notice or the mark comes from the built-in fonts, on one baseline. That holds whatever the helper sent for the characters the terminal shows.

A notice is a box of vtium's lines across the top of each of the head's displays. These are the notices:

- The start's console line, on every head, when the start skipped or partly ran sections of vtium.conf. The line names no error, because the log holds the errors.
- No keyboard found by the start's scan, on every head.
- The anti-lockout guard's notice, on the active head.
- The rescue key's notice, on the active head. With no active head, it shows on every head.
- A console's notice that its session ended for good under `oneshot`. It shows while that console is shown.

Each notice says in plain words what happened. A head shows each notice once, and it shows the newest four (`NOTICES_MAX`). A repeat of a notice changes nothing. A notice ends when any key reaches its head, or 30 s after it is first drawn. An ended console's notice is the exception: it stays and keeps no time. Once a notice goes, the frame beneath is drawn whole.

The on-screen display, the OSD, draws each head's status (`src/osd.rs`, ADR-1401 D5, vtium/vtium#169). It draws the status in the box across the top of each of the head's displays, and in the head's top-right cell. `osd` takes one of three values:

- **`osd = minimal`**, the default. The status is a `Mark` in the head's top-right cell. The mark is filled on the active head and hollow on the others. It shows on every head with a lit display when the roaming chord or the anti-lockout guard moves the active head. It never shows in normal use. A head that loses its last display drops what it showed. A head that is starting its sessions shows nothing.
- **`osd = full`.** The status is a line at the top of the box, such as `● desk · console 2 of 3`. The line shows on every lit head at those moves. It also shows on one head when that head shows another console, or when its display returns after it had none.
- **`off`.** Nothing of the status is drawn. Every notice still shows.

The box is drawn in the notice's colors while a notice is in it. It is drawn in the on-screen display's colors while the status line is alone. The dot is drawn in the on-screen display's colors. vtium.conf's `notice-foreground`, `notice-background`, and `notice-border` set the notice's colors. Its `osd-foreground`, `osd-background`, and `osd-border` set the on-screen display's colors. When they are unset, the notice's colors are vtium-render's `Colors::NOTICE`, dark on pale red. The on-screen display's colors are then `Colors::STATUS`, light on dark.

Under `render-timer = osd` or `both`, the console measures each display's frames. Once a second, it puts that display's render timer line in the box under the status line, whatever `osd` says. The line gives `Report::osd`'s figures: frames a second, median time a frame, and the share of the screen drawn. The console then draws the display again to show the line. That redraw counts in the next second's figures, so the figures include the cost of showing them.

The OSD stays for `osd-timeout`, 3 s by default, or always under `never`. vtium reads `focus-mark` as the older name of `osd` and `osd-timeout`, where those two keys are unset. vtium then logs a line that names the two keys.

The guards run after every display and input that is added or removed, and after a rescue (ADR-1401 D9). Under the open policy, the anti-lockout guard and the rescue key are on. Under the closed policy, both are off. The display guard is always on.

- **The display guard under open.** The display guard lights the boot display in the first head while the rules light no display. The guard lets the boot display go dark once the rules light another display. The guard uses the default `console` head when the file declares no head. It also uses the default head when the file has errors and none of its heads runs on the VT shown. That head runs its login and shows the file's console line.
- **The display guard under closed.** The display guard lights the boot display for a notice alone. The screen has no session, and no input reaches it. The notice stays until a head lights. The notice reads `No head has a connected display.`, or it is the start's console line. A closed file with no heads stays dark.
- **What the display guard sees.** A DRM card announces a display that the rules leave dark while vtium has no display lit, so the guard can light that display. A card may set a display off at its bind while another display is lit, and then never announce it. Once that lit display goes, the guard lets go, so that the card scans again and announces the display. A display that the guard lit goes dark again by its power state.
- **The anti-lockout guard.** The anti-lockout guard acts while a keyboard-class device is present but no keyboard reaches a head with a lit display. The guard then makes every keyboard roam. It opens an ignored keyboard, so that the keyboard delivers. It makes the boot display's head the active head when that head is lit, or else the first lit head. It shows a notice and the on-screen display. Each keyboard goes back to its rule once a keyboard reaches a lit head.
- **The rescue key.** The rescue key is `Ctrl-Alt-F<n>` for vtium's own VT. It works under the open policy, on any keyboard, the ignored ones included, unless the head that the keyboard's rule names is isolated. The rescue key makes that keyboard roam for the rest of the boot. The keyboard keeps roaming through an unplug, for the newest 16 devices (`RESCUED_MAX`). A notice on the head that the keyboard then types into names that head. With no active head, a notice on every head says that no head is active. vtium writes nothing to any file. A keyboard that the rescue key moved reaches a lit head while the active head is lit.

Each head composes its frames on a render thread of its own (ADR-1401 D2). So one head's redraw delays neither another head's frames nor the loop. The loop keeps the input, the ptys, the hotplug, the VT's switches, and the devices. For the devices, the loop keeps their buffers, cursor planes, blanking, and flips.

A frame is the head's screen. The loop takes the frame with the buffer token that its display lends (vtium-platform's frame contract). The thread composes the frame straight into the token's buffer. The thread only writes to that buffer. It draws the cells that the buffer lacks at its age. A buffer's age is how many frames ago it was last drawn. The loop gives the token back with the frame's damage. So the display presents the buffer that the frame was drawn into.

No view keeps a copy of its display's frame. Nothing copies a frame between buffers. So a display at 1920×1080 holds no 8,294,400-byte copy beside its own buffers. When vtium's notice box or the on-screen display changes, the renderer draws again the cells and the border under what the box covered. So no buffer keeps the old box, whatever the buffer's age. A view whose display lost its picture draws its next frame whole.

A display has one frame on its way at a time. A draw asked for meanwhile is taken from the screen as the screen is when the frame comes back. So no frame queues behind another. A frame may come back after the VT is released or the displays are blanked. Its display drops such a frame, and it draws whole at the next acquire. A job that the thread cannot take gives its token back unused.

A head's render thread starts when the head's first display is set up. The thread's stack is 128 KiB, or 8 MiB when `hwaccel` asks for the GPU path. The next paragraph describes the GPU path. When the thread's head is dropped, at a new reading of vtium.conf and at the exit, the loop joins the thread.

The loop waits at most `LET_GO_MS` for a thread that `hwaccel` gave a GPU, because a driver can hang while it destroys its GL context. See "Bounds" for the value. Past that time, the loop leaves the thread to end alone, and the log says that the GPU driver did not let go. vtium keeps each thread that it left. It joins such a thread at the first drop of a head after the thread ends, as at a reload of vtium.conf, or at the exit. Joining the thread frees the thread's stack.

A thread that still runs at the exit may be inside the GPU driver. The exit handlers of libEGL and Mesa would tear EGL down under that thread, which corrupts the heap or aborts. So vtium then flushes its output and ends at once, without running its exit handlers. The log says how many threads still ran. A test that leaves a thread on purpose joins the thread before the test returns. The GPU tests' seat joins every thread that its app left, as the seat drops.

A reload of vtium.conf and the exit first tell every head's thread to end. Then they wait for all of the threads against one deadline. So heads on a driver that hangs hold vtium for `LET_GO_MS` in all. At debug level, under the `render` target, each head logs a line once a second while it draws its frames. The line gives the time each frame took to compose, as the mean and the largest.

A head whose `hwaccel` is on, in a build with the `gpu` feature, draws on the GPU path (ADR-1303 D9). Before the head's render thread takes a frame, the thread makes the head's GL context. It makes that context on the render node of the card that drives the head's first display.

The loop does not wait for that set-up. It takes the thread's answer at the turn when the thread wakes the loop, and it logs each of the head's display lines then. Meanwhile, the loop takes the input, reads the ptys, and draws the other heads. The head's frames wait in its queue. The first frame sent while the set-up's result is not known makes the log say once that the head waits for the GPU driver. A head whose set-up never returns draws nothing until vtium restarts.

Tests:

- `start_returns_while_the_gpu_set_up_hangs_and_its_frames_wait_for_it` and `a_head_whose_gpu_set_up_hangs_holds_neither_the_loop_nor_another_head`, on a test GPU whose set-up waits until the test lets it go.
- `dropping_a_painter_whose_driver_hangs_letting_go_does_not_wait_for_it`, `letting_go_of_two_heads_whose_driver_hangs_waits_one_bound_in_all` and `heads_whose_driver_hangs_letting_go_hold_the_exit_one_bound_in_all`. The last test also checks each head's line that says the driver did not let go.

The thread keeps a pipeline for each display. It draws each frame through that pipeline into a frame of the display's size, kept in GL. Then the thread reads back into the display's buffer the part of that frame that the buffer lacks at its age. The display lends that buffer in memory, as it does on the CPU path. That read is the staging copy (ADR-1401 D2). Every display takes the staging copy until displays lend their buffers as dma-bufs. The notice box and the on-screen display go over the buffer afterwards, as on the CPU path.

Three things leave the head on the CPU path. They are a set-up that fails at any step, a card with no render node such as a framebuffer, and a build without `gpu`. The log then says why. Each display's line names the path that draws it, `text renderer [cpu]` or `text renderer [gpu]` (ADR-1303 D10).

During a run, the GPU path sorts its failures by their kind (ADR-1303 D9):

- A GL error may fail a frame, at any step up to the read back into the display's buffer. The renderer then forgets its history, and the CPU path draws that frame whole. So no buffer keeps part of the failed frame. The next frame on the GPU path draws whole too.
- Some failures leave the head on the CPU path until vtium restarts. These are a GL error in two of one display's frames in a row, or in three of its last 60 frames. An out-of-memory error and a lost context do the same. A fence that the GPU does not pass within `GPU_FENCE_WAIT_MS` counts as a lost context.

The loop then logs once why. It logs each of the head's displays' lines again, naming `cpu`. The loop logs a display's first frame that the GPU path failed, naming the display's connector. It logs none of that display's later failed frames. The GPU path counts the errors in frames, never in time. So a fault that fails every other frame ends the path at its third failure. A lone error ages out of the 60 frames before the next one comes.

`crates/vtium/src/gpu/flap.rs` holds both rules of the window, and the cap on trips back that this section describes below. It holds them in two small types with no GL in them. Table tests drive each type through a sequence of frames.

Tests, on a test GPU that fails the frames they queue a fault for, counted in frames:

- `a_gl_error_drops_one_frame_and_the_head_stays_on_the_gpu_path`
- `a_gl_error_in_every_other_frame_ends_the_gpu_path_at_the_third`
- `a_lone_gl_error_every_100_frames_never_ends_the_gpu_path`
- `a_frame_whose_read_back_fails_leaves_no_ghost_in_the_other_buffer`, on a display that lends two buffers in turn
- `a_displays_failed_gpu_frames_are_logged_once_by_its_connector`
- `a_second_error_running_out_of_memory_or_a_lost_context_leave_the_gpu_path_once`

A display can leave the head: it is unplugged, moved to another head, or gone dark. The loop then sends the display's leaving to the render thread, after the frames sent before it. The loop sends it at the loop's next turn that finds room in the queue. The GPU path then frees the display's pipeline, with its upright frame and glyph pools, and its staging frame. A display whose mode changed takes new ones at its next frame. Tests: `a_display_that_leaves_frees_what_the_gpu_path_kept_for_it`, which counts the displays that the GPU path keeps, and `a_display_that_leaves_while_the_queue_is_full_goes_once_the_queue_has_room`.

When the head's VT is released, the render thread first finishes the frames sent before. It then gives back each display's glyph and picture textures, its upright frame, and its staging frame. It keeps the GL context and its compiled programs. So a head in the background holds no textures. The first frame after the VT comes back makes the textures again and draws whole. That frame sets no display up again. The loop logs the GPU path's notes, such as glyph textures at their ceiling, naming the head. Tests: `a_release_gives_back_every_texture_and_keeps_the_programs`, `a_release_on_the_cpu_path_sends_nothing` and `a_head_on_the_gpu_path_gives_back_its_textures_while_the_vt_is_away`.

The GPU path sorts a display's set-up failures the same way. Out of memory or a lost context leaves the head on the CPU path until vtium restarts. A GL error counts as one of the display's failed frames, so the next frame sets the display up again.

A display is past the GPU's limits when its buffer is wider or taller than the GPU's largest renderbuffer or its largest viewport. The head checks that before it makes anything for the display. It checks when the display appears, and at each change of the display's size. The log line names both limits. While every display takes the staging copy, the frame that the copy reads back from is a texture. So the head also refuses a display past the GPU's largest texture.

A set-up may fail for any other reason, such as a size past the GPU's limits or a shader that does not compile. That failure puts the whole head on the CPU path while that display keeps its size. Each such time is a hold. The GPU path does not try the set-up again at each frame. The log says so once, and it names the display's connector and its size. The log gives each of the head's display lines again, naming `cpu`.

Meanwhile, the head keeps its GL context and each other display's pipeline. The head goes back to the GPU path when the display takes a size that the GPU path sets up, or when the display leaves the head. The log then gives each display line again, naming `gpu`. A display's next size may meet out of memory or a lost context instead. That ends the head's GPU path, and the log does not say that the head is back.

A head goes back to the GPU path at most three times in a run. The fourth hold keeps the head on the CPU path until vtium restarts. So a display that keeps re-plugging at a size the GPU cannot set up does not move the head between the paths at each plug. The log says so once, as it does for any end of the GPU path. The hold clears every display's window of GL errors, because the CPU path draws the frames in between.

## The session

- **`TERM` is `xterm-vtium` by default.** `xterm-vtium` is vtium's own entry, which the `vtium-terminfo` package installs. Some programs do not read terminfo, and guess from the name instead. Such a program treats a name that starts with `xterm-` as xterm-like. So mc, for one, turns its mouse on. The entry reports the mouse in SGR form, which has no column limit. The X10 form stops at column 223. `--term=kmscon` names the entry for the released `kmscon`'s name. The entry that the kmscon-terminfo package installs under that name reports the mouse in X10 form. Spec: ADR-1000, "The terminfo entry and TERM". Tests: `the_default_is_login_with_the_environment_reset`, `the_entry_reads`.
- **XTGETTCAP answers from the entry the session's `TERM` names, and only under that name.** XTGETTCAP is the request a program sends to ask the terminal for a terminfo capability. Under `xterm-vtium` and `vtium`, vtium answers from `install/xterm-vtium.ti`. Under `kmscon`, vtium answers from `install/kmscon.ti`. Under any other `TERM`, every name is unknown. vtium's entry holds every name and value of kmscon.ti, with `TN` and `name` naming `xterm-vtium`. It adds `invis` for SGR 8, concealed text. It also adds `Su`, `blink`, `it`, `smam` and `rmam`, `smir` and `rmir`, `ccc`, `initc` and `oc`, `Cs` and `Cr`, and `XR` and `RV`. It also adds the cursor keys, and Page Up and Page Down, with modifiers. Both entries have `Ms` for OSC 52. The kmscon-terminfo package installs a different entry under the name `kmscon`. That entry lacks `Ms`, `Smulx`, `Setulc`, `Sync`, `XM`, `XF`, `E3`, `BD`, `BE`, `PS`, `PE`, `fe`, `fd`, `kxIN`, `kxOUT`, `smxx`, `rmxx`, `sitm`, `ritm` and `dim`. It reports the mouse with `kmous=\E[M`, where kmscon.ti has `\E[<`. It ends `setrgbf` and `setrgbb` with `;m`. A program that reads the installed entry sees fewer of vtium's abilities than vtium has. A program that asks vtium with XTGETTCAP gets kmscon.ti's answers. Tier 1's `xtgettcap` probe checks those answers. Spec: ADR-1000, "The terminfo entry and TERM". Tests: `the_table_and_the_entry_agree`, `each_capability_does_what_it_names`, `each_entrys_name_gets_its_own_table`, `tools/conformance/tests/termcap.rs`.
- **Each session is told the terminal's name and version, and its head and console.** vtium sets `TERM_PROGRAM=vtium` and `TERM_PROGRAM_VERSION`, over any values the environment held. So a program can tell which terminal it runs in, whatever `TERM` names. vtium also sets `VTIUM_HEAD`, the head's name, and `VTIUM_CONSOLE`, the console's id (ADR-1401 D5). vtium sets no `KMS_START_SCRIPT`. That variable names a script for starting a graphical session from the console, and vtium installs no such script (the operator's decision on vtium/vtium#21). A `login` word that is `$NAME` becomes that variable of the session's environment, after the environment is reset. Tests: `without_reset_env_login_keeps_vtiums_environment`, `each_console_is_told_its_head_and_its_own_id_through_a_restart`.
- **The session's command starts once vtium's VT is shown.** So under `--no-switchvt`, the command waits until the VT is switched to. The command starts at the end of the turn that sets the displays up. It starts on the grid of every display set up by then, so it sees no SIGWINCH as it starts. See "No display" for details. A display set up a turn later, such as one that udev brings, still resizes the session (the operator's decision on vtium/vtium#99). A command started again starts on the grid that the session runs on. Test: `the_child_starts_on_the_grid_of_every_display_at_the_start`.
- **A child's exit closes its pty after the output it left is read.** See vtium-platform's README, "Behaviour". The next child starts from a hard reset (RIS).
- **The respawn limit times each start from that start, on the monotonic clock.** So after one slow restart, a command that fails at once still meets the limit. A slow exit after quick restarts starts the command again, with the count reset. Under the open policy, quick exits past the limit, on any console of any head, end the run with status 1. The unit's `OnFailure=` does not count a status of 0 as a failure. So status 1 lets `OnFailure=` start the getty fallback (ADR-1401 D1, the operator's decision of 2026-10-31). Tests: `a_head_restarting_too_fast_ends_vtium_and_hangs_up_every_head`, `a_hidden_consoles_crash_loop_ends_the_run`.
- **A session outlives a restart of vtium** (ADR-1401 D13). vtium gives a copy of each session's pty master to a keeper. The keeper is systemd's file-descriptor store, where the unit enables that store. Otherwise, when vtium runs as root on a VT, the keeper is vtium's holder, `vtium hold`, which listens on `/run/vtium/ttyN/hold`. Each copy is kept under the name `pty.<console>.<head>`. At the end of each turn, vtium tells the keeper which masters run. So the keeper drops a master whose session ended or whose console closed. While a copy stays open, the kernel does not hang up the pty. So a restart or a crash costs the session only its screen and scrollback.

  The vtium that starts next takes the masters back. When a head starts, it opens exactly the consoles that it has kept masters for, within the caps. It shows the console with the lowest id, and it opens no fresh console. Each console adopts its pty in place of starting a new session. The console sets the pty to the console's size, and sends SIGWINCH so that the program redraws. A head with no kept master opens its consoles as it always does. For an adopted pty, vtium watches the process that leads the pty's session, because vtium cannot wait for a process it did not start. vtium logs that session's end with no exit status. A session whose program ended meanwhile counts as the console's program exiting at the start, with no quick exit counted.

  vtium hangs up a master in three cases. Its head may be gone from vtium.conf, or the caps may leave no room for it. Or it may be the second master kept for one console. vtium gives up a keeper that fails, such as a holder that died, with one warning. vtium logs once a session that the keeper has no room for, and leaves that session unkept. As vtium leaves, it lets go of the sessions its keeper holds, without SIGHUP. systemd's stop then closes them, or the next vtium takes them. No session inherits the variables systemd sets for vtium's own service: `LISTEN_FDS`, `LISTEN_PID`, `LISTEN_FDNAMES`, `NOTIFY_SOCKET`, `FDSTORE`, `INVOCATION_ID`, `JOURNAL_STREAM`, `SYSTEMD_EXEC_PID` and the `MEMORY_PRESSURE_` ones. docs/systemd.md says what the unit and systemd do. ADR-1401 D13 records how each of these was decided. Tests: `a_kept_session_goes_back_to_its_console_at_its_size`, `a_head_with_kept_sessions_opens_exactly_those_consoles`, `a_second_master_for_one_console_is_hung_up_and_the_first_kept`, `no_session_inherits_systemds_variables`, `a_kept_session_that_ended_meanwhile_counts_as_an_exit`, `a_kept_session_with_no_head_is_hung_up`, `a_held_session_outlives_the_vtium_that_started_it`, the store's and the holder's in `src/survive/tests.rs`, vtium-platform's `a_released_pty_leaves_its_session_to_the_pty_that_adopts_it`, and tier 3's `heads-survive`.
- **vtium never keeps a console with no session.** The open chord may add a console whose session cannot start. That console leaves the head, and the head goes on showing the console it showed. A session may fail to start at a head's start, or when a console's program starts again. That failure ends vtium with status 1 (`Exit::Spawn`). So the unit's getty fallback takes the VT, instead of vtium leaving a console that takes keys and runs nothing (ADR-1401 D1, D5). Tests: `a_console_the_open_chord_cannot_start_leaves_and_the_run_goes_on`, `a_failed_open_tells_the_console_shown_nothing`, `a_failed_open_mid_ring_keeps_the_order_and_uses_up_its_id`.

## The blank

After `dpms-timeout` with no activity, every display powers down. The next activity powers the displays up. Activity is the user's input: a key press, a pointer's move, a button or the wheel, and the wake-up after the user switches back to vtium's VT. Some events neither wake the displays nor restart the countdown, because none of them sends the session anything or moves the pointer:

- A key release, which follows a press that already counted.
- A key with no keysym.
- A press partway through a compose sequence, a dead key's press among them. A compose sequence counts at the press that ends it.
- The end of a pointer frame, and the pointer's hide. These are vtium's own events.

The Linux console woke on any keyboard event, releases included (`kbd_event` in the kernel's drivers/tty/vt/keyboard.c).

For now, a change in which displays are attached counts as activity too. When the last display goes, that ends a blank in force and resets the idle clock. The blank does not run while no display is attached. The first display, and each display that comes after none, starts the countdown afresh. A display that comes or goes among others does not count. Nor does a re-take. A re-take sets the displays up again, and it keeps the blank and its timer as they were. While the displays are blanked, a re-take's set-up waits for the input that ends the blank (the operator's decision on vtium/vtium#21).

While the VT belongs to another session, as a released fake VT does, the countdown blanks no display. The user's input is then no activity, because the displays are the other session's. The acquire starts the countdown afresh and ends a blank in force. The acquire is the moment vtium takes the VT back. The idle lock (vtium/vtium#87) will count the user's input alone.

A program commands the blank with the Linux console's sequences while `program-blank` is on, as it is by default (the operator's decisions on vtium/vtium#79). `CSI 9 ; n ]` sets the timeout to n minutes, at most 60. A value of 0 turns the blank off. The sequence also wakes the displays, as on the Linux console. `CSI 13 ]` wakes them as a key does. The program's timeout lasts until a program changes it. RIS returns the timeout to `dpms-timeout`. A change restarts the countdown, and it leaves a blank in force. Output alone never wakes the displays, so a clock redrawing every second does not keep them lit. `setterm --blank N` writes `CSI 9` only under `TERM=linux`. Under vtium's own `TERM`, it refuses. A program cannot blank the displays at once. The Linux console's only way to do that is the `TIOCLINUX` ioctl, which has no counterpart on a pty.

From outside the session, `SIGRTMIN+1` blanks every display at once. `SIGRTMIN+2` wakes the displays as a key does. So a script or a power daemon can act without writing to the session's terminal (the operator's decisions on vtium/vtium#79). The signal's blank is the timer's blank. Input, a program's `CSI 13 ]`, or `SIGRTMIN+2` ends it. While the VT belongs to another session, vtium drops a blank that it is sent, because the displays are not vtium's to blank. Neither `dpms-timeout=0` nor `no-program-blank` holds the signals back.

`vtium blank --vt N` and `vtium wake --vt N` find the vtium on VT N. That vtium is the process named `vtium` that holds VT N's device (major 4, minor N) on a descriptor past its stdin, stdout, and stderr. VT N may be the VT that the process was started from. The two commands hold the process by its pidfd, and they check again that it is still that vtium. They send it the signal through the pidfd. So a process that took its pid in between is never signalled. They exit 1 when no vtium is found or the signal fails, and 2 for an argument they cannot take.

Under systemd, `systemctl kill --kill-whom=main -s SIGRTMIN+1 vtium@ttyN` sends the signal too. Without `--kill-whom=main`, the signal also reaches the login session. A real-time signal ends the session's programs by default. Reading a process's descriptors and signalling the process take the same right. So root and the user that vtium runs as may send these signals. A program on the terminal that runs as another user may not. A vtium started as root takes the signals from root alone. vtium's other signals are SIGTERM, SIGINT, and SIGPIPE, and SIGUSR1 and SIGUSR2 for the VT's switches. vtium sends `SIGRTMIN+4` to PID 1 for `key-power-off`. That signal is systemd's, and vtium never takes it.

## No display

At start, vtium waits `display-wait` (10 s by default) for a frame on a display's screen. The wait counts from when its VT is shown. With no frame by then, vtium exits with status 1, so the unit's getty fallback takes the VT. The wait runs only while the VT is vtium's. Another program may take the VT before vtium's first frame is on screen, as X does at boot when it starts on another VT (#270). vtium then waits for the VT to come back, as it does for a switch away later in its run. When the VT comes back, the wait starts again from the full `display-wait`. Under a closed policy, vtium never gives up. It holds its VT and waits however long it takes, as under `forever` (ADR-1401 D8).

A device whose displays are never set up, as when the modeset fails, counts as no display. So does an announced display whose every frame fails to show. `display-wait=0` exits at once without a display. `forever` waits for the first display however long it takes. `forever` is for a machine whose only display is a USB adapter (DisplayLink, `udl`), plugged in at any time after boot.

A frame reaches the screen at its flip. The loop reads the flip at the earliest in the turn after the frame's draw. So the wait runs out at the end of a turn after its due time. While a frame is on its way to a screen, the wait waits up to 1 s more for the flip (`wait::FLIP_WAIT`). So vtium does not exit just before a frame that it has already sent shows. Under `display-wait=0`, a display set up when the VT is shown is drawn, and its flip read, before the wait decides.

A head's command starts once one of its displays is set up. It starts on the grid of every display of the head set up by then, so it sees no SIGWINCH as it starts. While the wait runs with no display, the command waits. If vtium exits, the command never starts. Under `forever` with no display, the command waits for the head's first display, however long that takes.

Once a display has come, vtium never exits for want of one. When a head's last display goes, vtium logs it. vtium then does what the head's `when-display-lost` in vtium.conf says for that head (ADR-1401 D8). A mirrored head keeps its sessions while one of its displays remains.

- **`keep`** is the default for every head, and for the compiled-in `console` head. The head's sessions run on. The grid keeps the last display's size, so the program sees no SIGWINCH. The keys of the devices that reach the head still type into it, as the kernel console's tty takes keys through an unplugged monitor. The blank does not run. See "The blank" for details.
- **`hangup`** hangs up the head's sessions at once, as a serial line does when it loses its carrier. Every console's pty closes, and its programs get SIGHUP. Each console follows the respawn policy. Under respawn, its session starts again in the same console, with its id. Under `oneshot`, the session ends. A hang-up is vtium's own act, so it counts as no quick exit. An exit read in the hang-up's turn is the hung-up session's exit.
- **`hangup DURATION`**, such as `hangup 30s`, hangs the sessions up the same way once the time runs out with no display back. Each head keeps its own timer, which wakes the loop.

A head comes back only on a display that its rules match. vtium logs the return and draws the head whole. Where the display's size differs, the grid takes that size, with one SIGWINCH (the operator's decisions on vtium/vtium#21). A head whose display never lit receives no key, even from a keyboard that its rule claims. The active head never moves because a head's display left or came back. Only the anti-lockout guard moves it then. See "Heads" for details.

## The kernel

- **`vtium.enable=0` on the kernel command line turns vtium off for one boot** (ADR-1401 D9). vtium reads `/proc/cmdline` at its start, before vtium.conf, its VT and any card. When the key's last value is `0`, vtium logs one line that names the key. vtium then exits with status 1, so the unit's getty fallback gives the VT a login prompt. Any other value, and no `vtium.enable=` at all, change nothing. `check-config`, `--help`, `--version` and the subcommands still run. Tests: `vtium_enable_0_alone_turns_vtium_off`, `the_start_exits_1_on_a_command_line_that_turns_vtium_off`.
- **vtium shows the kernel's warnings and errors over its console** (ADR-1401 D15). The kernel's own console draws nothing on a VT in graphics mode. So vtium reads `/dev/kmsg` from the moment it opens it. vtium shows each message from the kernel itself whose level is warning or more severe. vtium shows a message only when the kernel's console log level lets the message's level through. That log level is the first field of `/proc/sys/kernel/printk`. So `quiet` and `loglevel=` work as they do for the kernel's console. The messages show in the notices' box, in the notices' colors, on the head that holds the boot display, and only while vtium's VT is shown. vtium never writes them into a console's screen or its pty. At most 5 show at once, the newest. The box's last line reads "Press Esc to dismiss this message (15)", or "these messages" when it holds more than one. The number is the seconds left. The loop's timer counts it down once a second, from the first frame that draws the newest message. A new message starts the count again at 15. At 0, the box goes on its own. Esc dismisses the box, and vtium keeps that Esc from the console's program. Any other key that reaches the head dismisses the box too, as it dismisses the notices, and then goes on to the program. Each second the box is drawn again whole, because the renderer reports a notice's area as one rectangle. A message longer than 240 characters ends in an ellipsis. A message that arrives while the VT is not shown, or while no head holds a display, is never shown later. Where vtium cannot open `/dev/kmsg`, it logs why and shows none. Tests: `warnings_from_the_kernel_show_and_info_does_not`, `a_console_log_level_of_3_hides_warnings`, `a_kernel_warning_shows_over_the_console_and_never_in_it`, `the_kernel_messages_end_with_the_line_esc_dismisses_them`, `the_kernel_box_counts_down_each_second_and_goes_at_0`, `a_new_kernel_message_restarts_the_count`, `esc_dismisses_the_kernel_box_and_stays_with_vtium`, `another_key_dismisses_the_kernel_box_and_reaches_the_program`.
- **`kernel-messages` decides who shows them while Plymouth runs.** Under `after-plymouth`, the default, vtium shows none while plymouthd runs, and it shows the messages that arrive once Plymouth has quit. It never shows later the messages that came while Plymouth ran. vtium tells that Plymouth runs from Plymouth's pid file, `/run/plymouth/pid`. The file must name a running process called `plymouthd`. So vtium needs no plymouth binary. Under `always`, vtium shows them whether Plymouth runs or not. Tests: `after_plymouth_holds_the_messages_back_while_plymouth_runs_with_no_replay`, `plymouth_runs_while_its_pid_file_names_a_running_plymouthd`.

## Displays and frames

- **A frame its display cannot take yet is drawn once the display can.** A display takes no frame while a flip, a vblank or a modeset waits, while it is powered down, or while its card sleeps. A frame that meets one of these waits stays pending. The loop draws the frame at the first turn that the display takes frames again, with no timer. So an idle session never goes on showing an older frame. A display that keeps taking no frame does not wake the loop for it (vtium/vtium#174). Tests: `a_frame_that_found_no_canvas_is_drawn_once_the_display_lends_again`, `a_display_lending_no_canvas_does_not_spin_the_loop`, vtium-platform's `a_display_lends_a_canvas_exactly_while_it_is_ready_for_a_frame` and `the_display_is_ready_for_a_frame_while_awake_on_and_not_flipping`.
- **With three buffers, a draw that a flood paces waits for the flip in flight.** During a flood of output, the coalescing holds a draw until a refresh has passed since the display's last present (`src/sync.rs`). A draw that the coalescing holds is a paced draw. The paced draw's deadline may come while the display's flip is still in flight. vtium then composes nothing, and draws once the flip ends, as it does with two buffers. A paced draw that first waited for a frame still composing waits for that frame's flip in the same way. With one buffer, or on a framebuffer, no draw waits for a flip. vtium draws into the buffer shown. A frame composed during the flip could not reach the screen before the flip ends. During a flood, the next change would draw over that frame before it got there. The wait costs no latency. The frame composed at the flip's end reaches the screen at the same vblank as a frame composed during the flip would. A draw that cannot wait still composes into the free third buffer at once. Such a draw is for a key, a key's echo, the pointer, or a display that lost its picture (ADR-1401 D2, vtium/vtium#361). Tests: `a_paced_draw_waits_for_the_flip_in_flight`, `a_paced_draw_that_met_a_frame_composing_waits_for_its_flip`, `a_draw_at_once_composes_ahead_while_a_paced_draw_waits`, `a_paced_draw_reaches_the_screen_as_soon_as_one_at_once`, `with_one_buffer_a_paced_draw_composes_at_its_deadline` and `a_paced_draw_waits_for_the_flip_with_two_or_three_drm_buffers`.
- **During a flip, a short write composes ahead only inside a key's window.** A short write is output that a turn of the loop parsed in full, less than `COALESCE_BYTES` of it (`src/sync.rs`). A key that vtium sends to the program opens a window on each display. The window closes at the first flip of that display that completes after the key was sent. With two or three buffers, every short write inside the window composes at once. That includes the key's echo, and any other change that the program makes just after the key. For example, the program may redraw a status line or a clock before it echoes the key. vtium cannot tell which bytes are the echo, so it does not try to. A short write that comes outside a key's window while the display's flip is in flight waits for the flip to end, as a paced draw does.

  The rule reads state, never a clock. The terminal counts the keys it sends to the program. Each display's view keeps that count from when its display's last flip completed. While the two counts differ, a key's window is open on that display. The window of a key sent while a window is open closes with that window, at the same flip. The frame that a key draws for itself does not close the window, so the echo that follows still composes at once. A key that sends the program nothing, such as a scroll key on the main screen or a modifier pressed alone, opens no window. With one buffer, or on a framebuffer, no short write waits.

  A status bar or a clock that redraws itself while no key's window is open composes at most once a refresh, at the end of the flip in flight. tmux's pane updates arrive as many short writes. They compose few frames that the next frame draws over before the display shows them. In the refresh after a key, a few more frames can compose. The keys bound how many, not the program's output (ADR-1401 D2, vtium/vtium#366). Tests: `a_short_write_after_a_key_composes_ahead_during_a_flip`, `a_short_write_no_key_caused_waits_for_the_flip`, `every_change_in_a_keys_window_draws_at_once`, `a_keys_window_closes_when_the_next_flip_completes`, `the_frame_a_key_draws_itself_leaves_its_window_open`, `with_one_buffer_or_a_framebuffer_no_short_write_waits`, `a_short_write_is_at_once_only_in_a_keys_window` and `a_key_sent_to_the_program_opens_a_window_its_next_flip_closes`.
- **Output no key caused reaches the screen at most once a refresh.** vtium draws anything a key caused as soon as it can. A short write is one case of this rule. Some programs use synchronized output (DEC private mode 2026), such as an editor, a terminal multiplexer, or a program built on a TUI toolkit. Such a program brackets each update so that the terminal shows the update whole. With two or three buffers, two draws compose at once inside a key's window: the end of such an update, and the draw that a held update owed. Any other such draw that comes while the display's flip is in flight waits for the flip to end, and composes then, as a paced draw does. The same window decides this as for a short write. With one buffer, or on a framebuffer, no update waits. An update stays whole either way. The program may have begun another update by the time the flip ends. The finished update then goes out with the next update's end. An update outside a key's window that waits reaches the screen at the end of the flip in flight, at most once a refresh (ADR-1401 D2, vtium/vtium#366). Tests: `a_synchronized_update_after_a_key_composes_at_once_during_a_flip`, `a_synchronized_update_no_key_caused_waits_for_the_flip`, `an_owed_draw_composes_at_once_only_after_a_key`, `with_one_buffer_or_a_framebuffer_no_synchronized_update_waits`, `a_synchronized_update_that_waits_is_never_drawn_in_part`, `a_hold_does_not_make_a_waiting_draw_compose_at_once` and `the_loop_holds_an_update_no_key_caused_for_the_flip`.
- **A display whose mode changes in place is laid out again at its new size.** A modeset can give a display that is already online a new mode on the same connector. This happens in two cases. When a modeset's test commit fails, every display falls back to its default mode. And a framebuffer wakes at whatever geometry another program set while the VT was away. The display then asks for a redraw. vtium reads the display's size again, and gives its view a new renderer at that size. vtium sets the head's grid and its pty from the new layout, and draws the next frame whole. At every redraw, vtium also reads the display's refresh rate again, whatever its size. So a mode that changes only the refresh rate paces the display's frames at the new rate (vtium/vtium#208, vtium/vtium#216). Tests: `a_display_whose_mode_changes_in_place_draws_whole_at_its_new_size`, `a_frame_composing_across_a_mode_change_is_dropped`, `a_mode_smaller_than_a_cell_and_back_draws_at_the_new_size`, `a_display_whose_refresh_rate_changes_in_place_paces_at_its_new_rate`, vtium-platform's `a_mode_changed_in_place_asks_for_a_redraw_at_the_new_size`, `a_geometry_changed_while_away_asks_for_a_redraw_at_the_new_size` and `a_refresh_rate_changed_in_place_asks_for_a_redraw`.
- **A renderer set that fails keeps the display's renderer, and the pointer on its cursor plane.** An arrow made from the failed set would have no font to size it by. The pointer would then show nowhere.

## Selection, copy and paste

The pointer drives vtium-term's selection. The seat keeps one selection buffer. The buffer holds what the user copied last, or what a program set last with OSC 52 while `clipboard-write` is on. The console has no system clipboard. The middle button pastes the buffer, and so do the keys that `key-paste` binds, Shift+Insert by default. They paste through vtium-term's `Terminal::paste`, filtered. The paste is bracketed while the program asks for that with mode 2004. The buffer holds at most the text of the scrollback and the screen, or vtium-term's `CLIPBOARD_MAX` bytes from one OSC 52.

The pointer also drives OSC 8 links and OSC 133 prompt marks, as ADR-1002 decides. At each pointer event and each key press, vtium tells the shown console's screen which cell the pointer is over, and whether Ctrl is held. So the frame names the link under the pointer. While Ctrl is held, the frame also carries the link's URI for the overlay row. vtium-render draws the overlay row on the bottom row, or on the top row while the pointer is on the bottom one. The overlay row shows the URI from the row's first column, in the default colors inverted. A URI longer than the row is cut at the row's end with `…`. The overlay covers only the cells that the URI takes.

Letting go of Ctrl sends no key to the program. So vtium also reads which modifiers a head's own keyboards hold. A head's own keyboards are the keyboards that deliver to it. vtium reads them whenever a keyboard's modifiers change, a keyboard goes, or the focus moves. It also reads them when the anti-lockout guard moves a keyboard, and when the VT comes back and the keyboards start afresh. So letting go of Ctrl, or unplugging the keyboard that holds it, ends the overlay.

The overlay belongs to the head that has the focus. The head that loses the focus shows no overlay, unless one of its own keyboards holds Ctrl. That head still underlines the link under its pointer, and it still draws its pointer. The head that takes the focus shows the overlay of the link under its own pointer at once, while the keyboard that follows the focus holds Ctrl.

A pointer that hides is over no cell, and so is a pointer in the strip that a display leaves past the grid. Such a pointer hovers no link. A click in that strip still selects at the grid's nearest cell. The pointer is over the shown console alone. A console chord leaves the console that it hides hovering nothing. The console that the chord shows hovers the link under the pointer at once, with the Ctrl that the chord holds.

Ctrl+click on a link copies its URI into the selection buffer, and clears the selection. Nothing is opened, and nothing reaches the program until the user pastes. Ctrl+right-click on a line of a command's output selects that output as whole lines and copies it. While a program tracks the pointer, both take Shift as well, as selection does. On the main screen, Ctrl+Shift+Up moves the view to the nearest marked prompt above its top row. Ctrl+Shift+Down moves the view to the nearest marked prompt below, or back to the live screen. On the alternate screen, both keys reach the program.

- **With no mouse tracking, or with Shift, the pointer selects and copies.** The left button's drag selects, and its release copies. A double click selects and copies a word. A triple click selects and copies a line, as xterm's `on3Clicks` default, `line`, does. A fourth click starts again. The right button clears the selection, where xterm's right button extends it. A click with no drag, or a double click on a space, leaves the selection buffer as it was. xterm's `SelectSet` does the same, because it takes a selection only when it is not empty. Three things clear the selection: a key, the pointer hiding while the VT is vtium's, blanked or not, and a change of mouse tracking. vtium-term's README says how the line is copied. Test: `a_double_click_selects_a_word_and_a_triple_click_a_line`.
- **A drag ends when the left button is no longer held, and at the VT's release,** since motion with no button held is not a drag. Test: `a_drag_ends_without_its_button_and_at_a_vt_release`.
- **The middle button pastes at its release,** by xterm's translation `~Ctrl ~Meta <Btn2Up>: insert-selection(SELECT, CUT_BUFFER0)`. **A key pastes too, once a press.** That key is `key-paste`, Shift+Insert by default, by xterm's translation `Shift <KeyPress> Insert: insert-selection(SELECT, CUT_BUFFER0)`. A repeat of the held key pastes nothing more. The paste is matched before the terminal's grabs. Tests: `key_paste_binds_the_paste`, `a_hostile_selection_is_pasted_filtered_once_a_press`.
- **Shift selects, pastes and scrolls back while the program tracks the pointer.** Spec: xterm's `ShiftOverride` in `button.c`, with `shiftEscape` false, its default. A button, the wheel included, or motion with Shift held is not reported. Shift and the wheel scroll the scrollback. vtium decides a button at its press. Until its release, the button selects or pastes, or is reported, whatever Shift does meanwhile. xterm decides each event by the Shift held then. A program can ask with XTSHIFTESCAPE 1 (`CSI > 1 s`) that Shift reach it. Such a program gets Shift in its reports. Shift then selects, pastes, and scrolls nothing, as xterm's `shiftEscape` true does. Tests: `shift_selects_and_pastes_while_the_program_tracks_the_pointer`, `shift_and_the_wheel_scroll_back_while_the_program_tracks_the_pointer`, `shift_pressed_during_a_reported_drag_changes_nothing`, `a_program_that_asks_for_shift_gets_it_in_its_reports`.
- **A wheel event is one report while the program tracks the pointer, else a zoom with Ctrl, else three lines of scrollback,** whatever its number of steps. Mode 1007 is set at start. On the alternate screen, while mode 1007 is set, a wheel step that vtium does not report goes to the program as three cursor-up or cursor-down keys. That is one key a line, as DECCKM encodes them. With mode 1007 reset, the wheel scrolls the view as elsewhere. Spec: ctlseqs' alternate scroll, as vtium-term's mode table states it. Test: `the_wheel_sends_cursor_keys_on_the_alternate_screen_under_mode_1007`.
- **Natural scrolling** reverses the wheel's report and its scroll, and with them the cursor keys that mode 1007 sends. It leaves Ctrl's zoom as the wheel turns. `natural-scrolling` is off by default. vtium.conf or the command line sets it at the start (vtium/vtium#203). Tests: `natural_scrolling_reverses_the_wheel_but_not_its_zoom`, `natural_scrolling_turns_the_report_and_the_scroll_but_not_the_zoom`, `natural_scrolling_comes_from_the_file_and_the_command_line`.
- **The pointer hides after 20 seconds with no pointer event by default,** and not when a key is typed. `pointer-hide-timeout` sets the time, and 0 never hides the pointer. `pointer-hide-while-typing` hides the pointer at each key sent to the program. `pointer-char` draws a character's glyph in place of the arrow (the operator's decisions on vtium/vtium#102). `soft-cursor`, off by default, has the renderer draw the pointer on every display, and it sets no cursor plane up. Tests: `typing_hides_the_pointer_under_pointer_hide_while_typing`, `soft_cursor_draws_the_pointer_in_software`.

## The bell

Under `bell`, off by default, a BEL from any console of any head rings the VT's bell. It rings once a turn, however many BELs came. It rings while mode 1042, set at start, lets BEL through. A program that resets mode 1042 rings nothing. Spec: ctlseqs' mode 1042, read for a console with no window to mark urgent, as vtium-term's mode table states it. Tests: `bell_rings_the_vt_at_a_bel_while_mode_1042_lets_it_through`, `two_heads_ringing_in_one_turn_ring_the_vt_once`.

## Key bindings

vtium takes some keys for itself before they reach the program. It matches them in the key order of ADR-1005 D7 (`src/grab.rs`):

1. The VT's keys.
2. The power keys.
3. The console and focus chords.
4. The paste.
5. The terminal's grabs, which scroll, jump between prompts, zoom, rotate, and reset.
6. DECARM's drop of a repeat.
7. The encoder.

Every key but the VT keys and the rescue key is a key binding of vtium.conf, a `key-` key. Each binding's built-in default in the key table is the key that vtium took before the keys were configurable. So with no vtium.conf, every key does on the main screen what it did before (ADR-1005 D10). Test: `the_built_in_bindings_are_the_keys_vtium_took_before`.

- **A key bound elsewhere acts on its new combination, and its old one reaches the program. An emptied key takes no combination.** Tests: `a_key_bound_elsewhere_acts_on_its_new_combination_and_its_old_reaches_the_program`, `an_emptied_key_reaches_the_program`, `the_key_bindings_take_what_vtium_conf_binds_and_nothing_when_empty`.
- **The scroll keys and the prompt jumps are the main screen's.** While the alternate screen is shown they reach the program. The other keys are vtium's on both screens. Tests: `the_scroll_keys_scroll_on_the_main_screen_and_reach_the_program_on_the_alternate`, `ctrl_shift_up_and_down_jump_between_the_marked_prompts`.
- **A combination that two keys bind goes to the key that comes first in the key order.** The reading of the configuration reports such a combination, at the start and in `check-config`. The report is at the line of the key that a source set. When both keys were set, the report is at the later key's line. The reading gives the combination to the first key alone. Tests: `a_combination_bound_twice_is_reported_and_goes_to_the_first_key`, `a_combination_bound_twice_goes_to_the_first_key_in_the_key_order`.
- **No key binds a combination that switches the VT.** The seat matches these combinations before every binding: Ctrl+Alt with F1 to F12, with any other modifier too, and XF86Switch_VT_1 to 12. The rescue key is one of them. A binding of one of them is reported with its file and line, and dropped. The key keeps its other combinations. Test: `a_binding_of_a_key_that_switches_the_vt_is_reported_and_dropped`.
- **`key-reset` resets the console shown, as RIS does, once a press, and no other console.** It calls vtium-term's `Terminal::reset`. That call drops the replies queued for the program, and abandons an image request that is out. The console's pty, paused for that request, then takes output again. The reset clears the screen and the scrollback, and it returns every mode to its start, the kitty keyboard protocol's flags among them. `key-reset` is matched before the encoder, so it acts whatever flags a program set. Tests: `the_reset_key_resets_the_console_and_its_keyboard_modes`, `the_reset_key_resets_the_shown_console_and_no_other`, `a_held_reset_key_resets_once`, `the_reset_key_ends_the_request_out_and_the_console_reads_on`.
- **A notice names the key vtium.conf binds,** its first combination, and leaves out the sentence that would name an emptied key. Tests: `a_notice_names_the_keys_vtium_conf_binds`, `the_ended_sessions_notice_names_the_key_vtium_conf_binds`.
- **Four key bindings keep their old names for now.** `grab-paste`, `grab-reboot`, `grab-power-off` and `grab-suspend` shipped before the maintainer renamed the key bindings to more accepted terms. vtium reads them as `key-paste`, `key-reboot`, `key-power-off` and `key-suspend` (`vtium_settings::keys::RENAMED`). The configuration's reading reports each line or option that uses an old name, with the name to write. The start logs the report. `check-config` prints the report on standard output, as a note that does not count against the file. So a vtium.conf from an earlier release still passes the check that vtium-config's install runs. Where a source sets both names, the new one wins, because the reading applies the old names before the new ones. vtium-config's `get`, Settings view, and base card show the value that an old name's line gives. Its `set` and `set --unset` of a key binding comment out the line that sets the key by its old name. So vtium-config moves a file to the new names. Tests: `an_old_key_binding_name_is_read_as_its_new_name_and_reported`, `the_new_name_wins_over_the_old_one`, `an_old_key_binding_name_is_a_note_and_the_check_passes`, vtium-settings' `setting_a_key_binding_comments_out_its_old_name`, vtium-config's `a_key_binding_set_by_its_old_name_shows_its_value`, `set_moves_a_key_binding_from_its_old_name` and `the_base_card_shows_and_edits_key_bindings`.
- **A vtium.conf edited by hand and the same file written by `vtium-config set` give the same keys.** `vtium-config set KEY ""` writes `KEY=`, which empties a key binding. Tests: `vtium_config_set_and_a_hand_edit_give_the_same_keys`, vtium-config's `set_writes_vtiums_own_keys_as_a_person_writes_them`.

## Releases and the keys held

A program can ask the kitty keyboard protocol for key releases. Such a program gets a release for every press it got, and never one for a key vtium took (ADR-1005 D7). The binary records each press that reaches a console's encoder, with the keyboard it came from (`src/app/held.rs`). A key's release goes to the console that received its press, through that console's encoder, wherever the keyboard types by then. A release with no record goes nowhere. So a key that vtium took never reaches the program, pressed or released. Such a key is a VT key, a chord, the paste, or a grab. A repeat reaches the encoder only while its press's record stands. So a key that vtium took keeps its repeats, even after a modifier is let go and the key matches no binding.

- **A console that stops receiving a keyboard gets a release for each of its keys held, at once.** A console receives a keyboard only while vtium's terminals are awake on the VT. The keyboard must also be routed to the console's head on this VT, and the head must show that console. So a VT switch sends the releases, newest key first. So do a console chord that shows another console, the focus chord moving the keyboard to another head, and an unplugged keyboard. Each release carries the modifiers of the key pressed before it on the same keyboard. With no key pressed before it, a release carries its own press's locks alone. So the program ends with every key let go. The key's real release later goes nowhere. vtium-term encodes these releases only while the program asked for releases. The specification does not say what a terminal does with keys held when it loses the keyboard. Tests: `a_vt_switch_lets_go_of_the_keys_held`, `a_console_chord_lets_go_of_the_keys_held`, `an_unplugged_keyboard_lets_go_of_its_keys_held`, `the_focus_chord_lets_go_of_the_keys_held_on_the_head_it_leaves`, `a_console_that_stops_receiving_a_keyboard_gets_its_keys_released`, `a_key_vtium_took_never_reaches_the_program_pressed_or_released`.
- **The modifiers reach the terminal as the input reports them.** This includes NumLock, Hyper, and Meta. So mode 1035 reads NumLock's state (vtium/vtium#356). The key bindings ignore NumLock, a state that no binding names. They ignore Caps Lock unless a binding names `<Lock>`. So Shift+Up scrolls with Caps Lock on. The key bindings match no key held with Hyper or Meta, which no binding can name (ADR-1005 D10, the note of 2026-11-12). Tests: `mode_1035_reads_the_num_lock_the_input_reports`, `num_lock_leaves_a_binding_and_hyper_or_meta_matches_none`, `caps_lock_leaves_a_binding_unless_the_binding_names_it`.

## The power keys

The power keys are the seat's, second in the key order (`src/power.rs`).

- **A power key acts once a press.** A repeat of a held chord asks nothing more, because a held key asks once. systemd takes seven Ctrl+Alt+Del in two seconds as a reboot that stops no service (`CtrlAltDelBurstAction=reboot-force`). Test: `a_bound_chord_acts_once_a_press`.
- **`key-reboot`** is unbound by default. When it is bound, it is matched after the VT's keys and before the terminal's grabs, only while the VT is vtium's. It leaves the selection. It asks init with `SIGINT` while `/proc/sys/kernel/ctrl-alt-del` is 0 or cannot be read, as the kernel itself does for Ctrl+Alt+Del. Otherwise it calls `sync()` and `reboot(RB_AUTOBOOT)`.
- **`key-power-off` and `key-suspend` power the machine off and suspend it.** Spec for powering off: systemd(1)'s `SIGRTMIN+4`, which starts `poweroff.target`. Spec for suspending: logind's `Suspend` method (org.freedesktop.login1(5)) in a build with `logind`. Where logind is not on the system bus or not built in, a shell that vtium starts writes `mem` to `/sys/power/state` (the kernel's `Documentation/admin-guide/pm/sleep-states.rst`). Because a shell does the write, the loop still serves the VT's switch to the kernel's suspend console. The operator's decision on vtium/vtium#21. Neither key calls `reboot(2)`. A minspec build on a host running logind suspends through sysfs too. So it passes logind's inhibitors by, and it skips logind's `PrepareForSleep` signal. No other session's lock-on-suspend runs. Tests: `power_off_asks_init_and_suspend_asks_the_host`, `a_suspend_waits_for_the_last_one_to_wake`, vtium-platform's `no_logind_on_the_bus_is_told_from_a_refusal` and `the_sysfs_child_is_reaped_from_the_loop`, and tier 3's power variants.
- **`key-power-off` warns where PID 1 does not take its signal.** At start and in `check-config`, vtium warns when the key is bound and PID 1 neither catches `SIGRTMIN+4` with a handler nor blocks it. vtium reads this from the `SigCgt` and `SigBlk` masks in `/proc/1/status`. vtium also warns when that file does not answer. The kernel drops a signal sent to PID 1 that PID 1 neither catches nor blocks, so the key would power nothing off. sysvinit catches the signal with a handler. systemd blocks it and reads it from a signalfd, so its bit is in `SigBlk` and not in `SigCgt`. busybox init does neither. Tests: `key_power_off_is_silent_where_init_takes_the_signal`, `key_power_off_warns_where_init_neither_catches_nor_blocks_it`, `key_power_off_names_why_an_unreadable_status_does_not_answer`, and tier 3's `power-off` and `power-off-sysvinit`.

## A fake VT

A fake VT is the VT vtium runs on when the seat has no kernel VTs. On a fake VT, vtium holds the seat's keyboards and pointers open for as long as it runs. So after Ctrl+Super+F12 releases the VT, the same chord can take the VT back. While that VT is released, vtium still sees every key typed into the other session and drops each one but the chord. A pointer's move, button, or wheel reaches no program, and it selects, pastes, or zooms nothing. No key or pointer action wakes a display, because the displays are the other session's.

The mouse moving in the other session still arms the pointer's hide. That hide hides the arrow, and it leaves the selection for the user's return. At the return, the arrow stays hidden until the pointer moves. vtium's input keeps adding up the moves made in the other session (vtium-platform's `src/input/pointer.rs`). So an arrow drawn at its old place would jump at the next move. A program on vtium's console can still set the keyboards' LEDs with DECLL. A held key's repeat timer still runs, and vtium drops its repeats. vtium takes no exclusive grab of a device (`EVIOCGRAB`), so the other session still gets all of its input. A kernel VT's release closes the devices instead. Tests: `a_released_fake_vt_keeps_the_keyboards_open_to_take_it_back`, `input_on_a_released_fake_vt_wakes_no_display`, `a_released_fake_vt_reports_no_pointer_action_to_the_program`, `a_pointer_hide_on_a_released_vt_keeps_the_selection`.

## Pictures

The `images` feature (ADR-1100 D10) adds code to three crates. It builds vtium-term with its image store and router. It builds vtium-render with the compositor's pictures. It builds vtium-image with the sixel and kitty graphics handlers. The minspec build, which leaves the feature out, carries none of that code. Every build reads the six image keys: `image-storage-limit`, `max-graphic-size`, `num-color-registers`, `private-color-registers`, `sixel` and `kitty-graphics` (ADR-1100 D11). A build without images then draws no picture.

In a build with images, each console's terminal gets the sixel and kitty handlers, with `max-graphic-size` and the color registers' keys as their limits. At every turn of the loop, between two input calls, each head gives each of its consoles three host events (ADR-1100 D5). The head gives each event only when the event's value changed:

- **The budget**: `image-storage-limit`. Under `auto`, the budget is four frames of the head's displays in RGBA, from 16 MiB to 192 MiB. vtium works it out again when a display joins or leaves the head, or changes size. A smaller budget evicts nothing at once. The store's next reservation evicts down to it.
- **What it offers**: sixel and kitty graphics. The console offers each one while its key is on, the budget is above 0, and every display of the head draws pictures. The CPU compositor draws pictures in this build. A head with no display yet offers them. A console that offers sixel reports DA1's attribute 4.
- **The cell size** its pictures are placed in. For the console shown, this is the head's cell. For a hidden console, it is the console's own cell. A picture keeps the cell it was made in, so a zoom draws it scaled.

The head's snapshot carries the frame's pictures to its render thread. Each picture shares its image's pixels (ADR-1100 D9). A renderer keeps scaled copies and its damage history under the image keys of one console's store. Every console's store numbers its keys from zero. So a console switch makes each display of the head a new renderer, as a font change does.

Kitty animations play through each console's animation clock (ADR-1102 D3). So do animated GIFs, which the store keeps the same way. The image store records only what the program's commands set. That is the frames, their gaps, whether the animation runs, its loops, and the frame that a command made current.

At each turn of the loop, the clock answers the commands that changed an animation. It moves each running animation on by its frames' gaps. It passes over gapless frames, which have a negative gap and never show. Its timer fires at most once every `ANIMATION_FLOOR_MS`. When a head takes its snapshot, the clock puts the frame it chose on every placement of an animated picture. It asks the store for that frame's pixels once for each picture. A turn that moves a frame draws the head again.

`v=n` plays the frames `n` − 1 times, and then stops on the last frame. `v=1` plays them forever. A run started past the first frame plays to the last frame before its first time through (ADR-1102 D4). The clock arms no timer while nothing plays, while its console is hidden, or while another program holds the VT or the displays are blanked. When its console shows again, the clock works out from the time where each animation has got to. It shows that frame at once, without playing the frames it missed.

Some handlers need the image helper (ADR-1101): for a file, shared memory, PNG, or zlib. Such a handler leaves a request, and its terminal takes no input until the reply. The image helper is its own program, `vtium-image`. It reads what a program names, and decodes it, as the session's user. So the console, which runs as root, does neither. vtium opens the program that `image-helper` names, once at start. By default, that is the path that vtium was built with (`VTIUM_IMAGE`). vtium refuses the program by the glyph helper's rules, and logs why. Each console has one image helper host from vtium-platform for as long as the console lives. The host starts that console's helper from the opened program, at the console's first request that needs it.

At the turn that finds a request, the head hands the request to the console's host, with the console's session. The session is the login child's pid and the owner of the pty. vtium reads the owner again for each request, by reopening the pty's slave from its master (ADR-1101 D2). The host either answers at once or sends the request. An answer at once goes straight back to the terminal, and the pty is never paused. When the host sends the request, the head pauses the console's pty. The head puts the host's socket in the loop, so that the loop wakes when the reply arrives. The head also holds the reply timer, `head::images::REPLY_TIMEOUT`, 2,000 ms. The reply goes back to the terminal, or `FAILED` does once the timer fires. The replies that the handler writes go to the program. The socket leaves the loop, and the pty resumes. The binary checks a reply's sizes against its request again before it hands the reply back.

A reply can fail, as from a lost socket or a reply that fails the host's checks. A failed reply means the host has stopped its helper and counted a crash. When the timer fires, the head tells the host to stop its helper, and no crash is counted. The console's next request starts another helper. After three crashes in one session (`IMAGE_CRASHES_MAX`), the host starts no more helpers for that console. The head tells that console's terminal that no helper runs. So the kitty handler answers such a request at once with the reply that ADR-1100 D7 gives for "no helper". That reply is `EBADF` for a file, a temporary file, or shared memory, and `EINVAL` for PNG and zlib. Every console answers the same way when vtium has no program to start.

A session that ends drops its request out with no reply, so that the reset that starts the next session takes effect. The host stops its helper and clears its crash count. Other consoles, drawing, and keys carry on while one console waits. A console past its crash limit leaves the other consoles' helpers alone. A temporary file may lie in vtium's own `TMPDIR`, which reaches the helper when it is an absolute path. `App::set_image_helpers` puts a test's stand-in hosts in place of the real ones.

## The font

vtium draws two kinds of font. It draws frits, which are font set files (ADR-1200, ADR-1301 D2). The helper, a program of its own, generates a frit's glyphs at run time. vtium also draws its built-in fonts. vtium parses no font file itself. vtium-font's PSF loader is behind a feature that the binary leaves out.

- **At start** the font is `font-name`, when a file or the command line sets it. Otherwise the font is vconsole's. For vconsole's font, `vconsole.font=` on the kernel command line wins over `FONT=` in `/etc/vconsole.conf`. Otherwise there is no font, and the built-ins draw with no log line. `font-engine=unifont` or `8x16` draws the built-ins too (ADR-1200 D9). A head's look wins over these, through the `font-name` of its `[look NAME]` section. See "Heads" for looks.

  A name is the frit `NAME.vtfrit` in `/etc/vtium/fonts`. A name that no frit bears becomes a frit with one source, made on the fly:

  - A path gives `source=file:PATH`, as `font-engine=psf` gives one.
  - An outline family gives `source=font:FAMILY`, as `font-engine=freetype` or `pango` gives one.
  - vconsole's font gives `source=vconsole`.
  - Any other name gives `source=kbd:NAME`.

  The helper is handed such a frit as text, with no file. The frit goes under the name it was given when that is a frit's name. Otherwise, as for a path or a family, it goes as `generated`, because the helper refuses a request naming anything else (D1). A frit whose `cell=` or `size=` vtium cannot read draws the built-ins, with one line naming the font and why. A source that the helper cannot read gives the helper's own line, and the built-ins go on drawing.
- **A frit** is generated in the cell it states with `cell=WIDTHxHEIGHT`, in pixels, read as text before the first frame. Otherwise it is generated in the cell that its first source gives (#145).

  **How the console learns the cell.** The helper tells the console that cell, because the console parses no font. The console asks for the cell at the height it draws at. That height is a configured `font-size` in points. Otherwise it is an outline frit's `size=` at the density, and otherwise the automatic rule. The console waits at most 100 ms for the answer (`OWN_CELL_MS`). This is the one wait on the helper. The console asks before the first frame, at an OSC 50 switch, and at each zoom of an outline frit. It asks again at a height only after a zoom. Every head that draws the frit shares each answer.

  **Bitmap and outline answers.** A bitmap first source answers with its own cell, when every later bitmap source's cell fits in it. With no `font-size` configured, the console takes that cell at the largest whole multiple that is not over the display's automatic height. The multiple is at least once. So a bitmap font keeps its own pixels whole (the operator's decision on #145, 2026-10-28). An outline first source answers with the cell that the W rule gives at the height asked. The console takes that cell at that height alone (the maintainer, 2026-11-01). The answer, and not the frit's text, says which kind the first source is. So a `font:` source that resolves to a bitmap font zooms as a bitmap frit. And when a bitmap first source is missing on the machine and an outline source answers, the frit zooms as an outline frit.

  **When the helper does not answer in time.** Three things leave a frit without the helper's cell: a refusal, no answer in time, and an outline cell of another height. An outline cell of another height also gives the helper up. A bitmap frit then takes the display's cell, and an outline frit takes the built-in font's width. One line says why. An answer that comes after the wait is kept (ADR-1200 D17, the maintainer, 2026-11-03). From the next frame, each head that draws the frit and takes a cell from it draws in that cell. The head's grid is laid out again, with one line. A refusal that comes late holds as one in time does. A late answer is dropped where the frit already holds an answer that came in time. For an outline frit, that is an answer at the height asked. For a bitmap frit, it is an answer at any height, because a bitmap frit's answer holds at every height.

  **What wins over the frit's cell.** An outline frit's `size=` is the size of its glyphs in the cell. A bitmap frit's `size=` is left aside. A configured `font-size` wins over the frit's cell and size (ADR-1200 D16). `font-size=0` does not. A head's look may set `cell`. The font that the head draws then gets that cell. The look's `cell` wins over the frit's `cell=` and `size=`, and over the top level's `font-size`, because the look is the more specific level. The look's own `font-size`, other than 0, wins over its `cell` (ADR-1403 D5). The built-in fonts take the look's `cell` too, so a head whose frit fails keeps the cell its look asked for.

  **When the built-in fonts draw.** A head draws the built-in fonts alone when nothing names a font, or when `font-engine` is `unifont` or `8x16`. It also does so when its look names `unifont` or `unscii-8`, or when the frit named cannot be read. It does so after an OSC 50 switch to a built-in font, too. A built-in font that is named keeps its own strike in the cell. `unscii-8` draws its 8×8 glyphs at the largest whole factor that fits, centered. So a 12×24 cell draws them at their own size. At twice that size, they would be 16 pixels wide, wider than the cell. `unifont` in a cell smaller than its 8×16 is cut to the cell.

  **A cell that vtium picks.** vtium may pick a cell's height from `size=`, `font-size`, or the display. Such a cell is as wide as the built-in font at that height (D17). The display's height is `font-size=0`'s automatic rule, which `font-size` below describes. That rule gives 8×8 at 320×240, 8×16 at 640×480, and 8×19 at 1366×768. The built-ins draw in the cell from the first frame. unifont draws at the largest whole factor that fits, and otherwise Unscii-8 draws. The built-in font is centered in a larger cell and cropped to a smaller one. The helper generates glyphs for that cell and never moves the cell. So the grid resizes only at a zoom, or at a display hotplug while the cell is the display's. The frit's `glyph-source=` and `glyph-source-<range>=` lines are the font's sprite policy. The configuration's keys override them (D1).

  **The helper's fill.** The console starts the helper, `vtium-config serve`, on the first need. It runs the helper as `nobody` when vtium is root. The helper follows the operator's fill model (2026-10-28). The characters that the screen shows, or newly shows, are asked for and answered first. While nothing is asked, the helper fills each display cell's coverage in this order: the screen's characters, then printable Latin and box drawing, then the rest. A waiting ask is answered before the helper's next batch. The console checks each answer for bounds and dimensions, and for being what was asked. It keeps the answer in memory for the boot. The answer redraws only the cells that show its characters. A character that the frit lacks draws in the built-in font (vtium/vtium#141).

  **The stores and the helper's failures.** The frits' stores together hold 16 MiB below 2 GiB of memory, 64 MiB from 2 GiB, and 128 MiB from 4 GiB. Each frit's store holds that limit divided by the heads. See "Heads" for details. A fill stops at its store's limit. An ask past the limit evicts the sets least recently on the screen. Those sets are asked for again when the screen shows them. vtium gives a helper up for the boot, and logs it once, when the helper fails or answers what is not a frame or not asked. The built-ins then go on drawing. vtium starts a helper again, at most 3 times a boot (`RESTARTS_MAX`), when it crashes, reaches its CPU limit, or gives no answer for 10 s (`ANSWER_MS`). vtium also starts it again when it leaves an ask unanswered for 60 s (`REQUEST_MS`), or exits with work outstanding. The console reads the kernel's font from its VT once at start, before the VT turns graphical. It hands that font to the helper with each request for a frit's `console:` source (D8).
- **Bold and italic** come from the helper by ask (ADR-1200 D21). The console keys each glyph by its text and its style: bold, italic, both, or neither. It asks for each style that the screen shows in a request of its own, which names the style. The helper draws the style from the frit's face for that style, or synthesises it. See vtium-config's README, "Styles". The console refuses an answer whose strikes are of another style than the one it asked for. The fill brings regular glyphs alone. Until a styled glyph arrives, and where the helper gives none, the built-in font draws the glyph in its own synthetic style. Bold is widened. Italic is sheared, a pixel row at a time, about its baseline (ADR-1302 D4). Tests: `an_italic_ask_names_its_style_and_its_glyphs_are_held_as_italic`, `a_strike_in_a_style_not_asked_for_gives_the_helper_up`, `a_style_draws_its_own_glyph_else_the_built_in_fonts_in_that_style`, `italic_and_bold_text_is_asked_for_in_its_style`.
- **The built-ins** are Unscii-8 for cells under 16 pixels, and unifont from 16. In a zh, ja, or ko locale, the built-in is unifont at every size, because Unscii-8 lacks those locales' characters (D7). The locale is the first of `LC_ALL`, `LC_CTYPE` and `LANG` vtium starts with.
- **Sizes are points,** 1/72 inch (the operator's decision on #145, 2026-10-28). `font-size` and an outline frit's `size=` draw at points × DPI ÷ 72 pixels (`font::points_to_pixels`). The result rounds to the nearest pixel, a half away from zero. It is at most vtium-font's `CELL_SIDE_MAX`. The density is `display-dpi`, with no line logged. Otherwise it is each display's density, measured from the physical size the display reports (vtium-platform's `Density`). vtium measures it down the display's rows, as vtium draws the display. Otherwise the density is 96 DPI, with one warning for each display that reports no size. Where displays differ, the lowest density converts, and a larger display draws larger by the layout rule. The team lead accepted this reading for the operator to confirm (2026-10-28). A configured `font-size` follows the displays' density until a zoom. `vtium check-config` opens no display. So it notes the density's source on standard output, outside its exit status. The start logs each display's density. Points do not apply to bitmap fonts. A frit made only of bitmap fonts takes its stated `cell=`, or its fonts' own cell. The built-ins step by their strikes. A `cell=` stays in pixels, an exact override.
- **Line spacing** (ADR-1302 D13). `font-line-spacing`, at the top level or in a look, adds a whole percentage of the text's height to each row. Without it, the frit's `line-spacing=` does. The added rows are split evenly above and below the text band, with the odd pixel above. So the grid has fewer rows. The cell that a look or a frit states, `cell` or `cell=`, is exact and takes no spacing. The cell that vtium works out takes the spacing. That includes the cell that a configured `font-size` gives in place of a frit's `cell=`. The text's height stays the height asked for, so zoom and `font-size` step as before. The console tells the helper the rows added with each ask and fill. The helper places its glyphs in the taller cell. The console asks for, and holds, a frit's glyphs by the cell and its rows added. It does so because two heads can draw one cell size with different spacing. The built-in font's glyphs are placed by their default fit. Line and block characters stretch by repeating their top and bottom rows. The rest keep their size, with blank rows above and below. The sprites draw at the whole cell, so they join from row to row. The underline and strike-through move down with the text band. A session's end reads `font-line-spacing` again with the other font keys (ADR-1201 D11). So the next login draws with the spacing that vtium.conf names then. The font is drawn again when the spacing changed.
- **`font-size`** picks the built-in's strike of its height in pixels. Otherwise it picks the tallest strike under that height, scaled by the largest whole factor that fits. `font-size=0` picks the height from the smallest display. It picks the height that gives at most 120 columns and at least 40 rows, and never under 16. For the columns, it takes a cell as half as wide as it is high. But where 16-pixel cells would leave fewer than 80 by 25 cells, it picks the font's smallest height. So 320×240 draws 40 by 30 cells of 8×8 (vtium/vtium#118). The fallback is tried once. When no font is in use yet and the lookup fails at the size asked, vtium tries `FALLBACK_SIZE`, 16. A second failure is the error. With a font in use, as at a zoom, a failure leaves that font. Tests: `a_small_display_takes_the_fonts_own_height`, `a_320x240_display_draws_40_by_30_cells_of_8x8`.
- **Zoom** steps through the font's sizes (D17). How it steps depends on the font:

  - A frit whose first source is an outline font steps by 1 point, to the next whole point whose pixels at the density differ. Each height takes the helper's cell for that height, or else a cell as wide as the built-in font at that height. At its stated cell's own height, the frit takes its stated cell. The frit steps down to the built-in's smallest height.
  - A bitmap frit steps by its stated or own cell's whole multiples. The built-ins in a look's `cell` step by that cell's whole multiples.
  - The built-ins in their own cell, and a bitmap frit with no cell, stated or own, step through Unscii-8's 8 and unifont's 16, 32 and on.

  Below the smallest, zoom stops, with one line naming the font and its height. A zoom in from a height above 150 pixels (`ZOOM_IN_MAX`) does nothing. Tests: `zoom_steps_through_the_strikes_and_their_multiples`, `zoom_steps_through_the_built_ins_and_stops_at_the_smallest`, `an_outline_frit_zooms_by_one_point`, `a_zoom_steps_an_outline_frit_by_one_point`.
- **The helper** is the program that `font-helper` names. The frits are in the directory that `font-frits` names. Each defaults to the path that vtium was built with (`VTIUM_FONT_HELPER` and `VTIUM_FONT_FRITS`). vtium opens the program once at start, and starts every helper from that open file. So a running console keeps the helper it started with across a package upgrade. vtium refuses a path that is not absolute, a file that is not a regular file, and a setuid or setgid file. It also refuses a file owned by an account other than root or the account vtium runs as, and a file that its group or others may write. vtium logs why it refuses (ADR-1200 D15). The opened file is close-on-exec, so neither the helper nor the session holds it. The helper starts through `/proc/self/fd`, which the kernel lets a process read as any account. So vtium needs `/proc` mounted to start the helper.

  vtium reads a frit only when it passes the same ownership check as vtium.conf (ADR-1401 D10, ADR-1403 D3), at the start and for OSC 50. Root owns the file, or the account vtium runs as owns it. Neither its group nor others can write it, or any folder the path crosses to reach it, through every symlink on the way. A frit that fails is not read. The font's own read logs one line, such as `` vtium does not read the font set g from "/etc/vtium/fonts/g.vtfrit", because other users can change "/etc/vtium/fonts/g.vtfrit" (mode 664). Run `chmod go-w /etc/vtium/fonts/g.vtfrit` so that only its owner can change it. vtium draws its built-in font instead. `` The reason after "because" is worded as vtium.conf's refusal words it. The start's configuration warnings leave the refusal to that read, so it is said once.

  `vtium check-config` reports the same refusal, under the check of the account it runs as. It reports the frit that `font-name` names, and each look's frit on its `font-name` line. Run as another account than root, it also notes where a start as root would refuse a frit that this account reads. It does the same for the font helper (`font::frit_text`, `check::judge`). Tests: `a_frit_others_can_change_is_not_read`, `a_refused_frit_is_logged_once_at_the_start`, `a_frit_the_ownership_check_refuses_is_reported`, `a_looks_frit_the_ownership_check_refuses_is_reported`.
- **OSC 50,** under `allow-font-ops`, on by default, switches the live console's font (ADR-1200 D5, D9). It switches to a frit in `font-frits`'s directory, or to a built-in, that the name names. Otherwise it switches to the frit made on the fly for the font that the configuration gives the head, by the name its query reports. The switch takes a new grid with a pty resize, as a zoom does. A frit gets the helper and the store that every head drawing it shares. The built-ins draw what the helper has not yet sent. A frit in the directory wins over a frit made on the fly under the same name, as at the start. So a name means one font. Anything else leaves the font, with one line saying why. That includes a path, a name that no frit bears, and a frit whose cell cannot be read.

  OSC 50's query names the frit or built-in in use. It names a frit made on the fly by the name that frit was given. A program that sends that name back returns to that font, at the size the head draws it at. A path or a family is not a frit's name. So the query reports no name for it, at the start and after a session's end returns the head to it. The query never reports the name of a font that is no longer shown. OSC 50 cannot name a path or a family. The output after a font request waits for the turn that switches. So a query written with the request names the new font, as `vtium-config set` writes it.

  A switch lasts for the session it came from. A session ends when its program exits, when vtium hangs it up under `when-display-lost = hangup`, or when the close chord closes its console. vtium acts when that session ends, or when the session in the head's only console ends. vtium then reads four keys of vtium.conf again: `font-name`, `font-size`, `font-engine` and `font-line-spacing`. It reads them with the reader it starts with. It returns the head to the font they give, at their size and spacing, before the console's next session starts. A zoom made in the session that ended is undone with it (ADR-1201 D11). A session ending in another console of the same head leaves the font. Where the `font-size` read again turns a configured size on or off, the frit the head draws is rebuilt to drop or take its own cell. An OSC 50 request that a hidden console still holds goes with its session. A font key that does not read is reported and dropped, as at the start. Every other key, and its reports, wait for the next start.

- **A cluster draws its own glyph, keyed by its whole text** (#144, ADR-1200 D20 to D22). A cluster is what a reader sees as one character, such as a letter with its accents. The console asks the helper for each cluster that the screen shows. The helper shapes the cluster with HarfRust and draws it whole. The store keys the glyph by the cluster's text. Until the cluster's glyph lands, and where the helper gives none, the cluster draws in one of two ways. Where its NFC form is one codepoint that the store holds, it draws that codepoint's glyph. Otherwise it draws its base's glyph with its marks. Either way, it leaves out the default ignorables and the rest of an emoji sequence. Where the helper is unavailable, every cluster draws that way, and the one line that says so names this. The arrival of a cluster's glyph redraws each cell showing any of its characters. Tests: `a_cluster_draws_its_own_generated_glyph`, `a_cluster_draws_its_precomposed_form_from_the_store`, `a_base_draws_with_its_marks_overstruck`, `a_cluster_the_screen_shows_is_asked_for_whole`.
- **The part of a cluster the font draws, in a build with the bidi feature** (ADR-1200 D22 step 3). The font set may have no glyph for some marks of a cluster. For example, no shipped font draws the superscript alef over lam with shadda and fatha. The helper then sends the cluster without those marks, under its own key. The console takes that part, though the ask named only the whole cluster. A console in such a build asks with the request kind that takes parts. The minspec build asks with the plain kind, and gets no part. It draws the cluster from its base and marks as before, so it carries none of this. The lookup draws that part as the font shapes it, and lays the missing marks over it, from the store or from the built-in font. Tests: `the_part_of_a_cluster_the_font_draws_is_taken`, `a_joined_letter_draws_the_part_of_it_the_store_holds`.
- **Joined letters, in a build with the bidi feature** (ADR-1004 D6). The console asks the helper for three things. It asks for each letter of a joining script, keyed with U+200D on each side that the letter joins. It asks for lam followed by alef, as their ligature. It asks for the Arabic presentation form that each of those draws where no font holds the joined form. The console reads what each display shows through `deferred::read_shown`. Tier 2 and the specimens read through that function too.

  The lookup tries the key first. Where the store does not hold the key, a letter draws the presentation form of its joined form. It takes that form from the store where the frit holds that codepoint. Otherwise it takes the form from the built-in font, but only while the store holds nothing for the letter. So a letter that the frit draws never takes a joined form from another font. Otherwise the letter draws its own glyph, unjoined. Lam-alef draws its ligature's presentation form the same way. Otherwise it draws lam's joined form in the right cell, and alef's final form in the left.

  `gen-lookup` generates the presentation-form tables from UnicodeData.txt. In such a build, the built-in font draws through the same lookup, with a store that stays empty. So GNU Unifont joins Arabic by its presentation forms. The arrival of a presentation form's glyph redraws the cells that show the letters it presents. Tests: `a_row_of_arabic_asks_for_its_joined_forms`, `the_built_in_font_draws_a_joined_letter_by_its_presentation_form`, `a_joined_letter_draws_from_the_store_before_any_presentation_form`, `lam_and_alef_draw_their_ligature_or_their_two_forms`, `an_arrived_presentation_form_redraws_its_letters`.
- **A cluster drawn from its parts** (ADR-1302 D14). The base's glyph takes each nonspacing mark's glyph over it. A spacing mark (General_Category Mc), such as a Devanagari vowel sign, stands beside its letter instead. It stands after the letter. It stands before the letter where its Indic_Positional_Category is Left, Top_And_Left, Bottom_And_Left or Top_And_Bottom_And_Left. A two-part vowel sign is drawn as its canonical parts. Where a letter and its spacing marks need more room than the letter's cells, they scale sideways together to fill them. A mark that the font already draws in place keeps the font's placement. For example, GNU Unifont draws every Devanagari, Bengali, Tamil and Malayalam vowel sign beside its letter, in a box as wide as the letter's. GNU Unifont also draws Myanmar's medial ra as a bracket round its consonant. Tests: `a_spacing_mark_stands_after_its_letter`, `a_pre_base_spacing_mark_stands_before_its_letter`, `a_letter_and_spacing_marks_wider_than_the_cells_scale_to_fit`, `a_spacing_mark_the_font_draws_beside_its_letter_stays_there`, `a_pre_base_mark_drawn_after_its_letter_moves_before_it`, `a_mark_drawn_before_its_letter_moves_after_it`, `a_spacing_mark_the_font_draws_round_its_letter_stays_there`, `a_mark_in_a_box_wider_than_its_letters_stands_beside_it`.
- **A frit's glyphs arrive while the console runs, and their arrival damages only the cells that show them** (#145, #149, the operator's decision, 2026-10-28). Damage is the set of cells that the next frame must draw again. Arrival is a damage source on the same path as program output. The answers that land between frames merge into one set per cell, and the next frame draws that set once. The cells drawn are read from the view that each buffer shows, scrollback and clusters included. A fill of characters that no buffer shows draws no frame. An eviction at the store's limit damages nothing. A character that the frit lacks draws in the built-in font, before the replacement glyph (vtium/vtium#141, ADR-1200 D7 and D22). The built-in font is unifont from 16 pixels, and Unscii-8 under 16. Test: `a_character_the_frit_lacks_draws_in_the_built_in_font`.

## Bounds

A configuration file is untrusted input. The bounds of each key's value are in `docs/config.md`.

| Bound | Value | Past it |
|---|---|---|
| `FILE_MAX` | 65,536 bytes of a file | The rest is not read, and the file is reported |
| `LINE_MAX` | 8,192 bytes of a line | The line is ignored and reported |
| `TEXT_MAX` | 4,095 bytes of a text value or a `login` command, `PATH_MAX` less its NUL | The value is ignored and reported |
| `REPORTS_MAX` | 64 reports | The rest are counted in one report |
| A head's render thread | a stack of 128 KiB, or 8 MiB when `hwaccel` asks for the GPU path, 16 frames each way, a frame on its way per display | A frame the full queue refuses goes back to its display, which draws at the next turn; the thread waits while the loop has not taken what it composed |
| `LET_GO_MS` | 3,000 ms the drop of a head waits for a render thread that `hwaccel` gave a GPU to end, and a reload of vtium.conf or the exit for every head's together: its frame's fence wait, at most `GPU_FENCE_WAIT_MS` (vtium-platform's bounds), and the driver destroying the head's GL context (ADR-1303 D9) | The thread is left to end alone, and the log says the GPU driver did not let go; an exit while it still runs skips the exit handlers |
| `head-consoles-max` | 4 consoles a head by default, 1 to 50 | A head's `consoles` past it opens this many, with a warning |
| `consoles-max` | 8 consoles every head together by default, 1 to 50 | Each head keeps its first; the others past it, in the file's order, do not open, with a warning |
| `HEADS_MAX` | 16 heads vtium.conf declares (vtium-settings's bounds) | The file is invalid, and the shipped rules run |
| A console's scrollback | `sb-memory`, at most a quarter of the machine's memory divided by `consoles-max` or by the heads, whichever is more | Its oldest lines go, as past `sb-memory` |
| `REPLY_TIMEOUT` | 2,000 ms a request to the image helper is out, in a build with images (ADR-1100 D7) | The request fails, the helper is stopped with no crash counted, and the console's pty resumes |
| `ANIMATION_FLOOR_MS` | 10 ms between two firings of the animation clock's timer, in a build with images (ADR-1102 D3) | A frame whose gap is shorter shows at the next firing, or is passed over when its time has gone |
| A frit's glyph store | the machine's store limit (16 MiB below 2 GiB, 64 MiB from 2 GiB, 128 MiB from 4 GiB) divided by the heads | A fill stops at it, as at the store's limit |
| The helper client's record of a cell in one style | four bitsets of every codepoint, held, lacked, asked for and brought by the fill, 136 KiB each, made only when a bit is first set; a style other than regular never fills, so at most 544 KiB for the regular record and 408 KiB for each other style's, 1.73 MiB for a cell the screen shows in all four styles (`helper.rs`, `Bits`) | Nothing past it: one record a cell and style the displays draw at, dropped with its cell |

## Limitations

A vtium not running as root refuses every image request while the session's program holds its terminal exclusive with TIOCEXCL. The exception is a session whose user logind names. The kernel refuses to reopen an exclusive pty's slave for an unprivileged process. So vtium cannot read the pty's owner.

## Not yet built

Some keys that a `kmscon` configuration file may hold are not in the key table yet. vtium reports each of them as a key it does not know:

- `multi-monitor`. Its values `clone` and `largest` wait for their own change. vtium lays several displays out as `scaled`, the operator's choice on vtium/vtium#21.
- `screen`.
- `kmscon`'s grab keys other than `grab-reboot`. vtium reads `grab-reboot` as `key-reboot`. See "Key bindings" above.

vtium takes `font-hinting`, checks its value, and warns when it is set. But nothing reads it yet. The font helper hints as the frit says.

## Left to tier 3

Each needs a real VT or display, which the boot tests stand in for:

- The panic hook under `panic=abort` on a real VT: the VT back in text mode with its keyboard before the message prints.
- The 100 ms the loop is served at exit for SIGUSR2 on a real switch back.
- A release a real flip in flight delays, acknowledged once the device reports asleep.
- A card that udev raises during `display-wait`.
- The getty fallback starting when no display comes under an open policy, and the fallback skipping the getty after a failure under a closed policy.
- Whether fbdev stays lit when a re-take while blanked defers its set-up to the input that ends the blank. On drm2d, the displays stay dark.
- What each power key asks of the machine. Tier 3's power variants press each power key on the console. They see the guest reboot both ways, power off with its services stopped and its filesystems unmounted, and suspend and resume.
