# vtium

The binary: the configuration and command line, the terminfo entry and the XTGETTCAP table generated from it, the session's command and environment, the respawn policy, the rules the terminal follows, and the seat and its heads wired to them through vtium-platform's loop. The rules are functions of what they are given, time included, so their tests need no VT, display or pty. The seat takes the time from the loop too: `tests/boot.rs` boots it with the fake VT, a video device in memory and a real child on a real pty.

## Setting it up

The vtium package (ADR-1500) installs `/usr/bin/vtium`, its glyph helper and the unit `vtium@.service`, and enables nothing. A build with images also installs the image helper, `/usr/bin/vtium-image`, and the sysusers file `vtium-image.conf`, from which `systemd-sysusers` creates the account the helper runs as at the login prompt (ADR-1101 D2). `vtium console` gives vtium a VT, or every VT, and takes them back (ADR-1500 D7). `enable` and `disable` need root, and as any other user they change nothing and say so; `status` runs as any user:

```sh
vtium console status                      # per VT: what systemd starts at boot, what logind starts when you switch to it, what runs now
sudo vtium console enable 3               # VT 3 is vtium's from its next start, and its getty is disabled
sudo systemctl start vtium@tty3.service   # start vtium on VT 3 now, which ends every session there
sudo vtium console disable 3              # VT 3 goes back to what it had from its next start
sudo vtium console enable --all           # every VT is vtium's, on a machine whose autovt@.service link does not name kmscon
sudo vtium console disable --all          # every VT goes back as vtium console found it
```

`enable --all` links `autovt@.service`, the unit logind starts on a VT when you switch to it and nothing runs there, to vtium, enables vtium at boot on VT 1, where logind never starts a console itself, and disables the gettys on VTs 2 to 6, so vtium starts on each the first time you switch to it. VT 6 is logind's reserved VT, where logind starts a console at every switch, even while the VT is in use, so `enable --all` and `enable 6` refuse while someone is logged in on VT 6 anywhere but inside a vtium running there, and `enable --all` also refuses while kmscon, the development install or a masked `vtium@tty6` is there without a link of VT 6's own, and says what to free first. A getty waiting at its login prompt on VT 6 holds no session: both verbs go ahead, and the next switch to VT 6 stops that getty, which ends nothing.

vtium console follows common convention: while a display manager is enabled, VT 1 stays the display manager's and its getty's, whatever VT the display manager uses now, and vtium takes other VTs. It never takes a VT that the system's intended configuration gives to another program: a unit enabled at boot that claims it, or an enabled display manager (linked as `display-manager.service`, or a display manager vtium knows by name enabled at boot), VT 1 and any VT its configuration names. What runs now adds to that and never frees a VT. A VT is held now when a graphical session or greeter is on it, which vtium asks logind for with `loginctl`, or when another console runs there as a unit named `PREFIX@ttyN.service`. A VT is held from the next boot when a unit that starts at boot names its getty in `Conflicts=`, as Arch's sddm.service names `getty@tty1.service`, or runs on it: an instance such as `cage@tty3.service`, or a unit with `TTYPath=/dev/tty3`. The display manager's own configuration adds the VT its greeter starts on: LightDM's `minimum-vt` (7 by default), greetd's `vt` or `--vt`, and SDDM's `MinimumVT`. Nothing frees a VT, neither a configuration file nor a greeter running on another VT. `enable N` refuses a held VT and says which signal it read, `enable --all` passes it by and says so, and `status` marks it and gives the reason under its table.

When vtium fails on a VT, its unit's fallback, `vtium-getty@.service`, runs `vtium console fallback ttyN`, which starts the VT's getty so that you have a login again. It starts nothing when the getty's start would stop another program: a unit that runs, waits to start or is enabled, and that conflicts with the getty, as a display manager conflicts with `getty@tty1`. Then the VT is left without a console, and the journal of `vtium-getty@ttyN` says why. It also starts nothing when it cannot ask systemd. Under a closed head-file policy the fallback skips itself (ADR-1401 D9).

Neither verb starts or stops vtium. Each prints the `systemctl start` or `stop` that does, and that command ends every session on the VT. Before `enable` changes a VT or moves `autovt@.service`, it records what was there in `/var/lib/vtium/console/`, the unit file each getty linked to included, and `disable` puts back exactly that. `vtium console` refuses a VT that the C reference's console holds. On a host that was not booted with systemd it changes nothing and says so, and there an inittab line or an init script runs `vtium --vt=ttyN --no-switchvt` on the VT ([docs/systemd.md](../../docs/systemd.md)).

### Sharing VTs with kmscon

kmscon, the C reference's console, and vtium can run on one machine, each on VTs of its own. When you switch to a VT that no console runs on, logind starts the unit `autovt@ttyN.service` there, N being the VT's number. systemd looks first for a link of that exact name, `/etc/systemd/system/autovt@ttyN.service`, which gives one VT a console of its own. Every VT without one falls back to the single template link, `/etc/systemd/system/autovt@.service`, so whichever console that link names gets all of those VTs. `sudo vtium console enable --all` points it at vtium. On Arch it points at the getty from the start, because systemd's package enables `getty@.service` when it installs; kmscon's own `sudo systemctl enable kmsconvt@` then fails on that link (it still enables kmscon at boot on VT 1), and only `systemctl enable --force kmsconvt@.service` points the link at kmscon. `vtium console status` says on its first line which console the link names.

**vtium holds the template link, and you want kmscon on one VT.** Give that VT a link of its own to kmscon. For VT 3:

```sh
sudo systemctl disable getty@tty3.service    # only where VT 3's getty is enabled at boot
sudo ln -s /usr/lib/systemd/system/kmsconvt@.service /etc/systemd/system/autovt@tty3.service
sudo systemctl daemon-reload
```

Nothing starts kmscon at boot or at once. logind starts it the next time you switch to VT 3 while no console runs there. `vtium console` sees the link and leaves VT 3 to kmscon: `enable 3` refuses it, `enable --all` names it and passes it by, and `disable` never touches it. The way back:

```sh
sudo systemctl stop kmsconvt@tty3.service    # ends every session on VT 3
sudo rm /etc/systemd/system/autovt@tty3.service
sudo systemctl daemon-reload
sudo systemctl add-wants getty.target getty@tty3.service    # only if you disabled VT 3's getty above
```

Use `add-wants` rather than `systemctl enable getty@tty3.service` there. `enable` also links `autovt@tty3.service` to the getty, and `vtium console enable 3` then refuses VT 3 until that link is gone.

`sudo systemctl enable --now kmsconvt@tty3.service`, run after the same `systemctl disable getty@tty3.service`, makes the same link and also starts kmscon on VT 3 at boot and at once. Without the getty's disable, systemd would start both kmscon and the getty on VT 3 at boot, and the two conflict. The way back:

```sh
sudo systemctl disable --now kmsconvt@tty3.service    # stops kmscon, which ends every session on VT 3, and takes it off boot
sudo rm /etc/systemd/system/autovt@tty3.service      # the link that disable leaves
sudo systemctl daemon-reload
sudo systemctl add-wants getty.target getty@tty3.service    # only if you disabled VT 3's getty
```

The guide prefers the hand-made link because two consoles started at boot both open the display card, and the second cannot draw while the first holds it. Do not run kmscon's own `systemctl enable kmsconvt@` while vtium holds the template link either. It fails on that link, and it still enables kmscon at boot on VT 1, beside vtium there.

**`/etc/systemd/system/autovt@.service` links to `kmsconvt@.service`**, as on a machine set up to run kmscon on every VT. `sudo vtium console enable N` gives vtium one VT at a time, and `sudo vtium console enable --all` refuses until kmscon lets go of the template.

**Moving from kmscon to vtium entirely:**

```sh
sudo systemctl disable kmsconvt@.service      # removes the template link and every VT's kmscon link
systemctl list-units 'kmsconvt@*'             # the VTs where kmscon still runs
sudo systemctl stop kmsconvt@tty2.service     # for each VT listed; ends every session there
sudo vtium console enable --all               # every VT is vtium's from its next start; it prints the command that starts vtium on VT 1 now
sudo pacman -R kmscon                         # if you want: removes kmscon itself
```

`systemctl disable` stops nothing, and logging out of a VT leaves its kmscon running. `vtium console enable --all` passes by every VT where kmscon still runs, names each one, and leaves its getty as it is, so that VT keeps its getty after a reboot. Stop kmscon there first, as above, or run `sudo vtium console enable N` for that VT once kmscon has stopped.

`pacman -R kmscon` leaves the `kmscon-terminfo` package, which holds the terminfo entry named `kmscon`. vtium sets `TERM=xterm-vtium`, whose entry the `vtium-terminfo` package installs, so vtium itself needs no `kmscon` entry. Keep `kmscon-terminfo` while anything still uses `TERM=kmscon`: a vtium run with `--term=kmscon` or `term=kmscon` in its configuration, `make vt-login` on a machine without the `xterm-vtium` entry, which then runs vtium with `--term=kmscon`, and an ssh login to this machine from a kmscon console elsewhere, which arrives with `TERM=kmscon`. Once nothing does, you may remove it with `sudo pacman -R kmscon-terminfo`.

### ssh from vtium

vtium sets `TERM=xterm-vtium` in its session, or `TERM=kmscon` when it runs with `--term=kmscon`. ssh passes `TERM` on to the remote host, and most hosts have no terminfo entry by either name, so the programs there cannot look up how to drive the terminal, and the remote shell misbehaves: zsh, for one, echoes every keystroke.

The fix the maintainer uses is to wrap ssh in the shell's rc file on the machine that runs vtium, so that a plain `ssh` from vtium presents the remote host with `xterm-256color`, an entry nearly every host has. In `~/.zshrc`:

```zsh
if [[ $TERM == (xterm-vtium|kmscon) ]]; then
  ssh() { TERM=xterm-256color command ssh "$@" }
fi
```

In `~/.bashrc`:

```bash
case $TERM in
xterm-vtium | kmscon) ssh() { TERM=xterm-256color command ssh "$@"; } ;;
esac
```

Remote programs then use only what `xterm-256color` describes, and none of vtium's own capabilities that the entry lacks. On a host you own you can install vtium's entry instead, from a machine that has it (the `vtium-terminfo` package installs it):

```sh
infocmp -x xterm-vtium | ssh host tic -x -
```

`tic` run as a user other than root compiles the entry into that user's `~/.terminfo` on the host. With the wrapper in place, `command ssh host` skips it, so that host gets `xterm-vtium`.

## Heads

The seat runs what `/etc/vtium/heads.conf` resolves to at the three levels of ADR-1401 D7, and never writes the file. With no file it runs the compiled-in configuration's one `console` head, silently. A file that root does not own, that its group or others can write, or that cannot be read as a file is never read: the shipped rules run, and every head shows `invalid config skipped, using builtin`. A trusted file runs under its policy, each error logged with its line and dropping what it takes: a valid file runs as written; a partly broken one runs what survives, with `config partly invalid, running what's valid` on every head; and a broken one runs the shipped rules with `invalid config skipped, using builtin` under open, and nothing under closed, where the boot display shows `vtium: config invalid, policy closed: input off` and no input is delivered. Each console line is followed by its next step from vtium-settings's catalog, such as `Run vtium check-config /etc/vtium/heads.conf to see why.` A head is a terminal of its own: its session's pty, screen and scrollback, its grid, laid out over its displays by the scaled rule (see "The font"), its density, zoom and rotation, and its font, `font-name` and `font-size` from vtium.conf with the head's profile over them; a profile other than `default` names the frit of its name until profiles have files. Each display walks the rules alone when it comes and joins the head the first match names; a display a rule sends `off`, or that no rule claims, is set off and logged, the latter with the rule that would give it the first head ready to paste. A DRM card sets such a display off before it announces it, a frame another master left included; a framebuffer's is set off after each wake-up and unblank. A head whose displays never appear starts no session, under `display-wait=forever` too. Each input device walks the rules alone when it comes: one a rule sends to a head delivers to that head alone, and one sent to `roaming`, or that no rule claims under the open policy, delivers to the active head; under the closed policy one that no rule claims is ignored. One sent to `ignore` is never opened, but under the open policy a keyboard, opened for the rescue key alone. Under vtium.conf's `mouse` off, the shipped rules send each pointer class to `ignore`, their tail that a partly broken open file's inputs walk included, so no pointer opens, one whose node also has udev's key class included. The active head starts on the head of the boot display, the connector lit at start, else the first connected one on the boot card, then the other cards, in the kernel's order, else the first head in the file with a display, and starts again as each display lights until the first key reaching a head or the first roaming chord, over every display lit since the start, one that left included, so a boot display lighting a turn late takes it and a display leaving never moves it; after, only the roaming chord and the anti-lockout guard move it: Ctrl-Super-Up to the next lit head that is not isolated, Ctrl-Super-Down to the previous, matched after the power keys and before the terminal's grabs, once a press. Only a roaming keyboard takes the roaming chord; pressed on a keyboard a rule sends to a head, it moves nothing and reaches that head's session as a key. The VT's keys switch the VT only from a keyboard that asks a head that is not isolated, its rule's head or, for a roaming keyboard, the active head; from an isolated head's keyboard they reach its session as keys, and from a roaming keyboard while no head is active they do nothing. Under the closed policy an event from a device the seat has no route for, as one queued before its device went, delivers nothing; under open it roams. A pointer moves within the grid of the head it delivers to, with the modifiers of the keyboards delivering there. The terminal of each head a keyboard delivers to has mode 1004's focus, so several hold it at once. The blank, the selection buffer and the power keys are the seat's. Each head holds consoles, a session each, one shown on every display of the head: it starts the head file's `consoles` as its first display lights, at most `head-consoles-max`, 4 by default, and every head together at most `consoles-max`, 8 by default, each head keeping its first and the others opening in the file's order, so the share does not depend on which display comes first. Ctrl-Super-Right and Ctrl-Super-Left show the next and the previous console of the head the keyboard delivers to, wrapping. Under the closed policy a head keeps the consoles it started with for as long as it runs: vtium takes Ctrl-Super-Return and Ctrl-Super-Backspace and does nothing with them, so neither reaches a session. Under the open policy Ctrl-Super-Return opens a console just after the one the head shows, starts the head's login in it on the grid the layout gives it, and shows it. Where the head has `head-consoles-max` consoles, or every head together has `consoles-max`, nothing opens: vtium logs a line naming the cap and shows a brief line at the top of the head, such as `No more consoles: desk has 4, its most.`, for `osd-timeout`, or 3 s under `never`, in place of the on-screen display's full line, and under `osd = off` only the log line. The new console's session starts while the console is still hidden, and the head shows it once the session runs. A session the chord cannot start leaves the run alive: vtium logs a line, the console leaves without being shown, so the console shown before is told nothing, its id stays given, and the brief line reads `No console opened: its login could not start.` A session that cannot start at a head's start, or when a console's program starts again, ends vtium with status 1, so the unit's getty fallback takes the VT (see "Departures"). Ctrl-Super-Backspace closes the console the head shows: its pty closes, so its programs get SIGHUP, and the head shows the console after it, or the first when it was the last; the closing console gets no focus-out and the console shown next gains the focus. On a head's last console it does nothing. Neither chord reaches a session, and from a roaming keyboard with no active head neither does anything. Each console keeps its own grid and zoom, and the head draws whole when the shown console changes. The font and the displays are the head's, so a hidden console's OSC 50 and blank sequences wait until it is shown, and its output after an OSC 50 waits with them; each console's OSC 52 selection is taken at once. A head's consoles run its head file's `login`, else vtium.conf's. Each console's session has `VTIUM_HEAD`, its head's name, and `VTIUM_CONSOLE`, the console's id, in its environment; a head gives its consoles ids from 1 as it opens them at its start, a console the chord opens takes the next id the head has not given, so no id is given twice in a run, and a console keeps its id when its session starts again. A console whose program exits keeps its place and follows the respawn policy, each console counting its own quick exits: under respawn its login comes back in the same console, from a hard reset, and no other console is touched; under `oneshot` the console ends and shows the notice that its session ended, the head ends once every one of its consoles has, and vtium exits with status 0 once every head has ended, a head whose display never lit counting as ended, since it has nothing to run. Quick exits past the limit, on any console of any head, end the run (ADR-1401 D1): every head's sessions hang up, and the log names the head. Under the open policy vtium then exits with status 1, so the unit's getty takes the VT, with no notice drawn. Under the closed policy it holds its VT, since a getty's login would take any keyboard: every head's display goes dark, no session starts again, no input is delivered, and the boot display shows that a session kept ending as soon as it started, for as long as vtium runs. Heads drawing one frit share its helper and its store, and a head drawing another frit has its own. The memory of every console and frit together is bounded (ADR-1401 D10; "Bounds"): each console's scrollback takes `sb-memory`, at most the most `sb-memory` may be on the machine, a quarter of its memory, divided by `consoles-max`, or by the heads when the head file declares more, since each head keeps its first console, so every console's together stay within that quarter; on a 512 MiB machine that is 128 MiB, 16 MiB a console for `consoles-max`'s 8, and 2,684,354 bytes each for 50 consoles. Left unset, `sb-memory` follows each console's grid inside that share: on minspec's grids it is what the 16 MiB minspec peak leaves after the console's two screens at their worst, 5,242,880 bytes at 170 by 48 and more on a smaller display, and a larger display keeps 5,242,880 bytes, worked out again whenever the console's grid changes; a user who wants a deeper scrollback sets `sb-memory`, up to the share (ADR-1001, "Memory"). Each frit's glyph store takes the machine's store limit, 16 MiB below 2 GiB, divided by the heads, since a head draws one frit at a time, so every frit's store together stays within that limit: 16 MiB with one head, 1 MiB each with 16.

vtium draws its own over a head's frames, outside the terminal's cells, so no pty, scrollback or reply sees it (ADR-1401 D5, D7), with vtium-render's `Notice` and `Mark` in the head's font. A notice is a box of vtium's lines across the top of each of the head's displays: the start's console line for a head file it skipped or partly ran on every head, naming no error, since the log holds the errors, no keyboard found by the start's scan on every head, the anti-lockout guard's on the active head, the rescue key's on the active head or, with no active head, on every head, and a console's notice that its session ended for good under `oneshot`, shown while that console is. Each says in plain words what happened. A head shows each notice once and the newest four (`NOTICES_MAX`), a repeat changing nothing. A notice ends on any key reaching its head, or 30 s after it is first drawn, but an ended console's, which stays and keeps no time; the frame beneath is drawn whole once it goes. The on-screen display, the OSD (`src/osd.rs`, ADR-1401 D5, vtium/vtium#169), draws each head's status in the box across the top of each of its displays and in its top-right cell. Under `osd = minimal`, the default, it is a `Mark` in the head's top-right cell, filled on the active head and hollow on the others, shown on every head with a lit display when the roaming chord or the anti-lockout guard moves the active head, and never in normal use. A head that loses its last display drops what it showed, and a head starting its sessions shows nothing. Under `osd = full` it is a line at the top of the box, such as `● desk · console 2 of 3`, shown on every lit head at those moves and on one head when it shows another console or its display returns after it had none. The box is drawn in the notice's colors while a notice is in it, and in the on-screen display's colors while the line is alone, and the dot is drawn in the on-screen display's colors. vtium.conf's `notice-foreground`, `notice-background` and `notice-border` set the notice's colors, and its `osd-foreground`, `osd-background` and `osd-border` set the on-screen display's; unset, they are vtium-render's `Colors::NOTICE`, dark on pale red, and `Colors::STATUS`, light on dark. Under `off` nothing of the status is drawn, and every notice still shows. The OSD stays for `osd-timeout`, 3 s by default, or always under `never`. `focus-mark` is read as the older name of the two keys, where they are unset, with a line in the log naming them.

The guards run after every display and input added or removed, and after a rescue (ADR-1401 D9), the anti-lockout guard and the rescue key on under the open policy and off under the closed one, and the display guard always on. Under open the display guard lights the boot display in the first head while the rules light no display, a `console` head where the file declares none, and lets it go dark once the rules light another. Under closed it lights the boot display for a notice alone, on a screen with no session that no input reaches, which stays until a head lights: `vtium: no display for any head`, or the start's console line; a closed file with no heads stays dark; a DRM card announces a display the rules leave dark while vtium has none lit, so the guard can light it, and one the card set off at its bind while another was lit, never announced, the guard lets go for the card to scan again and announce once that one goes. A display the guard lit goes dark again by its power state. The anti-lockout guard, with a keyboard-class device present, makes every keyboard roam, opening an ignored one to deliver, while no keyboard reaches a head with a lit display, and makes the boot display's head the active head when lit, else the first lit head, with a notice and the on-screen display; each keyboard goes back to its rule once one reaches a lit head. `Ctrl-Alt-F<n>` for vtium's own VT, pressed on any keyboard, the ignored ones included, makes that keyboard roam for the rest of the boot, through an unplug for the newest 16 devices (`RESCUED_MAX`), with a notice naming the head the keyboard then types into, on that head, or saying that no head is active, on every head, under the open policy, unless the head its rule names is isolated; nothing is written. A keyboard the rescue key moved reaches a lit head while the active head is lit.

Each head composes its frames on a render thread of its own (ADR-1401 D2), so one head's redraw delays neither another head's frames nor the loop, which keeps the input, the ptys, the hotplug, the VT's switches and the devices: their buffers, cursor planes, blanking and flips. A frame is the head's screen, taken by the loop with the buffer token its display lends (vtium-platform's frame contract). The thread composes the frame straight into the token's buffer, writing only, drawing the cells that buffer lacks at its age, and the loop gives the token back with the frame's damage, so the display presents the buffer the frame was drawn into. No view keeps a copy of its display's frame, and nothing copies a frame between buffers: a display at 1920x1080 holds no 8,294,400-byte copy beside its own buffers. When vtium's notice box or the on-screen display changes, the renderer draws again the cells and the border under what it covered, so no buffer keeps it whatever its age, and a view whose display lost its picture draws its next frame whole. A display has one frame on its way at a time; a draw asked for meanwhile is taken from the screen as it is when the frame comes back, so no frame queues behind another. A frame that comes back once the VT is released or the displays blanked is dropped by its display, which draws whole at the next acquire, and a job the thread cannot take gives its token back unused. Its thread starts at its first frame. The thread's stack is 128 KiB, and it is joined when its head is dropped, at a new head file and at the exit. At debug level, under the `render` target, each head logs once a second while it draws its frames the time each took to compose, mean and largest.

A DRM display keeps `video::BUILD_BUFFERS` buffers (ADR-1401 D2): three in a build that adds features on top of minspec, which today means `images` or `logind`, and two in the minspec build. One buffer is for a build smaller than minspec, which none is yet. vtium.conf's `display-buffers`, 1, 2 or 3, sets the count in place of the build's, and the seat passes it to each card it opens; a framebuffer keeps one buffer whatever it says.

## The blank

After `dpms-timeout` with no activity every display powers down, and the next activity powers it up. Activity is the user's input: a key press, a pointer's move, a button or the wheel, and the wake-up after the user switches back to vtium's VT. A key release, a key with no keysym, a press partway through a compose sequence (a dead key's among them), the end of a pointer frame and the pointer's hide neither wake the displays nor restart the countdown, as the C reference decided (`src/input/input_uxkb.c:431-545`, `src/input/input_pointer.c:67`, `src/seat.c:578-590`). A change in which displays are attached counts too, for now: the last display going ends a blank in force and resets the idle clock, and the blank does not run while none is attached; the first display, and each that comes after none, starts the countdown afresh. A display coming or going among others does not count, nor does a re-take: a re-take sets the displays up again and keeps the blank and its timer as they were, and while blanked its set-up waits for the input that ends the blank (the operator's decision on vtium/vtium#21). While the VT is another's, as a released fake VT is, the countdown blanks no display and the user's input is no activity, since the displays are the other session's; the acquire starts the countdown afresh and ends a blank in force. The C reference's DPMS timer blanked nothing while its seat was not in the foreground and reset when a display became active (`src/seat.c:520`, `src/seat.c:196-202`). The idle lock (vtium/vtium#87) will count the user's input alone.

A program commands the blank with the Linux console's sequences while `program-blank` is on, as it is by default (the operator's decisions on vtium/vtium#79). `CSI 9 ; n ]` sets the timeout to n minutes, at most 60, and 0 turns the blank off; it also wakes the displays, as on the Linux console. `CSI 13 ]` wakes them as a key does. The program's timeout lasts until a program changes it, and RIS returns it to `dpms-timeout`; a change restarts the countdown and leaves a blank in force. Output alone never wakes the displays, so a clock redrawing every second does not keep them lit. `setterm --blank N` writes `CSI 9` only under `TERM=linux`; under vtium's own `TERM` it refuses. A program cannot blank the displays at once: the Linux console's only way, the `TIOCLINUX` ioctl, has no counterpart on a pty.

From outside the session, `SIGRTMIN+1` blanks every display at once and `SIGRTMIN+2` wakes them as a key does, so a script or a power daemon acts without writing to the session's terminal (the operator's decisions on vtium/vtium#79). The blank is the timer's, and input, a program's `CSI 13 ]` or `SIGRTMIN+2` ends it; while the VT is another's, a blank sent is dropped, since its displays are not vtium's to blank. Neither `dpms-timeout=0` nor `no-program-blank` holds the signals back. `vtium blank --vt N` and `vtium wake --vt N` find the vtium on VT N, the process named `vtium` holding VT N's device (major 4, minor N) on a descriptor past its stdin, stdout and stderr, which may be the VT it was started from; they hold it by its pidfd, look again that it is still that vtium, and send it the signal through the pidfd, so a process that took its pid in between is never signalled; they exit 1 when none is found or the signal fails, and 2 for an argument they cannot take. Under systemd, `systemctl kill --kill-whom=main -s SIGRTMIN+1 vtium@ttyN` sends it too; without `--kill-whom=main` the signal also reaches the login session, whose programs a real-time signal ends by default. Reading a process's descriptors and signalling it take the same right, so root and the user vtium runs as may send these, and a program on the terminal running as another user may not; a vtium started as root takes them from root alone. vtium's other signals are SIGTERM, SIGINT and SIGPIPE, and SIGUSR1 and SIGUSR2 for the VT's switches; the `SIGRTMIN+4` it sends PID 1 for `grab-power-off` is systemd's, never one vtium takes. The C reference had no blank from outside and used no real-time signal.

## No display

At start vtium waits `display-wait` (10 s by default) for a frame on a display's screen, counted from when its VT is shown, and with none by then it exits with status 1, so the unit's getty fallback takes the VT. The wait runs only while the VT is vtium's. When another program takes the VT before vtium's first frame is on screen, as X starting on another VT does at boot (#270), vtium waits for the VT to come back, as it does for a switch away later in its run. When the VT comes back, the wait starts again from the full `display-wait`. Under a closed policy it never gives up: it holds its VT and waits however long it takes, as under `forever` (ADR-1401 D8). A device whose displays are never set up, as when the modeset fails, counts as none, as does a display announced whose every frame fails to show. `display-wait=0` exits at once without one; `forever` waits for the first display however long it takes, for a machine whose only display is a USB adapter (DisplayLink, `udl`) plugged in at any time after boot. A frame reaches the screen at its flip, which the turn after its draw reads at the earliest, so the wait runs out at the end of a turn after its due time, and while a frame is on its way to a screen it waits up to 1 s more for the flip, the C reference's wait for a page flip (`src/video/drm_shared.c:834-860`); under `display-wait=0` a display set up when the VT is shown is drawn, and its flip read, before the wait decides.

A head's command starts once one of its displays is set up, on the grid of every display of the head set up by then, so it sees no SIGWINCH as it starts. While the wait runs with none, the command waits, and if vtium exits it never starts. Under `forever` with none, it waits for the head's first display however long that takes.

Once a display has come, vtium never exits for want of one. When a head's last goes, it logs it and does what the head file's `when-display-lost` says for that head (ADR-1401 D8); a mirrored head keeps its sessions while one of its displays remains. Under `keep`, the default, every head's and the compiled-in `console` head's, the head's sessions run on: the grid keeps the last display's size, so the program sees no SIGWINCH; the keys of the devices reaching the head still type into it, as the kernel console's tty takes them through an unplugged monitor; and the blank does not run (see "The blank"). Under `hangup` the head's sessions are hung up at once, as a serial line losing its carrier: every console's pty closes, its programs get SIGHUP, and each console follows the respawn policy, its session starting again in the same console, with its id, under respawn and ending under `oneshot`; a hang-up is vtium's, so it counts as no quick exit, and an exit read in its turn is the hung-up session's. Under `hangup DURATION`, such as `hangup 30s`, they are hung up the same way once the time runs out with no display back, each head keeping its own timer, which wakes the loop. A head comes back only on a display its rules match, logged and drawn whole, and the grid takes its size where that differs, one SIGWINCH (the operator's decisions on vtium/vtium#21). A head whose display never lit receives no key, even from a keyboard its rule claims; and the active head never moves because a head's display left or came back, but by the anti-lockout guard (see "Heads").

## Selection, copy and paste

The pointer drives vtium-term's selection, and the seat keeps one selection buffer: what the user copied last, or what a program set last with OSC 52 while `clipboard-write` is on. The console has no system clipboard. The middle button and the keys `grab-paste` binds, Shift+Insert by default, paste the buffer through vtium-term's `Terminal::paste`, filtered, and bracketed while the program asks with mode 2004. The buffer holds at most the text of the scrollback and the screen, or vtium-term's `CLIPBOARD_MAX` bytes from one OSC 52.

The pointer also drives OSC 8 links and OSC 133 prompt marks, as ADR-1002 decides. vtium tells the shown console's screen which cell the pointer is over and whether Ctrl is held, at each pointer event and each key press, so the frame names the link under the pointer and, while Ctrl is held, carries its URI for the overlay row. Letting go of Ctrl sends no key, so vtium also reads which modifiers a head's own keyboards hold, the keyboards that deliver to it, whenever a keyboard's modifiers change, a keyboard goes, the focus moves, the anti-lockout guard moves a keyboard or the VT comes back, when the keyboards start afresh: letting go of Ctrl or unplugging the keyboard that holds it ends the overlay. The overlay is the focus's. The head that loses the focus shows none unless one of its own keyboards holds Ctrl, though it still underlines the link under its pointer and still draws its pointer, and the head that takes it shows the overlay of the link under its own pointer at once while the keyboard that follows the focus holds Ctrl. A pointer that hides, or that is in the strip a display leaves past the grid, is over no cell, so it hovers no link; a click in that strip still selects at the grid's nearest cell. The pointer is over the shown console alone: a console chord leaves the console it hides hovering nothing, and the console it shows hovers the link under the pointer at once, with the Ctrl the chord holds. Ctrl+click on a link copies its URI into the selection buffer and clears the selection; nothing is opened and nothing reaches the program until the user pastes. Ctrl+right-click on a line of a command's output selects that output as whole lines and copies it. While a program tracks the pointer, both take Shift as well, as selection does. On the main screen Ctrl+Shift+Up moves the view to the nearest marked prompt above its top row and Ctrl+Shift+Down to the nearest below, or back to the live screen; on the alternate screen both keys reach the program.

## Pictures

The `images` feature (ADR-1100 D10) builds vtium-term with its image store and router, vtium-render with the compositor's pictures, and vtium-image with the sixel and kitty graphics handlers. The minspec build, which leaves the feature out, carries none of that code. Every build reads the six image keys, `image-storage-limit`, `max-graphic-size`, `num-color-registers`, `private-color-registers`, `sixel` and `kitty-graphics` (ADR-1100 D11), and a build without images then draws no picture.

In a build with images, each console's terminal gets the sixel and kitty handlers, with `max-graphic-size` and the color registers' keys as their limits. At every turn of the loop, between two input calls, each head gives each of its consoles three host events (ADR-1100 D5), each only when it changed:

- **The budget**: `image-storage-limit`, or under `auto` four frames of the head's displays in RGBA, from 16 MiB to 192 MiB, worked out again when a display joins or leaves the head or changes size. A smaller budget evicts nothing at once; the store's next reservation evicts down to it.
- **What it offers**: sixel and kitty graphics, each while its key is on, the budget is above 0 and every display of the head draws pictures, which the CPU compositor does in this build. A head with no display yet offers them. A console that offers sixel reports DA1's attribute 4.
- **The cell size** its pictures are placed in: the head's cell for the console shown, the console's own for a hidden one. A picture keeps the cell it was made in, so a zoom draws it scaled.

The head's snapshot carries the frame's pictures to its render thread, each sharing its image's pixels (ADR-1100 D9). A renderer keeps scaled copies and its damage history under the image keys of one console's store, and every console's store numbers its keys from zero, so a console switch makes each display of the head a new renderer, as a font change does.

Kitty animations, and animated GIFs, which the store keeps the same way, play through each console's animation clock (ADR-1102 D3). The image store records only what the program's commands set: the frames, their gaps, whether the animation runs, its loops and the frame a command made current. At each turn of the loop the clock answers the commands that changed an animation, and moves each running animation on by its frames' gaps, passing over gapless frames, which have a negative gap and never show, its timer firing at most once every `ANIMATION_FLOOR_MS`. When a head takes its snapshot, the clock puts the frame it chose on every placement of an animated picture, asking the store for that frame's pixels once for each picture, and a turn that moves a frame draws the head again. `v=n` plays the frames `n` − 1 times and then stops on the last frame, and `v=1` plays them forever; a run started past the first frame plays to the last frame before its first time through (ADR-1102 D4). The clock arms no timer while nothing plays, while its console is hidden, or while another program holds the VT or the displays are blanked. When its console shows again, the clock works out from the time where each animation has got to and shows that frame at once, without playing the frames it missed.

A handler that needs the image helper (ADR-1101), for a file, shared memory, PNG or zlib, leaves a request, and its terminal takes no input until the reply. The helper is its own program, `vtium-image`, which reads what a program names and decodes it as the session's user, so the console, which runs as root, does neither. vtium opens the program `image-helper` names, by default the path vtium was built with (`VTIUM_IMAGE`), once at start, and refuses it by the glyph helper's rules, logging why. Each console has one image helper host from vtium-platform for as long as the console lives, and the host starts that console's helper from the opened program at the console's first request that needs it. At the turn that finds a request, the head hands it to the console's host with the console's session: the login child's pid and the owner of the pty, which vtium reads again for each request by reopening the pty's slave from its master (ADR-1101 D2). The host either answers at once, and the answer goes straight back to the terminal with the pty never paused, or sends the request: the head then pauses the console's pty, puts the host's socket in the loop so that the loop wakes when the reply arrives, and holds the reply timer, `head::images::REPLY_TIMEOUT`, 2,000 ms. The reply, or `FAILED` once the timer fires, goes back to the terminal, the replies the handler writes go to the program, the socket leaves the loop, and the pty resumes. The binary checks a reply's sizes against its request again before it hands it back. A failed reply, as from a lost socket or a reply that fails the host's checks, means the host has stopped its helper and counted a crash; when the timer fires, the head tells the host to stop its helper, and no crash is counted. The console's next request starts another helper. After three crashes in one session (`IMAGE_CRASHES_MAX`) the host starts no more helpers for that console, and the head tells that console's terminal that no helper runs, so the kitty handler answers such a request at once with the reply ADR-1100 D7 gives for "no helper": `EBADF` for a file, a temporary file or shared memory, and `EINVAL` for PNG and zlib. Every console answers the same way when vtium has no program to start. A session that ends drops its request out with no reply, so the reset that starts the next session takes, and the host stops its helper and clears its crash count. Other consoles, drawing and keys carry on while one console waits, and a console past its crash limit leaves the other consoles' helpers alone. A temporary file may lie in vtium's own `TMPDIR`, which reaches the helper when it is an absolute path. `App::set_image_helpers` puts a test's stand-in hosts in place of the real ones.

## The font

vtium draws frits, generated at run time by the helper (ADR-1200, ADR-1301 D2), and its built-in fonts, and parses no font file: vtium-font's PSF loader is behind a feature the binary leaves out.

- **At start** the font is `font-name` when a file or the command line sets it, else vconsole's (`vconsole.font=` on the kernel command line over `FONT=` in `/etc/vconsole.conf`), else none, and the built-ins draw with no line; `font-engine=unifont` or `8x16` draws the built-ins too (ADR-1200 D9). A head's own `font-name`, else its profile's frit, wins over these (see "Heads"). A name is the frit `NAME.vtfrit` in `/etc/vtium/fonts`; a name no frit bears becomes a one-source frit made on the fly, `source=file:PATH` for a path, as `font-engine=psf` gives one, `source=font:FAMILY` for an outline family, as `font-engine=freetype` or `pango` gives one, `source=vconsole` for vconsole's font, `source=kbd:NAME` for another name, which the helper is handed as text with no file, under the name it was given when that is a frit's name and as `generated` when it is not, as for a path or a family, since the helper refuses a request naming anything else (D1). A frit whose `cell=` or `size=` vtium cannot read draws the built-ins with one line naming the font and why. A source the helper cannot read gives the helper's own line, and the built-ins go on drawing.
- **A frit** is generated in the cell it states with `cell=WIDTHxHEIGHT`, in pixels, read as text before the first frame; else the cell its first source gives (#145). That cell is the helper's to tell, since the console parses no font: the console asks for it at the height it draws at, a configured `font-size` in points, else an outline frit's `size=` at the density, else the automatic rule, and waits at most 100 ms (`OWN_CELL_MS`), the one wait on the helper. It asks before the first frame, at an OSC 50 switch, and at each zoom of an outline frit; it asks again at a height only after a zoom, and every head drawing the frit shares each answer. A bitmap first source answers with its own cell, when every later bitmap source's cell fits in it, and with no `font-size` configured the console takes that cell at the largest whole multiple not over the display's automatic height, at least once, as the C reference scaled a PSF font (the operator's decision on #145, 2026-10-28). An outline first source answers with the cell the W rule gives at the height asked, which the console takes at that height alone (the maintainer, 2026-11-01). The answer, and not the frit's text, says which kind the first source is: a `font:` source that resolves to a bitmap font zooms as a bitmap frit, and when a bitmap first source is missing on the machine and an outline source answers, the frit zooms as an outline frit. A refusal, no answer in time, or an outline cell of another height, which gives the helper up, leaves the display's cell for a bitmap frit and the built-in font's width for an outline frit, with one line saying why. An answer that comes after the wait is kept (ADR-1200 D17, the maintainer, 2026-11-03): from the next frame each head drawing the frit that takes a cell from it draws in that cell, its grid laid out again, with one line, and a refusal that comes late holds as one in time does. A late answer is dropped where the frit already holds an answer that came in time: at the height asked for an outline frit, and at any height for a bitmap frit, whose answer holds at every height. An outline frit's `size=` is the size of its glyphs in the cell; a bitmap frit's is left aside. A configured `font-size` wins over the frit's cell and size (ADR-1200 D16); `font-size=0` does not. A cell vtium picks a height for, from `size=`, `font-size` or the display, is as wide as the built-in font at that height (D17); the display's height is `font-size=0`'s, the C reference's automatic rule with vtium/vtium#118's floor: 8x8 at 320x240, 8x16 at 640x480, 8x19 at 1366x768. The built-ins draw in the cell from the first frame: unifont at the largest whole factor that fits, else Unscii-8, centered in a larger cell and cropped to a smaller one. The helper generates for that cell and never moves it, so the grid resizes only at a zoom or, while the cell is the display's, a display hotplug. The frit's `glyph-source=` and `glyph-source-<range>=` lines are the font's sprite policy, and the configuration's keys override them (D1). The console starts `vtium-config serve` on the first need, as `nobody` when vtium is root, under the operator's fill model (2026-10-28): the characters the screen shows, or newly shows, are asked for and answered first; while nothing is asked the helper fills each display cell's coverage, the screen's characters, then printable Latin and box drawing, then the rest, a waiting ask answered before its next batch. Each answer is checked for bounds and dimensions and for being what was asked, kept in memory for the boot, and redraws only the cells that show its characters; a character the frit lacks draws in the built-in font (vtium/vtium#141). The frits' stores together hold 16 MiB below 2 GiB of memory, 64 MiB from 2 GiB and 128 MiB from 4 GiB, each frit's that limit divided by the heads (see "Heads"): a fill stops at its store's limit, and an ask past it evicts the sets least recently on the screen, which are asked for again when the screen shows them. A helper that answers what is not a frame or not asked, or fails, is given up for the boot and logged once, and the built-ins go on drawing; one that crashes, reaches its CPU limit, gives no answer for 10 s (`ANSWER_MS`), leaves an ask unanswered for 60 s (`REQUEST_MS`) or exits with work outstanding is started again, at most 3 times a boot (`RESTARTS_MAX`). The console reads the kernel's font from its VT once at start, before the VT turns graphical, and hands it to the helper with each request for a frit's `console:` source (D8).
- **Bold and italic** come from the helper by ask (ADR-1200 D21). The console keys each glyph by its text and its style, bold, italic, both or neither, and asks for each style the screen shows in a request of its own that names the style; the helper draws it from the frit's face for that style, or synthesises it (vtium-config's README, "Styles"), and the console refuses an answer whose strikes are of another style than the one it asked for. The fill brings regular glyphs alone. Until a styled glyph arrives, and where the helper gives none, the built-in font draws it in its own synthetic style: widened for bold and sheared for italic, a pixel row at a time about its baseline (ADR-1302 D4). Tests: `an_italic_ask_names_its_style_and_its_glyphs_are_held_as_italic`, `a_strike_in_a_style_not_asked_for_gives_the_helper_up`, `a_style_draws_its_own_glyph_else_the_built_in_fonts_in_that_style`, `italic_and_bold_text_is_asked_for_in_its_style`.
- **The built-ins** are Unscii-8 for cells under 16 pixels and unifont from 16, but in a zh, ja or ko locale, whose characters Unscii-8 lacks, unifont at every size (D7). The locale is the first of `LC_ALL`, `LC_CTYPE` and `LANG` vtium starts with.
- **Sizes are points,** 1/72 inch (the operator's decision on #145, 2026-10-28): `font-size` and an outline frit's `size=` draw at points × DPI ÷ 72 pixels, to the nearest pixel, a half away from zero (`font::points_to_pixels`), at most vtium-font's `CELL_SIDE_MAX`. The density is `display-dpi`, with no line logged; else each display's, measured from the physical size it reports (vtium-platform's `Density`), down its rows as vtium draws it; else 96 DPI, with one warning for each display that reports none. Where displays differ, the lowest density converts, and a larger display draws larger by the layout rule; the team lead accepted this reading for the operator to confirm (2026-10-28). A configured `font-size` follows the displays' density until a zoom. `vtium check-config` opens no display, so it notes the density's source on standard output, outside its exit status, and the start logs each display's. Points do not apply to bitmap fonts: an all-bitmap frit takes its stated `cell=` or its fonts' own cell, and the built-ins step by their strikes. A `cell=` stays in pixels, an exact override.
- **`font-size`** picks the built-in's strike of its height in pixels, else the tallest under it scaled by the largest whole factor that fits. `font-size=0` picks it from the smallest display: the C reference's rule, at least 16, but where 16-pixel cells would leave fewer than 80 by 25 cells, the font's smallest height.
- **Zoom** steps as the C reference's font's size step did (D17): a frit whose first source is an outline font, by 1 point, to the next whole point whose pixels at the density differ, each height in the helper's cell for that height, else as wide as the built-in font there, but its stated cell's, down to the built-in's smallest; a bitmap frit by its stated or own cell's whole multiples; the built-ins, and a bitmap frit with no cell, stated or own, through Unscii-8's 8 and unifont's 16, 32 and on. Below the smallest it stops with one line naming the font and its height.
- **The helper** is the program `font-helper` names, and the frits are in the directory `font-frits` names, each by default the path vtium was built with (`VTIUM_FONT_HELPER` and `VTIUM_FONT_FRITS`). vtium opens the program once at start and starts every helper from that open file, so a running console keeps the helper it started with across a package upgrade; it refuses a path that is not absolute, a file that is not a regular file, a setuid or setgid file, a file owned by an account other than root or the account vtium runs as, and a file its group or others may write, and logs why (ADR-1200 D15). The opened file is close-on-exec, so neither the helper nor the session holds it. The helper starts through `/proc/self/fd`, which the kernel lets a process read as any account, so vtium needs `/proc` mounted to start it.
- **OSC 50,** under `allow-font-ops`, on by default, switches the live console to a frit in `font-frits`'s directory or a built-in the name names, on a new grid with a pty resize, as a zoom does; a frit gets the helper and the store every head drawing it shares, and the built-ins draw what the helper has not yet sent. Anything else, a path, a name no frit bears or a frit whose cell cannot be read, leaves the font with one line saying why. Its query names the frit or built-in in use, a frit made on the fly by the name it was given. The output after a font asked for waits for the turn that switches, so a query written with it, as `vtium-config set` writes it, names the new font. A switch lasts for the session it came from. A session ends when its program exits, when vtium hangs it up under `when-display-lost = hangup`, or when the close chord closes its console. When that session ends, or the session in the head's only console, vtium reads vtium.conf's `font-name`, `font-size` and `font-engine` again with the reader it starts with and returns the head to the font they give, at their size, before the console's next session starts; a zoom made in the session that ended is undone with it (ADR-1201 D11). A session ending in another console of the same head leaves the font. Where the `font-size` read again turns a configured size on or off, the frit the head draws is rebuilt to drop or take its own cell. An OSC 50 request that a hidden console still holds goes with its session. A font key that does not read is reported and dropped, as at the start; every other key, and its reports, wait for the next start.

## Bounds

A configuration file is untrusted input. The bounds of each key's value are in `docs/config.md`.

| Bound | Value | Past it |
|---|---|---|
| `FILE_MAX` | 65,536 bytes of a file | The rest is not read, and the file is reported |
| `LINE_MAX` | 8,192 bytes of a line | The line is ignored and reported |
| `TEXT_MAX` | 4,095 bytes of a text value or a `login` command, `PATH_MAX` less its NUL | The value is ignored and reported |
| `REPORTS_MAX` | 64 reports | The rest are counted in one report |
| A head's render thread | a stack of 128 KiB, 16 frames each way, a frame on its way per display | A frame the full queue refuses goes back to its display, which draws at the next turn; the thread waits while the loop has not taken what it composed |
| A seat's name | letters, digits, `_` and `-`, as logind names seats, and a file name of at most 255 bytes | Its file is not read, and the name is reported |
| `head-consoles-max` | 4 consoles a head by default, 1 to 50 | The head file's `consoles` past it opens this many, with a warning |
| `consoles-max` | 8 consoles every head together by default, 1 to 50 | Each head keeps its first; the others past it, in the file's order, do not open, with a warning |
| `HEADS_MAX` | 16 heads a head file declares (vtium-settings's bounds) | The file is invalid, and the shipped rules run |
| A console's scrollback | `sb-memory`, at most a quarter of the machine's memory divided by `consoles-max` or by the heads, whichever is more | Its oldest lines go, as past `sb-memory` |
| `REPLY_TIMEOUT` | 2,000 ms a request to the image helper is out, in a build with images (ADR-1100 D7) | The request fails, the helper is stopped with no crash counted, and the console's pty resumes |
| `ANIMATION_FLOOR_MS` | 10 ms between two firings of the animation clock's timer, in a build with images (ADR-1102 D3) | A frame whose gap is shorter shows at the next firing, or is passed over when its time has gone |
| A frit's glyph store | the machine's store limit (16 MiB below 2 GiB, 64 MiB from 2 GiB, 128 MiB from 4 GiB) divided by the heads | A fill stops at it, as at the store's limit |
| The helper client's record of a cell in one style | four bitsets of every codepoint, held, lacked, asked for and brought by the fill, 136 KiB each, made only when a bit is first set; a style other than regular never fills, so at most 544 KiB for the regular record and 408 KiB for each other style's, 1.73 MiB for a cell the screen shows in all four styles (`helper.rs`, `Bits`) | Nothing past it: one record a cell and style the displays draw at, dropped with its cell |

## Departures

Each was the C reference's behaviour at kmscon `b1f7a7c5`.

- **A build without images reads the image keys and says nothing of them.** The C reference's build without images logged at every start, at the information level, that it turned `sixel` and `kitty-graphics` off, since both are on by default (`src/config.c:1221-1247`). vtium's minspec build never offers either, so the line would say nothing a reader needs.

- **A file is read whole up to `FILE_MAX`,** where the C reference read any length into memory (`src/misc/conf.c:533-590`).
- **Only a regular file is read.** A FIFO, a device or a directory at a configuration file's path is reported and skipped, and the file is opened without blocking; the C reference opened any path that existed (`src/misc/conf.c:542-556`), so a FIFO with no writer held the start forever.
- **A value that cannot be read is reported and the rest of the file is read.** The C reference stopped reading the file at a value its parser refused, such as `render-timer=fast` (`src/misc/conf.c:486-490, 504-512`), and read numbers with `atoi`, so `font-size=12px` was 12, `sb-size=abc` 0 and `sb-size=-1` 4294967295. vtium takes digits only, clamps a number to its key's bound, and reports both.
- **An unknown `palette` name is reported, and the value a lower source set stands.** The C reference drew `legacy` for any name it did not know (`src/tsm/tsm-vte.c:453-478` at libtsm eeaf2931).
- **A seat's file that cannot be read is reported and skipped;** the C reference failed the seat (`src/seat.c:786-790`).
- **Each option name is matched whole.** The C reference's `getopt_long` took any unique prefix (`--lo` for `--login`).
- **A command-line word that is no option refuses the start, with `--login` too.** The C reference's `getopt_long` moved it to the end of the arguments, so with `--login` it joined the command, and without it the C reference refused to start (`src/misc/conf.c:310-313`). `check-config` is the one such word vtium takes, wherever it stands before `--`.
- **A mode line is read whole:** a size is digits, each side 1 to 65535, and a name at most 63 bytes; anything else is reported. The C reference read it with `sscanf`, which took a leading number and ignored the rest (`src/config.c:564-617`).
- **`no-` turns off a switch only.** The C reference read `no-font-size=12` as `font-size=12` (`src/misc/conf.c:318-341`).
- **vtium reads `vtium.conf` in `/etc/vtium`, and never the C reference's `/etc/kmscon/kmscon.conf`.** The C reference read `kmscon.conf` in `/etc/kmscon` by default (`src/config.c:1349`). `--configdir` names another directory, as it did. vtium and `kmscon` are separate programs, so each reads a file of its own, and on a machine that runs both, a change to one program's configuration never changes the other's (ADR-1500 D4). The keys stay the C reference's ([docs/config.md](../../docs/config.md) says how to move a file from kmscon). Test: `the_files_are_read_from_etc_vtium_and_never_from_etc_kmscon`.
- **`configdir` is set on the command line only.** The C reference let `kmscon.conf` set the directory the seat's file was read from.
- **vtium logs information messages by default, and `debug` adds debug messages; there is no `verbose` or `silent`.** The C reference logged notices and above by default, information messages under `verbose`, debug messages under `debug`, and only warnings and above under `silent` (`src/shl/log.c:44-48`, `src/config.c:1515-1539`). vtium's default is the C reference's `verbose`, so that key would change nothing, and a file or command line that sets `verbose` or `silent` is reported as setting an unknown key.
- **`debug` in a seat's file turns debug messages on too.** The C reference set the log's level from the command line and `kmscon.conf` only (`src/config.c:1518-1539`), and the seat's file it read after them changed the level no more (`src/config.c:1553-1575`). vtium reads `debug` as it reads every other key, so the seat's file can set it like the main file. Test: vtium's `debug_logs_debug_messages_set_in_a_file_or_on_the_command_line`.
- **A seat's name is checked before it names a file;** the C reference formatted any name into the path (`src/config.c:1571`).
- **The respawn limit times each start from that start, on the monotonic clock.** The C reference recorded a start only when the exit before it was quick, in whole seconds of the wall clock (`src/misc/pty.c:747-767`), so after one slow restart a command that failed at once restarted without end. A slow exit after quick restarts now starts the command again with the count reset, where the C reference exited at the next exit whatever its timing.
- **Quick exits past the limit, on any console of any head, exit with status 1 under the open policy,** so the unit's getty fallback takes the VT. The C reference ended the process there too, every session with it, but with status 0, since its main returned the seat's start error, which is 0 once the start has succeeded (`src/main.c:201-227`, `src/terminal.c:1856-1868`), and its unit's `OnFailure=` does not count a status of 0 as a failure. Spec: ADR-1401 D1, the operator's decision of 2026-10-31. Tests: `a_head_restarting_too_fast_ends_vtium_and_hangs_up_every_head`, `a_hidden_consoles_crash_loop_ends_the_run`.
- **A session that cannot start is not kept waiting.** The C reference ignored a terminal whose pty would not open: the session stayed registered and shown, and the terminal tried to open it again at each activation (`src/terminal.c:1713-1726, 1771-1772`, `src/seat.c:624-628`). vtium never keeps a console with no session. ## C notes: glyph arrival and damage

How the C reference's flow drew, as the logical reference for vtium's damage path, at libtsm `eeaf293` and kmscon `b1f7a7c5`:

- libtsm's screen stamped each cell and each line with an `age` from the screen's counter `age_cnt` as it changed (`src/tsm/tsm-screen.c:114-127, 176, 544-552`), raised the counter once a frame (`screen_inc_age`, `src/tsm/libtsm-int.h:546-550`), and on the counter's wrap set every age to 1 and raised `age_reset` (`screen_age_wrap`, `src/tsm/tsm-screen.c:214-236`). The draw took a cell's age as the largest of its own, its line's and the screen's, or 0 under `age_reset` (`src/tsm/tsm-render.c:284-292`), and the renderer drew the cells newer than the age its buffer held.
- kmscon's text layer emptied a buffer's ages with `kmscon_text_redraw_all` (`src/render/text.h:214-217`), so its next draw marked every cell changed, on each font set and unset (`kmscon_text_unset`, `src/render/text.c:322`, which `kmscon_text_set` calls first), each resize (`src/render/text.c:351`), each rotation (`src/render/text.c:432`), a switch of screen and a failed draw or swap (`src/render/text.c:751, 766, 864`), and in bbulk for two frames after the default or decoration colors changed (`src/render/bbulk.c:1797-1810`).
- bbulk rasterised a glyph lazily in its draw path: `find_glyph` looked the cell's key up and rendered it with `kmscon_font_render` on a miss (`src/render/bbulk.c:529-557`, called at 1427). A glyph existed the moment a frame asked for it, so no glyph arrived between frames and no arrival damaged anything.

## Limitations

A vtium not running as root refuses every image request while the session's program holds its terminal exclusive with TIOCEXCL, unless logind names the session's user: the kernel refuses to reopen an exclusive pty's slave for an unprivileged process, so vtium cannot read the pty's owner.

## Not yet built

Each is the C reference's and waits for its own change: drawing through the GPU, which `hwaccel` asks for and which warns at start (vtium draws in software), the `multi-monitor` key's `clone` and `largest` (vtium lays several displays out as `scaled`, the operator's choice on vtium/vtium#21), the render timer's on-screen display, and the C reference's keys the table lacks: `multi-monitor`, `screen`, the grabs but `grab-reboot`, and the rest.

vtium takes `font-hinting` and `font-line-spacing`, checks their values and warns when one is set, but nothing reads them yet: the font helper hints and spaces lines as the frit says.

Two parts of ADR-1002 wait outside this crate. vtium-render does not draw the overlay row, though the frame vtium hands it carries the row. vtium-platform sends no event when a key is let go, so releasing Ctrl with the pointer still leaves the overlay until the next pointer event or key press.

- `soft-cursor`, off by default, has the renderer draw the pointer on every display and sets no cursor plane up (`src/config.c:1387`, `src/terminal.c:1269-1270`). Test: `soft_cursor_draws_the_pointer_in_software`.
- `grab-reboot` is unbound by default (`src/config.c:1409`). Bound, it is matched after the VT's keys and before the terminal's grabs, only while the VT is ours, and leaves the selection; it asks init with `SIGINT` while `/proc/sys/kernel/ctrl-alt-del` is 0 or cannot be read, and otherwise calls `sync()` and `reboot(RB_AUTOBOOT)` (`src/seat.c:479-513, 584-636`).
- A wheel event is one report while the program tracks the pointer, else a zoom with Ctrl, else three lines of scrollback, whatever its number of steps (`src/terminal.c:1492-1497, 1639-1650`).
- Natural scrolling reverses the wheel's report and its scroll, and with them the cursor keys mode 1007 sends, and leaves Ctrl's zoom as the wheel turns, as the C reference's `natural-scrolling` did, off by default (`src/config.c:1386`, `src/terminal.c:1474-1476, 1646` at kmscon origin/main). vtium.conf's `natural-scrolling` sets it at the start (vtium/vtium#203). Tests: `natural_scrolling_reverses_the_wheel_but_not_its_zoom`, `natural_scrolling_turns_the_report_and_the_scroll_but_not_the_zoom`, `natural_scrolling_comes_from_the_file_and_the_command_line`.
