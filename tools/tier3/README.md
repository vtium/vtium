# tier3

Tier 3 for vtium: vtium's install tree, installed in a pinned Arch Linux guest under QEMU/KVM and started by systemd on a VT, as a system would run it, with a real kernel VT and a virtio-gpu KMS device. A script logs in over the emulated keyboard, draws fixed screens, captures each one and compares it with its golden. The exit status is the verdict. The harness is also the way to put any test content on a real VT: a screen is a shell script in `guest/screens/`.

Every golden is in `goldens/`, one directory a variant (Goldens, tolerances and masks). The goldens of seven variants began as copies of an earlier harness's captures (The copies). Every golden is now vtium's own (`goldens/README.md`). The harness lives and changes here. No run or self-test of tier 3 reads a checkout outside this tree or runs code from one.

## Running it

```sh
make tier3-image             # fetch, verify and provision the guest image, unless the cache holds one built from the same inputs
make tier3-minimal           # the install tree, then the minspec variants: 1 vCPU, 512 MB, unifont, a PSF font, 320x240 and 640x480
make tier3                   # the install tree, built with images for the default variants, then every variant; VARIANTS="..." for some
make tier3-run VARIANTS=2d-potato-min   # the last run's tree, or TREE=DIR, without building
make tier3 JOBS=2            # up to two variants at once, each in its own VM
make install-tree DESTDIR=D  # vtium's install tree alone
make tier3 FEATURES=images   # the tree's console built with vtium's images feature, which the size budget does not judge (The install tree)
make tier3-images            # the tree built with images, then the images variants: sixel, kitty and the image helper's pictures, and the helper before login (Pictures)
make tier3-image-nosystemd   # fetch, verify and provision the guest without systemd, unless the cache holds it
make tier3-nosystemd         # the install tree, then the variants on the guest without systemd (The guest without systemd)
make tier3 VARIANTS="two-outputs-mirror two-cards-mirror usb-keyboards"   # two outputs, two cards, USB keyboards (Outputs and keyboards)
make tier3 JOBS=4 VARIANTS="heads-two-heads heads-partly-open heads-closed-broken heads-policy-typo heads-closed-unmatched heads-off heads-kiosk heads-closed-nodisplay heads-open-nodisplay heads-survive"   # the head variants (Head files)
make tier3 VARIANTS="seat-seatd seat-logind panic-sysrq kmsg-notice"   # vtium built with libseat on seatd and on logind, a kernel panic and a kernel message (The seat and a kernel panic)
make test-tools              # the harness's self-tests, with no guest
tools/tier3/showcase.sh      # the showcase: fetch its fonts, run showcase-1920x1080 and write docs/showcase/ (The showcase)
```

`T3_IMAGES=DIR` names the guest image cache (default `$XDG_CACHE_HOME/vtium/tier3/images`). `make install-tree` takes the binary from `CARGO_TARGET_DIR` when it is set. The report is `target/tier3/report.json`, and each variant's captures, serial log and event log are in `target/tier3/run/<variant>/`. QEMU's unix sockets, for QMP, VNC and the agent's port, are not there. A unix socket's path can be at most 107 bytes long, and a path under a deep checkout can be longer. So each QEMU gets a directory of its own for its sockets, readable by you only, under `$XDG_RUNTIME_DIR` (or under the system's temporary directory, such as `/tmp`, when that is unset). The driver removes the directory when the QEMU stops. When a worker dies and leaves its QEMU running, the runner kills that QEMU and removes its socket directory.

Host needs: `qemu-system-x86_64` with `/dev/kvm`, `qemu-img`, `xorriso`, `gpg`, `curl`, `tic`, `git` and Python 3.12 or later, standard library only, and `zstd` for the showcase's fonts. Everything runs as the invoking user; nothing needs root. QEMU runs headless, one VM per variant with the vCPUs and memory the variant names, and the driver stops every VM it starts by the PID it started. The GL variant also needs the host's render node (`T3_RENDERNODE`, default `/dev/dri/renderD128`); no variant opens a card node.

Every image tier 3 reads is one these scripts fetched or built: anything else in the cache, such as links an older harness left at the top of the cache, is neither read nor changed.

## The install tree

`make install-tree DESTDIR=D` stages vtium as a system installs it, with vtium-config beside it. `make tier3` and `make tier3-minimal` build it into `target/tier3/install`, emptied first, under the run lock.

`HWACCEL=on|off` and `DISPLAY_BUFFERS=1|2|3` set the defaults of `hwaccel` and `display-buffers` that the tree's console and vtium-config are built with (ADR-1500 D8). make reads each one from its command line or from the environment, so one exported in the shell reaches the tree too. make refuses a value out of range before it builds. Unnamed, the key table's own defaults stand.

`FEATURES='...'` on make's command line names the vtium crate's features the tree's console is built with, such as `images` or `logind`, separated by spaces or commas. With none, the default, the tree is the minspec tree. A FEATURES exported in the shell is ignored. The tier 3 targets pass the list to `t3.py run --features`, which builds the tree with it and with each feature a variant of the run needs (`"tree_features"`), and records the tree's features in the report: `make tier3`'s default variants need `images`, so it builds their console with images, and `make tier3-minimal`'s need none, so its tree is the minspec tree. The run that builds `target/tier3/install` also writes `target/tier3/run/tree.json`, the tree's features and digest, and removes it first, so a failed build leaves none. `make tier3-run` on that tree reads its features from there, and refuses a FEATURES that differs, a tree with no record, and a tree whose digest is not the recorded one. `make tier3-run TREE=DIR` runs a tree built elsewhere, which has no record, with the features FEATURES declares, none by default. The size budget judges the minspec tree alone (Size, below).

| `/usr/bin/vtium-image`, `/usr/lib/sysusers.d/vtium-image.conf` | with `images` in FEATURES only: the image helper, `crates/vtium-image-helper` built for release, and `crates/vtium/install/vtium-image.conf`, from which `systemd-sysusers` makes the helper's account for the login prompt (ADR-1101 D1, D2). The tree goes on the run's disc as `tree.tar`, every entry owned by root, and `guest/setup` unpacks it over the guest's root through the guest's directory links. What the harness needs of the build:

| | |
|---|---|
| Files | `/usr/bin/vtium` and `/usr/lib/systemd/system/vtium@.service`, which `setup` links `autovt@.service` to with `vtium console enable --all`. A run refuses a tree without either. |
| Process | named `vtium`. `guest/t3` reads its VmRSS by that name. |
| Configuration | `/etc/vtium/vtium.conf`, where `setup` installs the variant's `guest/vtium*.conf`, which goes on the disc as `vtium.conf`. |
| Image helper | when the tree holds `vtium-image.conf`, `setup` runs `systemd-sysusers` on it, as a package's install hook does, and reports the helper's mode and the account's ids on its `TIER3-INSTALL-OK` line (`images:`); a variant that draws pictures fails unless the helper is there, mode 755, and the account's ids are not 0. |
| Log | stdout and stderr, which `setup` routes to the journal and the serial console. The driver waits for `vt: using tty /dev/tty2`, and `/dev/tty3` after the VT switch; requires every `Display NAME with backend [...] text renderer [...]` line to name the variant's renderer; reads the benchmark figures from the `terminal: render-timer: ...` lines `render-timer=log` writes (`t3_bench.py`); and reads `cell size WxH` when present. |
| Revision | `log: vtium Revision REV`, the first such line on the console. A run fails every case of a variant whose console logged no such line, or logged another name. |
| Size | the binary at most 3,670,016 bytes (3.5 MiB), the operator's budget (`BINARY_BUDGET` in `t3_impl.py`), raised from 2.50 MiB to 3 MiB on 2026-10-29 and to 3.5 MiB on 2026-10-31 by the operator's decisions recorded in ADR-1200 D19. The minspec link packs relative relocations (`-z pack-relative-relocs`, DT_RELR), which takes the binary from 2,627,808 to 2,561,720 bytes; `make minspec`, `make arm` and `make install-tree` fail on a binary with no DT_RELR. DT_RELR needs glibc 2.36 at run time (vtium/vtium#143's floor) and binutils 2.38 (or lld 15) at build. A run whose binary is larger than the budget fails, whatever its cases; raising the budget is a decision recorded in an ADR, this one ADR-1200 D19. The budget judges the minspec tree alone, built without features: a tree whose console carries a feature, such as images or the GPU path, is measured and reported, and its size fails nothing. |

The guest must hold no kmscon, libtsm or vtium package, and `setup` reports the digest of the `tree.tar` it unpacked, which must be the run's. The digest shows the guest unpacked this run's archive. What built the tree is the console's own account, its Revision line, which each variant records as `console`.

## How a run works

1. `make tier3-image` provisions the base once: a qcow2 overlay on the pristine image, booted with a cloud-init seed disc (`guest/user-data.in`). Cloud-init creates the user `tester` (password `tester`, prompt `$ `, no MOTD), installs the packages, links `autovt@.service` to `kmsconvt@.service`, enables the boot hook `tier3-install.service`, disables itself and powers off.
2. The run takes the run lock (`target/tier3/lock`), checks the goldens, and builds the tree.
3. Each variant boots a throwaway overlay of the base with a second disc labelled `T3PKG`: `tree.tar`, the variant's configuration, the screen scripts, `guest/t3` and `guest/setup`. The boot hook runs `setup`, which unpacks the tree, routes the console's log to the serial console, links `autovt@.service` back to `getty@.service`, where Arch's systemd package links it, gives vtium every VT as a user does with `vtium console enable --all`, and makes the second serial port (ttyS1) the event port: the login shell and each screen script write a line there. Changing anything on the disc never needs a new base image.
4. The driver (`t3.py`, with QEMU in `t3_qemu.py`) talks QMP on a unix socket. It waits for `TIER3-INSTALL-OK`, and fails the variant at once with the line's text when the setup writes `TIER3-INSTALL-FAIL` instead, then for systemd's `Started User Login Management` and `Reached target Login Prompts`, then presses Ctrl+Alt+F2: logind starts `autovt@tty2`, which is vtium. It waits for `vt: using tty /dev/tty2` and a drawn login prompt, logs in, and waits for the login shell's line on the event port. Then it types `t3 NAME` for each screen in `SCREENS` (`t3_evaluate.py`). `t3` clears the screen and the scrollback (ED 3), so every screen starts with empty scrollback. After each, the driver waits for the screen script's line on the event port, then captures until two captures a second apart are identical and differ from the screen before, and, for a screen that `SHOWS` lists, show its pictures (Pictures). A screen can be followed by key chords (`KEYED`), each a case of its own, captured once the screen has changed; a key that changes nothing fails its case. An image screen that reports images not offered drew no picture for its keys, so they are not pressed: its keyed cases fail with the refusal, and the screens after it still run. In a variant with images, the screen's own case fails with the refusal too, whatever its golden says.
5. VT switch: Ctrl+Alt+F3, then Ctrl+Alt+F2. `vt-switch` passes when the second instance on tty3 draws a screen that is neither blank nor the one just left. `vt-restore` then requires the tty2 screen to equal the last screen's golden exactly: `cjk`, or `img-png` in the images variant (`RESTORED` in `t3_evaluate.py`).
6. Pointer, on `2d-potato-min` alone: QEMU's `screendump` leaves the cursor plane out, so the case `pointer-plane` reads it from the guest (`t3_pointer.py`). The driver moves the pointer twice with QMP `input-send-event`, which the q35 machine's VMware mouse takes and vtium reads as a virtual mouse, waits for vtium's log line that the display shows it on its cursor plane, and after each move types `t3 pointer`, whose script prints the guest's DRM atomic state (`/sys/kernel/debug/dri/N/state`, which `setup` makes readable on that variant's guest) on the event port. One plane besides the primary must show a framebuffer, its corner the arrow's hotspot up and left of the pixel the mouse points at, worked out as vtium works it out; once the pointer hides, 20 s after its last move, none may, though the readings type keys meanwhile. The case is a check without a golden: its capture, the last reading's screen, is kept only when every reading passed.
7. The driver checks every `Display` line names the variant's renderer, reads each benchmark screen's figures, and compares every capture with its golden.

Each step waits for state the driver can observe: a line on the serial log or the event port, or a screen that has changed and then settled. Every wait has a timeout that fails the case and names what it waited for. On a slow host a capture taken too early can fail its case; it cannot pass it. The one fixed pause is 50 ms between key chords, since QEMU's input queue is bounded. A password typed before the prompt is discarded by PAM, so when no login follows within 20 s the driver types it once more. A step that fails part way keeps the captures taken before it, and each remaining case fails with the error.

## Concurrent runs

`JOBS=N` runs up to N variants at once, each in its own worker process and VM; the default, 1, runs them one after the other. The report lists variants in the requested order. GL variants share the host's render node and never run together. A second run started while one holds the run lock exits at once with the holder's PID. A worker that dies fails its own variant only, and the driver kills any QEMU of that variant it left. A worker still running after `T3_DEADLINE` seconds (default 1800) is sent SIGTERM, stops its VM and fails its variant, and QMP commands time out after 30 s. A run sent SIGTERM or Ctrl+C stops its workers and VMs before it releases the lock, and writes a report in which the unfinished variants fail.

The first six variants in the table, the four 2D ones and the two GPU ones, draw text from tier 3's text font set, the frit (a font set file) `tier3-text` in `guest/frits/tier3-text.vtfrit` (ADR-1503 D9). Tier 3 judges whether vtium draws each script's characters, so the frit names one well-known open font for each script, in fallback order: DejaVu Sans Mono for Latin text and box drawing, with its Bold, Oblique and Bold Oblique faces each named by `style=`, then Noto Sans CJK SC for Chinese, Japanese and Korean, then Noto Color Emoji. vtium does no system font search, so a character none of them holds draws in the built-in font. `guest/setup` installs the frit into `/etc/vtium/fonts` with no set built (`"deferred_frits"`), and vtium's glyph helper generates its glyphs at run time (ADR-1200). The guest image holds DejaVu Sans Mono and Noto Color Emoji. Noto Sans CJK SC is the showcase's pinned copy (`t3_showcase.py`): `t3.py` fetches it into the showcase's font cache when the cache lacks it, the run's disc carries it (`"text_fonts"`), and `guest/setup` installs it into `/usr/local/share/fonts/vtium-tier3`, where the frit names it. The guest image's own CJK font, WenQuanYi Micro Hei, is in no frit.

`make tier3` runs the first five (`DEFAULT_VARIANTS`). The configurations of those five state `display-dpi=86`: vtium draws `font-size` in points at the display's density (ADR-1200 D17), where the first renderer drew 16 as a 16-pixel em at a fixed 72 DPI, and at 86 DPI 16 points are 19 pixels, so vtium draws in a 10x19 cell, the grid of the earlier harness's goldens. At 32 points the cell is 20x38 by the W rule (a cell is as wide as the letter W at the cell's height, ADR-1200 D17), one pixel wider than those goldens' 19x38, so `2d-7680x2160-font32` draws a narrower grid. Every screen draws pictures, so these variants' console is built with images (`"tree_features"`), and with `gpu` too for `gl-1280x800`. A run builds one tree for all its variants, with every feature any of them needs, so the default run's tree is built with `gpu images`, and its 2D variants run a console built with `gpu` whose `hwaccel` is off, which draws on the CPU path. Every golden of the four 2D variants is vtium's capture; `goldens/README.md` says what each shows, the ones re-baselined with the font set `tier3-text` included. `gl-1280x800` draws on vtium's GPU path with `hwaccel` on, under virgl as `gpu-1280x800` does, and every `Display` line must name the `gpu` renderer. Each of its cases is judged by `2d-1280x800`'s golden of the same case, exactly (`GOLDENS_OF` in `t3_evaluate.py`), since the GPU path draws the CPU path's bytes (ADR-1303 D1, D11), so it passes and fails where `2d-1280x800` does. The variant has no goldens of its own. `make tier3-minimal` runs the four minspec variants. The two potato ones draw every screen, and their goldens began as the captures of an earlier minimal build with the same font backends vtium has. Their image screens draw no picture (`"images": False`): each must report images not offered, and the keys that act on pictures are not sent.

`gpu-1280x800` runs the installed console with `hwaccel` on (`vtium-hwaccel.conf`, `vtium.conf` with `hwaccel`), its tree built with `gpu` and `images` (`"tree_features"`), on `2d-1280x800`'s display through virtio-gpu with virgl, whose render node in the guest the head makes its GL context on (ADR-1303 D9), and which takes the host's render node as `gl-1280x800` does. Every `Display` line must name the `gpu` renderer, so a console that falls back to the CPU path fails every case. No golden judges it: each case is judged by `2d-1280x800`'s capture of the same case in the same run, byte for byte (`SAME_AS_CAPTURE`, `judge_by_capture` in `t3_scenario.py`), since the GPU path draws the CPU path's bytes (ADR-1303 D1), as tier 2 judges it. A case `2d-1280x800` fails on its golden is judged there, and a run that leaves `2d-1280x800` out fails every case of `gpu-1280x800` rather than pass it. It runs only when named, as `make tier3 VARIANTS="2d-1280x800 gpu-1280x800"`.

The two small displays are minspec's floor and the size at which everything vtium supports is usable (vtium/vtium#75, docs/architecture.md). They draw `SMALL_SCREENS` (`t3_evaluate.py`): `small-console`, written for 40 columns, then `sgr`, `boxdraw`, `underline-styles`, `underline-colour`, `strike`, `wide-margin` and `cjk`, so `vt-restore` compares with `cjk` as in every variant. Their fonts are `tools/testfont`'s, which the run writes into `target/tier3/fonts` and the disc carries to `/usr/local/share/tier3-fonts`, so no console font of the guest's reaches them. Each PSF variant names the frits in `guest/frits` that `guest/setup` installs into `/etc/vtium/fonts`, with nothing built before the console starts; the helper generates their glyphs at run time (ADR-1301 D2): the small displays' test fonts each with a built-in set after it filling what the font lacks, Unscii-8 at 8x8 and unifont at 8x16, and kbd's default 8x16 alone for `2d-potato-min-psf`, whose goldens an earlier harness captured from that font. At 320x240 no font size is set: where 16-pixel cells would leave fewer than 80 by 25, the default size is the font's own, 8 (vtium/vtium#118).

The two frit variants check the deferred pipeline (ADR-1301 D2) on the minspec machine, both in `make tier3-minimal`. Their font is the frit `guest/frits/dejavu-mono.vtfrit`, which names the guest's DejaVu Sans Mono; `guest/setup` installs it into `/etc/vtium/fonts` with no set built (`"deferred_frits"`), so the console asks the helper for its glyphs at run time. `2d-640x480-frit` draws `FRIT_SCREENS` (`t3_scenario.py`), `small-console` and `cjk`, once the helper's glyphs have arrived. The frit states no cell, so the console asks the helper for the font's own cell before its first frame and draws 71 by 30 cells of 9x16 (ADR-1200 D17): Latin in DejaVu Sans Mono, and CJK, which the font lacks, in the built-in unifont (vtium/vtium#141). `2d-640x480-frit-held` draws the same screens with a helper that never answers (`"helper": "held"`: `guest/setup` puts `sleep` in place of `vtium-config`), which is the screen before the helper's first answer: the built-in unifont throughout, until the console gives the helper up after 10 s and logs one line. Each frit request the helper answers logs its timings to the serial log (`the font's glyphs at WxH are generated`). Their goldens are vtium's own, provisional until the operator reviews them.

The power variants run only when named, as `make tier3 VARIANTS="power-reboot power-reboot-hard power-off power-suspend-off power-suspend-logind"`. Each presses the power keys (vtium/vtium#21) on the console's login prompt, in the order of its cases, and its cases are checks without a golden (`t3_power.py`). A case's capture is the screen before its key, and it passes when the console log after the key shows vtium's line for the key and then the action carried out, with no kernel panic, and a case that ends the VM passes only on QEMU's SHUTDOWN event for it: `guest-reset` for a reboot, `guest-shutdown` for a power-off.

| Case | Key | Passes when the console shows |
|---|---|---|
| `reboot` | `key-reboot`, `kernel.ctrl-alt-del` at 0 | systemd's `Unmount All Filesystems` and `System Reboot` targets reached, then the kernel's `reboot: Restarting system` |
| `reboot-hard` | `key-reboot`, `kernel.ctrl-alt-del` at 1, which the variant's disc sets | the kernel's `reboot: Restarting system` with neither target |
| `suspend` | `key-suspend`, vtium built with `logind` | vtium's line that logind took the request and systemd's `Sleep` target, in either order, then `System Suspend`; QMP sees the guest suspended, wakes it, and vtium draws its screen again |
| `suspend-sysfs` | `key-suspend`, the minspec build | vtium's line that it writes `mem` to `/sys/power/state`, and no `Sleep` target; QMP sees the guest suspended, wakes it, and vtium draws its screen again |
| `power-off` | `key-power-off`, on a guest that has not slept | systemd's `Unmount All Filesystems` and `System Power Off` targets reached, then the kernel's `reboot: Power down` |
| `power-off-after-s3` | `key-power-off`, after `suspend` or `suspend-sysfs` | a known failure of the guest's (`t3_power.KNOWN`): the same lines, then a kernel panic with QEMU still running. It passes with a note while it fails that way, and fails once it no longer does |

QEMU runs with `-no-reboot`, so a reboot ends the VM as a power-off does, and each has a variant of its own.

After an S3 resume the guest does not power off, whichever path suspended it. The suspending variants log the kernel at info level, so the console shows systemd stopping the services, `systemd-shutdown` unmounting every filesystem, the kernel entering S5 (`ACPI: PM: Preparing to enter system sleep state S5`) and `reboot: Power down`; QEMU's machine stays on, 10 s later `reboot(2)` returns to `systemd-shutdown`, which exits, and the kernel panics with PID 1 gone. A guest that has not slept powers off with the same key. vtium's part, `SIGRTMIN+4` to PID 1, is the same in both, so the failure is the guest's ACPI power-off after S3 in QEMU's q35 machine. `power-suspend-logind` runs vtium built with `--features logind`, which `t3.py` builds into `target/tier3/features-logind` with the minspec profile and puts on the variant's disc, where `setup` installs it over the tree's binary; the budget judges the tree's binary.

Three findings from the first runs shaped this table. At 7680x2160 each XRGB buffer is 63 MiB, and with QEMU's default `max_hostmem` (256 MiB) the second instance on tty3 fails to create its buffers; 1 GiB clears it. Once virgl owns the scanout, QMP `screendump` fails with "no surface", so the GL variant captures over VNC on a unix socket (raw RFB, `t3_qemu.py`). QEMU 11.1's `screendump` pads each PPM row to a multiple of 4 bytes while the header gives the width, so `t3img.read_ppm` drops the padding and refuses a body of any other size.

## The seat and a kernel panic

These variants run only when named, as `make tier3 VARIANTS="seat-seatd seat-logind panic-sysrq kmsg-notice"` (`t3_seat.py`). The guest image holds seatd, the seat manager, and libseat, which a vtium built with the `libseat` feature links (`guest/user-data.in`). seatd's service stays off unless a variant starts it.

`seat-seatd` and `seat-logind` run vtium built with `libseat` (`"features"`, which `t3.py` builds into `target/tier3/features-libseat`) on the minspec machine with `vtium-minimal.conf`. `guest/setup` gives vtium's unit a drop-in that sets `LIBSEAT_BACKEND` to the variant's seat manager, so libseat takes no other backend. For `seat-seatd`, setup starts seatd. Each variant logs in, draws `sgr` and `cjk`, and switches VTs through the seat manager. Its cases are judged by `2d-potato-min`'s goldens (`GOLDENS_OF` in `t3_evaluate.py`), since the seat changes where the devices come from and not what vtium draws. Its check `seat` reads the console's log after the VT switch. It passes when the seat seat0 opened, every keyboard and pointer vtium used opened through the seat manager first, and vtium never fell back to the kernel's VT. libseat's logind backend takes the seat from vtium's own logind session, which only the unit's `PAMName=vtium` and vtium's PAM file give it (ADR-1400 D3). So `seat-logind` passes only on a tree whose unit opens that session.

`panic-sysrq` crashes the guest's kernel while vtium shows its login prompt on tty2. It runs the agent (`guest/t3-agent`), whose request `panic` runs `echo c > /proc/sysrq-trigger` as root. Its check `kernel-panic` passes once the console shows `Kernel panic - not syncing: sysrq triggered crash` and the screen has settled after it. The capture, `target/tier3/run/panic-sysrq/kernel-panic.png` in the report, is the evidence of what a person sees at a kernel panic while vtium holds the VT (ADR-1401 D15). The check judges nothing of the picture, and its note says whether the screen differs from vtium's last frame.

`kmsg-notice` proves that vtium reads `/dev/kmsg` and shows a kernel message on screen (ADR-1401 D15). vtium shows only messages that the kernel itself logged, and a line written to `/dev/kmsg` is logged with the user facility, so the agent's request `kmsg` makes the kernel log one. It calls mount(2) for tmpfs with the unknown option `vtium_tier3_warning`, and the kernel refuses it with `tmpfs: Unknown parameter 'vtium_tier3_warning'` at level err. The agent calls mount(2) itself, because mount(8) passes options through fsconfig(2), whose errors go back to the caller and not to the kernel's log. The case `kernel-message` waits for that line on the console, then captures the screen once it has changed from the login prompt and settled, within the 15 s vtium shows the message. Its golden, `goldens/kmsg-notice/kernel-message.png`, is provisional.

The showcase is the set of screens the documentation shows a newcomer (ADR-1502 D6): vtium's own drawing on a VT of the guest at 1920x1080, written into `docs/showcase/` with a page that shows each one. `showcase-1920x1080` draws them: the default machine, 4 vCPUs and 4096 MB, with a `virtio-vga` display whose EDID gives 1920x1080, its console built with the `images` feature (`"tree_features"`) and drawing on the CPU path, `cpu`. ## Outputs and keyboards

Three variants put more than one display or keyboard in front of vtium, each run only when named, on the minspec machine at 640x480 in the 8x16 test font, judged by vtium's own goldens (`t3_devices.py`). They record vtium as it is today: one grid drawn on every display, and every keyboard typing into it.

| Variant | Machine | Cases |
|---|---|---|
| `two-outputs-mirror` | `virtio-vga` with `max_outputs=2`: one card, two outputs | `sgr` and `cjk` captured from each output, `vt-switch`, `vt-restore` from each, and `mirror` |
| `two-cards-mirror` | `virtio-vga` and a second card, `virtio-gpu-pci`, one output each | the same, from each card |
| `usb-keyboards` | `virtio-vga`, with an xHCI controller at `0000:15:00.0`, a hub in its port 3 and a keyboard in the hub's port 2 | `cjk`, `vt-switch`, `vt-restore`, `udev-examples` and `keyboard-hotplug` |

A variant's `outputs` lists the outputs it captures after the first, each by QMP `screendump`'s `device` and `head`. A case drawn on one is named with the output's suffix (`cjk@1`, `cjk@card1`) and has its own golden; `vt-restore@1` is compared with `cjk@1`. A virtio-gpu head after the first reports itself disconnected until a display asks for its size, which a headless QEMU never does, so the driver gives each such output a VNC server on a unix socket of its own (`vnc1.sock`) and, before the guest boots, asks it for the output's size with RFB's SetDesktopSize (`t3_qemu.vnc_set_size`); the head then shows as connected with that size as its mode. `mirror` is a check without a golden: every case with a golden, as each other output drew it, must be identical to the first output's. A variant with outputs fails, and its captures are dropped, unless the console logs one `Display` line for each output, so a capture of an output vtium never set up, which shows QEMU's own screen, cannot pass.

The USB controller sits behind the second of two PCIe root ports; the first holds 19 buses beyond its own, so the firmware's depth-first numbering gives the controller bus 0x15 and the keyboard the `ID_PATH` `pci-0000:15:00.0-usb-0:3.2:1.0`, the port the example rule names as the record writes it. `udev-examples` has the guest read the example files the tree installs with its own udev, as `tester` and changing nothing (`guest/screens/udev-examples.sh`): `udevadm verify --no-style` on `71-vtium-local.rules`, which must exit 0 and print nothing, so every rule is checked; `udevadm test --extra-rules-dir` with it for each keyboard, which must give the keyboard in that port `VTIUM_HEAD=panel`, the PS/2 keyboard `VTIUM_ROLE=token` and every other keyboard no `VTIUM_` property. `guest/setup` installs `vtium.hwdb` into the guest's `/etc/udev/hwdb.d` as an administrator would, its token's match changed to the PS/2 keyboard (`b0011v0001p0001`), and runs `systemd-hwdb update`, so the token's property comes from udev's own `60-evdev.rules`, which looks the fragment's `evdev:` entries up. The fragment as shipped is also built into a scratch root with `systemd-hwdb update --strict`, which must print nothing, and queried for the token and the numpad it names, which must get `VTIUM_ROLE=token` and `VTIUM_ROLE=numpad`, and a device of the numpad's vendor it does not name, which must get nothing. `keyboard-hotplug` runs after it. QEMU sends a key no console binding claims to the keyboard plugged in last, so the check first pulls the boot's USB keyboard out with QMP `device_del`, and the console's keys then reach the PS/2 keyboard. `guest/screens/keyboard-hotplug.sh` lists the guest's keyboards with their event nodes and the PS/2 keyboard's interrupt count (IRQ 1 in `/proc/interrupts`), which tells its keys from a USB keyboard's. The script runs twice on the console's keyboard, and the count must rise between the runs, the control. A USB keyboard is then plugged into the hub's port 3 with QMP `device_add`, bound to the first display's console so QMP `input-send-event` types on it alone: vtium must log the event node the guest lists for it as a keyboard, and the script runs twice on it, listing it and leaving the count unchanged. Last, `device_del` pulls it out, and once QEMU reports `DEVICE_DELETED` the console's keyboard runs the script again, which must not list it. Both are checks without a golden.

## Head files

Nine variants install heads, rules and looks as the sections of `/etc/vtium/vtium.conf` in the guest, root's and writable by no one else, as an administrator would (ADR-1401, ADR-1403), and check what the guest's real KMS device and systemd make of them, which unit tests cannot (`t3_heads.py`). Each runs only when named, on the minspec machine at 640x480 in the 8x16 test font, and each names the policy its checks expect. A variant names a head file, one of `guest/heads/` or a shipped one under `docs/heads/`, which holds a flow: its `version` and `policy` lines, then its sections. The disc's vtium.conf is the variant's configuration, vtium's own keys, with the head file below it (`t3_heads.guest_conf`), so the head file's two lines join the top level and its sections follow, and the console's messages name each line by its number in that whole file.

A console that gives no login leaves the driver no shell in the guest, so these variants run the agent, `guest/t3-agent`, as root from `t3-agent.service`, which `guest/setup` installs from the disc. The agent reads one request a line from the guest's third serial port, ttyS2, which QEMU connects to a unix socket in its socket directory, and answers on the same port, each line of the answer to request N as `T3-AGENT N ...` and the last as `T3-AGENT-END N`. Only root can open ttyS2, so a program of the session's, which can write the event port, cannot forge an answer. It has ten requests, and refuses any other, spelled even one character differently, running nothing (`HeadsTest` feeds it injections on a pty): `state`, which reports the guest's systemd version, the active state, sub-state, result, condition and restart count of `vtium@tty2`, `vtium-getty@tty2` and `getty@tty2`, what systemd logged this boot of vtium's unit and its fallback as one word for each event in order (each failure with its result, each restart with its count, each start and stop of vtium, and each time the fallback skipped itself on its condition or started the getty), when `getty@tty2` and `serial-getty@tty2` last left their inactive state and how often each restarted, every job systemd has queued, every timer and its state, the login sessions and their ttys, whether vtium's marker `/run/vtium/tty2.closed` exists, the programs on tty2, the login programs running, the VT shown, the PS/2 keyboard's and the USB controller's interrupt counts, the keyboards the guest lists, the key presses the second keyboard sent once watched, and the PID and age of vtium on tty2, its unit's main process; `watch`, which counts the key presses of the keyboard in the USB hub's port 3.3, read from its own evdev node, until it is pulled out; `kill KILL` and `kill ABRT`, which send that signal to vtium on tty2; `hangup`, which hangs tty2 up with the call systemd's `TTYVHangup=` makes; `start`, which starts vtium's unit on tty2 again; `restart`, which restarts that unit, as after an upgrade; `stop`, which stops it; `ptys`, which reports each process that leads a session on a pty with the pty and its size, how many pty masters vtium on tty2 has open, and each answer a line typed in a session wrote to `/tmp/t3-answer-WHAT`; `reset-failed`, which clears that unit's failed state and its count of starts; and `limit`, which sends SIGKILL to each vtium the unit starts on tty2, at most 12 times, until the unit stops restarting, and then, if the unit failed on its start limit, starts it once more and reports whether systemd refused.

## The guest without systemd

`docs/systemd.md` lists what vtium does on a host whose PID 1 is not systemd; this guest judges that column. It is Debian 13 with sysvinit as PID 1, provisioned from the pins above by `make tier3-image-nosystemd` into the cache's `base/` as `sysvinit-<digest>.qcow2`, keyed by the files in `guest-sysvinit/` it is built from (`SYSVINIT_INPUTS`), and linked from `target/tier3/vm/base-sysvinit.qcow2`. Its one boot under systemd, with cloud-init, masks the image's apt timers and purges `unattended-upgrades` before its first fetch, so nothing newer than the snapshot is installed, then installs `sysvinit-core` and `sysv-rc` in place of `systemd-sysv` (and `libpam-systemd`), and `libxkbcommon0`, the one library of vtium's the image lacks; changes the inittab's `tty2` line from getty to `t3-console`; makes `/etc/rc.local`, which initscripts runs at the end of the runlevel, the boot hook; and powers off with `systemctl`, as sysvinit's `shutdown` is the one installed and systemd does not hear it. Alpine was ruled out because it is not glibc, and Devuan because it publishes no disk image for excalibur and no dated snapshot to pin its packages to.

Each boot after that runs sysvinit. The boot hook finds the run's disc with `blkid`, with or without udev, and runs `guest-sysvinit/setup`, which installs the tree and the screens as `guest/setup` does, and `t3-console`, the inittab's line: `vtium --vt=ttyN --no-switchvt` as `docs/systemd.md` says an init runs it, its log stamped onto the serial console as systemd's journal stamps it, so the driver reads it the same. Its report line adds PID 1's name and path, whether `/run/systemd/system` exists and the udev daemons running, and the driver fails the variant unless PID 1 is `init`, the directory is absent and udev runs as the variant says. vtium starts on tty2 at the boot, while tty1's getty is shown, and waits there; tty3 keeps its getty, but in `sysvinit-two-vts`, whose setup gives tty3 a second vtium and has init read the inittab again. The driver presses Ctrl+Alt+F2 once tty2's console has logged its VT, and the run goes on as under systemd.

On every guest the login must report a pty (`T3-LOGIN /dev/pts/N`): vtium's session runs on one, and a login on `/dev/ttyN` is a getty's, drawn by the kernel's console, as when the keys reached a VT vtium did not hold.

## Goldens, tolerances and masks

The goldens are `goldens/<variant>/<screen>.png`, full resolution and lossless, for every variant but those judged another way (`"verdict"` in `t3_scenario.py`) and those judged by another variant's goldens: `GOLDENS_OF` in `t3_evaluate.py` names the directory each of those compares with, today `2d-1280x800/` for `gl-1280x800`, so `goldens/` holds no directory for `gl-1280x800`. The check before a run refuses a golden that no case compares with, and a provisional row for a golden that does not exist. A keyed case's golden is named after the case; `photo-scrollforward` and `vt-restore` are compared with another screen's (`SAME_AS`). Comparison is exact unless a sidecar `<screen>.tol` sits beside the golden, holding `max_delta=`, `max_pixels=` and `mask=x0,y0,x1,y1` lines (end-exclusive); `#` starts a comment, and a malformed sidecar fails its case.

| Status | Meaning | Gate |
|---|---|---|
| `pass` | identical outside the masks | passes |
| `near` | differs, within both limits of the case's sidecar | passes |
| `provisional` | compared with a golden that `provisional.tsv` lists, not yet reviewed: the status it would get is noted | passes |
| `fail` | differs beyond the tolerance, or the case could not run | fails |
| `missing` | no golden | fails |
| `capture` | a case of the showcase, which no golden judges, captured (The showcase) | passes |

The run exits 1 on any `fail` or `missing`, or a minspec tree's binary over the budget. Nothing here writes a golden. A new golden is a capture of vtium's, added in a commit of its own that lists it and what it shows, as `goldens/README.md` does. It stays in `provisional.tsv`, as `VARIANT/SCREEN` and why, until the operator has reviewed it; removing its row makes it judge. A run refuses to start when a golden or sidecar under `goldens/` is one no case compares with, or `provisional.tsv` lists a golden that does not exist. A case whose golden does not exist yet is `missing`, so its first capture is in the report.

## Report

- `run_id` is fresh for every run, so a comparison can tell two runs from one run saved twice.

- `build` names the tree and its `tree_sha256`, `features` (the vtium features its console was built with, `[]` for the minspec tree), `binary_bytes` and `installed_bytes` (the regular files it installs), `budget` (the binary's budget and whether it is met, or `null` for a tree built with features, which the budget does not judge), and `consoles`, each `NAME REVISION` the variants' consoles logged.
- Each case carries `status`, `description` (the header comment of its screen's script with its `# look-for:` lines, or its entry in `CHECKS`), `wrong` (its `# wrong-looks-like:` lines), `text` (the lines its script prints, colors removed, or `null`; see `guest/screens/README.md`), `golden`, `actual`, `diff` and their thumbnails as PNGs, `tolerance`, and `stats` (`pixels`, at most 16 `bbox` regions, `max_delta`).
- Under `variants`, each variant records `installed` (the tree the guest reported, with every other field of its `TIER3-INSTALL-OK` line), `kernel` (the guest kernel's `uname -r`, which `setup` reports on that line; a guest that reports none fails the variant), `displays` (the console's `Display` lines), its QEMU `device` and `qemu` (the devices after it), `config`, `cell`, `cpus` and `memory_mb`, `bench` (each benchmark screen's figures), `rss_kb` (the console's VmRSS after each screen, the largest across its processes), `resident` (after the first screen, and the peak with the screen it followed), `startup_ms` (from the Revision line to the first `Display` line), `console`, `timing` (seconds to the end of each phase) and any `error`.

The run prints each case's status, then the tree, its binary against the budget and the consoles that ran, and each variant's guest kernel and resident memory.

## Benchmarks

The benchmark scenarios run as screens. S1, text scrolling with no image, is `s1-scroll`. A2 is `mpv-sixel` (mpv `--vo=sixel` playing ffmpeg's testsrc2 pattern) and A4 is `tmux-2x2` and `tmux-3x3` (the same pattern in every pane of a tmux grid). `flood` sends sixel pictures in 4 KB parts for 4 seconds, a stream that changes the screen rarely. `sync-clock` redraws a status bar, a clock and a progress row in a synchronized update (mode 2026) every 4 ms for 5 seconds with no key pressed, as a program's own timer does, and measures how many frames the console composes for updates no key caused (ADR-1401 D2). Each is drawn and compared with its golden like any screen, apart from `sync-clock`, a check without a golden whose figures are reported and whose capture shows only that the screen finished. Each benchmark reports its window on the event port as `T3-BENCH NAME start=S end=E KEY=N...`, both times from `/proc/uptime`, the clock that also stamps the console lines. `t3_bench.py` takes the console's render-timer lines whose seconds overlap the window, which `render-timer=log` writes once a second per display: frames presented and queued, their CPU time and their damaged area.

`img-tmux-pane`, the images variant's, fails when the console's mean damage per frame, over the window or in any one second wholly inside it, passes the playing pane's pixels (Pictures). `mpv-sixel` fails when the console's CPU time per frame mpv sent passes the clip's 33.3 ms frame interval, when it presents under 90% of mpv's frames a second, or when mpv showed no frame (`t3_bench.bottleneck`); a variant where the console is known to be the bottleneck goes in `KNOWN_BOTTLENECKS` with its issue. A tmux grid fails when tmux sent no sixel picture. `flood` fails when no frame is presented in a second wholly inside the window, or when more than 20 passes a second draw nothing. A build with the render timer configured that logs no line in the window fails the case.

The figures are measured on a guest: a vCPU preempted by the host still counts as the thread's CPU time, so compare builds with `JOBS=1`, several runs each, on a host doing nothing else.

## Self-tests

`make test-tools` runs `test_t3img.py` (image I/O and the masked compare) and `test_t3.py`: the captions and screen text, the tree and its budget, the guest's account of its install, the checks a run makes before it starts (`PreflightTest`), where provisioning fetches and builds the images, the base image's inputs, each variant's machine, the console lines the driver reads, the QEMU command line, the benchmark figures and verdicts, the serial reader, the guest without systemd's variants, disc, login and account of its init and udev, the device variants' outputs, VNC size request, mirror check, reading of the udev examples, hotplug helpers and the examples' install paths, the frits and gallery tool the tree stages, and the head-file variants' cases, disc, agent's port and requests, and each check's verdict both ways (`HeadsTest`). `SixelGoldenTest` reads the colors and cells of the copied sixel goldens. `PicturesTest` pins the test pictures and checks each file against its picture, the GIF through a GIF reader of its own (`gif_frames`), `ImagesVariantTest` the images variant's cases, tree, disc, guest account and make target, and `PictureGoldenTest` the images variant's goldens (Pictures). `ShowcaseTest` checks the showcase's variant and its `capture` status, its scenes and what they leave out, its fonts' pins and frits, the fetch, its pictures and palettes, the gallery's pictures and photographs' pins, the shell scene's gallery and that it keeps to its six rows, run on a stand-in terminal that answers the gallery tool's questions (`test_gallery_scene`, with `tools/gallery/tests/terminal.py`), and the page `compose` writes (The showcase).

## What changed from the earlier harness

The earlier harness judged another console's packages and could run a vtium build in their place. Here it judges vtium's install tree alone:

- **The build:** `make install-tree` in place of `make pkg` and `pkg-minimal` in a docker dev image. The package path (`pacman -U`, `--pkg-dir`, `--pkg-name`), the library commit checks, the image-helper probe in `setup`, `upstream.mk`'s comparison runs (`--compare-only`) and the stand-in tree are gone. A minspec variant needs no build of its own: the configuration selects the font.
- **The goldens:** all in `goldens/`, the copied ones and vtium's; the harness writes none: `tier3-bless` is gone.
- **The paths:** `target/tier3/` for the work directories, the report, the lock, the tree and the VM directory, whose `images` links to vtium's image cache, `T3_IMAGES`, from which tier 3 reads only the images vtium's scripts fetched and built.
- **The size:** the binary against `BINARY_BUDGET`, failing the run past it, in place of the main package's size against 1.77 MiB, which was reported and not judged.
- **The console:** a run fails unless the console logs itself as vtium.
- **The image:** `make tier3-image` fetches and verifies the pristine image with `fetch-image.sh` when the cache lacks it; the earlier harness had no rule that ran it.
- `tier3-gl` and `tier3-selftest` are folded into `make tier3 VARIANTS=gl-1280x800` and `make test-tools`.
