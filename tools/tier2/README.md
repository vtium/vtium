# tier2

Tier 2 for vtium: the renderer draws known screens into memory, and each is compared pixel for pixel with its golden (vtium/vtium#17). The bytes go through `vtium-term` and the frames through `vtium-render`, into a double-buffered display in memory. The goldens are the judge: a difference from a golden past its sidecar's tolerance fails the case.

The crate is a workspace member, so `cargo test --workspace` builds the tool and runs its self-tests. Every file the run reads is in this tree, and the goldens are in `goldens/`. The run stays out of the default test run, in a Makefile target that CI's `tier2` job runs on every pull request and whose report and images it keeps:

```
make tier2                       # every screen against its golden, after make tier2-fonts
make tier2-fonts                 # fetch the outline fonts into their cache
target/release/tier2 render      # draw every screen into out/render, judging nothing
target/release/tier2 compare GOLDEN ACTUAL [--tol FILE] [--diff OUT.ppm]
target/release/tier2 fetch-fonts # what make tier2-fonts runs
```

`run` takes `--out DIR` (default `out/` here, which git ignores). It writes each drawn screen to `out/actual/`, each difference to `out/diff/`, and the report to `out/report.json`, deleting any earlier report first. The report's `tools` names vtium's commit as `vtium`, `+dirty` with uncommitted changes, which `make tier2` passes in `T2_VTIUM_REV` as tier 3's report records it; a run started by hand records none. It exits 0 when every case passes, 1 when one does not, and 2 when it refuses to run. `compare` exits 0 on pass or near, 1 on fail and 2 on an input it refuses. Nothing here writes a golden.

## The screens

The goldens that were drawn first came from a renderer that used an outline font, DejaVu Sans Mono through FreeType, with Noto's CJK and color emoji fonts. Two of them judge vtium where no outline glyph shows: `blocks` and `blocks-spaced`, which hold only box-drawing and block sprites and spaces. They are drawn in a face that holds the space alone, in the cell DejaVu Sans Mono gave (9x16 at 16 pixels; 12x28 at 22 pixels with 6 rows of spacing), and a screen drawn that way is refused if any cell holds a character that is not a sprite or a space.

The outline screens draw text from a test font set (a frit, vtium's font set file) that names one open font for each script, in the frit's fallback order (ADR-1503 D9): DejaVu Sans Mono 2.37 with its Regular, Bold, Oblique and Bold Oblique faces, each named by `style=`, then Noto Sans CJK SC 2.004, then Noto Color Emoji 2.051. `src/fonts.rs` pins each font by its URL and SHA-256, and `make tier2-fonts` fetches them into `$XDG_CACHE_HOME/vtium/tier2/fonts` (or the directory `VTIUM_TIER2_FONTS` names) and checks each against its SHA-256; DejaVu Sans Mono's four faces come from its release archive, which is unpacked with `tar` and removed. No font is committed, and no font of the system's reaches tier 2. `make tier2` runs `make tier2-fonts` first, and an outline screen whose fonts are absent or not their pinned bytes is an `error` that names `make tier2-fonts`. CI's tier2 job caches the fonts under a key of `src/fonts.rs`.

An outline screen draws as the console draws a frit: through vtium's own face for a frit (`vtium::font::Chosen`), at 16 pixels, in the cell the frit's first source gives there, DejaVu Sans Mono's 9x16. Tier 2 reads what the screen shows in each style, bold, italic, both or neither, after its bytes and again after its second part, as the console reads its displays to ask the helper for glyphs; vtium-config's engine, the one the helper runs (ADR-1301 D2), generates those glyphs from the frit with the cache as its only font directory; and the console's store of generated glyphs holds them, as it holds the helper's answers. A character that no source of the frit holds draws in the built-in font, fitted to the cell, as the console draws it.

A screen tier 2 owes and cannot draw yet is listed in `pending.tsv` with what it waits for, and none is listed now. A screen whose drawing shows a defect is drawn by `screens::WAITING`, which `tier2 render` draws and `tier2 run` does not, so no golden records the defect, and it is listed in `pending.tsv` with the issue that owes the fix; when the fix lands, the screen moves to `screens::CASES`. A golden that no screen draws is `missing`, and fails. A screen that takes up a pending row adds its golden to `goldens/`, provisional until the maintainer reviews it, and the row goes.

## The judge

A case is compared with its golden exactly, outside any mask its sidecar gives. The comparison, its verdicts and its regions are tier 3's (`tools/tier3/t3img.py`), so the two tiers judge images one way. A sidecar `<name>.tol` beside a golden holds `max_delta=`, `max_pixels=` and `mask=x0,y0,x1,y1` lines, masks end-exclusive; no sidecar means exact.

| Status | When |
|---|---|
| `pass` | identical outside the masks |
| `near` | different within both of the sidecar's limits |
| `pending` | a screen `pending.tsv` lists |
| `provisional` | a golden in `provisional.tsv`, not yet reviewed: compared, and the status it would get noted, never failing |
| `fail` | different past the tolerance |
| `missing` | no golden, or a golden no screen draws |
| `error` | the screen did not draw, or its golden or sidecar was refused |

Each list is checked before any case runs: a pending row that a screen draws or whose golden `goldens/` holds, a provisional golden no screen draws, and two screens of one name are each refused.

Refused rather than judged: a PPM that is not P6 with a maxval of 255, with a side of 0 or past 16384, or with a raster shorter or longer than its header says; a sidecar line that is not `key=value`, an unknown or repeated key, a value that is not a decimal number, a `max_delta` past 255, one limit at 0 with the other not, and a mask that is empty, inverted or reaches past the golden. A mask that hides no difference is noted in the report.

## The GPU path

`run` judges each screen on the GPU path too, as the case `<screen>@gpu`, when tier 2 is built with its `gpu` feature, which `make tier2` turns on. It draws on Mesa's llvmpipe, through vtium-platform's software context and the binary's adapter (`vtium::gpu::PlatformGl`), and a run that cannot set llvmpipe up reports one `error` case and fails; CI's tier2 job installs Mesa's EGL and llvmpipe for it. A GPU case passes when its drawing equals the CPU path's, is `near` within its sidecar, fails past it, and is `pending`, with the reason, for a screen the GPU path does not draw yet; its drawing and difference go to `out/actual/` and `out/diff/` under the case's name. The GPU path is judged against the CPU path's drawing of the same screen, which the run judges exactly against the screen's golden (ADR-1303 D1, "How the GPU path is judged"). `src/gpu.rs` draws each screen as `draw` does, in every configuration that must draw the same bytes, through `Renderer::draw_gpu`: into two buffers the GL makes in memory, whose ages follow the swaps, a second part fed after two frames, and the console's overlay in a frame of its own after the last, as the GPU path takes it from the console. It reads the buffer shown last back and compares it with the CPU path's drawing within the GPU path's own sidecar, `gpu/<screen>.tol`; the golden's sidecar never judges the GPU path, and no mask hides a GPU difference. Each GPU sidecar is exact for now, `max_delta=0` and `max_pixels=0`: the maintainer decided on 2026-11-03 to judge the GPU path exactly while every screen it draws measures no difference from the CPU path's drawing on llvmpipe, as all 110 do, the twenty picture screens among them. A picture screen is judged a second time as `<screen>@gpu-copy`, with each picture at another size drawn from the CPU path's copy (ADR-1303 D2): that case reads no sidecar and is always judged exactly, since the copy step's textures hold the CPU path's pixels. A self-test holds each sidecar to that, so a sidecar that widens fails until the decision and the test change with it. The sidecars stay provisional: ADR-1303 proposed a starting tolerance of 1 level and 3 per cent of a screen's pixels for GPUs that round differently, and a GPU that needs it brings that question back to the maintainer.

The GPU path draws every orientation in color; a 1-bit screen waits for present's depth reduction, and `gpu::waits` says so. The console's overlay reaches the GPU path upright, in the text's view, as it takes it from the console: each area the CPU path's overlay covers is mapped back into the view (`Surface::view_area`), and each of its pixels read from the display pixel the CPU path turned it to (`Surface::place`). A self-test draws a notice and the focus mark at the three turns on llvmpipe, on the CPU path's pixels. The self-tests draw through the whole GPU path on the tests' stand-in GL, which draws nothing and reads back zeros, and see the comparison fail: the judge sees a GPU path that draws nothing.

## vtium's goldens

The goldens in `goldens/` are reviewed vtium output, kept byte for byte as the operator accepted them, which judge vtium as the copied goldens do; `goldens/README.md` gives who drew each and what it shows. No tool here draws a golden. A new screen's golden is vtium's output, lands in a commit of its own, and stays in `provisional.tsv` until the operator has reviewed it.

Moving a golden is a change to the judge: it lands in a commit of its own, with each moved value listed.

## Not yet

- **PNG.** Tier 3's goldens are PNG, which tier 3's own `t3img.py` reads; tier 2's compare reads PPM only, and reading PNG is its next step should it judge a tier 3 golden.
- **fbdev.** vtium draws fbdev's XRGB8888 framebuffer with the same renderer and the same pixels as drm2d; other layouts are converted by `vtium-platform`, whose tests hold the conversion (vtium/vtium#18).
- **The GPU path's ink past a cell.** The GPU path still cuts each glyph's ink at its own cell, so the GPU cases of the screens whose ink passes its cell fail until the GPU path composes ink as the CPU path does (ADR-1306 D9): `bold`, `combining`, `emoji-spaced-12` and the ink screens.
- **The GPU path's 1-bit screens.** `gpu::waits` keeps them pending until present reduces the depth (ADR-1301).
