# Architecture

vtium is a Cargo workspace. Each crate owns one responsibility, and the dependency arrows point one way: from the binary down to the terminal state and the platform.

```text
vtium (binary)
├── vtium-platform   displays (DRM/KMS, fbdev), VT, seat, input, pty, event loop
├── vtium-settings   the key table, vtium.conf's line syntax and editor, and the head file: its reader, parser, rules, guards and one writer
│   ├── vtium-font   the cell's largest side, for font-size's bound (constants only)
│   └── vtium-term   the scrollback's bounds and default (constants only)
├── vtium-render     frames to pixels: CPU compositor; GPU path behind a feature
│   ├── vtium-term   screen, cells, lines, scrollback, modes, SGR, replies
│   │   ├── vtium-parse   bytes to actions: the bounded escape-sequence parser
│   │   └── vtium-image   the image store, its rules, the handler trait, the decode types (feature `images`)
│   │       └── vtium-parse
│   └── vtium-font   glyphs: the built-in Unifont and Unscii-8, the glyph chunk format, sprites
└── vtium-image      (feature `images`; not used by the binary yet)

vtium-config (binary)   the font and settings tool and the glyph helper: every font decoder, the outline rasterizer and shaping
├── vtium-font
├── vtium-platform
└── vtium-settings
```

The tree is the workspace as built today. vtium-term takes vtium-image as an optional dependency, behind vtium-term's `images` feature. vtium-image depends on vtium-parse alone and names a line by an opaque key, so it never needs vtium-term (ADR-1100 D1, D10). The binary also lists vtium-image as an optional dependency, behind the binary's own `images` feature, and is to use it to send the image helper its requests and to work out the `auto` budget; no code in the binary uses it yet. Once a renderer draws placements, vtium-render is to reach the image types through vtium-term's frame. The minspec build links none of the image code.

vtium-config, the font and settings tool, is a binary of its own, which a user runs as `vtium config`: the console binary replaces itself with vtium-config and holds nothing of the tool but that hand-off (ADR-1201 D12). The install tree carries it beside the console, outside the console's binary and outside the minspec size budget, which judges the console alone. The console starts it as its glyph helper, which reads a frit's fonts and sends their glyphs to the console (ADR-1200), so the font decoders and the rasterizer stay out of the console.

Two crates may use `unsafe`: `vtium-platform`, for ioctls and FFI, and `vtium-image-helper`, in its one module `src/fork.rs`, which forks the helper's worker (ADR-1101 D1). Both carry `#![deny(unsafe_code)]` and allow it at each site, with a SAFETY comment. Every other crate's library carries `#![forbid(unsafe_code)]`, and the programs' own entry points, the `main.rs` of `vtium`, `vtium-config` and `vtium-image-helper`, use no `unsafe`.

`vtium-settings` holds the key table, every key and command-line option vtium reads with its type, default, bound and description, which the console reads its configuration by and vtium-config shows and edits it by (ADR-1201 D1), and the one reading of a vtium.conf line, which the console's reader and vtium-config's line-by-line editor share. It takes only constants from vtium-font and vtium-term, the bounds and defaults the table states. It also parses and evaluates the head file of [ADR-1401](architecture/platform/ADR-1401-heads-a-terminal-per-physical-display-placed-by-a-first-match-ruleset.md): its heads, its rules and the guards. `vtium` links it, and `vtium check-config` runs the same parser and evaluator, so a file checked before it is installed gets the verdict it gets at boot. `vtiumctl` will link it too once it is built. Profiles have no file of their own yet.

`vtium-platform` makes its syscalls through rustix (vtium/vtium#6), with one kind of exception: vtium calls libc where rustix has no call. Five files do, `src/fds.rs` (`close_range` and `fcntl` to mark descriptors close-on-exec), `src/rt_signal.rs` (the signalfd, the signal set and mask, `pidfd_send_signal` and `pthread_kill`, because rustix has no safe call for real-time signals), `src/power.rs` (the `kill` that signals PID 1), `src/image_helper/start.rs` (`dup2` onto descriptor 3, the ids it reads, `prctl` to drop capabilities, `close_range` and a pidfd signal to the helper's process group) and `src/image_helper/identity.rs` (the password and group database lookups and the process's real, effective and saved ids). `src/logind.rs` and `src/image_helper/login.rs` also declare `extern "C"` blocks for the sd-bus and sd-login functions of libsystemd or libelogind, and `login.rs` calls libc's `free` on what they return. DRM's ioctls go through `drm-ffi`, keys through libxkbcommon and the device monitor through libudev, the C libraries at the crate's boundary. With the `gpu` feature, `src/gpu/` opens two more when a GL context or a GBM device is made and links neither: libEGL as `libEGL.so.1`, through khronos-egl's `dynamic` feature, and libgbm as `libgbm.so.1`, through libloading; GL itself is reached through the function table glow loads from EGL. Its `unsafe` sites are the ioctls rustix does not wrap, in `src/ioctl.rs` with a test that each request number equals the kernel header's, and the console font's in `src/vt/font.rs`; the mmap of a framebuffer in `src/mmap.rs`; the close-on-exec marking in `src/fds.rs`; the real-time signals' set, mask, signalfd and `pidfd_send_signal` in `src/rt_signal.rs`; power-off's kill in `src/power.rs`; the pre-exec hooks of the pty child and the suspend shell, which make only raw syscalls (both reset every signal's disposition and clear the signal mask, and the pty child's makes it a session leader with the pty as its controlling terminal); and, with `gpu`, the GL, EGL and GBM calls in `src/gpu/`: libEGL and libgbm opened and their functions taken by name, GBM's device and buffers and their queries, EGL's displays, context, dma-buf images and device queries, GL functions glow lacks loaded by name, and every GL call of the safe GL type `Context`, which checks what keeps each sound by itself. The crate's README lists them. C stays at that boundary, and libseat (vtium/vtium#34) will join it there. The crate denies `unsafe_code`, so each site carries an `#[expect]` with its reason.

The console starts its children, the session on the pty and the power keys' suspend shell, only from its one thread, marking every inherited descriptor close-on-exec just before the fork (vtium/vtium#133); a new thread that opens descriptors must revisit that call, which a descriptor opened between the marking and the fork would pass.

## The minspec build

The default build is minspec: the smallest complete console. It covers drm2d or fbdev, the CPU renderer, bitmap fonts, the parser and screen, the pty and keyboard input. Images, outline fonts and the GPU path are features added on top. `cargo build --profile minspec` builds it size-optimised, and `make minspec` links the binary with packed relative relocations (DT_RELR), which needs glibc 2.36 at run time (vtium/vtium#143) and binutils 2.38 at build. Tier 3 measures its size and memory on every run, and fails a run whose binary is over its budget, 3,670,016 bytes ([tools/tier3/README.md](https://github.com/vtium/vtium/blob/main/tools/tier3/README.md)).

The machine minspec is judged against is a single-board computer that presents a DRM buffer (vtium/vtium#75):

- ARM cores, Cortex-A53 class or older, aarch64 and armv7;
- 512 MB of memory or less;
- a DRM dumb buffer to draw into, with no GPU vtium uses;
- displays that may be small, down to SPI panels through tinydrm.

The display floor is a 320x240 panel with an 8x8 font, a 40 by 30 grid. There vtium starts, draws and stays correct, and a shell, line editing and vim are usable; a program that needs 80 columns is not promised to fit. At 640x480 with an 8x16 font, 80 by 30, everything vtium supports is usable. The 8x8 font is the built-in Unscii-8, which draws every cell under 16 pixels high (ADR-1200 D7).

Tier 3's x86 variant keeps the small-machine standard: 1366x768, 1 vCPU, 512 MB.

`make arm` builds the minspec profile for `aarch64-unknown-linux-gnu` and `armv7-unknown-linux-gnueabihf`, and `make arm-test` runs the workspace's tests on aarch64 under qemu-user, with no cross toolchain and no root ([tools/arm/README.md](https://github.com/vtium/vtium/blob/main/tools/arm/README.md)).

## Other terminals

ADR-1000's tables hold, for every mode and feature, a column for each of several other terminals, among them xterm, foot, Ghostty, WezTerm and kitty, filled where that terminal's behaviour was verified. vtium reads the code of permissively licensed implementations and names the source of anything it adapts. For a GPL-licensed terminal it reads only documentation and specifications, and may run the program to compare its screens. [CONTRIBUTING.md](https://github.com/vtium/vtium/blob/main/CONTRIBUTING.md) states the rule for kitty: "Implement from published protocol specifications and from permissively licensed implementations such as Ghostty, WezTerm, foot and libsixel. kitty is GPL-3.0, and its source is not read while working on vtium, by a person or by an agent. kitty as a running program may be used for black-box comparison." The rule keeps vtium's code under the MIT licence, so that anyone can use it.

## How it is judged

By vtium's harness, in tiers:

- **Unit tests** in each crate, run by `cargo test`.
- **Conformance:** byte streams in, screen state and replies out, compared with reviewed goldens. They cover the parser and terminal state with no display.
- **Capability probes:** each capability vtium claims has a probe that fails when the capability is missing, judged against the capability list (below).
- **Pixel tests (tier 2):** the renderer draws known screens, compared pixel for pixel with goldens.
- **VM runs (tier 3):** vtium's install tree boots on a VT of a QEMU/KVM guest with a real KMS device, keys are typed into it, and its screenshots are compared pixel for pixel with goldens, including a minspec variant on the small-machine standard, which also records the size and memory figures that [features.md](features.md#small-machines) lists. That run, `make tier3-minimal` at `c107f9a` on 2026-11-01, gave 47 passes, 28 listed departures and 16 cases against provisional goldens, with no failure. Pictures have their own variant, `images-640x480`, which builds the tree with the `images` feature and runs only when named (`make tier3-images`); it judges them against vtium's own goldens, which are provisional. Tier 3 boots two pinned guests: Arch Linux from the archive snapshot of 2026-10-20, with systemd, and Debian 13 with sysvinit ([tools/tier3/README.md](https://github.com/vtium/vtium/blob/main/tools/tier3/README.md)).
- **Fuzzing:** `make fuzz` runs each crate's fuzz targets for 60 seconds, or `FUZZ_TIME=N`, and appends a row for each target to that crate's `fuzz/runs.tsv`. It needs nightly Rust and cargo-fuzz. Fuzzing is not a gate.
- **VT review:** the maintainer judges a build by eye on a real VT, guided step by step, started only by the steering session ([vt-review.md](vt-review.md)).

Work is built in bundles of items that don't collide, then evaluated once per bundle.

## Determinism

The screen, the scrollback, the modes, the cursor, the image store and the replies follow from the bytes a program sends, with time entering only at the places named below.

| Rule | The check that fails when it breaks |
|---|---|
| **Chunking invariance.** The state after a byte stream does not depend on how the stream was split or how fast it came. The input work bound (a fixed pixel count per input call) and the pause while an image decodes change when work is done, never what state results. | A property test feeds each stream whole and cut at random points, mid-UTF-8, mid-sequence, at the work bound and across a pause, and compares the full state and the reply bytes. The streams come from a grammar-aware generator and from raw random bytes, and a failure prints its seed. |
| **Bounds.** Every resource has a bound. The parser's are in `vtium-parse`'s bounds table; the image store's, the scrollback's and the replies' are rows of their own crates' bounds tables, added with those crates. Input past a bound gives the state its row describes. | A flood past each row of a bounds table gives that row's state. |
| **A lazy rewrap matches an eager one inside the scrollback's byte budget.** A width change leaves the oldest scrollback rows waiting, and inside `sb-memory` they rewrap to what rewrapping at once gives. Past it, the rows dropped follow what each costs as held, waiting or rewrapped, so a lazy and an eager rewrap may keep different oldest lines; the byte count is exact either way (ADR-1003's note of vtium/vtium#131). | `reflow_is_the_same_chunked_and_lazy_or_eager` and `the_byte_budget_holds_through_resizes_and_its_count_is_exact` (`crates/vtium-term/tests/reflow.rs`). |
| **Eviction follows the bytes.** The image store evicts by rank, then by a per-store use clock that only stream events advance (a transmission, a placement, or a command that names an existing image, such as a kitty put or query by id; ADR-1100 D5), and placed kitty images oldest transmission first. A reservation that cannot fit is refused before anything is evicted. A sixel placed on the screen's own lines is never evicted, so a store full of them refuses. | The flood test fed whole and chunked ends in the same store, with frames drawn at different points. |
| **Time enters in named places only.** A decode the helper does not finish in 2 seconds (the timer is held in `vtium-platform`) gets the `FAILED` reply, the helper is stopped and the next request starts a new one, and input stays paused until either outcome, so no input reorders around it. Mode 2026's timeout, held in `vtium-platform`, changes when a frame shows, never the state behind it. The conformance runner's fixture host answers synchronously, so no case depends on time, and the chunking test runs against it. The binary's respawn limit, 5 quick restarts within 2 seconds, is given each exit's time from the monotonic clock, which the event loop reads; it decides only whether the session's command starts again, never the terminal's state. The binary's animation clock (`crates/vtium/src/animation.rs`, ADR-1102) is given the monotonic time at each turn of the event loop and picks the frame each animated picture shows; it changes what a display draws, never the image store, which records only the commands a program sent, so a replay prints the same store however long its stream took to arrive. | `clippy::disallowed_methods` denies `Instant::now`, `SystemTime::now` and `thread::sleep`. The list lives in the workspace `clippy.toml`; `vtium-platform` and `vtium-render`, which hold the timers, allow the lint, and the eviction test guards the render timer's effect on state. The respawn policy (`crates/vtium/src/respawn.rs`) and the animation clock take the time as an argument, and their tests pass the times in. |
| **Placement follows each device** (ADR-1401 D11). The head, roaming, ignore or off a display or an input reaches depends only on its own identity and the head file's rules, never on the order devices are reported or on when one is plugged in; the guards read the set of devices present, never their order. | `each_device_lands_the_same_in_every_report_order` (`crates/vtium-settings/tests/determinism.rs`) walks seeded generated devices through generated rulesets in every report order and at every hotplug point and compares where each lands; a failure prints its seed. |
| **No order from a hash.** std's `HashMap` iterates in a randomised order, so nothing that reaches the screen, a reply or eviction iterates one. | `clippy::disallowed_types` denies `HashMap` and `HashSet`, listed in the workspace `clippy.toml`. `vtium-platform` and the binary allow it where no order reaches state. |
| **No input-reachable panic.** Arithmetic, casts and indexing on program-controlled values are checked, saturating or explicitly wrapping, and nothing unwraps. | `arithmetic_side_effects`, `cast_possible_truncation`, `cast_possible_wrap`, `cast_sign_loss`, `indexing_slicing`, `unwrap_used`, `expect_used`, `panic`, `unreachable` and `todo` are denied in the `lib.rs` of `vtium-parse`, `vtium-term`, `vtium-image` and `vtium-render`; CI runs clippy with warnings denied. An allowed site carries `#[expect(..., reason = "...")]`. Tests and fuzzing build with overflow checks. |
| **No reflection.** A reply is built only from vtium's state, fixed strings, and values it parses and re-encodes: numbers, a selector from a fixed set (such as the BEL or ST that ended the query), and hex. It never contains raw request bytes or text stored from the stream, so injected sequences can rewrite the screen but cannot type into the program reading the replies. An XTGETTCAP name is printed in uppercase hex from the matched table entry. Title reporting answers with a fixed empty title, and OSC 52 reads stay off. | A test sends every query vtium answers with a random token in each field it accepts, and fails if any reply contains the token or any substring of the injected text of 4 bytes or more. It also pins each reply's exact bytes for a fixed-state fixture. The list of queries is generated from the code that writes replies, so a new reply cannot escape it. Title reporting after a hostile OSC 0 or 2 gives the fixed empty title, and an OSC 52 query gives no reply. |

The release and minspec profiles set `panic = "abort"`, so any panic ends the console. They leave overflow checks off: a missed overflow then wraps, which is defined behaviour, and the lints and fuzzing are what find it.

## Tables, references and maps

A fact vtium states in more than one place has one source. Where a test can be written, the other places are generated from the source or checked against it, and the test fails on drift. The coverage map and the path tables are kept by hand, in the change that alters what they describe.

| Source | What is generated or checked | The test fails when |
|---|---|---|
| The mode table in `vtium-term`: one row per ANSI or DEC private mode vtium recognises, with kind, number, name, status (supported, partial, ignored, refused), default (fixed or a host setting), reset, what the host must do, terminfo, spec and tests | The dispatch's and the resets' calls into each mode's accessors, and the DECRQM replies; `docs/modes.md` and `docs/modes.tsv`, describing the build with `images` | The committed `docs/modes.md` or `.tsv` differs from the table; a number with no row (DEC 0-65535, ANSI 0-255) gets a DECRQM reply other than 0, or SM and RM of it change any of the terminal's state (cell contents, tab stops and image state included); a number with a row replies 0; SM, RM or DECRQM do anything but expand the table; a mode's state is reachable outside its accessors, which vtium enforces with module privacy; a supported mode's row names no test that sets and resets it, or names a test that does not exist |
| The parser's bounds: rows in `vtium-parse`'s `src/bounds.rs`, from which its constants take their values | The bounds table in the crate's README | The committed table differs from the rows |
| The capability list: each probe `works` or `missing`, with the issue for each gap; a `works` probe may name the feature it needs | The probe verdicts | A `works` probe fails, or fails to fail without its feature; a `missing` probe passes; a probe is not in the list, or the list names one that does not exist |
| The key table, `crates/vtium-settings/src/keys.rs`, which the binary reads its configuration by: one row per configuration key and command-line option, with its type, default, bound, the crate that reads it and its source | `docs/config.md` and the installed example, `crates/vtium/install/vtium.conf.example` | Either committed file differs from the table |
| The commented template of the head file, `crates/vtium-settings/templates/heads.conf` (ADR-1401); the default profile's and the default frit's templates are not built yet | vtium's compiled-in configuration, parsed from it; once they are built, the files `vtiumctl template` writes and the generated copies the source tree carries for cross-built images | The compiled-in configuration differs from the template's parse (`the_compiled_in_configuration_is_the_parse_of_the_template`, `crates/vtium-settings/tests/template.rs`) |
| The terminfo entry | The XTGETTCAP table | The committed table differs from the entry |
| The conformance list of expected differences: each case where vtium's output differs from its golden on purpose, with its reason, the specification vtium follows and vtium's expected output | The conformance runner's expected output | A case differs from its golden and is not listed, or a listed case matches the golden |

The coverage map lists each feature vtium builds, the tests that guard it and the paths they reach (font, renderer, display), and the issue for each gap. A gap is closed by a light test in the same change or filed.

Every directory of tests or data carries a README with a table of what each path is.
