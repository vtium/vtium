# ADR-1101: The image helper is its own sandboxed program, run as the session's user

## Summary

- **Decided:** The image helper is its own program, `/usr/bin/vtium-image`. It reads the files and shared-memory objects a program names, and decodes PNG, zlib and the formats iTerm2's pictures arrive in, for the console, which runs as root and does neither (ADR-1100 D7). vtium opens the program once when it starts and starts every helper from that open file, the way it starts the font helper. The helper runs as the session's user: the user of the login's own logind session where logind runs, otherwise the owner of the session's pty, and never root by fallback. Before anyone logs in, file media are refused, and pictures sent inline decode as `vtium-image`, an account the package creates, or else as `nobody`. The helper starts with an empty environment, no new privileges, no capabilities, a memory cap, a cap on the size of any file it writes and only its socket, and installs a seccomp filter, a short list of the system calls it may make, which answers any other call with ENOSYS. For a one-off request it forks a worker, which opens what the request names under the file rules and then locks itself in with landlock, so it can open nothing more while it decodes. When a console sends a stream of inline pictures of the same format and size, as a program re-sending video frames does, the helper keeps one long-lived worker for the stream, locked in and filtered as a one-off worker is, which writes each frame into one of two reply files the helper keeps in memory for the stream; the maintainer chose it after a measurement on real streams. Requests and replies are single packets on a socket pair, and pixels come back premultiplied, in the store's one format, in memory files sealed against change; the files a stream's pool reuses are sealed against shrinking and growing only. A request not answered in 2 seconds fails and the helper is killed. Three crashes stop image decoding on that console until its session ends. A shared-memory object is removed only when the session's user owns it, which is the protection, and only after a valid picture was read from it. Every decoder is pure Rust and linked into the helper only.
- **Trades away:** A fork for each one-off request, which costs a fraction of a millisecond on a desktop and more on a small board. A frame a hostile program crafts inside a stream of inline frames can reach the later frames of that stream on that console, which the maintainer accepted. A list of system calls that must be kept right as the decoders, the Rust standard library and the C library change, guarded by a gate. Three crashes, which a hostile stream can cause on purpose, stop that console's pictures that need the helper until its session ends. A shared-memory object that holds no valid picture stays in `/dev/shm`, which the kitty spec does not allow. A logged-in root's helper runs as root, as ADR-1400 decided, where the font helper refuses root. The helper crate holds `unsafe` in one module, where every vtium crate but vtium-platform forbids it. The 32-bit ARM helper runs without seccomp.
- **One-way?** No. Both ends of the wire come from one build, and a running console starts only the helper it opened, so the wire changes in one release. The pre-login account's name becomes expensive to change once packages create it on machines.
- **Probes:**
  - *Not confident (crash limit):* after the image helper crashes three times, vtium stops decoding files, PNG and compressed pictures until the machine restarts, so a hostile file shown three times cannot keep retrying against the decoder. Sixel and raw kitty pictures keep working. Is a stop for the whole boot what you want, rather than until that console's session ends?
  - *Not confident (stream variants):* for a program re-sending video frames, the record measures three ways and lets the numbers decide: a fresh worker and fresh memory each frame; a fresh worker each frame writing into memory kept ready; or one long-lived worker per stream. If the second comes within a quarter of the third's time per frame, vtium takes the second, which keeps each picture's decoder apart from the next. Is a quarter the margin you want?
  - *Confident (a worker per request):* the helper forks a fresh worker for each picture, which locks itself to the one file that picture names, because a process locked by landlock can never open the next picture's file. Yes or no?
  - *Not confident (armv7):* `seccompiler`, the crate that builds the filter, has no 32-bit ARM target, so on the armv7 build the helper runs with landlock and the rest of its sandbox but no seccomp filter, and logs that once. The other way is a filter of vtium's own for 32-bit ARM. Is landlock alone on armv7 acceptable?
- **Inversion:** Between "the console reads and decodes everything itself, as root" and "every picture in a newly started, separately sandboxed program". The answer keeps one long-lived helper per console, started from the program vtium opened, and narrows each picture's work to a worker that can reach only that picture's file.

## Context

ADR-1100 D7 sends PNG, zlib, files, temporary files, shared memory and iTerm2's formats to an image helper, so the console, which runs as root, never opens a file a program names and never decodes a format whose decoder faces a program's bytes. ADR-1400 D2 carries the C reference's helper forward and left four questions to the helper's own record: whether it is a second program or vtium itself, the pre-login account's name, whether seccomp or landlock narrows it, and what to do about the removal of shared-memory objects that any program writing to the terminal can ask for. ADR-1100 D12 says the helper "needs its own record, which decides its sandbox". The maintainer decided all four on 2026-11-01.

The C reference built this helper in kmscon ADR-103's step 4b as `kmscon-image-helper`, a separate program running as the session's user, with libpng and zlib. Its open questions were a filter, which it never built, and a list of residuals from its security review. Nothing of vtium's helper exists yet. The font helper, `vtium-vitrify serve` (ADR-1200 D15), already shows the pattern: a separate program the console starts, sandboxed, with an empty environment and its own process group, checked, never trusted, and restarted a bounded number of times.

## Decision

Terms used below: a *request* is what the console asks the helper for one picture (ADR-1100 D7's request type); the *session's user* is the account that logged in on the console; *file media* are the files, temporary files and shared-memory objects a kitty command names (`t=f`, `t=t` and `t=s`); *inline media* are the bytes a program sends inside the escape sequence itself.

### D1: the program, and how vtium starts it

- **Its own program.** The helper is `vtium-image`, built from a crate of its own, `crates/vtium-image-helper`, and installed as `/usr/bin/vtium-image` unless vtium was built with another path, as the font helper's path is chosen when vtium is built. The helper links the decoders of D6; the console links none of them (ADR-1100 D7). The minspec build installs no helper.
- **`unsafe` in one module.** The helper forks a worker for each request (D4), and every Rust binding of `fork` is `unsafe`, since a forked child of a process may call only what is safe after a fork. The crate therefore forbids `unsafe` everywhere but one module, which holds the fork and the code the child runs before it returns to safe Rust, and which a reviewer of any change to it audits line by line. Nothing in the helper maps memory itself: it reads with `read` and `pread` and writes the reply with `pwrite` (D7), so the module needs no `mmap`. The rest of the crate reaches the kernel through `rustix` and the crates of D9.
- **Started from the program vtium opened at start.** The `image-helper` key names the program, `/usr/bin/vtium-image` by default, as the `font-helper` key names the font helper's (the maintainer, 2026-11-01). vtium opens the program once when it starts, checks the file it opened, and starts every image helper from that open file, through `/proc/self/fd`, the way it starts the font helper. A package upgrade replaces the program by renaming a new file into place, so the open file stays the old program, and a running console keeps starting the helper it was built with. An old console therefore never talks to a new helper, and a fix to the helper reaches a console when the console starts again (the maintainer, 2026-11-01). Both helpers start the same way so that one rule, and one requirement that `/proc` is mounted, covers both; the helper needs `/proc` for its file rules in any case (D5).
- **Refused unless only root can change it.** vtium refuses a program path that is not absolute, a file that is not a regular file, a file owned by an account other than root or the account vtium runs as, a file that its group or others may write, and a file that is setuid or setgid, the font helper's rules. A program that is missing or refused is logged once, and every request answers as ADR-1100 D7's "Without a helper" says: file media EBADF, PNG and zlib EINVAL.

### D2: whose account the helper runs as

vtium finds the session's user again before each request, and stops a running helper whose account differs, as when one user logs out and another logs in. The rules are the C reference's, which ADR-1400 D2 carried forward:

| Situation | File media | Inline PNG and zlib |
|---|---|---|
| vtium built with `logind`, logind running, and the login child in a logind session of its own whose class is a login: `user`, `user-early`, `user-light` or `user-early-light` | read as that session's user, root included | decoded as that session's user |
| logind running, and the login child in no session of its own: the login prompt, a command vtium started without a login, a session the child shares with vtium itself, or any lookup that fails | refused with EBADF, and no helper is started | decoded as `vtium-image`, else as `nobody`, else refused |
| vtium built without `logind`, or no logind running | read as the owner of the session's pty, as `login` sets it; refused when that owner is root | decoded as the pty's owner; when that owner is root, as `vtium-image`, else as `nobody`, else refused |

- **Whether logind runs.** vtium asks sd-login how many seats exist: more than none means logind runs, none means it does not, and an error counts as running, so an unknown state refuses files rather than reading them. A host without systemd but with elogind answers the same way through libelogind (`docs/systemd.md`). A build without the `logind` feature, which links neither library, always takes the pty's owner, as ADR-1400 records.
- **logind first.** logind's answer is the identity PAM authenticated. The pty's owner is file metadata that any root process in the session can change, so where the two disagree vtium logs it and uses logind's.
- **Root.** A root login that logind authenticated runs its helper as root, as ADR-1400 D2 decided and the C reference did; the font helper refuses root, and the image helper does not, so that root's own programs can show root's own files. It holds no capability (D3), so it reads a file only where the file's permission bits let uid 0 read it, as any other account reads. The filters of D9 hold a root helper as they hold any other. The pty's owner being root is never enough: that is the login prompt on a host without logind.
- **vtium not running as root.** A vtium started as an ordinary user can start a helper only as itself. It starts one only when the session's user is vtium's own user, with every user and group id set to vtium's, and otherwise refuses file media and inline media alike, since it cannot start a helper as anyone else, as the C reference refused them. A vtium not running as root that holds group 0 in any form, real, effective, saved or supplementary, refuses every request the same way. One function makes that check, and it reads vtium's group list at the size `getgroups` reports, where the C reference checked in two places and treated more than 256 groups as holding group 0.
- **The pre-login account.** `vtium-image` has home `/`, no login shell and no files, and runs with its primary group only. The package installs a sysusers file, `vtium-image.conf`, from which `systemd-sysusers` creates it. A host without `systemd-sysusers` has no such account unless a package script or the administrator creates one, and the helper then runs as `nobody`, which works but shares its account with NFS root squashing and with daemons that run as `nobody`. An account that resolves to uid 0 or gid 0 is passed over for the next. vtium looks the accounts up once, the first time it needs one, and remembers the answer, missing accounts included, so a slow name service cannot stall the login prompt on every picture; an account created later takes effect when vtium starts again.
- **Before login nothing is removed.** A temporary file or shared-memory object named at the login prompt stays where it is, since no helper may remove a file before anyone has logged in.

### D3: how the console starts the helper

vtium-platform starts the helper in the C reference's order. The console resolves the account, its primary group and its supplementary groups in its own process before it forks, since a child forked from a process with threads may call only functions that are safe after a fork. The child then:

1. starts a session of its own with no controlling terminal (`setsid`), so the helper cannot reach the terminal vtium was started from;
2. clears its signal mask;
3. puts `/dev/null` on descriptors 0, 1 and 2, its end of the socket on descriptor 3, and closes every other descriptor except the open program file, which stays open, marked close-on-exec, so the start in step 7 can name it and the helper never holds it;
4. sets its memory cap, `RLIMIT_AS`, to three times the request's `max_bytes` plus 64 MiB, room for what it reads, an inflated copy and the decoded picture; the largest file it may write, `RLIMIT_FSIZE`, to `max_bytes` plus the request's `max_frame_bytes` (D7), which is 0 unless the request asks for a GIF's frames, which bounds each memory file it fills, since the memory cap counts only the memory a process maps and not a memory file's pages; a core size of 0; and the descriptors it may hold, `RLIMIT_NOFILE`, soft and hard, to 64, where the helper holds about a dozen at its busiest, which no process of the helper can raise without `CAP_SYS_RESOURCE`, and which the filter of D9 keeps it from setting;
5. sets its supplementary groups, then its group ids, then its user ids, real, effective and saved, and reads them back, ending at once on any mismatch;
6. drops every capability and sets no-new-privileges: before step 5 it removes each capability from its bounding set, which a vtium running as root can do and an unprivileged vtium has no need to, and after step 5 it clears its permitted, effective, inheritable and ambient sets. A logged-in root's helper therefore starts as uid 0 with no capability, and the empty bounding set keeps the start in step 7 from granting it any, as a start as uid 0 otherwise does;
7. changes to `/` and starts the helper from the open program file, through `/proc/self/fd`, with an empty environment.

The file-size cap bounds each memory file, and workers can make neither a memory file nor a socket (D9), so a worker taken over can fill only the reply file it was handed and the send buffer of its channel to the helper, beyond the memory its memory cap counts. The helper parent makes one reply file for each request and the stream's two pooled files. Nothing but its descriptor limit bounds how many memory files a helper parent that was itself taken over could make; the parent reads no picture's bytes, only vtium's requests and its workers' outcomes.

The helper runs in its own process group, which vtium kills whole (D8), and vtium holds a pidfd for it from the start, so it never signals a process it has already reaped. vtium's own `TMPDIR`, which the temporary-file rule of D5 needs, reaches the helper as an argument, so its environment stays empty, where the C reference passed `TMPDIR` as its only environment variable.

### D4: one helper per console, and a worker per request

- **Its life.** Each console has at most one helper, started at the console's first request that needs it. One request is out at a time (ADR-1100 D7). The helper exits after the idle interval ADR-1301 D2 sets with no request, and vtium stops it when the console's session ends, when the session's user changes, when a request's `max_bytes` is larger than the one its memory cap was set from or its `max_bytes` and `max_frame_bytes` together are larger than the sum its file-size cap was set from, and on a failure (D8). The next request starts a new one.
- **How the helper talks to a worker.** Before it forks a worker, the helper makes a Unix socket pair of the sequenced-packet kind for it. For each request, the helper makes the reply's memory file itself, or takes one from a stream's pool (below), and sends the worker over the pair the request, its inline memory file where it has one, and the reply's memory file. The worker sizes a fresh reply file, writes it with `pwrite` and seals it against shrinking, growing and writing, or writes a pooled one with `pwrite`, which its seals against shrinking and growing still allow (D7), and answers on the pair with the outcome, the width and height, the bytes ignored, the reason, and, for a shared-memory object, the device and inode it read. The helper sends vtium the reply (D7), removes a shared-memory object that held a valid picture (D5), and takes the next request.
- **A one-off worker for each request.** For a request that is not part of a stream, the helper forks a worker that handles that request alone: the worker adds a second seccomp filter that refuses forking and making memory files (D9), so it can start no process of its own whatever its account, opens what the request names under the file rules (D5), removes a temporary file that must be removed, locks itself in with landlock (D9), reads, inflates or decodes, answers, and exits. A landlock domain only ever narrows, so a process locked to one request's file could never open the next one's; a fresh worker for each such request is what lets each picture's decoder reach only that picture's file.
- **A stream of frames.** Programs that play video by re-sending a picture for each frame, as timg, ncplayer and mpv do, send pictures of one format and one size, one after another. The helper calls it a *stream* once `STREAM_AFTER`, 3, inline requests from the console in a row carry the same flags and the same picture size: for raw pixels compressed with zlib, the same pixel description; for PNG and ADR-1103's formats, the same width and height the earlier replies decoded. It counts requests, never time. Only inline frames make a stream. A frame from a file, a temporary file or shared memory takes a fresh worker and a fresh reply file, as a one-off request does, since a stream worker cannot open it and the measurement below found no gain in reusing reply files for such frames. The helper parent never parses a frame, so it cannot see a PNG's or an ADR-1103 file's size before a worker decodes it. When a frame in a stream decodes to another size, the stream worker reports the mismatch and writes nothing, the stream ends, and the helper runs the request again as a one-off, with a fresh worker and a fresh reply file. That is safe because an inline frame's memory file is sealed, so the second run decodes the same bytes the first one read. A stream ends on the first request that does not match, on any outcome but a picture, when `STREAM_IDLE_MS`, starting at 1,000 ms, passes with no request on the helper's existing idle timer, or on a crash, which counts toward the console's limit of D8.
- **The stream worker** (the maintainer, 2026-11-02). When a stream starts, the helper makes `REPLY_POOL_FILES`, 2, reply memory files of the stream's reply size, faulted in once, and forks one long-lived *stream worker* for the console's stream, which serves every later frame that matches. The pool's size comes from the width and height a worker reported, so the helper makes the pool only when that width and height are within the request's largest and width × height × 4 is within its `max_bytes`; otherwise the frames go on as one-off requests. The stream worker sets itself up as a one-off worker does, with the second seccomp filter and a landlock domain that grants no filesystem rights, which it enters before it reads anything, so it can open no file at all. For each frame, the helper sends it the request, the frame's inline memory file and the next pooled file; it writes the pixels into the pooled file with `pwrite` (D7) and answers. It keeps its memory from frame to frame, so it does not fault in fresh memory for its decoder on each frame. When the stream ends, the helper closes their channel, and the stream worker exits and is reaped; a stream worker that does not exit holds the helper until vtium's timer stops it (D8). A hostile frame can reach the later frames of the same stream on that console. The helper cannot tell one program from another, so any program in that console's session whose frames match continues the stream, not only the program that sent the hostile frame. The maintainer accepted that a hostile frame reaches its stream's later frames: "if someone wants to break the parser, that's on them" (2026-11-02).
- **What a frame costs.** The fork of a worker from the small helper costs about 0.1 ms. What a fresh worker pays for each frame is mostly fresh memory: a new reply memory file of about 33 MB at 3840x2160 takes about 8,000 page faults as it is written, and the decoder rebuilds its buffers.
- **The measurement.** The helper's work item measured three ways to serve a stream on 2026-11-02, on the maintainer's desktop, an AMD Ryzen 9 9950X3D on Linux 7.2: (1) a fresh worker with a fresh reply file for each frame; (2) a fresh worker for each frame, writing into a pooled reply file; and (3) the stream worker. Each frame ran the real request path under the worker's filters and landlock domain. Against the stream worker, a fresh worker for each frame writing into the pool cost 12% more a frame on 1366x768 frames of raw 32-bit pixels compressed with zlib (`f=32,o=z`), 23 to 26% more on 1366x768 inline PNG frames, and 3 to 4% more at 7680x2160. On raw 32-bit frames from shared memory (`t=s,f=32`) at 7680x2160, a fresh worker took 39.02 ms a frame writing into the pool and 35.35 ms writing a fresh file, so frames from shared memory and files take (1). The maintainer chose (3) for inline frames. Inline uncompressed raw frames never reach the helper, since the console's handler decodes them itself (ADR-1100 D7). Tier 3's guest and the ARM board the `arm-native` CI job runs on are not measured yet. `STREAM_AFTER`, `STREAM_IDLE_MS` and `REPLY_POOL_FILES` are named constants of the helper crate.
- **A crash ends the helper.** A worker, one-off or stream, shares its helper's address layout, so a worker killed by a signal makes the helper exit, and the next request starts a new helper from the program, whose layout is chosen afresh. D8 counts these crashes.

### D5: the file rules

These are the C reference's rules, which follow the kitty spec, except where this section says otherwise.

- **Where a file may be.** The path is resolved first, following symlinks and failing on a loop, as the spec asks. A resolved path in `/proc`, `/sys`, or `/dev` other than `/dev/shm`, is refused before anything is opened, since merely opening a file can have side effects.
- **Only a regular file is opened.** The worker opens the resolved path as a path-only descriptor through `openat2` with symlinks refused, which opens nothing; `fstat` on it must show a regular file, and `fstatfs` must show no kernel pseudo-filesystem wherever it is mounted: procfs, sysfs, debugfs, tracefs, securityfs, cgroup, devpts, configfs, bpf, pstore, efivarfs, the security modules' filesystems, binfmt_misc, nsfs, anonymous inodes, usbfs and rpc_pipefs. Only then does it open the file itself, read-only, without making it a controlling terminal and without blocking, through `/proc/self/fd`, and the device and inode must match the path-only descriptor's. A FIFO or a device is therefore never opened. The path of the opened descriptor must pass the location check again, which catches a symlink swapped in after the first check.
- **How much is read.** The request's offset and most bytes (kitty's `O` and `S`) bound the read: from the offset to the lesser of the offset plus the most and the file's end, or to the end when the most is 0. An offset at or past the end, or a read shorter than the picture needs, is a failure to read. Bytes past what the picture needs are not read.
- **One answer for every failure to read.** A missing file, an unreadable one, one that is not regular, one in a refused place and one too short all answer `UNREADABLE`, which the kitty handler answers `EBADF:Failed to read image file`, as the spec requires, so a program learns nothing about files it cannot read itself. The reason goes to vtium's log at debug level.
- **Temporary files** (`t=t`). One is read only when its resolved path lies in `/tmp`, `/dev/shm` or vtium's own `TMPDIR`, and contains `tty-graphics-protocol`, as the spec asks; any other is refused and left alone. Once opened, the worker removes it before it locks itself in, whether the read succeeds or not, as kitty and Ghostty remove it. A refused `t=t` command after login still goes to the helper as a discard, which removes the file under these rules and reads nothing, since the spec gives the file's removal to the terminal.
- **Shared-memory objects** (`t=s`). The name may start with one `/` or none, as the spec requires terminals to accept, and must contain no other `/`, must not be empty, `.` or `..`, and is at most 255 bytes. The worker opens it beneath `/dev/shm` through `openat2`, with no symlink followed and no escape from the directory, under the regular-file rule above, reads it under the same bounds as a file, and copies what it needs into its own memory file, so the console never maps the program's object. The helper, which is not locked in, removes the object once the worker reports a valid picture read from it, and only when the session's user, the helper's own account, owns it (the maintainer, 2026-11-01). A valid picture is, for raw pixels, the bytes the picture needs; for PNG, a picture that decoded; for zlib, data that inflated to what the picture needs. A refused `t=s` command sends no discard.
- **What protects the user's objects.** Any program that writes to the terminal, `cat` of a hostile file among them, can name a shared-memory object. The owner check is the protection: only objects the session's user owns can go, and those are the user's to risk, up to running a malicious program; beyond that check vtium relies on the kernel's own protections (the maintainer, 2026-11-01). The C reference checked the owner too. The valid-picture rule protects little on its own: a command for raw 32-bit pixels one pixel in size (`t=s,f=32,s=1,v=1`) reads a valid picture from any object of 4 bytes or more. It keeps in place only an object a picture cannot be read from, such as one too short.
- **How a file is removed.** The worker, for a temporary file, or the helper, for a shared-memory object, removes the resolved path, never the path as given, and only the file that was checked: it opens the resolved path's parent directory through `openat2` with symlinks refused, checks with `fstatat` without following a symlink that the entry still has the device and inode that were read and that the helper's own account owns it, and only then unlinks the entry from that directory. A failure leaves the file in place and is logged, and the program's reply does not change. Without the owner check, a root helper, which ignores the sticky bit of `/tmp` and `/dev/shm`, could be made to remove another user's file.

### D6: decoding

Every crate that reads a program's bytes in the helper is pure Rust, linked into the helper only, and approved by the maintainer for the helper only, with what it pulls in (2026-11-01). Each decoding path takes a fuzz target, run in-process outside the memory cap, as the C reference's sanitizer runs could not be under its cap; the target of each path covers every crate on that path.

| Path | Crates that read the program's bytes |
|---|---|
| PNG (kitty's `f=100`, and iTerm2's pictures) | `png`, which inflates through `fdeflate` (it also pulls in `flate2` and `miniz_oxide`, which only its encoder uses) |
| zlib (kitty's `o=z`) | `miniz_oxide`, the inflater already in vtium's tree |
| JPEG (iTerm2's pictures, ADR-1103) | `zune-jpeg`, on `zune-core` |
| GIF (iTerm2's pictures, ADR-1103) | `gif`, which decodes its LZW data through `weezl` |
| Described pixels from a file or shared memory (kitty's `f=24` and `f=32` with `t=f`, `t=t` or `t=s`), raw or zlib, and sent inline with zlib (`t=d` with `o=z`) | vtium-image's conversion function (D7), and `miniz_oxide` for zlib |
| The request | the helper's own request reader |

- **PNG.** The worker reads the header first: a width or height past `max-graphic-size`, or width × height × 4 bytes past the request's `max_bytes`, is refused before any pixel is allocated, as `TOO_LARGE` and `OVER_BUDGET`. It decodes to 8-bit RGBA, expanding palette, grey, 16-bit and interlaced pictures, with no gamma or color-profile correction, as the C reference did, and premultiplies the result into the store's format through the conversion function of D7, as the helper does with every picture it decodes. A stream that does not decode is `CORRUPT`, and so is a palette that is not whole entries of three bytes, or has more than 256 of them. A palette picture whose transparency chunk has more entries than its palette decodes opaque: `png` ignores such a chunk, and the C reference showed such files.
- **zlib** inflates as a stream that stops at `max_bytes` (`OVER_BUDGET`). It follows the C reference's rules for how much comes out: once the picture's bytes are out the rest is ignored, and where the request asks for exactly that many bytes, one byte more is `CORRUPT` and fewer is `TOO_SHORT`.
- **JPEG and GIF** are ADR-1103's, which says how the request asks for them.
- **An animated GIF** (ADR-1103). When the request carries the frames flag (D7) and the GIF holds more than one frame, the worker decodes every frame and composes each into a whole picture of the GIF's own width and height, by the disposal rules that ADR-1102 D1 maps onto composition. Every frame it returns is therefore whole, and the console never runs a GIF's disposal rules, which stay in the sandbox with the rest of the GIF's parsing. The worker reads the GIF's width and height from its header first and checks them against `max-graphic-size` and `max_bytes` before it allocates a pixel, as for a still picture, and it clips a frame whose rectangle reaches past them. Before it writes each frame past the first, it checks that the frame count stays within the request's `max_frames` and that the frames past the first, width × height × 4 bytes each, stay within `max_frame_bytes`, in checked 64-bit arithmetic. When either check fails, or a frame past the first does not decode, it returns the first frame alone, as a still picture, with the reason for vtium's log. It writes each frame into the reply file with `pwrite` once the frame is composed, so in memory it holds at most the file it reads, the canvas, and the copy of the canvas that disposal method 3 restores, and the memory cap of D3 needs no more room. It reports each frame's delay as the GIF gives it, in hundredths of a second, and the loop count of the GIF's NETSCAPE2.0 application extension, or that the GIF has none; the iTerm2 handler turns them into gaps and loops (ADR-1103 D2). It premultiplies every frame, as it does every picture. A GIF of one frame, and any GIF in a request without the frames flag, decodes to its first frame as before. A request with the frames flag takes a one-off worker and never counts toward a stream (D4), since its reply file holds many frames. The GIF path's fuzz target decodes every frame.
- **What was ignored.** The reply reports how many bytes of the source went unused, as the C reference's version 2 did, and vtium logs the count at debug level, never the file's name. A PNG whose end chunk was removed and junk appended decodes and reports none ignored, which the C reference accepted and vtium accepts too.

### D7: the wire between vtium and the helper

- **The socket.** A Unix socket pair of the sequenced-packet kind, so the kernel keeps each message whole; the helper's end is descriptor 3. A message is one packet carrying at most one descriptor. Each packet begins as each of the font helper's frames does, with a kind and the packet's length, then fixed fields, all little-endian, then a variable part. vtium receives with close-on-exec set on any descriptor that arrives, and a packet that is short, truncated, of an unknown kind, or carries a descriptor it should not is a failed reply.
- **The hello.** The helper's first packet, sent once it has set itself up, gives its wire version, the landlock version the kernel offers, 0 for none, and whether its seccomp filter is in force, which vtium logs once a boot when either is missing (D9).
- **The request** carries a version, the request's id, the medium (`d`, `f`, `t` or `s`), its flags (inflate, PNG, exact, discard, and ADR-1103's any-image and frames flags), the name's length (1 to 4,095 bytes for a named medium, 0 for inline bytes), the offset, the most bytes to read, the fewest bytes the picture needs, the largest width and height, `max_bytes`, `max_frames` and `max_frame_bytes`, followed by the name. `max_frames` and `max_frame_bytes` are 0 unless the request carries the frames flag; then `max_frames` is at most ADR-1102's `FRAMES_MAX`, and `max_frame_bytes` is the most that the console's frame allowance could hold for the picture's frames past the first, counting the frames of other images it could free (ADR-1102 D1). A request for raw pixels that the helper reads or inflates, from a file, a shared-memory object or inline bytes compressed with zlib, also carries a *pixel description* the handler builds from its protocol's keys (ADR-1100 D7): the layout, 3 bytes a pixel for RGB or 4 for RGBA; whether the alpha is straight or premultiplied; the width and height; and whether the bytes are zlib-compressed. The helper never sees a protocol's keys or strings. These are ADR-1100 D7's request type, field for field. Inline bytes travel in a memory file vtium writes and seals against shrinking, growing and writing before it sends it. The helper exits on a version, flag or field it does not know, and on a combination the C reference's version 2 refused, such as a discard with any other flag, which vtium reads as a failure, and on the frames flag without the any-image flag.
- **The reply** carries a version, the status (`OK`, `UNREADABLE`, `TOO_SHORT`, `CORRUPT`, `TOO_LARGE` or `OVER_BUDGET`), the request's id, the width and height of a decoded picture, the frame count, which is 1 for every reply but an animated GIF's, the GIF's loop count and whether it has one, the bytes ignored, a flag that says whether the reply's memory file is a pooled one (below), and, in the variable part, each frame's delay in hundredths of a second, 2 bytes a frame, followed by a reason of at most 255 bytes for vtium's log. An `OK` reply other than a discard's carries one memory file, written with `pwrite` and sealed against shrinking, growing and writing, or a pooled file (below): exactly width × height × 4 bytes of premultiplied RGBA for each frame the reply counts, the frames one after another, the store's format, whether the helper decoded the picture or converted described pixels. The reply carries no opacity flag; the console finds the opacity itself (below).
- **One input format.** Every `OK` reply holds premultiplied RGBA, so the console has one input format and one path for it. Once the reply passes the console's checks (below), vtium-platform hands its memory file to the protocol handler unread, and the handler first reserves the picture's bytes under the console's image budget (ADR-1100 D5), and an animated GIF's frames past the first under the frame allowance (ADR-1102 D1), so the budget can refuse a picture before any of its pixels are copied. Only then does the handler read exactly width × height × 4 bytes for each frame once, into the buffer the budget granted, memory only the console holds: it copies a sealed file out of a read-only mapping and reads a pooled file with `pread`. It never reads the file again. A file that hands over fewer or more bytes than the picture needs fails the copy, and the handler gives the reservation back; the kitty handler answers EBADF, and the iTerm2 handler drops the picture. Working on that copy, it clamps each color to its pixel's alpha, reading each value once, and finds whether every pixel is opaque by ANDing the alphas in the same pass, which costs almost nothing; an image with frames is opaque only when every frame is (ADR-1102 D1), and the pass over every frame counts as input work (ADR-1100 D5). It publishes the image to frames only after the clamp. A helper that lies about the pixels, or writes a pooled file while the console reads it, therefore gives that one picture wrong pixels, never a value out of range. The helper sends no opacity flag, since a false "opaque" from a compromised helper could hide the pictures beneath that one: the compositor draws nothing under the topmost opaque picture that covers a cell (ADR-1100 D4). Raw pixels sent inline and uncompressed stay with the console's handler, which decodes them as they stream in (ADR-1100 D7).

  > Edited 2026-11-02: the maintainer decided that the console copies a reply's pixels once, and the build that does so copies them only after the budget has granted their buffer. The bullet said that the console read the bytes once and did not say when, and a file of the wrong length failed the reply.
- **Pooled reply files** (the stream worker's, D4) are made with `MFD_ALLOW_SEALING` and sealed against shrinking and growing (`F_SEAL_SHRINK` and `F_SEAL_GROW`), which still allow `pwrite` within the file's size, so the helper can write a pooled file again for the next frame. They carry no write seal, since a file sealed against writing can never be written again. The console reads a pooled file only with `pread`, by the clamp rule above, and never maps it. It requires `F_GET_SEALS` to show both seals, which also proves that the descriptor is a memory file. A compromised helper therefore cannot pass some other regular file it can open: one on a FUSE or NFS mount whose read never returns, which would hang the root console's loop after the 2-second timer has stopped, or `/proc/kmsg`, which a logged-in root's helper, running as root, could open. The fixed size leaves no race on the file's length. The console handles a reply before it resumes the pty and before the next request goes out, so once the next request is sent the helper may write the file again.
- **Memory files,** sealed and pooled, are made with `MFD_ALLOW_SEALING` and with the kernel's no-execute seal (`MFD_NOEXEC_SEAL`), so no one can make one executable; a kernel older than 6.3 refuses that flag with EINVAL, and the memory file is then made without it.
- **The console's checks,** before it reads a pixel, in the C reference's order: a request is out; the length is exact and the reason within 255 bytes; the version, id and status are known; the ignored count is 0 on an error or discard and within the request's bounds otherwise; an `OK` reply other than a discard's carries exactly one descriptor, of a regular file; the seals hold shrinking and growing (`F_SEAL_SHRINK`, `F_SEAL_GROW`), and writing too (`F_SEAL_WRITE`, never `F_SEAL_FUTURE_WRITE` in its place) unless the reply's flag marks a pooled file, read before the size, since until the shrink seal is set the helper could cut the file under a mapping and fault the root process, and a descriptor without seals is no memory file; the frame count is 1, or, for a request with the frames flag, between 1 and `max_frames` with the frames past the first within `max_frame_bytes`; the variable part holds one delay for each frame; the size is exact, the frame count × width × height × 4 bytes, its product checked for overflow; and the picture fits `max-graphic-size` and `max_bytes`. Then vtium copies the pixels as above and checks them against the request again (`Reply::checked`, ADR-1100 D7). Any failure is a failed reply.
- **One encoding.** Both packets are encoded and decoded in one module that both ends link, beside ADR-1100 D7's request and reply types in vtium-image, so the two ends cannot read the fields differently.
- **One conversion.** One function in vtium-image, which both ends link, turns RGB, straight RGBA and premultiplied RGBA into the store's premultiplied RGBA. The helper uses it for described pixels and for the pictures it decodes, and the console's sixel and inline raw decoders use it too, so the same pixels sent inline (`t=d`) and through shared memory (`t=s`) store the same bytes. vtium's fixture host for the replay interface converts its straight `.rgba` fixtures and raw fixtures through the same function, so tier 1, whose image digest hashes premultiplied pixels, exercises the premultiplied path.

### D8: timeouts, failures and restarts

- **The timer.** The binary holds a 2,000 ms timer on each request while the console's pty is paused, in `crates/vtium/src/head/images.rs`. ADR-1100 D7 says how the timer reads the loop's clock and what vtium-platform does with the helper process when the timer fires. A reply that passes the checks ends the request and resumes the pty.

  > Edited 2026-11-02: the steering session placed the timer in the binary, in `crates/vtium/src/head/images.rs`, and left the helper process to vtium-platform. The bullet read: "vtium-platform holds a 2,000 ms timer on each request while the console's pty is paused (ADR-1100 D7)."
- **A failure.** The timer firing, the socket closing or failing, or a reply that fails a check ends the request. vtium kills the helper's process group, its worker included, before it reaps the helper, which leads the group: through the pidfd with the kernel's process-group flag where the kernel has it, from Linux 6.9, and otherwise by signalling the group's id, which cannot be reused while its leader is not yet reaped. It then reaps the helper, hands the terminal `FAILED`, which the kitty handler answers EBADF, or for a discard answers its own refusal, and resumes the pty. The next request starts a new helper.
- **Crashes, a bounded number a session.** A worker killed by a signal, a helper that ends with another status than 0, and a reply that fails a check each count as a crash; a timeout does not, since a large picture on a slow board can take that long honestly. After `IMAGE_CRASHES_MAX`, 3, crashes on one console, vtium starts no more image helpers for that console until its session ends, logs that once, and answers that console's requests as ADR-1100 D7's "Without a helper" says; other consoles keep theirs (the maintainer, 2026-11-01). The helper replies as soon as a worker's outcome is in and exits 1 when that worker is then killed by a signal, as a decoder that corrupts its heap and aborts after its outcome is, so vtium reads the status of a helper it finds exited, or whose socket it finds closed, through its pidfd before it reaps it; a helper that idles out or loses vtium's socket exits with status 0. A helper whose socket ends while a request is out fails that request whatever its status, and counts a crash only when its status is not 0: a helper that idles out just as vtium sends a request exits 0 with the request unread, and an honest helper never exits 0 once it has read one. Linux reports a sequenced-packet socket whose peer closed with a packet still unread as `ECONNRESET`, which vtium reads as the socket ending. Each helper start lays out its address space afresh, so an unbounded count would let a hostile picture retry until a guess at the layout lands, the reason the font helper bounds its restarts (ADR-1200 D15).
- **The session's end.** A console whose session ends drops its request without a reply, kills its helper, and clears its crash count, and the next session starts with none out.

### D9: the filters

- **seccomp.** After its setup and before it reads its first request, the helper installs a seccomp filter, an allow-list of the system calls it and its workers make: reading and writing its socket and descriptors, `pread` and `pwrite`, sending and receiving packets with a descriptor, making, sizing and sealing memory files, the memory calls the Rust allocator makes, opening through `openat2` and reading through `/proc/self/fd`, the `stat` and `statfs` family, reading a link, removing a directory entry, closing, forking a worker and waiting for it, which each worker's own second filter then refuses (D4), exiting, signal masks and handlers, reading its limits and setting any of them but the descriptor limit of D3, getting random bytes, the landlock calls, `prctl` with `PR_SET_NO_NEW_PRIVS` and no other option, `seccomp` with `SECCOMP_SET_MODE_FILTER` and no other operation, which a worker needs to add its own filters until its last one refuses it, and the futex and scheduling calls the Rust standard library makes. Every other call is answered ENOSYS rather than killing the helper, so where a C library update tries a newer call, such as `clone3`, the library falls back to the older one it knows (the maintainer, 2026-11-01). It allows creating a socket only as a Unix socket pair of the sequenced-packet type, `socketpair` with `AF_UNIX` and `SOCK_SEQPACKET`, its flags aside, and no other family or type, for the channel to each worker. A Unix datagram pair would let a process send to any datagram socket its account may write by path, such as `/dev/log` or journald's, which a worker's landlock domain stops only from landlock version 9, and Debian 13 and Ubuntu 24.04 ship kernels below it. It allows `clone` only without `CLONE_PARENT` and every `CLONE_NEW*` flag, the form a fork takes, so no process of the helper makes a child that belongs to vtium or a namespace of its own. It allows `fcntl` only for the commands the helper uses: reading and setting a descriptor's flags and its status flags, the status flags never with `O_ASYNC`, adding and reading seals, and duplicating a descriptor close-on-exec. No process of the helper can therefore make another process the owner of a descriptor's signals (`F_SETOWN`) and have the kernel signal it, as a taken-over worker could have done to any process its account owns. It allows `prlimit64` only on the calling process itself, pid 0, so no other process's limits change, and `setrlimit` and `prlimit64` set no descriptor limit, so a worker taken over cannot raise its own past 64 even where a mistake left the hard limit higher, and `mmap` and `mprotect` only without `PROT_EXEC`, so no process of the helper makes memory executable. Among the calls the list leaves out are creating any other socket or connecting one, starting a program, tracing a process, signalling another process, mounting, and every `ioctl`. The list is one named constant in the helper crate for each architecture the filter is built for; a call made under another architecture's numbering kills the process, since the filter cannot read its number. The filter is built and installed through `seccompiler`, a pure-Rust crate.
- **32-bit ARM.** vtium also builds for `armv7-unknown-linux-gnueabihf`, and `seccompiler` builds filters for `x86_64`, `aarch64` and `riscv64` only. On armv7 the helper installs no seccomp filter and runs with landlock and the rest of its sandbox, and its hello tells vtium, which logs it once a boot. The maintainer accepted landlock alone on armv7, logged (2026-11-02).
- **The worker's own filters.** Each worker adds a second filter that refuses forking, starting a program, making a memory file and making a socket pair, since the helper makes every memory file a worker writes and every channel a worker talks on. On a kernel without landlock, each one-off worker adds a third filter once it has opened its source and removed a temporary file, which refuses `open`, `openat`, `openat2` and `unlinkat`, so it opens and removes nothing more, as its landlock domain would otherwise ensure. A stream worker adds the third filter before it reads anything. A worker's last filter, its second where the kernel offers landlock and its third where it does not, also refuses `seccomp`, so once it is in, the worker can add no filter. The helper builds the worker's filters once, for the landlock version its kernel offers.
- **landlock.** Each worker, once it holds the descriptor it will read and has removed a temporary file it must remove, enters a landlock domain that handles every filesystem access right the kernel's landlock version knows and grants none of them, so it opens and removes nothing more and reads only the descriptor it holds (the maintainer, 2026-11-01). The domain also handles binding and connecting TCP sockets, from landlock version 4, and from version 6 it is scoped, so the worker can signal no process outside its domain and connect to no abstract Unix socket made outside it. On armv7, where the helper has no seccomp filter, these keep a worker off TCP and from signalling other processes, on kernels that offer them; a worker there can still make other kinds of socket, and change another process's limits. A worker for inline bytes enters the domain before it reads anything. Landlock is reached through the `landlock` crate, the Linux landlock maintainers' own Rust binding. On a kernel without landlock, before 5.13 or with landlock turned off, the worker goes on without it, and vtium logs that once a boot from the helper's hello.
- **Each worker checks its sandbox.** Before it reads a request, a worker checks that vtium's socket, descriptor 3, is closed in it, and that it runs under one more seccomp filter than the helper, each counting its filters from `/proc/self/status` once its filter is in. Once it has locked itself in, it checks that it cannot open `/`, wherever the kernel offers landlock or the third filter is in force. A worker that finds any of these wrong exits without an outcome, which the helper counts as a crash. Each outcome also says whether the worker could open `/` as it answered, probed apart from the lock, and the helper reads the seccomp filters the worker that answered runs under from the worker's `/proc/<pid>/status`, before it reaps the worker, so the pid is still its child's: the helper's own and the worker's second, and on a kernel without landlock its third. The helper exits as on a crash when either is not what it expects, so a worker whose lock or second filter was skipped altogether fails too. The gate therefore fails when a control is removed. D10 says what these checks prove.
- **The gate.** A test starts the real helper program, built as installed, under its filter, and sends it every kind of request: inline raw bytes, inline PNG, inline zlib, a file, a temporary file, a shared-memory object, a discard and a refused path, checking each reply. A call the filter wrongly refuses fails a request, and the gate with it, so a stale list cannot pass. The test sends the same requests again with landlock hidden from the helper by a seccomp filter of the test's own, as on a kernel without landlock, so the gate also runs the workers' third filter. A second test installs the filter in a child and sees a call outside the list, such as creating an internet socket, a Unix datagram socket pair, a fork into a new namespace or setting the descriptor limit, answered ENOSYS, and sees the calls the conditions refuse fail against a `sleep` process the test started: pointing a descriptor's signals at it, changing its limits, and making memory executable. Both run on `x86_64` in the gates and on `aarch64` in the `arm-native` CI job.
- **The font helper.** The same two filters should come to the font helper, `vtium-vitrify serve` (ADR-1200 D15), as a follow-up: its own list of calls, and landlock limiting it to the frit's fonts once it has opened them (the maintainer, 2026-11-01).

### D10: what the C reference left open, and the gates

The C reference's security review left residuals that vtium closes here, each with a test:

- **One gid-0 check,** made in one function and sized from `getgroups` (D2).
- **rpc_pipefs is refused,** tested in tier 3's guest, where a test running as root can mount it, since mounting needs a privilege the gates do not have.
- **The pre-login refusal,** tested end to end through a terminal, its pty and the real helper; the tier 3 work carries that test, since it needs the real console.
- **The sysusers file creates `vtium-image`,** checked on tier 3's Arch Linux guest, together with the fallback to `nobody` when the account is removed.
- **A PNG without its end chunk** decodes and reports nothing ignored, accepted as in the C reference (D6).

The workers' checks of their own sandbox (D9) prove two things of different strength. The seccomp filters a worker runs under are counted by the kernel and read by the helper. A process can never remove a filter, and each worker's last filter refuses adding one, so from the moment that filter is in, the count can neither fall nor rise, whatever the worker does, a worker taken over included. A worker that skipped its last filter therefore shows one filter too few, and one that added a filter before its last shows one too many. Everything a worker reports of itself, its outcome's flag that it could open no directory and the checks it makes before it reads, proves that vtium's own code took each step, in a run whose worker is still running vtium's code: a mistake in vtium that skips a step fails the gate. Once a hostile picture has taken a worker over, the worker runs the attacker's code, and its report proves nothing; the sandbox the kernel enforces is what still holds then.

The helper's work item gates each control ADR-1400 D2 lists with a test: the session of its own, the ids read back, the ambient capabilities cleared, the empty environment, the credentials resolved before the fork, the restart rules, and the seals checked before the size, a pooled file without both its seals refused, and the console's copy clamped and its opacity found before the image is published; and the gates of the helper's issue: the identity modes (refused before login, the session's user, group 0, a vtium not running as root), the path refusals (a symlink to a refused place, a file that is not regular, a shared-memory name that escapes `/dev/shm`), the shared-memory owner check, the memory cap, the crash limit, a fuzz target for each decoding path, and tier 3's kitty file-media screens.

## C notes: the C reference's flow

How the C reference ran its helper, read at kmscon `b1f7a7c5`.

- **The host.** `src/image_host.c` started the helper (`start_helper`, `resolve_creds`, `exec_helper`), kept one request out (`image_host_send`, `send_request`, `data_memfd`), received and checked replies (`receive`, `map_reply`), ended a request on the timer or a failure (`timer_event`, `fail`, `stop_helper`), and checked group 0 (`gid_zero`). `resolve_creds` refused to start a helper as anyone but kmscon's own user when kmscon was not root (lines 128-131). Its memory cap was `HELPER_AS_BASE`, 64 MiB, plus three times `max_bytes`.
- **The identity.** `src/image_identity.c` found the session's user (`image_identity_find`, `logind_uid`, `logind_running`, `login_class`), the pre-login account (`prelogin_user`, `prelogin_candidate`), and checked group 0 a second time (`own_gid_zero`).
- **The helper.** `src/image_helper.c` checked each request (`request_valid`), opened files and shared memory (`open_source`, `open_file`, `open_regular`, `open_shm`, `location_ok`, `temp_ok`, `pseudo_fs`), removed them only when its own uid owned them (`delete_checked`, `open_shm`, `discard`), read (`read_bounded`), inflated through zlib (`inflate_bounded`), decoded through libpng (`decode_png`), and wrote and sealed its output through a mapping (`out_create`, `out_seal`). It unlinked a shared-memory object once opened, whatever the outcome.
- **The wire.** `struct kmscon_image_request` of 64 bytes and `struct kmscon_image_reply` of 32, in host byte order, at version 2 (ADR-103's Notes of 2026-10-24).

## Where vtium departs

From the C reference:

- **A shared-memory object is removed only after a valid picture was read from it,** where the C reference removed it once opened, whatever the outcome, and a refused `t=s` command sends no discard. Both remove only an object the helper's own account owns.
- **A shared-memory name may lack its leading `/`,** as the kitty spec requires, where the C reference refused it.
- **The helper's environment is empty,** and vtium's `TMPDIR` reaches it as an argument, where the C reference passed `TMPDIR` as its only environment variable.
- **The helper installs a seccomp filter, and each worker a landlock domain,** where the C reference had neither.
- **A worker handles each request, and one long-lived worker a stream of inline frames,** where the C reference's helper handled every request in one process.
- **A logged-in root's helper holds no capability,** where the C reference's kept root's.
- **The helper caps the size of each file it writes** at `max_bytes`, and the descriptors it holds at 64, where the C reference capped its address space alone.
- **Crashes are bounded at three for each console's session,** where the C reference restarted its helper after every failure.
- **Every decoder is a pure-Rust crate,** where the C reference used libpng and zlib.
- **The wire is little-endian, and its packets begin with a kind and a length,** where the C reference's was in host byte order.
- **The reply is written with `pwrite` into a memory file made with the no-execute seal,** where the C reference wrote through a mapping.

From the kitty spec:

- **A shared-memory object that held no valid picture is left in place,** where the spec has the terminal read the object, then unlink it (the maintainer, 2026-11-01).

## Consequences

### Positive

- The console, which runs as root, opens no file a program names and decodes no PNG, JPEG, GIF or compressed data.
- A fault in a decoder costs one request and, past three on one console, that console's pictures that need the helper until its session ends; it never costs the console itself or another console.
- A decoder that is taken over reaches only the one file its request named, or, in a stream worker, no file and only the later frames of its stream. It cannot open another file, start a program, open a socket, signal another process, change another process's limits or make memory executable, and it runs as the session's user with no capability; on armv7 the seccomp part of that is missing.
- An old console never talks to a new helper, so the wire can change in any release.

### Negative

- Each one-off request costs a fork and fresh memory, and so does each frame from a file or shared memory, which no stream worker serves, and the helper costs a start after each idle exit.
- A hostile frame in a stream of inline frames can reach the later frames of that stream on that console.
- A logged-in root's helper reads only what uid 0's permission bits allow, so a root program cannot show a file root could read only through a capability.
- The system-call list needs care as the decoders, the standard library and the C library change; the gate catches a stale list, and the ENOSYS answer keeps a missing call from killing the helper.
- A stream that crashes the helper three times stops file, PNG and compressed pictures on that console until its session ends.
- An invalid shared-memory object is left in `/dev/shm`, a departure from the spec; a valid one the user owns can be removed by any program that writes to the terminal.
- A kernel without landlock runs the workers without it, and the armv7 helper runs without seccomp.
- The helper crate holds `unsafe` in one module.

### Neutral

- The identity code, which finds the session's user, serves the font helper too, which ADR-1200 D15 says runs as the session's user once this work lands; each helper keeps its own pre-login account, `vtium-image` here and `nobody` there.
- The package gains a sysusers file and a program.

## Alternatives Considered

- **vtium itself in a helper mode,** started again with a flag. Rejected (the maintainer, 2026-11-01): the console would link the decoders, and the minspec binary's size budget would pay for them.
- **One process handling every request, with no worker.** Rejected: a landlock domain only narrows, so a long-lived process could not be locked to one request's file and still open the next one's.
- **A fresh worker and a fresh reply file for every frame of a stream, and nothing more.** Not taken for inline frames (the maintainer, 2026-11-02): each frame pays for fresh memory, about 8,000 page faults at 3840x2160. Frames from files and shared memory are served this way.
- **A fresh worker for each frame writing into a pool of reply files,** the second way measured. Not taken (the maintainer, 2026-11-02): on inline frames it cost 23 to 26% more a frame than the stream worker at 1366x768 for PNG and 12% for zlib, and on frames from shared memory at 7680x2160 it was slower than fresh files.
- **Starting a stream by time,** such as frames arriving faster than some rate. Rejected (the maintainer, 2026-11-02): the helper counts matching requests, so what it does follows the bytes and never how fast they came.
- **A long-lived stream worker for shared-memory frames.** Not taken: a worker that can open the next frame's object can open the user's other objects too; a fresh worker for each frame serves such a stream and opens only the one object its request names.
- **A fresh helper program started for each request.** Not taken: each start costs an `exec` and the whole sandbox setup, which a client sending a picture per video frame through shared memory pays at its frame rate; a fork of an already sandboxed helper costs a fraction of that.
- **The worker removing the shared-memory object.** Not possible: the worker knows whether its picture was valid only after it has locked itself in, and a landlocked worker can remove nothing, so the helper, which is not locked in, removes it.
- **Starting the image helper through `execveat` in vtium-platform** while the font helper starts through `/proc/self/fd`. Not taken: one way for both helpers keeps one rule, and the helper needs `/proc` mounted in any case.
- **A seccomp filter that kills the helper on a call outside its list.** Rejected (the maintainer, 2026-11-01): a C library update that tries a newer call would kill every helper, where ENOSYS lets the library fall back.
- **A seccomp filter of vtium's own for 32-bit ARM.** Not taken now: it would be a second filter builder to keep right for one architecture; the probe above asks the maintainer.
- **No filter, relying on the account switch, no-new-privileges, the empty environment, the memory cap and the file rules,** as the C reference did. Rejected (the maintainer, 2026-11-01): a filter narrows what a taken-over decoder can reach beyond what the account allows.
- **Never removing shared-memory objects.** Rejected (the maintainer, 2026-11-01): every client that sends pictures through shared memory would leak them.
- **Removing a shared-memory object once opened, whatever the outcome,** as the C reference and the spec do. Not taken (the maintainer, 2026-11-01): an object a picture could not be read from stays; the owner check, which vtium keeps either way, is what protects the user's other objects.
- **A GIF's frames returned as the rectangles the GIF stores, with their disposal methods, for the console's handler to compose.** Not taken: the GIF's disposal rules, read from a program's bytes, would run in the console's root process, and the console would need a second input format beside whole premultiplied pictures. The helper composes them, so the store still holds whole frames, as ADR-1102 D1 requires.
- **libpng and zlib,** as the C reference used. Rejected (the maintainer, 2026-11-01): pure-Rust decoders keep C out of the helper, and `miniz_oxide` is already in the tree.
- **A crash limit for the whole boot,** as the font helper's. Not taken (the maintainer, 2026-11-01): one console's hostile stream would stop pictures on every console until the machine restarted.
- **Unlimited restarts,** as the C reference had. Rejected: each restart is another guess at the address layout for a hostile picture.
