# ADR-1100: One image pipeline: protocol handlers feed a store of placements that travel with lines

## Summary

- **Decided:** vtium keeps the C reference's image flow as one pipeline. The pipeline is designed around two image protocols, sixel and kitty graphics. A handler for each reads its control string, decodes what is safe to decode in the console and hands the rest to the sandboxed image helper, with the console's input paused until the helper answers. A thin front end for iTerm2's inline images (OSC 1337 `File=`) is carried for compatibility, so programs that send them work, and is no protocol of its own standing. It splits each picture between the two: it decodes it on the kitty path, sending the whole image file to the sandboxed helper as kitty's PNG payloads go, and places it under sixel's rules, at the cursor, moving with the text and cut by text and erases, since iTerm2 gives a program no ids or delete command to manage a picture afterwards. Each console has one store of images and placements, with a main and an alternate buffer. A placement is anchored to the line holding its top row and travels with the text. Every placement carries the tag of the protocol whose rules it follows, and one function in vtium-image maps a tag to that protocol's rules: what cuts it, how a region scroll moves it, whether it can be evicted while on the screen, and the layer it draws in. Nothing else in vtium can match on a tag. At equal z a later picture draws over an earlier one, except that two kitty pictures keep kitty's own rule, the lower id below; a newly arrived kitty picture that kitty's rule puts under one already shown slides in just beneath it, so the draw order is always one fixed order and nothing already shown moves. The store's use clock moves only on stream events, so eviction follows the bytes and never the drawn frames. Each console has its own budget, and the compositor's scaled copies live in a cache of the renderer's own that never evicts a stored image. A frame carries the placements with their pixels shared. The whole pipeline is the `images` Cargo feature, and the minspec build carries none of it.
- **Trades away:** A sixel is held as premultiplied RGBA, 4 bytes a pixel, where palette indices would take 1 or 2. A file or compressed image costs a round trip to the helper, and that console's output waits for it. With a budget per console, a vtium running several consoles can hold several budgets of images at once. A picture a frame in flight still shows keeps its memory after its image is deleted, until that frame is done. The C reference's goldens that draw a sixel and a kitty picture at equal z in one frame differ from vtium's draw order.
- **One-way?** No while nothing is built. It becomes expensive once tier 1's image goldens are judged against vtium's output and programs rely on the replies, and once the handlers, the compositor and the helper are built against the store's interface.
- **Probes:**
  - *Not confident (a budget per console):* each console gets its own image budget, `image-storage-limit`, covering its main and alternate screens, so what one console keeps depends only on what its own programs sent. The C reference had one budget for the whole process, where one console's pictures could push out another's. With four consoles, vtium may then hold four budgets of pictures at once. Is a budget per console what you want? (Answered 2026-11-01; see `considered`.)
  - *Confident (scaled copies apart):* when a display draws a picture at a size other than its own, as on a zoomed or rotated display, the scaled copy lives in the renderer's own cache, and drawing it never pushes a stored picture out of the scrollback, as the C reference's scaled copy could. Yes or no? (Answered 2026-11-01; see `considered`.)
- **Inversion:** Between "images are cell content" (sixel's own model, where text over a picture replaces it) and "images are a free layer text never touches" (the kitty spec's model). The answer keeps one layer of placements and gives each protocol the erase and scroll rules its own specification describes, held in one function so a third protocol adds a tag and one arm.

## Context

vtium needs one image pipeline that the sixel handler, the kitty graphics handler, the iTerm2 compatibility handler, a picture over a picture, pictures in the CPU compositor, the sandboxed image helper, kitty animation and a static image at the login prompt all build on. `crates/vtium-image` holds only its crate documentation today. ADR-1000 lists the rows this record serves: `image.pipeline`, `image.sixel`, `image.kitty`, `image.kitty-animation`, `image.kitty-relative`, `image.kitty-placeholders`, `image.overlap`, `image.compositor`, `image.helper`, `image.iterm2`, `image.login`, `query.xtsmgraphics`, and the modes `DEC-80` (DECSDM), `DEC-1070` (private sixel color registers) and `DEC-8452` (sixel cursor to the right), each in the `images` layer.

The C reference built this in kmscon ADR-103 and its Notes: one store per screen buffer in libtsm, two protocol front ends, a helper process for files and compressed formats, and one budget for the whole process. vtium takes that logic flow and leaves its structure.

Several of vtium's own records already decide parts of the pipeline's surroundings. ADR-1001 gives each line a permanent `LineId` for placements to anchor to, and says that a placement added, moved, clipped or removed marks the cells under its old and new boxes. ADR-1003 decides how an anchor moves through a rewrap. ADR-1300 fixes the color glyph format, premultiplied RGBA, and the row scratch that pictures are composed in. ADR-1400 D2 carries the C reference's helper forward: its own process, the session's user, never root by fallback, a 2-second timeout with input paused. ADR-1401 D1 gives each head its consoles, each a session with its own screen, and D2 gives each head a render thread of its own. `docs/architecture.md` names the eviction rule and the decode timeout among its determinism rules. A review of vtium's frame path found that the line, damage and frame models already have room for placements, and that the head's `Snapshot` carries none yet.

The image section of vtium's notes on the C reference, a page of the docs that is gone, left two questions this record answers: how eviction orders images across stores once each store has its own use clock, and whether the compositor's scaled pictures share the image budget.

vtium sets its own performance targets and measures them on vtium (the maintainer, 2026-11-01). Meeting or measuring the C reference's targets, such as ADR-103's A5 and A7, is not a condition of this record or of its build.

### D2: the store

- **One store for each console,** a console being ADR-1401 D1's session with its own pty, screen and scrollback. The store holds two buffers, main and alternate, and each buffer has its own images, its own kitty ids and numbers, and its own placements, as kitty keeps the two screens apart and the C reference kept one store per screen buffer (the maintainer, 2026-11-01). The two buffers share one budget and one use clock (D5).
- **An image** has a key, a 64-bit number the store counts up and never reuses; its protocol tag; for kitty, its id (1 to 2^32-1) and image number, if it has them; its width and height; its pixels, premultiplied RGBA, 4 bytes a pixel, the color glyph format of ADR-1300, for every protocol (the maintainer, 2026-11-01), held behind a shared reference so a frame can hold them without a copy; whether every pixel is opaque; for a tag whose rules say a new picture covers older ones per cell, which cells it covers fully and which it leaves empty, which a picture drawn over another picture uses; the use stamp and the transmission stamp of D5; and whether kitty's `N=1` marked it transient.
- **A placement** has a key, counted up and never reused; its image's key; its protocol tag; its anchor, which is the key of the line holding its top row and a column; its box in cells; its offset in pixels inside its first cell; the rectangle inside its box, in pixels, that its picture is drawn into, which is the whole box from its offset unless the picture keeps its aspect inside a box of another shape, as kitty's `c` and `r` and iTerm2's sizing keys can ask (ADR-1103); its source rectangle in the image's pixels, which is the crop; its z; the layer its tag's rules give it (D4); its sequence number and its place in the stack of placements at its depth (D4); its kitty placement id, or none; and the cell size in pixels it was made in, which is the unit of its pixel values.
- **Two kinds of kitty placement have no line of their own** (D13). A relative placement has, in place of an anchor, its parent placement and its offset from it in cells. A virtual placement, made for Unicode placeholders, has neither an anchor nor a parent, only its size in cells. Both count toward their buffer's placement count and its charges like any placement.
- **Cutting splits a placement into pieces.** Each piece is a placement of the same image with a smaller box, and its source rectangle follows from that box. The picture itself is never cut or copied. A piece clipped to nothing is removed, and a sixel's image goes when its last piece goes (D3).
- **The store's maps are ordered.** Images and placements are kept in ordered maps by key, and an index from line key to the placements anchored there is used for lookups only. Nothing orders lines by their key, as ADR-1003 notes that line ids are unique but carry no order. Whatever reaches the screen, a reply or eviction is taken in key order, sequence order or use order, never from a hash.
- **Bounds.** The limits are named constants in vtium-image's bounds table, each row with its reason, starting from the C reference's values and moved later by measurement on vtium (the maintainer, 2026-11-01): 1024 images and 4096 placements in each buffer; an image side of 65,535 pixels, below which `max-graphic-size` sets the working limit (D11); a cell of at most 1024 pixels a side; a box of at most 10,000 cells in each direction, columns and rows each; 512 bytes of the budget charged for each image beside its pixels, which pays for its first placement; and 256 bytes charged for each placement of an image past its first. Every size computed from a program's numbers is checked arithmetic, in 64 bits.
- **A count bound in one buffer.** A new image or a new placement past its buffer's count evicts in D5's order from that buffer alone, and is refused when nothing there may go. A cut or a scroll cannot be refused, since text and erases always land: one that would pass the placement count keeps the largest pieces and drops the smallest, as if their cells were erased, and pieces whose 256-byte charge the budget refuses are dropped the same way, smallest first.

### D3: the protocol tag and the rules function

Every image and placement carries the tag of the protocol whose rules it follows: the protocol that made it, or sixel for a picture the iTerm2 compatibility handler placed. The tag's variants are private to one module of vtium-image, `rules`, and that module's one public function maps a tag to a table of rules. The store and vtium-term's screen ask the table. The frame entry carries what the rules resolved, the layer, the draw order and the kind's printed name, so the compositor reads no tag and asks no rule, and vtium-replay prints a placement's kind from the name the table gives. Code outside the module cannot name a variant to match on it. vtium enforces this by module privacy, where a check that searches the source would be needed in C, and a `compile_fail` doctest shows a match outside the module failing to build. A third protocol adds a tag and one arm of the function.

The store knows two tags, sixel and kitty. The iTerm2 compatibility handler has no tag of its own. It decodes each picture on the kitty path, sending the whole image file to the sandboxed helper as kitty's PNG payloads go (D7), and places it under the sixel tag, since iTerm2 gives a program no ids or delete command to manage a picture afterwards (the maintainer, 2026-11-01), so every rule in the sixel column applies to it, and a replay prints its kind as `sixel`. vtium carries OSC 1337 `File=` so that programs that send it work, never as an image protocol of equal standing to sixel and kitty (the maintainer, 2026-11-01). Mapping its pictures onto sixel's rules follows what the protocols themselves describe and adopts no one terminal's special handling, such as WezTerm's pictures kept in cells (the maintainer, 2026-11-01, for protocol compatibility).

| Rule | Sixel | Kitty graphics |
|---|---|---|
| A character written into a cell it covers | Cuts the part under that cell | No effect |
| ED 0, ED 1, EL, ECH, DECSED, DECSEL, and a rectangle erase or fill (DECERA, DECSERA, DECFRA) over it | Cuts the part under the erased cells | No effect (kitty spec: "The other commands to erase text must have no effect on graphics") |
| A rectangle copy (DECCRA) into cells it covers | Cuts the part under the destination, as a write there does | No effect |
| ICH, DCH, and printing in insert mode on a row it covers | Cuts the part from the cursor to the end of the row, since shifting part of a picture by whole cells would tear it | No effect |
| A new picture of the same tag over it | The parts under the cells the new picture covers fully are removed, and a piece left with no set pixel is removed, the per-cell coverage the operator chose for the C reference | No effect |
| A region scroll (margins, IL, DL) | The part inside the moving band moves with it, the placement splits at the band's edges, and parts pushed out of the region are clipped | A placement wholly inside the band moves and is clipped at its edges (kitty spec: only images "entirely within the page area" scroll, and are clipped). One that crosses an edge keeps its place on the screen: after the scroll it is anchored to the line that then holds its top row, as the C reference did |
| Eviction while placed on the screen's own lines | Never | Allowed, oldest transmission first (D5) |
| Its layer | Above text, at z 0 | From its z (D4) |
| Kitty's delete commands | Never reach it | Reach it, by the spec's table |
| Its image without placements | Is freed, since nothing can name it again | Stays until it is deleted or evicted, so a lowercase delete keeps its data (kitty spec), except an image left without placements when a relative placement's parent goes (D13) |
| Its printed kind | `sixel` | `kitty` |

The events every placement meets alike are D8's and are not in the table. Between left and right margins, a region scroll moves a rectangle of the screen, and D6's paragraph on left and right margins gives what each rule does there.

> Edited 2026-11-12: the sentence on left and right margins is new.

**A sixel dot is one pixel.** The sixel handler draws every dot of a sixel picture as one square pixel, whatever aspect the string asks for: the pixel aspect that the DCS string's first parameter selects, and the aspect that raster attributes give as Pan;Pad, are read and not applied (the maintainer, 2026-11-01). xterm, WezTerm and mlterm draw sixel dots the same way, and the C reference did too. DEC's VT340 manual draws each dot twice as tall as it is wide unless the picture says otherwise, so vtium lists this as a departure from the specification. For example, a program that sends a circle 100 dots wide and 100 dots high without stating its aspect gets a circle 100 pixels across, where the VT340 would draw an oval 100 pixels wide and 200 pixels tall. Most programs, libsixel's `img2sixel` among them, state that their dots are square, so the two rules agree for them. The C reference's sixel goldens assume square dots.

### D4: the order a frame draws placements in

A frame draws, from the bottom: the default background; the layer below backgrounds, kitty placements with z below -1,073,741,824; the cell backgrounds that are not the default; the layer below text, kitty placements with z from -1,073,741,824 to -1; glyphs and decorations; the layer above text, kitty placements with z of 0 or more and every sixel placement, the iTerm2 handler's among them; and last, above every placement, the selection's tint, then the cursor, the pointer, vtium's own notices and the head's focus mark (ADR-1401), so no program's picture can hide them (the maintainer, 2026-11-01). The lowest layer shows only through cells whose background is the default, which the frame cell's `default_bg` tells the compositor (ADR-1001).

> Added 2026-11-06: ADR-1306 D7, accepted 2026-11-06: ink that reaches a cell from a neighbouring glyph, beside it or in the rows above and below, is part of that cell's glyphs and decorations, so pictures below the text show it on top and pictures above the text and sixels hide it. A picture's change repairs only the cells it covers, and a picture's cells do not cut that ink.

**The selection over a picture.** On a selected cell that a picture covers, the compositor blends the selection's color over the picture at partial strength, a named constant of vtium-render, so the picture and the selection both stay visible (the maintainer, 2026-11-01). A selected cell that no picture covers draws as it does in a frame without pictures.

> Edited 2026-11-01: the maintainer decided that the selection draws above pictures as a tint. The sentence ended "the cursor, the pointer and vtium's own notices and marks, so no program's picture can hide them", where "marks" meant the head's focus mark.

Within a layer, placements draw by z. The placements at one z in one layer form a stack, bottom to top, and the frame draws each stack in that order. The store keeps the stack as placements arrive, with these rules:

- **A later picture goes on top.** A sixel, or a kitty picture that kitty's rule below does not place lower, goes on the top of its stack when it arrives, so a program can order its pictures on purpose by the order it sends them (the maintainer, 2026-11-01). The order of arrival is the sequence number: a per-store count, taken by each placement when it is made, in the order its string reached the pipeline.
- **Two kitty pictures keep kitty's rule.** Between two kitty placements of different image ids, the lower id draws below, whatever their order of arrival, as the kitty spec says: "If two images with the same z-index overlap then the image with the lower id is considered to have the lower z-index" (the maintainer, 2026-11-01). Two placements of the same image keep their order of arrival, which the spec leaves undefined. A kitty picture whose image has no id, sent with neither `i` nor `I`, has no id to compare: it goes on top as a sixel does, and a later kitty picture looking for the first higher id passes over it. The maintainer confirmed this on 2026-11-01.
- **A kitty picture slides in beneath the first higher id.** When a kitty placement arrives, the store looks up its stack from the bottom for the first kitty placement whose image id is higher than the new one's. When there is one, the new placement goes directly beneath it; when there is none, it goes on top. Kitty placements in a stack are therefore always in order of id, and every pair that involves a sixel is in order of arrival, with one exception: a sixel lying above the kitty picture a newcomer slides beneath stays above the newcomer, although it arrived first. Nothing already in the stack moves, so the order is one fixed order, decided by the bytes alone, and never a loop. The maintainer confirmed this rule on 2026-11-01.
- **Pieces of one placement.** A cut or a scroll that splits a placement makes its pieces in a fixed order: for a cut, the part above the cut cells, the part to their left, the part to their right, and the part below; for a region scroll, top to bottom. The first piece that still shows any of the picture keeps the placement's key and its place in the stack; each other piece takes a new key, counted up in the order the pieces were made, and sits directly above the pieces before it. The pieces of one placement therefore stay together at its place, in the order they were made, so a frame numbers them the same way every time, as the C reference's `placement_split` and `frame_rec_cmp` did. Pieces cover different cells, so their order changes no pixel. A piece cut again splits the same way at its own place. Where a cut or a scroll passes the placement count (D2), the pieces that stay are the largest by area, ordered largest first, with pieces of equal area in the order they were made, and the largest keeps the placement's key and its place; below the bound the order they were made in holds. vtium follows the C reference's `placement_split` there so that its goldens at the bound stay valid.
- **Replacements.** A kitty placement that replaces one with the same image and placement id is a new arrival: it takes a new sequence number and goes where a newly arrived kitty picture goes, on top, or beneath the first higher id. The maintainer's answer that a replacement "draws on top" (point 11) is refined by the kitty id rule he chose later the same day (second round, Q3): it draws on top unless a kitty picture with a higher id is already in its stack.

An example. A program shows kitty picture 2, then a sixel chart over it, then kitty picture 1, all overlapping at z 0. ### D5: the budget and eviction

- **A budget for each console** (the maintainer, 2026-11-01). `image-storage-limit` bounds the bytes of every image in one console's store, main and alternate buffers together. An image costs width × height × 4 bytes plus its 512-byte charge, as the C reference counted it (the maintainer, 2026-11-01), and each placement of an image past its first costs 256 bytes (D2). Kitty animation frames past an image's first take an allowance of their own, five times this budget, so they never evict a still picture (ADR-1102, the maintainer, 2026-11-01). The store reserves an image's whole cost before it allocates a byte of it, and a payload buffered for the helper reserves each growth before it grows (D7).

  > Edited 2026-11-02: the maintainer gave kitty animation frames past an image's first an allowance of their own, five times this budget (ADR-1102, `considered`), so the sentence on that allowance is new. In git at 991986ba the bullet went from "each placement of an image past its first costs 256 bytes (D2)." straight to "The store reserves an image's whole cost".
- **The default, `auto`,** is four frames of the console's head's displays in RGBA, width × height × 4 added over the head's displays, at least 16 MiB and at most 192 MiB: 16 MiB at 1366x768 and 31.6 MiB at 1920x1080. The frame count, the floor and the cap are named constants of vtium-image's bounds table, so they are easy to adjust and can later become configuration keys if that is warranted (the maintainer, 2026-11-01). The binary computes `auto` again when a display joins or leaves the head or changes mode, and a smaller `auto` evicts nothing at once: the next reservation evicts down to the limit it finds, as the C reference settled after a font change briefly uncounted a display. A limit set in the configuration applies as set. `0` turns both protocols off (D10).
- **Host events.** A display joining, leaving or changing mode, a set limit and a protocol offered or withdrawn (D10) are host events. Each falls between two input calls, as a resize does (ADR-1003, "Determinism"), so what a console's store holds follows from its bytes and its host events in order, never from when frames were drawn.
- **Refused before anything is evicted.** When a reservation would pass the budget, the store first counts what eviction may free. When that falls short, it evicts nothing and refuses: kitty answers ENOSPC, and a sixel, the iTerm2 handler's included, is dropped. The C reference made the same fix. The image a kitty transmission replaces is held while the store makes room, so a refused replacement keeps the old image, a fix the C reference made too.
- **The eviction order,** across the console's two buffers:
  1. images with no placement, transient ones before the rest, each least recently used first;
  2. images whose every placement lies in the scrollback, least recently used first, with their placements;
  3. images whose rules allow eviction while placed on the screen's own lines, kitty's, oldest transmission first, with all their placements.

  An image whose rules never allow eviction while placed on the screen's own lines, a sixel, is never evicted while it is, so a store full of them refuses. The screen's own lines are the buffer's visible rows, never the scrollback. A count bound evicts in the same order from one buffer alone (D2).
- **The use clock is the store's own.** It is a count that moves by one at each stream event that touches an image: a transmission, a placement made, and a command that names an existing image, such as a kitty put or query by id or number. Each image takes the clock's value as its use stamp at each such event, and as its transmission stamp when it is transmitted. A drawn frame, a snapshot, a resize, a VT switch and a display's arrival never move it, so eviction follows the bytes. The C reference renewed every drawn image's use on each frame, on a clock shared by the whole process, so its eviction order depended on which frames were drawn and when; vtium lists that as a departure. Each stamp is unique within the store, so the order is total.
- **The renderer's scaled copies are outside this budget** (the maintainer, 2026-11-01). A display that draws a picture at another size keeps the scaled copy in a cache of the renderer's own. Each display has its own cache, which holds at most twice the bytes of that display's screen in RGBA, width × height × 4 × 2: about 16 MB at 1920x1080 and about 130 MB at 7680x2160. The factor is one named constant of vtium-render's bounds, as the C reference bounded its cache at twice the screen (the maintainer, 2026-11-01). A copy that does not fit is drawn scaled for that frame without being kept, so the cache changes speed and never pixels, the rule ADR-1300 D3 sets for glyphs. No scaled copy ever evicts a stored image. The C reference let a scaled copy for a picture on screen evict pictures in the scrollback (ADR-103's Notes, Q1); vtium lists that as a departure, because the store would then depend on what was drawn.

  > Edited 2026-11-01: the maintainer set the cache's bound. The bullet said the cache was "bounded per display (the CPU compositor work sets the bound; the C reference's was twice the screen in RGBA)".
- **Scans count as input work.** Every walk over placements, on a scroll, an ED 2, a kitty delete or an eviction, adds what it visits to the input call's work, as decoded pixels do, so a flood of line feeds or ED 2 against a full store stops the input call early and the rest is taken by the next call, as the C reference counted them. The work bound is a named constant of vtium-term's bounds table, starting from the C reference's 2^24 a call. It changes when work is done and never the state that results (`docs/architecture.md`, "Chunking invariance").

### D6: the handler trait

A handler turns one protocol's control strings into store and screen changes. vtium-image defines the trait, and each protocol module implements it:

- **`start`** takes the string's introducer: a DCS string's parameters, or the start of an APC or OSC string the router has matched to the handler.
- **`feed`** takes the string's data. A DCS or APC string comes in the pieces the parser hands out as they arrive: a sixel string grows its picture as its bands arrive, and a kitty string decodes its base64 into the pending image, so neither holds a whole payload it can decode as it goes. A PNG or zlib payload sent directly is the exception: its base64-decoded bytes are buffered in the console, under the budget, to be handed to the helper whole (D7). An OSC string reaches its handler in one piece, since the parser collects an OSC string whole (Routing, below). `feed` reports the work it did (D5).
- **`finish`** runs when the string ended with its terminator, which `StringEnd::is_complete` reports. It places the picture, or makes a decode request (D7), and replies.
- **`cancel`** runs when the string was cancelled, by CAN, SUB, another C1 control, or an ESC not followed by `\`. The handler drops what it holds and releases what it reserved; nothing is placed and nothing is answered. Acting only on a complete string is vtium-parse's listed departure from the C reference, which acted on a string however it ended.
- **`decoded`** takes the helper's answer to the handler's request, and places, stores or replies as `finish` would have.
- **`reset`** runs on RIS, before the store empties, so each handler drops what it keeps between strings and gives back what it reserved: the sixel handler its shared color registers, the kitty handler a chunked upload in progress and its reservation.

Each method gets one context, which vtium-term implements. It gives the handler:

- the console's store and the buffer in use, to read;
- a decode request sink;
- the cell size in pixels and the grid's size;
- the cursor, which a handler reads and moves through the context;
- the index the screen does at the bottom margin, as many rows at a time as the handler asks, which a sixel uses to scroll past the region;
- a scroll of the scroll region by a number of rows that leaves the cursor where it is, which the sixel handler uses so that a picture that fits the region scrolls the region first and then moves whole, as the C reference placed it;
- the scroll region's four margins: its top and bottom rows, and its left and right columns, which are the screen's first and last columns while left and right margin mode (DECLRMM) is reset;
- the state of modes 80, 1070 and 8452, read through the same report DECRQM gives, which the sixel handler reads to place a picture, to choose its color registers and to move the cursor after it;
- the number of sixel color registers in force, which XTSMGRAPHICS sets and `num-color-registers` caps;
- the reply sink, the protocol switches, the limits of D11, and the input-work count;
- one general way to edit the store. It hands the handler the store's buffer in use together with the line key of each row of the screen, so the handler can find what lies at a cell, and takes back the boxes the edit changed, which vtium-term marks in `Damage` as it marks every other store change (D1).

A handler therefore adds a store operation of its own, such as one of kitty's deletes by cell, row or column, inside vtium-image, and vtium-term needs no new method for it. A handler never reaches the screen's lines itself, so every scroll it causes passes through the screen and the store hooks of D8.

**Left and right margins.** While DECLRMM is set, DECSLRM's left and right margins make the scroll region a rectangle: the rows from the top margin to the bottom margin, and the columns from the left margin to the right margin. A line feed at the bottom margin, SU, SD, IL and DL then move only the cells inside the rectangle, and nothing enters the scrollback. A line feed scrolls the rectangle only while the cursor is between the left and right margins, as vtium-term's line feed does for text. The protocols use the rectangle as follows.

- **A region scroll inside the rectangle.** D3's region-scroll row applies to the rectangle, with all four of its edges. The part of a sixel placement inside the rectangle moves with it, the placement splits at the rectangle's edges, and the parts pushed out of the rectangle are clipped, as the text under them is. A kitty placement wholly inside the rectangle moves and is clipped at its top and bottom edges, and one that crosses any of the four edges keeps its place. The kitty graphics protocol says: "When page margins are defined and the index commands are used, only images that are entirely within the page area (between the margins) must be scrolled. When scrolling them would cause them to extend outside the page area, they must be clipped." vtium reads the page area as the rectangle between all four margins.
- **Sixel scrolling (mode 80 reset).** The picture's top left is the cursor's cell, with margins or without them. The VT330/VT340 graphics manual says that "Scrolling occurs when the sixel active position reaches the bottom margin of the graphics page", and xterm's ctlseqs quotes DEC STD 070 as saying that video devices "will scroll when advancing the Sixel active position past the bottom margin". Neither text speaks of left and right margins, since the VT330 and the VT340 have none. vtium places a sixel as cell content (D3), so a picture scrolls the region as the line feeds that move the cursor down past it would: the region scroll before the picture and the index after it both move the rectangle, and only while the picture's left column is between the left and right margins. With that column outside them, nothing scrolls, and the picture is placed at the cursor and runs past the bottom margin.
- **The cursor after a sixel.** With mode 8452 set, the cursor goes to the column after the picture's right edge, as ctlseqs gives it ("Sixel scrolling leaves cursor to right of graphic"), and stops at the column where CUF stops: the right margin when the picture's left column is not past the right margin, and the screen's last column otherwise. With mode 8452 reset, it goes to the picture's left column, as it does without margins.
- **Sixel display mode (mode 80 set).** The margins play no part. The VT330/VT340 graphics manual says that with sixel scrolling off "the sixel active position begins at the upper-left corner of the active graphics page", so the picture sits at the screen's top left, cut to the screen, as it does without margins.
- **The cursor after a kitty placement.** The kitty graphics protocol says that "the cursor must be moved to the right by the number of cols in the image placement rectangle and down by the number of rows in the image placement rectangle. If either of these cause the cursor to leave either the screen or the scroll area, the exact positioning of the cursor is undefined, and up to implementations." vtium moves the cursor right as far as the column where CUF stops. When the placement reaches past that column, the cursor goes down one row more, to the column where CR goes: the left margin when the cursor's column is not left of it, and the screen's first column otherwise. Without margins, those columns are the screen's last and first.
- **iTerm2 pictures** follow the sixel column of D3 and are placed as a sixel with sixel scrolling is (ADR-1103), so the sixel rules above apply to them. iTerm2's documentation of `File=` says nothing about margins.

### D7: the decode boundary and the barrier

- **In the console:** sixel, base64, and raw RGB, RGBA and palette-index pixels sent inline and uncompressed (kitty's `f=24`, `f=32`, `f=8` and `f=16` with `t=d` and no `o=z`, D15), each converted into premultiplied RGBA as it arrives. These decoders face anything a program writes, and each takes a fuzz target, built with the sixel and kitty handlers.
- **In the helper:** PNG (`f=100`), zlib (`o=z`), file, temporary-file and shared-memory media (`t=f`, `t=t`, `t=s`), the image formats iTerm2's `File=` sends, and the conversion of the raw pixels the helper reads or inflates into the store's premultiplied format (the pixel description, below). The console never opens a file or shared-memory object a program names and never inflates or decodes PNG; it holds the bytes of a directly sent PNG or zlib payload only to hand them over. The helper runs as the session's user in ADR-1400 D2's sandbox, and the image helper's own record decides its file rules, its identity modes and whether a syscall filter narrows it.
- **The request and reply types live in vtium-image,** in the C reference's mechanical terms, so the helper sees no protocol's keys or strings: what to open (a path, a shared-memory name, or the received bytes), where to start, the fewest bytes the image needs and the most that may be read, whether to inflate or decode, and, for a refused temporary file or shared-memory object, a discard that removes it and reads nothing. The largest image the request may return comes from the budget and `max-graphic-size`, and the helper checks a picture's header against it before it allocates. A reply is one outcome: OK with the pixels, premultiplied in the store's format, or `UNREADABLE`, `TOO_SHORT`, `CORRUPT`, `TOO_LARGE`, `OVER_BUDGET` or `FAILED`. The handler turns the outcome into its protocol's reply, such as kitty's EBADF, EINVAL or ENOSPC. The console checks every reply's sizes before it maps or stores anything, as it checks the glyph helper's chunks (ADR-1200 D15).

### D8: how a placement travels with text

The events below act on every placement alike; the cutting and region-scroll rules each tag has are D3's. A relative placement and a virtual placement have no line of their own, so they follow D13 instead: a relative placement goes where its parent goes, and a virtual placement is on no line at all.

| Event | What happens to the placements |
|---|---|
| Scrolling the whole screen (LF or IND at the bottom margin, SU, SD, RI at the top) | They move with their lines, and lines entering the scrollback carry them. |
| A line dropped from the scrollback past `sb-size` | Placements anchored there are clipped by that row and anchored on the next line. |
| ED 2 | Every placement on the screen's own lines is removed, as kitty's `a=d` does (kitty spec: the clear screen code "should also clear all images", "so that the clear command works"). A kitty image keeps its data, as a lowercase delete keeps it, which is the C reference's reading where the spec says nothing; a sixel's image goes with its last placement. |
| ED 3 | Placements anchored on the dropped scrollback lines go. |
| A width change on the main screen | The rewrap of ADR-1003 returns, for each anchor in the rows it rewrapped, the row and column now holding that cell, and the store moves the placement there. A placement wider than the columns left keeps its whole picture and overflows the far edge, the right one for text running left to right. Rows not yet rewrapped keep their anchors until they are reached. |
| Any other resize | Lines keep their placements, and drawing clips at the right edge and the bottom; lines the height change moves to or from the scrollback carry theirs. |
| A cell size change (zoom, or a head's grid at another size) | A picture scales with its box, so it stays aligned with the text around it. |
| Entering or leaving the alternate screen (47, 1047, 1049) | The alternate buffer is emptied, on entry as the kitty spec asks ("all images in the alternate screen must be cleared, just as all text is cleared") and on leaving, as the C reference did, so a full-screen program's pictures do not hold memory after it exits. The main buffer's placements show again on leaving. |
| RIS | Both buffers are emptied. |
| DECSTR | No effect, since a soft reset leaves the text. |
| A region scroll that clips the top of a placement or a piece | The part that remains is anchored to the line that holds its new top row after the scroll, as the C reference re-anchored it at its row. |
| Moving the view through the scrollback | No effect on the store. A frame finds placements by walking the visible lines, and as many lines above the top as the tallest placement has rows, so a picture whose top has left the view still draws its lower rows. |
| Every change above | vtium-term marks the cells under each placement's old and new box changed (ADR-1001). |

### D9: the frame, the snapshot, and mode 2026

- **The frame gains a placement list:** every placement with a visible row, in the draw order of D4. Each entry carries its image's key, its visible row (negative when its top is above the view) and column, its box, its pixel offset, the rectangle inside its box its picture is drawn into (D2), its source rectangle, the cell size it was made in, its z, its layer, the kind's printed name from the rules table (D3), its image's width and height, whether its image is opaque, a shared reference to the image's pixels, and the number and pixel revision of the frame those pixels are, which together with the image's key name the pixels the entry shows (ADR-1102 D3). The entry carries no tag. vtium-term builds the list through its store's frame call, handing it the line keys of the rows the frame shows and the runs of placeholder cells it reads on those rows, and the store adds an entry for each run (D13), so the compositor draws a placeholder picture as it draws any placement. An entry for an animated image, a kitty image with frames or an iTerm2 picture's animated GIF (ADR-1103), carries its animation state, and the head's snapshot takes the whole pixels of the frame the binary's animation clock chose from vtium-image's frame code, which composes that frame when the store keeps it as a change (ADR-1102 D3).

### D13: relative placements and Unicode placeholders

Two parts of the kitty graphics protocol give a placement a position that is not a cell of its own. A *relative placement* takes its position from another placement, its *parent*, and moves when the parent moves. A *virtual placement* is drawn wherever a program writes *placeholder* characters into the text, which is how a kitty picture survives inside a program such as tmux that redraws the screen without knowing about pictures. vtium builds both as the kitty spec describes them (read 2026-11-01), and the maintainer brought both into this wave (D12). The C reference answered both with EINVAL and left them to step 5 of its ADR-103, so it has no goldens for them; vtium's own replay cases judge them, provisional until the maintainer reviews them.

The figure shows a relative placement following its parent, and a virtual placement drawn through four placeholder cells.

![Two panels. A, a relative placement: a kitty picture three cells wide and two high, the parent, has its top left cell in the third row and fourth column of a grid ten cells wide and six high, and a second picture, its child, made with H=4 and V=1, sits four columns right and one row down from the parent's top left cell. After the screen scrolls up two rows, both have moved up two rows together, and the child keeps its offset. Deleting the parent deletes the child. **Relative placements.**

- **What makes one.** A kitty put, or a transmission that also places, which carries `P` makes a relative placement of its image. `P` is the parent's image id and `Q` the parent's placement id, both in the buffer in use. A `Q` of 0, or none, names a placement of image `P` that has no placement id, as the spec's text reads it; where there are several, the one made last, a choice the spec leaves open that a black-box run of kitty checks (D14). `H` and `V` offset the relative placement from its parent's top left cell, in cells: positive values move right and down, negative ones left and up.
- **Where it draws.** The store links a relative placement to its parent's placement and keeps its offset; it has no line of its own (D2). Its top left cell is always worked out from its parent: the parent's origin plus the offset. A placement's origin is the cell that holds its picture's top left corner as it was placed, so a parent whose top was clipped, by a line dropped from the scrollback or by a region scroll, keeps its children where they were against its picture. Everything that moves the parent moves its children with it: a scroll, the scrollback, a rewrap, a region scroll that moves the parent, and a replacement of the parent by a put with the same `i` and `p`, which keeps the parent's children. A region scroll moves a child only through its parent; the child's own place against the margins plays no part. Drawing clips a child at the screen's edges as it clips any placement.
- **How long it lives.** A relative placement lives as long as its parent. When the parent goes, by a kitty delete, by its image's eviction or a new transmission of its image, by ED 2 or by an emptied buffer, its children go too, and their children in turn. When that leaves a child's image with no placement at all, the image is deleted as well, as the spec asks ("If the image that the relative placement is a placement of, has no more placements, the image is deleted as well"); this is the one case where a kitty image left without placements does not stay (D3). A kitty delete that selects placements by where they draw, such as `d=a`, `d=c`, `d=p`, `d=x` and `d=y`, and ED 2, which removes the placements on the screen's own lines (D8), take a relative placement by the cells it draws on, and its own children with it.
- **What is refused.** A chain of relative placements may be at most `RELATIVE_DEPTH_MAX`, 8, placements deep below a placement that is not relative, the least the spec allows; a deeper one is answered `ETOODEEP`. A placement that would make a cycle, as a replacement can when a parent is replaced as a child of its own child, is answered `ECYCLE`. A parent that does not exist is answered `ENOPARENT`. A virtual placement may be a parent and never a child, so `U=1` with `P` is answered `EINVAL`. A refused command places nothing. Each answer is a fixed message in the closed set of kitty replies (D6), and `RELATIVE_DEPTH_MAX` is a row of vtium-image's bounds table.
- **The cursor and the stack.** Placing a relative placement never moves the cursor, whatever `C` says, as the spec's note requires. A relative placement draws at its own z, in the layer its z gives, and takes its place in its stack when it arrives, as any kitty placement does (D4).
- **Eviction and the frame.** D5 ranks a relative placement by the lines it draws on. The store keeps each buffer's relative placements in an index of their own, and the frame takes each one whose box reaches a visible row, so a child whose parent lies far above the view still draws.

**Unicode placeholders.**

- **The virtual placement.** A kitty put with `U=1` makes a virtual placement: an image, a placement id, a size in cells (`c` and `r`, or the image's own size in cells at the console's cell size where they are left out), a source rectangle and a z, with no position. Making one never moves the cursor. It lies on no line, so no screen event reaches it: no scroll, erase, ED 2 or rewrap. It goes only by a kitty delete whose `d` is `i`, `I`, `r`, `R`, `n` or `N`, as the spec says, by its image's eviction or new transmission, by RIS, and with the alternate buffer when that buffer is emptied. It counts toward its buffer's placement count and charges (D2, D5), and D5 ranks its image with the kitty images that may be evicted while they show, oldest transmission first.
- **The placeholder cell.** A placeholder is the character U+10EEEE written into a cell as text, followed by up to three combining diacritics from the spec's list of 297 row and column diacritics. The first diacritic gives the cell's row in the picture, the second its column, and the third the top byte of the image id; a diacritic's value is its place in the list, counted from 0. The cell's foreground color names the image: a palette color (SGR 30 to 37, 90 to 97, or 38;5) gives its index, and a direct color (38;2) its 24-bit value, below the top byte. The cell's underline color (SGR 58) names the placement id in the same way, and the default underline color names none. The default foreground color, or an image id of 0, names no image. The cell's background is drawn under the picture, so it shows where the picture is transparent. A placeholder cell's foreground color names an image and is never drawn as a color, so when vtium-term resolves the cell's colors for a frame it takes the cell's foreground to be the default foreground color. Reverse video (the maintainer, 2026-11-02), whether SGR 7 on the cell, DECSCNM's reverse screen or a selection drawn by swapping colors, then swaps the cell's background with the default foreground, exactly as it does for a space with the same background, so the picture's transparent pixels show what a blank cell with the same attributes shows, and never the color that encodes the image id. vtium-term applies this rule where it resolves every cell's colors, and the renderer draws the background it is given. The cell's other attributes do nothing to the picture, and the cell draws no underline or strike-through.

  > Edited 2026-11-02, after a review of vtium-term's frame: the frame swaps a cell's foreground and background for SGR 7 and for DECSCNM, which would put the color that encodes a placeholder's image id behind the picture. The bullet said nothing about reverse video.
- **The diacritic table.** vtium-term, which reads placeholder cells (below), holds the 297 diacritics as a table taken from Ghostty's table of them (`src/terminal/kitty/graphics_unicode.zig` in Ghostty, at commit 0b1729e945), which Ghostty published under the MIT license and derived from the list the kitty spec publishes. The table's source file and vtium-term's README carry Ghostty's copyright line and the MIT notice. vtium-term checks the table against the Unicode Character Database version it pins, 18.0.0: every one of the 297 code points must be a nonspacing combining mark (General_Category `Mn`) with canonical combining class 230 (Above) and no decomposition mapping of its own, and the table must run in increasing code point order with no code point twice. That check catches an entry that is not such a mark, but passes a wrong entry that is still an above mark in order, so vtium-term also pins the whole table to Ghostty's list with a checksum worked out from Ghostty's file at that commit.

- **Diacritics left out.** Along each row, from left to right, a cell with diacritics missing takes them from the placeholder cell to its left by the spec's three rules: with no diacritic, a left neighbor with the same foreground and underline colors gives its row, its column plus one and its top byte; with only a row, a left neighbor on the same picture row with the same colors gives its column plus one and its top byte; with a row and a column, a left neighbor on the same picture row with the same colors and the column before gives its top byte. A row or column that no rule gives is 0, and so is a top byte that no rule gives.

A hard line break restarts the count. The bullet said only "Along each row".

A third mark whose value is past 255 cannot be a byte, so it counts as left out too, and the cell takes its top byte by the rules above, or 0. The bullet said neither.
- **Placeholders are text.** vtium-term holds a placeholder as it holds any character with its combining marks, a cluster in its line's arena (ADR-1001), so a placeholder travels as text does: through a scroll, the scrollback, a rewrap (ADR-1003), an erase, an insertion or deletion of characters, a rectangle copy, and a program's redraw of its own panes. U+10EEEE is one cell wide. A placeholder with a row and a column diacritic takes 8 to 10 bytes of its line's cluster arena besides its length byte, more than the 6 bytes a cell the line's cluster budget allows other cells, so ADR-1001 lets a cluster that starts with U+10EEEE keep its first three marks whatever the budget, up to 17 bytes with its length byte (the maintainer, 2026-11-02). Every placeholder therefore keeps the row, column and top byte it was written with, wherever it starts in its line, and a cell written without them takes them from the cell to its left by the rules above.
- **Who reads placeholder cells, and what crosses to the store.** vtium-term owns the cells, so vtium-term alone reads placeholders. The store never sees a cell, a diacritic or a color; it knows lines only by their keys (D2). vtium-term reads a row's cells from left to right, applies the rules for diacritics left out, and groups the placeholder cells into *runs*. A run is a stretch of side-by-side placeholder cells on one row that name the same image id and the same placement id, lie on the same row of the picture, and show consecutive columns of it. For each run, vtium-term hands the store seven values: the key of the line that holds the run and the run's first column; the number of cells in the run; the image id, all 32 bits, with the top byte from the third diacritic; the placement id, or none; and the picture row and picture column of the run's first cell. A run never continues from one row to the next, so a picture row that a rewrap splits over two rows becomes two runs, and the second starts at the picture column after the last one the first shows. The store learns of placeholders only through these runs.
- **When vtium-term reads them.** vtium-term keeps no list of runs between reads. It reads them from the cells each time they are needed, so a write, an erase, an insertion or deletion of characters, a scroll or a rewrap that moves placeholder cells needs no step of its own: the cells move as text, ADR-1001's damage marks them changed, and the next read finds them where they now are. vtium-term reads runs at three times:
  1. **For a frame,** on the rows the frame shows. It hands the runs to the store's frame call together with those rows' line keys (D9).
  2. **For a store decision that needs a virtual placement's position on the screen,** on the screen's own lines of the buffer the decision concerns. The store needs positions only for a relative placement whose parent is virtual (A virtual parent, below), so vtium-term reads runs only while the store reports that the buffer holds such a placement, and only for the requests that can delete or evict one: a kitty delete that selects by cell, row or column, and a reservation that may evict (D5). It hands the runs with the request, beside the line keys the store already takes, and the read counts as input work (D5).
  3. **For damage,** on the screen's own lines, when the store reports that a virtual placement was made, replaced or deleted, or that the image it shows was transmitted again. The store reports the buffer and the kitty image id, and vtium-term marks changed every placeholder cell of that image; the read counts as input work (D5).

  A read may pass over a row that vtium-term knows holds no placeholder cell, as long as it never passes over a row that holds one.

The second read above named only those deletes and the reservation.
- **How a virtual placement is drawn where its cells are.** A virtual placement has no line, so the store draws it only through the runs it is handed. The store's frame call turns each run into an ordinary frame entry (the maintainer, 2026-11-02). It finds the run's virtual placement: the one with the run's image id and placement id in the buffer shown, or, for a run that names no placement id, the virtual placement of that image made last, under the spec's text: "the terminal may choose any virtual placement of the given image". It fits the picture to the virtual placement's size in cells, with its aspect kept and centered in that box, as the spec asks ("The image will eventually be fit to the specified rectangle, its aspect ratio preserved"). The entry's anchor is the run's line and first column, its box is the run's cells, its source rectangle is the part of the fitted picture under those cells, and its drawn rectangle is the part of those cells the picture covers. A run whose image or virtual placement is not found makes no entry, and where part of a run lies outside the virtual placement's rows or columns, the entry covers only the part inside, so a cell with no picture draws its background and nothing else. The entries take their virtual placement's z, layer and place in its stack (D4), the store puts them into the draw order with the placements it holds, and the entries of one virtual placement draw in the order of their rows, then their columns. The compositor draws them as it draws every entry, and knows nothing of placeholders. The frame call reads the runs and the store and changes neither, so the state still follows from the bytes.

- **Damage.** A placeholder cell that is written, erased or moved is marked changed as any text is (ADR-1001), and a change to a virtual placement or to the image it shows marks that image's placeholder cells through vtium-term's read for damage (above).

### D14: vtium presents itself as a kitty-compatible terminal

vtium presents itself as a terminal compatible with kitty's protocols, under its own name (the maintainer, 2026-11-01). For each kitty protocol it takes, the kitty graphics protocol among them, vtium follows kitty's published specification, and where the specification is silent or leaves a choice open, it follows kitty's own behaviour, found by running kitty as a black box; kitty's source is never read (CONTRIBUTING.md). It answers kitty's graphics query (`a=q`) as kitty answers it, and it answers the specification's feature queries as the bullets below say (the maintainer, 2026-11-13, `considered`). It keeps `TERM=xterm-vtium` and does not set `KITTY_WINDOW_ID`, so a program that checks for kitty by name or by that variable does not take vtium for kitty. The choices D13 and ADR-1102 make where the spec is silent are vtium's readings until a black-box run of kitty confirms or corrects them, and their goldens stay provisional until then. ADR-1000 states the same principle for kitty's protocols beyond graphics.

The specification added feature queries in its version 0.50.0. kitty 0.49.2, the version run as a black box on 2026-11-13, refuses the `e` key as a malformed command, so no run settles these rules. Each rests on the specification's section "Querying support for protocol features" (`basis`).

- **What a feature query is.** A feature query is a query (`a=q`) that carries the key `e`. The value of `e` names the action the program asks about: `t`, `T`, `q`, `p`, `d`, `f`, `a` or `c`. vtium reads the query's other keys as that action reads them, as the specification says.
- **The answer.** vtium answers at once with `i=ID,e=E,KEYS;OK`. KEYS lists each key of the query whose value is not the key's default and is one vtium takes for that action, with that value. vtium checks each key on its own, as a real command of that action would take it, and not against the query's other keys. The specification lets the keys come in any order. vtium writes `i`, then `e`, then the keys in the byte order of their letters, capitals first. Its answer to the specification's example, `a=q,i=31,e=T,U=1,C=1`, is then the example's own reply, `i=31,e=T,C=1,U=1;OK`.
- **What the answer leaves out.** vtium never reports `a`, `i`, `I`, `m` or `q`, as the specification says. It never reports a key that the action does not read, such as `U` for `t`, or a key at its default, such as `f=32`.
- **What vtium reports.** vtium reports every one of the eight actions. So `e=f`, `e=a` and `e=c`, which the specification names for detecting animation, report it (ADR-1102 D6). It reports `U=1` for `T` and `p`, the Unicode placeholders of D13, and `P`, `Q`, `H` and `V`, the relative placements of D13. It reports `f=8` and `f=16` for `t`, `T` and `q`, and not for `f`, which refuses them (D15). For each other key, it reports the values a command of that action takes within vtium's bounds.
- **An action vtium does not know.** A feature query whose `e` names no action is answered `i=ID;OK`, with no `e` and no keys. The specification says that an answer without `e` means the action is not supported.
- **What a feature query never does.** A feature query stores nothing. vtium ignores its payload and its `m`, so it never opens an upload in chunks, and it has no effect on images or on an upload that is open (D16). A feature query without `i` gets no answer, since the specification requires the key. Its `q` applies as on any query, so `q=1` hides the answer.
- **`e` on another action.** The specification says that "the e key is only allowed in query actions". vtium refuses a command of another action that carries `e` with its own text, `EINVAL:invalid argument`, and does nothing else (the maintainer, 2026-11-13, `considered`). This rule comes before D16's rule for chunks: a direct transmission that carries `e` while an upload is open is refused, and neither continues nor ends the upload (the maintainer, 2026-11-13, `considered`).

The paragraph's fourth sentence read: "Kitty's specification has no feature query, so vtium answers none (edited 2026-11-02; D13's Detection bullet says why)."

> Edited 2026-11-13, later: the maintainer settled how vtium treats `e` on another action (`considered`). The bullet's last sentence read: "What vtium does with a command of another action that carries `e` waits on the maintainer (For the operator's check)."

### D15: kitty's palette formats, and raw data short of its picture

Kitty's specification added two raw formats in kitty 0.50.0, `f=8` and `f=16`, in which each pixel is an index into the terminal's palette (a palette-index picture). With `f=8` a pixel is one byte, the index, and the picture is opaque. With `f=16` a pixel is two bytes, the index and then the alpha, from 0 for transparent to 255 for opaque. vtium takes both and turns the indices into colors when the picture arrives, so the store keeps its one premultiplied format (the maintainer, 2026-11-06, `considered`). A later palette change does not recolor a picture already stored.

- **Where the colors come from.** The kitty handler asks the terminal for its colors through the handler's context once, when the transmission's first chunk arrives, and converts every pixel of that transmission with them, whatever arrives between its chunks. vtium-term answers with the palette its frames draw through: the palette vtium.conf configured, with the colors a program has since set through OSC 4, 10, 11, 12, 17 and 19. A host that gives no colors gets `f=8` and `f=16` refused with EINVAL.
- **What each index means,** as the specification's table gives it. Indices 0 to 247 are the colors of the 256-color table that SGR 38;5 reads: the 16 ANSI colors, the 6x6x6 cube and the first 16 grays of the gray ramp. 248 is the default background and 249 the default foreground. 250 is the selection's background (OSC 17) and 251 the selection's foreground (OSC 19). 252 is the cursor's color (OSC 12) and 253 the color of the text under the cursor. 254 is the color kitty highlights a link with when the pointer is over it, and 255 is reserved and means the default foreground.
- **Colors vtium takes from the cell.** The specification says that when a terminal takes one of the colors at 250 to 253 from the cell it is drawn over, 250 and 252 are the default foreground and 251 and 253 the default background. vtium takes them from the cell in these cases: the selection while OSC 17 has set no background, which vtium then draws inverted; the selection's foreground while OSC 19 has set none; the cursor while OSC 12 has set no color, which vtium then draws inverted; and the text under the cursor always, since vtium has no color of its own for it. A color a program has set is used as it is.
- **Index 254 is the default foreground.** vtium highlights no link under the pointer, so it has no link color of its own. The default foreground is the color the specification gives the reserved index 255, and it stays readable against the default background.
- **Alpha.** An `f=16` pixel's alpha applies to the color its index gives, which is then premultiplied as a `f=32` pixel's is. The specification says that 248 is always drawn opaque, ignoring the window's background opacity; vtium draws no window with background opacity, so 248 needs no rule of its own.
- **The media.** vtium takes `f=8` and `f=16` sent directly and uncompressed (`t=d` with no `o=z`), which the console decodes as the bytes stream in (D7). The image helper's pixel description (ADR-1101 D7) carries RGB and RGBA only, so `f=8` or `f=16` from a file, a temporary file or shared memory, or with `o=z`, is refused with EINVAL, and a temporary file or shared-memory object is removed as every refused one is.
- **Animation.** The specification says that animation and frame composition are not supported for pictures in these formats, and vtium refuses them as kitty 0.50.0 does (the maintainer, 2026-11-06, `considered`; `basis`). A frame (`a=f`) in `f=8` or `f=16` on any picture, and a frame in any format on a picture that arrived as palette indices, answer `EINVAL:Animation is not supported for indexed color images`. A composition (`a=c`) on such a picture answers `EINVAL:Composition is not supported for indexed color images`. The store remembers which pictures arrived as palette indices, and a picture sent again under the same id in another format takes frames again.

  > Edited 2026-11-06, the maintainer's answer on kitty 0.50.0's differences: the bullet read "**Animation.** The specification says that animation and frame composition are not supported for pictures in these formats, so a frame (`a=f`) sent as `f=8` or `f=16` is refused with EINVAL. A picture that arrived as palette indices is stored as colors, so vtium takes frames in the other formats onto it, as onto any picture."
- **Detection.** A program finds out whether vtium takes the formats with the graphics query, as the specification suggests: `a=q` with `f=8` is answered OK.
- **Raw data without its size.** A raw upload (`a=t`, `a=T` or `a=q`, in `f=8`, `f=16`, `f=24` or `f=32`, from any medium) that leaves out `s` or `v` is answered `EINVAL:Zero width/height not allowed`, as kitty 0.50.0 answers it (the maintainer, 2026-11-06, `considered`; `basis`); vtium answered `EINVAL:invalid argument`. ### D16: kitty uploads in chunks, and what arrives while one is open

A program that sends a picture's data directly splits the base64 into chunks, each one a graphics command of its own. Every chunk but the last carries `m=1`. The specification says what a client must send, but not what a terminal does with another command that arrives while an upload is open. The maintainer decided that vtium's rules for this are written clean-room (the maintainer, 2026-11-13, `considered`). They come from the specification and from black-box runs of kitty 0.49.2, and their author read neither kitty's source nor vtium's code for them (`basis`). Where the specification is silent, vtium follows kitty, as D14 says. Where kitty's behaviour loses a later command's data or leaves kitty's own state broken, the maintainer chose the rule (the maintainer, 2026-11-13, `considered`).

Four terms. An *upload* is a picture or a frame whose data comes in several commands. The first command carries the keys and `m=1`, and each later command is a *chunk*. An upload is *open* until a chunk with `m=0`, or with no `m`, ends it, or until something below ends it early. A *direct transmission* is a command whose action is `t`, `T` or `f`, or is left out, and whose medium is `d`, or is left out.

- **One open upload in each buffer.** The main screen and the alternate screen each hold at most one open upload, as each holds its own kitty ids (D2). A command reaches the upload of the buffer in use when the command arrives. Switching screens ends neither upload. In kitty's runs, an upload opened on the main screen survived a trip to the alternate screen, and an upload made on the alternate screen meanwhile was stored there alone.
- **What a chunk is.** While an upload is open, every direct transmission is its next chunk, whatever keys it carries. vtium takes the chunk's data, its `m` and a `q` other than 0, and ignores every other key. A whole picture that names another image, the same image, `i=0`, no image or an image number therefore ends the open upload as its last chunk, and the image it names is not made. A frame (`a=f`) that arrives during a picture's upload is that upload's next chunk too, since a frame's own chunks carry `a=f` and the action cannot tell a chunk from a new command. The specification says that chunks "must have only the m and optionally q keys", and kitty took every transmission but the frame as a chunk in the runs.
- **Each chunk's data.** vtium decodes each chunk's base64 on its own and appends the bytes. A chunk that does not end on a group of four characters is read as unpadded base64, as kitty read it: two characters left over give one byte, three give two, and one gives none.
- **The reservation, and the old image under the same id.** At the first chunk, vtium reserves the upload's whole cost from the console's image budget, as D5 reserves any picture's, or a frame's cost from the frame allowance (ADR-1102 D1). The old image under the same id stays counted while the upload is open, so the store holds both within the budget, and keeping the old image can never take the store past it. When eviction cannot make room for both, vtium refuses the upload at its first chunk with `ENOSPC:image storage is full` and opens no upload. The old image and its placements stay until the upload ends and vtium accepts its data, and only then does the new image replace them, as the specification asks. A put during the upload therefore finds the old image. An upload that is refused, fails or ends early leaves the old image as it was. The specification says that "terminals must not display anything, until the entire sequence is received and validated", and kitty, which removed the old image at the first chunk, did not keep to that.
- **A cap on an upload's data.** The bytes an open upload has taken, whatever commands added them, never pass its reservation. For raw data, the reservation is fixed at the first chunk: width × height × 4 bytes and the 512-byte charge (D2). That is more than any raw format needs, so a correct upload always fits, and bytes past what the picture needs are ignored up to the reservation, as D15 says. A chunk that would take the upload past its reservation fails the upload. vtium answers `EINVAL:invalid argument`, drops the data and gives back the reservation, and each later command is a command of its own. The answer is EINVAL because the program sent more data than its own keys allow, which only the program can fix; ENOSPC would tell the program that the store is full, which is not so. PNG and zlib data sent directly is buffered for the helper, and its reservation grows before each chunk is kept (D5, D7). A chunk whose growth the budget cannot take fails the upload in the same way, with `ENOSPC:image storage is full`.
- **`q` across chunks.** The upload's `q` is its first chunk's. A later chunk's `q` other than 0 replaces it, and a later `q=0` changes nothing, as in kitty's runs.
- **One answer for an upload.** An upload gets at most one answer, at the chunk that ends it. That is its last chunk, unless a refusal at the first chunk or a failure at the cap ends it sooner. A chunk that keeps the upload open is never answered. The answer is the one a single command would get with the first chunk's keys and the data of every chunk: a frame's carries `r`, as ADR-1102 D2 gives it, and a query's says OK or gives its error and stores nothing. A check of the data, such as D15's ENODATA, counts the bytes of every chunk together. With `q=2` the upload sends no answer at all, as kitty's `q=2` sent none in the runs. Every answer vtium sends is one line made of fixed messages and numbers it re-encodes (D6, Replies), no longer than a named constant of vtium-image's bounds table that covers the longest line the closed set of answers can form. So no command makes vtium send more than one line of that size, and an upload of any number of chunks makes it send at most one.
- **Where an `a=T` upload's picture goes.** It goes at the cursor as it is when the last chunk arrives, with the first chunk's display keys. The specification asks for this: "the cursor position used to display the image must be the position when the final chunk is received".
- **A first chunk refused by its keys.** When the first chunk's keys alone decide a refusal, vtium answers at once and opens no upload. Such refusals include an unknown format, both `i` and `I`, raw data with no width or height, a side past `max-graphic-size`, a box past `BOX_CELLS_MAX`, an unknown medium, and a reservation the budget cannot take. Each command that follows is then a command of its own, as in kitty's runs. A check that needs the data waits for the last chunk.
- **What ends an upload early.** vtium ends the open upload, drops its data and gives back its reservation, with no answer for it, when one of four things arrives. A delete (`a=d`) ends it, with any `d` and whether or not it matches anything, as the specification requires: "the partial upload must be aborted". A transmission from a file, a temporary file or shared memory ends it, and vtium then handles that transmission on its own, as kitty did. RIS ends it, through the kitty handler's `reset` (D6). While kitty graphics is not offered, the start of any APC string ends it (D6, Routing). A chunk cut off by CAN or SUB ends the upload too, since the upload can no longer be completed, and vtium then answers `EINVAL:invalid argument` under the upload's `q` (the maintainer, 2026-11-13, `considered`). The commands that follow are commands of their own. A string cut off before its keys end is not yet known to be a chunk, and leaves the upload open. A transmission from a file, a temporary file or shared memory never opens an upload, whatever its `m` says. When a console's session ends, its open uploads go with its store, and nothing answers, as D7 drops a request out at that moment.
- **What leaves an upload open.** vtium carries out a put, a composition and an animation control on their own, as kitty did in the runs. It answers a feature query and leaves the upload as it was, as the specification says (D14). It answers a query (`a=q`) on its own too, from the query's own keys and data, ignores the query's `m`, and leaves the upload open, so a program that starts after another stopped halfway through an upload still finds kitty graphics. Text, control functions, CSI sequences, and OSC, DCS and APC strings that are not kitty graphics commands do what they always do. A sixel or an iTerm2 picture does what it always does and leaves the kitty upload open, since the specification's "graphics related escape codes" are its own commands. The specification's sentence on the cursor expects such output between chunks.
- **A clear leaves an open upload alone.** ED 2, and the clear that comes with entering the alternate screen, remove what is on the screen, and an open upload has no cells on the screen yet. So neither reaches it, and an `a=T` upload places its picture after the clear.
- **No upload open.** While no upload is open, a command that looks like a chunk is a command of its own, with the defaults for the keys it leaves out. `m=1` on it opens a new upload.
- **Where vtium departs from kitty.** kitty kept an upload open after RIS, ED 2 or the alternate screen's clear, with its data gone. It took the next transmission as the upload's chunk and answered `EILSEQ:More payload loading refers to non-existent image`. kitty also answered a query during an upload with the query's id and then lost the upload, answered a frame during a picture's upload with `EINVAL:Frame width 2 larger than image width: 0` and lost the upload, and sent no answer to a frame or a query sent in chunks. vtium does none of these, by the rules above.

## C notes: the C reference's flow

How the C reference handled images, as the logical reference for the decisions above, read at kmscon `b1f7a7c5` and libtsm `eeaf293`.

- **Stores.** libtsm kept a `struct tsm_image_store` for each screen buffer and reached the one in use through `cur_store`. Placements were listed on their line (`placement_attach`) and cut by `placement_split` and `placement_cut`; screen events reached the store through `screen_images_scroll`, `screen_images_cut`, `screen_images_erase_screen`, `screen_images_clear_alt`, `screen_images_reset` and `screen_images_discard_line` (`libtsm/src/tsm/tsm-image.c`). In a region scroll, `screen_images_scroll` left a kitty placement that crossed an edge where it was and re-anchored it through `placement_pend` to the line that took its row (`tsm-image.c:777-783`).
- **Eviction.** `image_rank` gave each image its rank, `image_order` its order within the rank (`transmitted` for kitty images on the screen, `last_use` otherwise), and `image_victim` picked the next to go across both buffers, or from one buffer for a count bound (`store_make_room`, `placement_make_room`). `evictable_bytes` counted what could go before anything went. `screen_images_frame` stamped `last_use = ++image_clock` on every placement each frame drew (`tsm-image.c:1120`), and `image_clock` was one static counter for the whole process (`tsm-image.c:46-50`).
- **Bounds and charges.** `TSM_SCREEN_IMAGE_OVERHEAD` (512), `TSM_SCREEN_IMAGES_PER_STORE` (1024), `TSM_SCREEN_PLACEMENT_OVERHEAD` (256), `TSM_SCREEN_PLACEMENTS_PER_STORE` (4096) and `TSM_SCREEN_IMAGE_MAX_CELLS` (10,000, checked against a box's columns and rows each, `tsm-image.c:1899`) in `libtsm.h`; `placement_make_room` charged the placement overhead, and `screen_images_settle` paid a debt the budget refused by dropping the smallest placements first.
- **Draw order.** `frame_rec_cmp` sorted a frame's placements by z, which also set the band, then kitty before sixel, then image id, then creation order, a placement's pieces by key (`tsm-image.c:951-967`).
- **Modes.** `tsm-modes.def` marked 80, 1070 and 8452 `HOST_SIXEL`, and `mode_offered` in `tsm-vte.c` reported their fixed state through `MODE_FIXED` while `vte_sixel_on` was false.
- **The selection under pictures.** kmscon's bbulk composed a cell under a picture in `compose_covered` (`src/render/bbulk.c:1355-1402`), with its text, selection colors included, below the top band's pictures, so a picture above text hid a selected cell.
- **XTSMGRAPHICS.** `vte_xtsmgraphics` answered status 1 for every item while sixel was off (`tsm-vte-image.c`), and the minimal build's own `vte_xtsmgraphics` answered `CSI ? Pi ; 1 S` always (`libtsm/src/tsm/tsm-vte-image-none.c:75-84`).
- **Resets and an APC while kitty was off** (libtsm `src/tsm/tsm-vte-image.c`). `vte_image_reset`, which RIS called, dropped the sixel decoder and the shared registers and set the register count back to the host's. `tsm_vte_set_sixel_registers`, the host's call to set the register count and `private-color-registers`, called `vte_image_reset` and `vte_modes_reset_hard`, which reset the modes only RIS resets, 80, 1070 and 8452 among them. `vte_apc_start` called `tsm_kitty_cancel` on every APC string while kitty was off, which dropped an upload in progress and its reservation.
- **Routing and the pause.** `vte_dcs_start`, `vte_dcs_collect` and `vte_dcs_end` fed the sixel decoder (`tsm_sixel_feed_some`, `tsm_sixel_finish`), and `vte_apc_start`, `vte_apc_collect` and `vte_apc_end` the kitty parser (`tsm-vte-image.c`). A bounded input call stopped at `VTE_INPUT_WORK`, 2^24 (`tsm-vte.c:3690`), and took nothing while `vte_image_paused` held. kmscon's `kmscon_pty_pause` and `kmscon_pty_resume` stopped and restarted a pty's reads (`src/misc/pty.c`), tested by `test_pause` in `tests/test_pty.c`, and `tsm_vte_image_reply` delivered the helper's answer.
- **The host.** `image_host.c` started and killed the helper, `image_identity.c` found the session's user, `image_helper.c` applied the file rules and decoded PNG and zlib, and `render/image_budget.c` held the process's one budget, whose `make_room` trimmed the renderers' pictures before evicting libtsm's images.
- **The replay.** `tsm-replay`'s fixture host answered requests from a case's fixture files, which vtium's replay interface carries as "The fixture host".
- **Refusals in the log.** `vte_sixel_finish` logged a sixel picture it did not store or place with `llog_debug`, each time (`tsm-vte-image.c:161-171`), and `log_excess` logged a kitty upload's bytes past `s` and `v` with `llog_dprintf` at `LLOG_DEBUG`, "since a video can send it every frame" (`tsm-kitty.c:806-826`). A refusal it answered to the program, such as ENOSPC, it did not log.

## Where vtium departs from the C reference

- **The use clock is each store's own and moves only on stream events.** The C reference renewed every drawn image's use on each frame, on one clock for the whole process, so its eviction depended on which frames were drawn (D5).
- **Each console has its own budget,** where the C reference had one for the whole process across every screen (D5).
- **Scaled copies never evict a stored picture.** The C reference's scaled copy for a picture on screen could evict pictures in the scrollback (D5).
- **At equal z, a sixel and a kitty picture draw in the order they arrived,** with a newly arrived kitty picture slid beneath the first higher kitty id. The C reference drew every sixel above every kitty picture (D4); the goldens D4 names can differ.
- **Modes 80, 1070 and 8452 answer DECRQM with 0 in the minspec build,** where the C reference answered their fixed state (D10).
- **A placement's change marks the cells under it,** by ADR-1001's rule, where the C reference left each renderer to damage placement rectangles itself.
- **Rectangle operations cut cell-content pictures** as the erases and writes they are (D3); the C reference had no rectangle operations.
- **A width change rewraps the main screen and carries each anchor** (D8, ADR-1003); the C reference never reflowed.
- **A handler acts only on a string ended by its terminator,** vtium-parse's listed departure.
- **The cursor, the pointer and vtium's notices draw above every placement** (D4); ADR-103 gave them no place in its order.
- **The selection tints a picture that covers a selected cell** (D4), so both stay visible, where the C reference composed a selected cell like any other cell, so a picture above text hid the selection.
- **Relative placements, Unicode placeholders and animation are supported targets** (ADR-1000), which the C reference answered with EINVAL; the kitty handler builds the first two (D13), and kitty animation builds on this pipeline (ADR-1102).

## Where vtium departs from the specifications

- **A palette-index picture keeps the colors it arrived with.** Kitty's specification redraws an `f=8` or `f=16` picture in the terminal's current colors whenever they change; vtium turns its indices into colors once, as it arrives, so a later palette change, a theme change included, leaves it as it was (D15).
- **`f=8` and `f=16` are taken only sent directly and uncompressed.** The specification lets every medium and `o=z` carry them; vtium refuses them from a file, a temporary file or shared memory, and with `o=z`, with EINVAL, because the image helper's pixel description has no layout for palette indices (D15).
- **A sixel dot is one square pixel,** where DEC's VT340 manual draws each dot twice as tall as it is wide unless the picture says otherwise (D3). The C reference drew square dots too, so vtium's sixel goldens hold.

> Edited 2026-11-06: the departure "A picture that arrived as palette indices takes frames." is gone, since vtium now refuses frames on such a picture as kitty does (D15).

## Consequences

### Positive

- One store, one budget and one compositor path serve every protocol, so a fix or a speed-up in any of them serves all.
- A protocol's rules sit in one place, and the compiler stops any other code from branching on the protocol.
- A console's pictures follow from its own bytes and host events, whole or chunked, whatever was drawn and however its output interleaved with another console's.
- A program orders its pictures at equal z by the order it sends them, across protocols, except that a kitty picture slides beneath any kitty picture with a higher id, as kitty's own rule asks.
- No file or shared-memory object a program names is opened by the console's root process, and no PNG or zlib payload is decoded there.
- The minspec build carries no image code at all.

### Negative

- A sixel takes two to four times the bytes palette indices would.
- A file or compressed image pauses that console's output for a round trip to the helper, up to 2 seconds when the helper hangs.
- Several consoles can each hold a full budget of pictures, and frames in flight can keep deleted pictures alive past the budgets.
- A picture too large for the scaled-copy cache is scaled again on every frame it draws.
- The C reference's goldens that mixed sixel and kitty at equal z judged a different order, so those cases were listed as departures.
- Every handler, the compositor and the helper build against the store's interface, so changing it later touches all of them.

### Neutral

- iTerm2's inline images work through a thin compatibility front end that places each picture as a sixel, so the store, its rules and the compositor know only sixel and kitty.
- The replay interface already carries the image commands and the fixture host the C reference's goldens were made with, and vtium-replay gains them with `images`.
- The frame path review's remaining items (a buffer token for each display, drm2d's logic apart from its dumb buffers) are not this record's, and nothing here closes them off.
- The image helper's own record decides the helper's sandbox beyond ADR-1400 D2, and kitty animation's own record decides animation frames.

## Alternatives Considered

- **One budget for the whole process,** as the C reference had. Rejected (the maintainer, 2026-11-01): one console's output could evict another console's pictures, in an order that depends on how the two consoles' outputs interleave in time.
- **Scaled copies inside the image budget,** as the C reference's bbulk kept them. Rejected: a frame drawn or not drawn would then change what the store keeps, which the determinism rules forbid.
- **Sixel above kitty at equal z,** the C reference's order. Rejected (the maintainer, 2026-11-01): a program could not order a sixel and a kitty picture on purpose by sending them in that order.
- **Arrival order for every pair, kitty included.** Rejected (the maintainer, 2026-11-01): it departs from the kitty spec's id rule.
- **A new kitty picture on top, with the higher ids lifted above it.** Rejected (the maintainer, 2026-11-01): it moves pictures already on the screen, so a picture could jump in front of a sixel drawn after it.
- **A sort key of z, then id, then arrival.** Not taken: with a sixel between two kitty pictures whose ids run against their arrival, the three pairwise rules form a loop that no sort key satisfies; a stack the store keeps as placements arrive always has one answer.
- **Branching on the protocol in the store and the compositor,** as the C reference's code did. Rejected: the maintainer asked for one function to hold every protocol rule, and a private tag lets the compiler hold the line.
- **The image store inside vtium-term,** with vtium-image holding only the decoders. Not taken: the store, its rules and its budget are one unit that the handlers act on, and keeping them in vtium-image leaves vtium-term without image code in the minspec build and vtium-image free of vtium-term.
- **vtium-image depending on vtium-term,** with the binary wiring the two together. Not taken: vtium-term would then reach the store on every screen event through a hook object the binary installs, so every scroll and erase would pass through that hook in every build, minspec included, where an optional dependency leaves the minspec build with no image code at all.
- **Inflating zlib in the console,** which already holds an inflate for its built-in fonts (ADR-1200 D6). Not taken: the C reference sent zlib to its helper, and a fault in a decoder facing a program's bytes then costs that request and a helper restart, never the console.
- **Holding sixel pictures as palette indices.** Rejected (the maintainer, 2026-11-01): one pixel format keeps one composition path; the C reference's cost note measured the trade.
- **Waiting for a measurement of the C reference's A5 and A7 targets** before building the store. Rejected (the maintainer, 2026-11-01): vtium sets its own performance targets and measures them on vtium.
