# ADR-1500: vtium is packaged from a recipe repo per package manager, and lives beside the C reference's package

## Summary

- **Decided:** vtium's packaging recipes live in one repository per package manager in the vtium GitHub organization, each a git submodule of vtium under `packaging/<manager>`. Arch comes first, in `vtium/vtium-arch`, published to the AUR under the maintainer's account: `vtium-git`, built from the tip of GitHub's `main` or, by a documented setting, from a local checkout and branch, and `vtium`, built from a signed version tag, the first being the pre-release `v0.1.0-alpha.1`. The package installs vtium beside the C reference's own Arch package, `kmscon`, and takes none of its files or unit names: it installs `/usr/bin/vtium`, the glyph helper `/usr/bin/vtium-vitrify`, and the units `vtium@.service` and `vtium-getty@.service`. The user gives vtium one VT, or every VT on a machine that runs no C reference console, with the subcommand `vtium console enable`, and takes them back with `vtium console disable`, which restores the units it changed as they were. A development install, `make vt-install`, moves to names of its own (`vtium-dev@.service`, `vtium-dev-getty@.service`, `/usr/local/bin/vtium-dev` and its own helper) so that the packaged vtium and a development vtium run on separate VTs at once. Both read the same configuration. An upgrade replaces the files and never restarts a running vtium; the new build runs from that VT's next start. Every problem the packaged vtium shows becomes an issue.
- **Trades away:** Packages that anyone on the AUR can install before vtium is ready for them, at their own risk. The development install's current names: `make vt-install` and the docs that name `vtium@ttyN` for it change. A second repository to keep, and a submodule pointer to move when it changes. The packaged vtium runs behind development on purpose.
- **One-way?** Expensive: the packages are published to the AUR, so other machines can install them by their names and enable `vtium@ttyN` by that name, and a rename strands them. A signed tag, once published, is never moved.
- **Probes:**
  - *Confident (upgrades):* an upgrade of the package never restarts vtium on a VT. The new build runs from that VT's next start: a reboot, a failure, or a restart the user asks for.
  - *Confident (no start):* `vtium console enable` and `disable` change only what starts on a VT next time, at the next boot or the next switch to it, and never start or stop vtium, so they never end the session you typed them in; each prints the `systemctl start` or `stop` that makes the change now, with a warning that it ends every session on that VT.
  - *Not confident (shared head file):* the development vtium and the packaged one read the same `/etc/vtium/heads.conf`, so a key that only the newer build knows breaks the file for the older one.
- **Inversion:** Between one install that the last build overwrites, as `make vt-install` over a package would, and a second machine for the packaged build. vtium keeps two installs on one machine under separate names, sharing the configuration.

## Context

The maintainer wants vtium installed on this machine the way a user installs it, through a package manager, and kept running there while development goes on. The package is a real test of what development alone never exercises: the maintainer's own head file and profiles in daily use, a package manager installing vtium's tree, upgrades under a running console, and removal. Arch is the package manager on this machine, and other package managers follow.

Two installs already compete for the names a package would take. `make vt-install` writes `/usr/local/bin/vtium` and the units `vtium@.service` and `vtium-getty@.service` into `/etc/systemd/system`, where a unit file overrides one of the same name in `/usr/lib/systemd/system`, the directory a package installs into. Left as it is, a development install would silently take over the packaged unit on every VT. And this machine runs the C reference's program as Arch ships it, the `kmscon` package (10.1.0) and its `kmscon-terminfo` package, which own `kmsconvt@.service`, `kmscon.service`, `/etc/kmscon/kmscon.conf.example`, `/usr/share/terminfo/k/kmscon` and, by its enablement, `/etc/systemd/system/autovt@.service`. `make install-tree`, the tree that tier 3 installs in its guest, stages vtium under several of those same paths, because vtium ships as a drop-in replacement for the C reference.

A VT (a Linux virtual console, switched with Ctrl-Alt-F<n>) runs one console at a time. logind starts `autovt@ttyN.service` on a VT that nothing holds when the user switches to it, and on this machine `autovt@` points at the C reference's `kmsconvt@`.

## Decision

### D1: one recipe repository per package manager, submoduled into vtium

- Each package manager's recipes live in their own repository in the vtium GitHub organization, and vtium holds each as a git submodule at `packaging/<manager>`. A submodule is a pointer from vtium's tree to one commit of the other repository, so vtium's history records which recipes go with which code, and the recipes keep their own history and can be published from their own repository.
- Arch comes first: `vtium/vtium-arch`, at `packaging/arch`. It holds `vtium-git`, which builds the latest `main`, and `vtium`, which builds a signed version tag (D2). Both names are vtium's on the AUR, which reserves no name, so each is published as soon as it can build: `vtium` from the first pre-release. Debian, Fedora and Nix each get a repository of their own later, named `vtium/vtium-<manager>` in the same way.
- A recipe stays thin: it calls vtium's own make targets to build and stage the files, so the knowledge of which file goes where lives in vtium's tree. vtium's Makefile gains a staging target for a package that lives beside the C reference's (D3), `make install DESTDIR=DIR PREFIX=/usr`, which every manager's recipe calls, with `make install-terminfo DESTDIR=DIR PREFIX=/usr` for the terminfo package (D3). Each refuses a `DESTDIR` that is unset, empty or resolves to `/`. The recipes and `make install` build with the host's toolchain, as a distribution's package build does, with no pinned sysroot and no glibc floor; only `make install-tree`, the tree tier 3 installs, links against the pinned Debian sysroot. Until `make install` reaches GitHub's `main`, the Arch recipe does the same install steps itself, inside its `package()` function, so that it builds from the `main` that exists today; it moves to the target once the target is on `main`.
- The Arch packages are published on the AUR, Arch's user repository, under the maintainer's account. `vtium-arch` holds one directory per package and a publish script that pushes each directory to that package's AUR repository, so the AUR always carries what `vtium-arch` holds. `vtium-git`'s history is published as it is, and each recipe's `Maintainer:` line gives the maintainer's plain email address. Anyone may install them, at their own risk. The maintainer builds them on this machine with `makepkg` the same way.

### D2: what the packages build

- `vtium-git` builds the tip of GitHub's `main`. Only reviewed work whose CI passed reaches `main`, so the packaged vtium is never a branch in progress.
- A documented setting in `vtium-arch` points the build at another git source and branch instead, such as a local checkout (`git+file:///path/to/vtium`, with `#branch=integration`), through makepkg's source entry (PKGBUILD(5)). makepkg clones that source, so the build takes the branch's last commit and never a checkout's uncommitted changes. The setting is read from the environment of the `makepkg` run, and `vtium-arch`'s README names it.
- The package follows Arch's rules for a package built from version control: it is named `vtium-git`, provides and conflicts with `vtium`, and computes its version in `pkgver()` from the commit it built, so `pacman -Q vtium-git` names the commit that the journal's `vtium Revision` line names at start.
- Each recipe reads `VTIUM_FEATURES` from the environment of the `makepkg` run and builds the console with those features, as in `VTIUM_FEATURES='images logind' makepkg -f`. Unset, it builds the minspec console, the build tier 3 judges, and the published `.SRCINFO` is made with it unset. `make install` takes the same list as `FEATURES='...'`.
- `vtium` builds one version tag, the first being the pre-release `v0.1.0-alpha.1`, tagged on `main` once the work this record starts has merged there. Its source entry names the tag and asks makepkg to check its signature (`git+https://github.com/vtium/vtium.git#tag=v0.1.0-alpha.1?signed`, PKGBUILD(5)), and its `validpgpkeys` holds the one key that signs vtium's tags, so makepkg refuses a tag that key did not sign. `vtium` conflicts with `vtium-git`, so a machine holds one of the two.
- **Signatures.** The maintainer signs each version tag with their key, `33F9B54FD2A4B6A4110749B3BA464FC9847A832A`. `vtium-arch` ships that key's public half under `keys/pgp/`, named for its fingerprint, so a builder can import it before building `vtium`. `vtium-git` checks no signature: the tip of `main` is a merge commit that GitHub signs with its own key, which says only that GitHub made the merge. Commits stay unsigned, because a delegated agent's signing would ask for the passphrase at every commit.

### D3: living beside the C reference's package

- The package installs `/usr/bin/vtium` and the glyph helper at `/usr/bin/vtium-vitrify`, the path the console runs it from when its build names none (`crates/vtium/src/helper.rs`). It installs `vtium@.service` and its getty fallback `vtium-getty@.service` into `/usr/lib/systemd/system`, generated from the shipped units in `crates/vtium/install/` by one generator in vtium's tree, which `make vt-install` uses too (D4). The generated `vtium@.service` is the shipped `kmsconvt@.service` with five changes: its name; an opening comment of its own in place of the shipped one, which named the C reference's units, saying to enable the unit one VT at a time by naming the VT, that enabling the template with no VT named fails and links nothing, that vtium on every VT is a separate step taken by hand, and that a failure starts `vtium-getty@`; `OnFailure=vtium-getty@%i.service`; `Conflicts=kmsconvt@%i.service` with `After=kmsconvt@%i.service`, so that starting vtium on a VT stops the C reference's console there first, as it stops a getty; and the shipped `DefaultInstance=tty1` replaced by `DefaultInstance=name-a-VT/vtium@ttyN`, which names no VT. systemctl refuses that value when it enables the template, before it links anything, and ignores `DefaultInstance=` when it enables an instance. So `systemctl enable vtium@.service` with no VT named fails and links nothing on every machine, while `systemctl enable vtium@ttyN.service` links `getty.target.wants/vtium@ttyN.service` and `autovt@ttyN.service` as before. With no `DefaultInstance=` at all, systemctl links `Alias=autovt@.service` before it fails on the template: on a machine with no `autovt@.service` yet, that makes `autovt@.service` point at `vtium@.service`, and logind then starts vtium on every VT it spawns. With `DefaultInstance=tty1` the template enable would enable VT 1. The cost is that `systemctl list-unit-files` shows `vtium@.service` as bad, and `systemctl is-enabled vtium@.service` fails; each `vtium@ttyN` reads enabled or disabled as usual (measured with systemd 262; systemd 254's `install.c` parses and links in the same order). `vtium-getty@.service` is the shipped `kmsconvt-getty@.service` under its new name, with an opening comment that names `vtium@.service`.
- The package never ships `kmsconvt@.service`, `kmsconvt-getty@.service` or `kmscon.service`, and never takes `autovt@.service`, which stays the C reference's while its package is installed. The shipped unit's `Alias=autovt@.service` stays in the generated unit, so that enabling vtium on one VT links `autovt@ttyN.service` for that VT alone and logind starts vtium there, never the C reference's console.
- The package puts the example configuration at `/usr/share/doc/vtium/kmscon.conf.example`, beside the example udev rules and hwdb fragment, because the C reference's package owns `/etc/kmscon/kmscon.conf.example`. It ships no `/etc/kmscon/kmscon.conf` and no `/etc/vtium/heads.conf`: they are the user's.
- vtium names itself `TERM=xterm-vtium` by default (ADR-1000), and its terminfo entry ships only under that name, in a package of its own built by the same recipe as the console: `vtium-terminfo` beside `vtium`, and `vtium-terminfo-git` beside `vtium-git`, which provides and conflicts with `vtium-terminfo`. No package ships an entry named `kmscon` or the source of one, so the machine keeps the `kmscon-terminfo` package for the name `kmscon`, and the C reference's sessions keep the entry they were built for. A terminfo package installs only `/usr/share/terminfo/x/xterm-vtium`, compiled with `tic -x`. `vtium-git` builds GitHub's `main`, which holds no `crates/vtium/install/xterm-vtium.ti` until the work that adds it reaches `main`; until then the recipe's `vtium-terminfo-git` step stops with a message naming the missing file, so the whole build fails and nothing half-made is published.
- The package enables and starts nothing: the VT to give vtium is the user's choice, and the user always names it. The user gives vtium one VT with `vtium console enable N` (D7), and starts vtium there with `systemctl start vtium@ttyN.service` once no session on VT N needs to survive, from another VT or over ssh; the start stops the getty on that VT through `Conflicts=`. `vtium console enable N` refuses a VT that the C reference's console holds, so on such a VT the user first disables `kmsconvt@ttyN` there, and the way back enables it again after `vtium console disable N`. `vtium-arch`'s README points at D7's subcommand for both directions.
- vtium on every VT is for a machine that runs no C reference console on purpose, and the user asks for it with `vtium console enable --all` (D7); enabling the template can never do it. `vtium-arch`'s README names it beside the one-VT command, and the package's install message points there. The way back is `vtium console disable --all`, which gives back the template link and the gettys that `enable --all` took.
- Removing the package removes its files and changes no unit's state, so the user first runs `vtium console disable --all`, while `/usr/bin/vtium` is still installed, and stops each running `vtium@ttyN`, and then enables `kmsconvt@ttyN` again where the C reference's console held that VT. The package's removal message names these steps, and names a template link `autovt@.service` to `vtium@.service` and each `autovt@ttyN.service` link to `vtium@.service` that it finds, because a link left behind names a unit that no longer exists, and it is the link logind follows when it starts a console on that VT.
- Later, once the C reference's package is gone from the machines vtium is installed on, a variant of the package may install the shipped units under the names `kmsconvt@` and `kmsconvt-getty@`, and the example under `/etc/kmscon`, as the drop-in replacement that `make install-tree` stages. That variant is not built.

### D4: the packaged vtium and a development vtium never collide

The packaged vtium owns the unit name `vtium@` and `/usr/bin/vtium`. `make vt-install` moves to names of its own, so the two run on separate VTs at once, and `make vt-check` and the other review runs borrow a third VT and touch neither. What each one owns, and what they share:

| What | The packaged vtium | The development vtium (`make vt-install`) | Shared, and why |
|---|---|---|---|
| The console binary | `/usr/bin/vtium` | `/usr/local/bin/vtium-dev` | Separate |
| The glyph helper | `/usr/bin/vtium-vitrify` | `/usr/local/bin/vtium-dev-vitrify`, which `make vt-install` installs root-owned with mode 0755 beside the console; the development console is built to run that path (`make vt-dev-console`), and vt-install refuses a console built for another helper | Separate. The console and its helper speak a wire format that changes between builds, so each console runs the helper built with it |
| The units | `vtium@.service`, `vtium-getty@.service` in `/usr/lib/systemd/system` | `vtium-dev@.service`, `vtium-dev-getty@.service` in `/etc/systemd/system`, with `ExecStart=/usr/local/bin/vtium-dev`, `OnFailure=vtium-dev-getty@%i.service`, `Conflicts=` with `After=` naming `vtium@%i.service` and `kmsconvt@%i.service`, and `DefaultInstance=name-a-VT/vtium-dev@ttyN`, for the reason D3 gives. `make vt-uninstall` names a template link `autovt@.service` that points at `vtium-dev@.service`, and leaves it in place | Separate. A unit in `/etc/systemd/system` overrides one of the same name in `/usr/lib/systemd/system`, so a shared name would let the development unit replace the packaged one on every VT |
| A VT's `autovt@ttyN.service` link | Made by `vtium console enable N` (D7), through `systemctl enable vtium@ttyN` | Made by `make vt-install VT=N` | One link per VT, so one of them per VT. `systemctl enable` on a VT whose link names another unit fails, and still adds the unit to `getty.target`'s wants, so the user disables it again (measured); `make vt-install` refuses a VT where `vtium@ttyN` is enabled or the link names another unit, and the `Conflicts=` in the development unit stops the other on that VT if both are started |
| `/etc/kmscon/kmscon.conf` | Read | Read | Shared, with the C reference's console too. It is the user's configuration, and a key that only the newer build knows is logged and ignored by the older one |
| `/etc/vtium/heads.conf` and the frits in `/etc/vtium/fonts` | Read | Read | Shared: they hold the maintainer's heads and profiles, which the package exists to test in daily use. The maintainer chose one head file for both: the C reference's console still runs on other VTs, so one file is enough. A key that only the newer build knows still breaks the file for the older one, which then sets it aside under `policy = open` and shows its panic screen under `policy = closed` |
| `/run/vtium/ttyN.closed` and `/run/vtium/ttyN/` | Written for its VT | Written for its VT | Shared directory, one file and one directory per VT. One vtium runs per VT, so each marker belongs to the vtium on that VT, and each getty fallback reads its own VT's marker (ADR-1401 D9) |
| `/run/vtium-vt.lock` | Never taken | Never taken | The review runs' alone: one review run at a time |
| `/var/lib/vtium-dev-install` | Never read or written | `make vt-install`'s record and manifests | `make vt-install`'s alone, named like the development install's other files |
| The process name | `vtium` | `vtium-dev` | Separate. `vtium blank --vt N` and `vtium wake --vt N` find a process named `vtium` or `vtium-dev` |

- `make vt-install` and `make vt-uninstall` move to the new names, and the development helper goes through the same copies by temporary name and rename, the same checksum record and the same uninstall as the other files. vt-install refuses a VT where `vtium@ttyN` is enabled or running, as it refuses one where `kmsconvt@ttyN` runs.
- When the review runs pick a free VT, they pass over a VT where `vtium@ttyN` or `vtium-dev@ttyN` is enabled or running, and they refuse such a VT when it is named with `VT=N`, as they treat a VT that `make vt-install` holds, because an enabled vtium that is not running is the maintainer's console all the same.
- A review run uses the helper built with the vtium it runs. `run-vt.sh` copies that helper to `/run/vtium-vt/vtium-vitrify`, root-owned with mode 0755 in a directory only root can write, and runs vtium with `--font-helper=/run/vtium-vt/vtium-vitrify` (ADR-1200 D15), so a review run never starts the packaged or the development helper. The run also compiles the checkout's terminfo entry, `xterm-vtium`, into `/run/vtium-vt/terminfo`, and gives the demo, the guide and the shell `TERMINFO` naming it, so they read the same entry `vtium-terminfo` ships. The run does not pass `TERMINFO` to `/bin/login`'s session, so a login run (`make vt-login`) reads the system's entries: the packaged `xterm-vtium` when `vtium-terminfo` is installed, and otherwise vtium runs with `--term=kmscon`, which the run says before it starts, since the machine keeps `kmscon-terminfo` for that name. The run removes `/run/vtium-vt/` when it ends.
- No VT on this machine holds a development install today (measured), so nothing installed under the old names needs moving. A machine that has one runs `make vt-uninstall VT=N` before it updates its checkout past this change.

### D5: updates

- The packaged vtium runs behind development on purpose. The maintainer rebuilds and upgrades it when they choose, and each upgrade exercises what a user's upgrade does: new files under a running console, a unit file changed under systemd, and the next start running the new build.
- An upgrade replaces the files and never restarts a running `vtium@ttyN`, because a restart hangs up every session on that VT. The package's install script restarts nothing, and Arch's systemd hook only reloads the unit files. A running vtium keeps the build it started with in memory, and the new build runs from that VT's next start: a reboot, a failure that its unit's `Restart=on-failure` starts again, or a restart the user asks for.
- To run the new build on purpose, the user logs out of the sessions on VT N and runs `systemctl restart vtium@ttyN.service` from another VT or over ssh; every session still on VT N ends. `journalctl -b -u vtium@ttyN.service | grep Revision` shows the build that VT runs, and `pacman -Q vtium-git` the build installed. The package's upgrade message names the restart, the sessions it ends, and the VTs whose `vtium@` is running.
- A running console keeps the helper it started with: vtium opens the helper's program once at start and starts every helper from that open file (ADR-1200 D15). An upgrade replaces `/usr/bin/vtium-vitrify` by renaming a new file into place, so the old console goes on starting the old helper, and the new helper runs from that VT's next start, with the new console.

### D6: what the package tests, and what happens to what it finds

- The packaged vtium tests the maintainer's head file and profiles in daily use, the staging target and the recipe as a package manager runs them, upgrades under a running console, the units beside the C reference's, a development vtium and the review runs on other VTs, and removal.
- Each problem it shows becomes an issue, chased like any other: on vtium/vtium when vtium, its units or its staging target is at fault, and on vtium/vtium-arch when the recipe is. The issue names the package's version and the revision the journal shows. It enters the plan's order, its fix carries a test that fails before the fix, and the packaged vtium takes the fix at its first build after the fix reaches `main`.

### D7: `vtium console` gives VTs to vtium and takes them back

- `vtium console` is a subcommand of the vtium binary. It makes the changes to systemd's units that give one VT, or every VT, to the packaged vtium, `vtium@.service`, and the changes that give them back, so that the user types one command in place of the steps D3 once had them type by hand. Its verbs are `enable N`, `enable --all`, `disable N`, `disable --all` and `status`. N is a VT's number from 1 to 63, or its name, `ttyN`. `disable` takes exactly one of N and `--all`; a bare `disable` is refused with the usage, so that a mistyped command never takes back every VT.
- It works on `vtium@.service` alone. vtium looks for a unit file, and for the template link `autovt@.service`, along systemd's unit search path in its order (systemd.unit(5)): `/etc/systemd/system`, `/run/systemd/system`, `/usr/local/lib/systemd/system`, `/usr/lib/systemd/system`, and `/lib/systemd/system`, a split-usr host's vendor directory, as on Debian. The first directory that has the file decides, as it does for systemd. When no directory has `vtium@.service`, or the first that has it masks it by a link to `/dev/null`, `enable` and `disable` change nothing, say that the vtium package installs the unit or name `systemctl unmask vtium@.service`, and exit with status 1, and `status` says the same on its first line and then shows the VTs as it always does. A masked template is refused before anything is written, because `systemctl enable vtium@ttyN.service` refuses it too (measured), after vtium would have written its records and the template link. The drop-in tree that `make install-tree` stages names its unit `kmsconvt@.service`, as the C reference did, and there `systemctl enable kmsconvt@.service` gives every VT to vtium (C notes). The development install's `vtium-dev@` stays `make vt-install`'s (D4).
- **Root.** `enable` and `disable` change files under `/etc/systemd/system` and `/var/lib/vtium`, which only root may write. When vtium's effective user is not root, they change nothing, say that the verb needs root, give the same command run as root, such as `sudo vtium console enable --all`, and exit with status 1. vtium never runs sudo itself. `status` reads only what any user may read, and any user may run it.
- **Without systemd.** vtium checks that the host was booted with systemd the way sd_booted(3) does: by whether `/run/systemd/system` is a directory. When it is not, as on a host whose PID 1 is sysvinit, OpenRC, runit, s6 or busybox init, with elogind or without it, every verb changes nothing, says that this host does not run systemd and that its init runs `vtium --vt=ttyN --no-switchvt` on a VT where it ran a getty (docs/systemd.md), and exits with status 1. This check comes before the root check, so a user is never told to use sudo for a command that cannot work.
- **It starts and stops nothing.** Starting vtium on a VT, or stopping it, ends every session on that VT, the session the user typed the command in included. So `enable` and `disable` change only which console systemd and logind start on a VT next time. For each VT they change, they print when that is, at the next boot or the next time logind starts a console there, and the command that makes the change now, with a warning that it ends every session on that VT: `systemctl start vtium@ttyN.service` after `enable`, `systemctl stop vtium@ttyN.service` after `disable`.
- **It masks nothing.** A mask is the administrator's own choice, so vtium never masks or unmasks a unit. `enable N` refuses a VT whose `vtium@ttyN` is masked, naming `systemctl unmask vtium@ttyN.service`, and every verb but `status` refuses a masked `vtium@.service` (the bullet before). A masked `getty@ttyN` is left as it is.
- **A display manager keeps VT 1.** A display manager, such as sddm or gdm, is enabled by linking `/etc/systemd/system/display-manager.service` to its unit, and it starts on VT 1 at boot; sddm's unit on this machine has `Conflicts=getty@tty1.service` and `After=getty@tty1.service`. A vtium enabled at boot on VT 1 would start beside it and race it for the display card's DRM master. So while `display-manager.service` exists in `/etc/systemd/system` and is not masked, `enable 1` refuses, naming the display manager's unit, and `enable --all` passes VT 1 by: it neither enables `vtium@tty1` nor touches `getty@tty1`, and it says that the display manager keeps VT 1. `status` names the display manager on a line of its own and in VT 1's row.
- **The C reference's console.** The C reference's console ("kmscon" in this section) holds VT N when `kmsconvt@ttyN.service` is enabled or running, or when `/etc/systemd/system/autovt@ttyN.service` links to `kmsconvt@.service`. It holds the template link when `/etc/systemd/system/autovt@.service` links to `kmsconvt@.service`, and logind then starts it on every VT that has no link of its own. vtium on every VT is for a machine that runs no C reference console (D3), so `enable --all` refuses while kmscon holds the template link or any VT, and `enable N` refuses while kmscon holds VT N. Each refusal changes nothing and names the commands that free the VT: for one VT, `systemctl disable --now kmsconvt@ttyN.service`, which ends every session on it, and `rm /etc/systemd/system/autovt@ttyN.service`, which `disable` leaves (measured); for the template, `systemctl disable kmsconvt@.service`, which removes every link to `kmsconvt@.service` (measured). `enable N` on a VT that kmscon does not hold works while kmscon holds the template link, because VT N's own `autovt@ttyN.service` link wins over the template, as it did in D3's one-VT steps.
- **What `enable N` does.** systemd starts the units that `getty.target` wants at boot, and logind starts `autovt@ttyN.service` on a VT that nothing holds when the user switches to it. `enable N`:
  1. Refuses VT N, changing nothing, when kmscon holds it; on VT 1, when a display manager is enabled; when the development install holds it (`vtium-dev@ttyN` enabled or running, or `autovt@ttyN.service` linking to `vtium-dev@.service`), naming `make vt-uninstall VT=N`; when `vtium@ttyN` is masked; and when `/etc/systemd/system/autovt@ttyN.service` exists and is anything but a link to `vtium@.service`, naming it, because `systemctl enable vtium@ttyN.service` then fails after it has already added vtium to `getty.target`'s wants (measured).
  2. Writes the record `/var/lib/vtium/console/ttyN` when no record for VT N exists yet, before it changes anything else. The record holds the path that `getty.target.wants/getty@ttyN.service` links to when the getty is enabled, and is empty when no getty is enabled there.
  3. Runs `systemctl enable vtium@ttyN.service` unless vtium is enabled there already. It links `getty.target.wants/vtium@ttyN.service` and `autovt@ttyN.service` to `vtium@.service`, so systemd starts vtium on VT N at boot and logind starts vtium there in place of the getty.
  4. Runs `systemctl disable getty@ttyN.service` when the getty is enabled. vtium is enabled before the getty is disabled, so a run cut short never leaves VT N with no console enabled.
  Each step that finds its work done skips it, so running `enable N` again finishes a run that was cut short, and on a VT already given to vtium it says so and changes nothing.
- **What `enable --all` does.** It gives vtium the template link, which logind follows on every VT that has no link of its own, VT 1, and the VTs whose gettys systemd starts at boot:
  1. Refuses, changing nothing, when kmscon holds the template link or any VT, or when `/etc/systemd/system/autovt@.service` exists and is not a link.
  2. Writes the record `/var/lib/vtium/console/autovt@.service`, which holds the path `autovt@.service` linked to, or is empty when there was no link, unless the template already links to `vtium@.service` or a record exists.
  3. Links `/etc/systemd/system/autovt@.service` to `vtium@.service`, by making the link under a temporary name in the same directory and renaming it into place. No systemctl verb can make this link: `systemctl enable vtium@.service` is refused before it links anything, as D3 chose.
  4. Does `enable N` for VT 1, unless a display manager keeps it or the development install holds it. VT 1 is on screen from boot, before any switch, so logind never starts a console there, and on a machine with no display manager only `getty.target`'s wants give it one.
  5. For each VT from 2 to 6 whose `getty@ttyN` is enabled, writes its record and runs `systemctl disable getty@ttyN.service`, and enables no `vtium@ttyN` there. A getty enabled there would hold the VT from boot, and with it gone logind starts vtium through the template link the first time the user switches to the VT. vtium is not enabled at boot on those VTs because each vtium started at boot opens the display card, and the first to open it keeps the card's DRM master while its VT is not shown, so a second one started at the same time cannot draw until vtium drops master after opening the card on a VT that is not shown. logind starts consoles by itself only on VTs 1 to 6 (`NAutoVTs=6`, logind.conf(5)'s default), so a getty enabled on a VT above 6 stays enabled, and `enable --all` names it and says that `vtium console enable N` gives that VT to vtium.
  6. Runs `systemctl daemon-reload`, so the manager reads the new template link.
  A VT that the development install holds keeps it, because its own `autovt@ttyN.service` link wins over the template, and `enable --all` names each such VT. So does a VT whose own `autovt@ttyN.service` links to another unit, such as a getty's alias that `systemctl enable getty@ttyN.service` made; `enable --all` names it and the link that holds it.
- **What `disable N` does.** It undoes `enable N` in the opposite order, so VT N always has a console enabled:
  1. When the record `/var/lib/vtium/console/ttyN` holds a path, links `getty.target.wants/getty@ttyN.service` to that path again, by a link under a temporary name renamed into place. That enables the getty exactly as `enable N` found it: linked to the same unit file, with no `autovt@ttyN.service` alias, which `systemctl enable getty@ttyN.service` would add (measured). `systemctl add-wants` would link to the first getty unit file on the search path, such as an override in `/etc/systemd/system`, which may not be the file the want linked to (measured). An empty record enables no getty. With no record at all, or one that holds neither, VT 1 alone gets `systemctl add-wants getty.target getty@tty1.service`: that is the state D3's earlier hand-typed steps left, and VT 1 has no login at boot without its getty.
  2. Runs `systemctl disable vtium@ttyN.service` while vtium is enabled there.
  3. Removes `/etc/systemd/system/autovt@ttyN.service` while it links to `vtium@.service`: `disable` leaves it (measured), and logind would go on starting vtium on VT N.
  4. Removes the record, and runs `systemctl daemon-reload` when it changed a link by hand.
  On a VT where vtium is not enabled, no `autovt@ttyN.service` links to `vtium@.service` and no record names the VT, `disable N` says so and changes nothing. While the template links to `vtium@.service` and no getty is enabled on VT N, logind still starts vtium on VT N after `disable N`, so vtium says so, names `vtium console disable --all`, and exits with status 1.
- **What `disable --all` does.** It does `disable N` for each VT where `vtium@ttyN` is enabled, where `autovt@ttyN.service` links to `vtium@.service`, or where a record names the VT. Then, while `autovt@.service` links to `vtium@.service`, it links the template back to the path the record holds, or removes the link when the record is empty. With no record, as on a machine set up by D3's earlier hand-typed steps, it removes vtium's link and adds nothing when a directory later on the search path has a template link, such as Debian's `/lib/systemd/system/autovt@.service`, which is then in force again; with none, it links the template to `getty@.service`, the link systemd's preset makes from getty's own `Alias=autovt@.service`. It then removes the record and runs `systemctl daemon-reload`. A template link that names any other unit is left as it is, and so are the development install's VTs. `systemctl disable vtium@.service` cannot do this work: it fails on the template's `DefaultInstance=` as the template's enable does, and changes nothing (measured).
- **The records.** A machine may have gettys enabled on several VTs, as this machine has on VTs 1 to 6, and `systemctl preset getty@.service`, which D3's earlier hand-typed way back used, enables only `getty@tty1`. The records let `disable` give back exactly what `enable` took. They live in `/var/lib/vtium/console/`, one small text file each, in a directory that vtium creates owned by root with mode 0755. Each is written under a temporary name and renamed into place. A VT's record holds the getty's link target or nothing (`enable N`, step 2), and the template's record holds the template link's target or nothing (`enable --all`, step 2). A VT's record that holds anything but nothing or a path to `getty@.service`, and a template record that holds anything but nothing or a path to a unit file named `PREFIX@.service` other than `vtium@.service`, is taken as no record.
- **What `status` prints.** First, one line on what logind starts on a VT that has no link of its own, from the template link in force on the search path: vtium, a getty, kmscon, another unit, or nothing when there is no link. Then a table with a row for each VT from 1 to 6, the VTs logind starts consoles on by default, and for each VT up to 63 where a console is enabled, linked, running or recorded. Its columns are the VT, the console systemd starts there at boot (`getty.target`'s wants), the console logind starts when the user switches to it (VT N's own `autovt@ttyN.service` link, or else the template link), and the console running there now. A column with nothing in it shows `-`. It exits with status 0, or 1 when it cannot read systemd's state.
- **How vtium reads and changes the state.** It reads the links under `/etc/systemd/system`, the template link along the search path and its records itself, and asks the running manager only which consoles run, with `systemctl list-units --state=active`. It changes the units through `systemctl enable`, `disable`, `add-wants` and `daemon-reload`, and changes by hand only the three links no systemctl verb makes or removes as they were: the template link, a VT's leftover `autovt@ttyN.service` link to `vtium@.service`, and a getty's want linked back to the unit file the record names.
- **Exit statuses.** 0 when the verb did what it was asked or found it done, 1 when it refused or a step failed, and 2 for words it cannot take, as `vtium blank` does. A step that fails stops the run: vtium names the step and prints systemctl's message, and running the same verb again finishes the change, while the opposite verb undoes what was done.

### The maintainer's answers

The record asked the maintainer three questions, and each answer is written into the decision above (`considered`, 2026-11-01).

1. **The terminfo entry.** This machine keeps `kmscon-terminfo` for the name `kmscon`, and vtium ships its own entry only as `xterm-vtium`, in the terminfo packages of D3.
2. **The head file.** The development vtium and the packaged one share `/etc/vtium/heads.conf` (D4).
3. **The helper after an upgrade.** A running console keeps the helper it started with (D5, ADR-1200 D15).

## C notes: the C reference's packaging

- The C reference shipped two units, `scripts/systemd/kmsconvt@.service.in` and `scripts/systemd/kmscon.service.in` (kmscon b1f7a7c5), and its terminfo entry, `scripts/terminfo/kmscon.ti`. Its `kmsconvt@.service` started a getty directly on failure, with `OnFailure=getty@%i.service`, and enabled VT 1 when it was enabled with no VT named, through `DefaultInstance=tty1`.
- To give every VT to the C reference, its unit's opening comment told the user to run `systemctl enable kmsconvt@` (`scripts/systemd/kmsconvt@.service.in`, kmscon b1f7a7c5). On a machine with no template link yet, that template enable linked `autovt@.service` to the unit through its `Alias=autovt@.service`, so logind started the C reference's console on every VT it spawned, and its `DefaultInstance=tty1` enabled VT 1, which its `Conflicts=getty@%i.service` took from the getty at boot. On a machine where the getty's preset had already linked `autovt@.service` to `getty@.service`, as systemd's preset does on Arch, the enable failed with "already exists and is a symlink to getty@.service", linked only `getty.target.wants/kmsconvt@tty1.service`, and left the template on the getty (measured with systemd 262 on vtium's shipped `kmsconvt@.service`, whose `[Install]` section is the C reference's). Either way it left `getty@tty1`, and every other getty enabled at boot, enabled, and `DefaultInstance=tty1` enabled the C reference's console on VT 1 even where a display manager started there at boot, so the two raced for the display. The C reference documented no way back: that enable line in the unit's comment is the only place its tree names enabling or disabling the unit. The measured way back would have been `systemctl disable kmsconvt@`, which removes every link to the unit, the template link included, and so leaves `autovt@.service` linked to nothing until the getty's preset links it again.
- Arch's `kmscon` package installs those units under `/usr/lib/systemd/system` and splits the terminfo entry into its own package, `kmscon-terminfo`, on which `kmscon` depends. On this machine the entry is the one from release 10.1.0, which lacks features that the C reference's own entry at b1f7a7c5 lists.

## Where vtium departs from the C reference

- **No default VT for the packaged unit.** vtium's packaged unit refuses an enable that names no VT and links nothing (D3), where the C reference's unit took VT 1 (C notes), so it never starts by accident on a VT that a desktop or another console holds, nor on every VT logind spawns.

- **A display manager keeps VT 1.** The C reference's `DefaultInstance=tty1` enabled its console on VT 1 beside a display manager there (C notes). `vtium console` refuses VT 1 while `display-manager.service` is enabled, and `enable --all` passes it by (D7).
- **vtium on every VT is one command with an exact way back.** The C reference gave every VT to its console through the template enable, which left the enabled gettys enabled, failed where the template link already named the getty, and had no documented way back (C notes). `vtium console enable --all` (D7) disables the gettys it displaces and records what it changed, and `vtium console disable --all` puts back the template link and each getty as it found them.

## Consequences

### Positive

- The maintainer runs a packaged vtium every day, so the head file, the profiles, the upgrades and the units are tested in the way users meet them.
- Development keeps its own install and its review runs while the packaged vtium runs, and neither replaces the other's files or units.
- The C reference's console keeps every file, name and default it had, so it stays usable on any other VT and the comparison with it stays honest.
- The recipes call vtium's own targets, so vtium's tree says once which file goes where, and a new package manager adds a recipe and a repository, not a second account of vtium's layout.
- A user's sessions never end because of an upgrade.
- A VT, or every VT, goes to vtium and comes back with one command each (D7), and the way back gives back exactly the gettys and the template link that were there.

### Negative

- `make vt-install`, `make vt-uninstall`, the review runs' VT checks, `vtium blank` and `vtium wake`, the VT review guide and docs/systemd.md change for the new names and the new checks, and the generator of the units moves out of `tools/vt/vt-install.sh` into a place both installs use.
- After an upgrade, a VT can run an older build than the one installed until it restarts.
- vtium has a second repository to keep, and a change to it reaches vtium's tree only when someone moves the submodule's pointer.
- Removing the package leaves the user to run `vtium console disable --all` first, or the VT shows nothing when switched to.
- Until vtium drops DRM master after opening the card on a VT that is not shown, two vtiums started at boot race for the card, and the loser cannot draw. `enable --all` therefore enables vtium at boot on VT 1 alone, and the other VTs get vtium only when the user first switches to them. `vtium console enable N` on a second VT enables a second vtium at boot, and meets the race.
- `vtium console` writes records under `/var/lib/vtium/console/`, which outlive the package when the user removes it without running `vtium console disable --all` first.
- `vtium console` reads systemd's links under `/etc/systemd/system` itself, so it follows systemd's on-disk layout for `getty.target`'s wants and the `autovt@` aliases; that layout is measured with systemd 262 only.

### Neutral

- `packaging/` holds only submodules. A clone without `--recurse-submodules` has empty directories there, and no gate, CI job or build reads them.
- The recipes build with the host's toolchain and need a network connection only for the crates: `prepare()` runs `cargo fetch --locked`, and `build()` runs offline with `--frozen`.
- Each later version tag moves `vtium`'s recipe to that tag, and the publish script pushes it to the AUR.

## Alternatives Considered

- **Recipes in vtium's own tree,** under `packaging/` as plain files. Rejected by the maintainer: a recipe repository of its own can be published and versioned apart from vtium, and the submodule still ties each recipe to the code it builds.
- **A package that replaces the C reference's,** providing and conflicting with `kmscon` and installing the drop-in tree that `make install-tree` stages. Rejected by the maintainer for now: the C reference's console stays installed on this machine beside vtium. D3 leaves it as a later variant.
- **A local builder only, published later.** Replaced by the maintainer: the packages go on the AUR now, since the maintainer holds an account there and the names stay vtium's.
- **Checking a signature on `vtium-git`'s source.** Rejected: the tip of `main` carries GitHub's signature on its merge commit, which proves nothing about vtium's maintainer.
- **Signed commits.** Rejected: an agent's every commit would ask for the passphrase; the signed tag is what a builder checks.
- **Building the local checkout by default.** Rejected by the maintainer: `main` holds only reviewed work with green CI, and the setting in D2 reaches a local checkout when one is wanted.
- **One set of names for both installs,** with `make vt-install` replacing the package's files. Rejected: the maintainer wants the packaged vtium kept running while development goes on, and a unit in `/etc/systemd/system` overrides the packaged one on every VT.
- **Keeping the development binary's name `vtium` in a directory of its own,** such as `/usr/local/lib/vtium-dev/vtium`, so that `vtium blank` finds it without change. Not chosen: `ps`, `pgrep` and the journal then show two processes with one name, and telling them apart is the point of separate names.
- **Restarting vtium after an upgrade,** as some packages restart their daemons. Rejected: a restart hangs up every session on the VT, so the user chooses when.
- **Enabling vtium on a VT from the package's install script.** Rejected: the VT to give vtium is the user's choice, and a VT given by mistake ends the session on it.
