# ADR-1500: vtium is packaged from a recipe repo per package manager, under names of its own

## Summary

- **Decided:** vtium's packaging recipes live in one repository per package manager in the vtium GitHub organization, each a git submodule of vtium under `packaging/<manager>`. Arch comes first, in `vtium/vtium-arch`, published to the AUR under the maintainer's account: `vtium-git`, built from the tip of GitHub's `main` or, by a documented setting, from a local checkout and branch, and `vtium`, built from a signed version tag, the first being the pre-release `v0.1.0-alpha.1`. The package installs vtium under vtium's own names: `/usr/bin/vtium`, the glyph helper `/usr/bin/vtium-vitrify`, and the units `vtium@.service` and `vtium-getty@.service`, which `make install-tree`, the tree tier 3 installs in its guest, stages too. vtium treats `kmscon`, the C reference's program, as an unrelated program, and takes none of its files or unit names. vtium still answers to the `kmscon` name where a program needs it: the names and replies programs know vtium by are compatible identities, which ADR-1000 keeps, and no packaging change removes one. The package's install script gives vtium every free VT with the subcommand `vtium console enable --all`, and its removal script gives them back with `vtium console disable --all`, which restores the units it changed as they were (D3, D7). The user can also give vtium one VT with `vtium console enable N`, and take VTs back with `vtium console disable`. A development install, `make vt-install`, moves to names of its own (`vtium-dev@.service`, `vtium-dev-getty@.service`, `/usr/local/bin/vtium-dev` and its own helper) so that the packaged vtium and a development vtium run on separate VTs at once. Both read the same configuration. An upgrade replaces the files and never restarts a running vtium; the new build runs from that VT's next start. Every problem the packaged vtium shows becomes an issue. Each package manager's main package, `vtium` and `vtium-git` on the AUR, builds vtium for an ordinary desktop or laptop: the GPU path, pictures and logind, frits (font set files) for trying several fonts, and the head file's template for more than one display. Two minspec recipes sit beside it in the same recipe repository: `vtium-minspec`, the build with no features that tier 3 judges, and `vtium-minspec-gpu`, the same build with the GPU path, which it leaves off; both keep two buffers for each display. `vtium-arch`'s CI builds them and their `-git` twins as a check, and no minspec package is published to the AUR, because the maintainer does not want AUR packages that differ from `vtium` only in build options. A person who wants the minspec console on Arch builds it from the `vtium` recipe with `VTIUM_FEATURES`. `vtium` and `vtium-git` build the GPU path from the release `v0.1.0-alpha.5` on. `v0.1.0-alpha.5` left `hwaccel` off by default in them, and from `v0.1.0-alpha.6` on they turn it on by default, since the GPU path now has a guard that stops a head from switching back and forth between the GPU path and the CPU path while a display keeps failing; `vtium-minspec-gpu` and its `-git` twin leave it off (ADR-1303 D9). `vtium` ships the picture gallery tool as `vtium-gallery`, and no package bundles a font. An optional `vtium-fonts` package, published on the AUR, is a curated set of fonts chosen to go with the frits vtium ships, and it grows as new frits are added. It installs no font file itself and depends on the distribution's font packages (D8).
- **Trades away:** Packages that anyone on the AUR can install before vtium is ready for them, at their own risk. The convention that a package enables nothing: installing vtium claims the free VTs. The development install's current names: `make vt-install` and the docs that name `vtium@ttyN` for it change. A second repository to keep, and a submodule pointer to move when it changes. The packaged vtium runs behind development on purpose. The main package pulls in the GL libraries that the GPU path loads, and takes longer to build than the minspec console. A machine that wants neither cannot install the minspec console from the AUR; its user builds it with `makepkg` from the `vtium` recipe.
- **One-way?** Expensive: the packages are published to the AUR, so other machines can install them by their names and enable `vtium@ttyN` by that name, and a rename strands them. A signed tag, once published, is never moved.
- **Probes:**
  - *Confident (upgrades):* an upgrade of the package never restarts vtium on a VT. The new build runs from that VT's next start: a reboot, a failure, or a restart the user asks for.
  - *Confident (no start):* `vtium console enable` and `disable` change only what starts on a VT next time, at the next boot or the next switch to it, and never start or stop vtium, so they never end the session you typed them in; each prints the `systemctl start` or `stop` that makes the change now, with a warning that it ends every session on that VT.
  - *Not confident (shared head file):* the development vtium and the packaged one read the same `/etc/vtium/vtium.conf`, whose sections are the head file and the looks, so a key in a section that only the newer build knows is an error there for the older one.

## Context

The maintainer wants vtium installed on this machine the way a user installs it, through a package manager, and kept running there while development goes on. The package is a real test of what development alone never exercises: the maintainer's own head file and profiles in daily use, a package manager installing vtium's tree, upgrades under a running console, and removal. Arch is the package manager on this machine, and other package managers follow.

Two installs already compete for the names a package would take. `make vt-install` writes `/usr/local/bin/vtium` and the units `vtium@.service` and `vtium-getty@.service` into `/etc/systemd/system`, where a unit file overrides one of the same name in `/usr/lib/systemd/system`, the directory a package installs into. Left as it is, a development install would silently take over the packaged unit on every VT. And this machine runs the C reference's program as Arch ships it, the `kmscon` package (10.1.0) and its `kmscon-terminfo` package, which own `kmsconvt@.service`, `kmscon.service`, `/etc/kmscon/kmscon.conf.example`, `/usr/share/terminfo/k/kmscon` and, by its enablement, `/etc/systemd/system/autovt@.service`. kmscon is an independent product, which vtium does not replace. vtium was built against the C reference as its starting point, and every vtium install stands on its own: the package, and `make install-tree`, the tree that tier 3 installs in its guest, install vtium's units under vtium's own names.

A VT (a Linux virtual console, switched with Ctrl-Alt-F<n>) runs one console at a time. logind starts `autovt@ttyN.service` on a VT that nothing holds when the user switches to it, and on this machine `autovt@` points at the C reference's `kmsconvt@`.

## Decision

### D1: one recipe repository per package manager, submoduled into vtium

- Each package manager's recipes live in their own repository in the vtium GitHub organization, and vtium holds each as a git submodule at `packaging/<manager>`. A submodule is a pointer from vtium's tree to one commit of the other repository, so vtium's history records which recipes go with which code, and the recipes keep their own history and can be published from their own repository.
- Arch comes first: `vtium/vtium-arch`, at `packaging/arch`. It holds `vtium-git`, which builds the latest `main`, and `vtium`, which builds a signed version tag (D2), and beside each the two minspec recipes, `vtium-minspec` and `vtium-minspec-gpu`, with their `-git` twins. `vtium-arch`'s CI builds the minspec recipes as a check, and they are not published to the AUR (D8). Both names, `vtium` and `vtium-git`, are vtium's on the AUR, which reserves no name, so each is published as soon as it can build: `vtium` from the first pre-release. Debian, Fedora and Nix each get a repository of their own later, named `vtium/vtium-<manager>` in the same way.
- A recipe stays thin: it calls vtium's own make targets to build and stage the files, so the knowledge of which file goes where lives in vtium's tree. vtium's Makefile gains a staging target for vtium's package (D3), `make install DESTDIR=DIR PREFIX=/usr`, which every manager's recipe calls, with `make install-terminfo DESTDIR=DIR PREFIX=/usr` for the terminfo package (D3). Each refuses a `DESTDIR` that is unset, empty or resolves to `/`. The recipes and `make install` build with the host's toolchain, as a distribution's package build does, with no pinned sysroot and no glibc floor; only `make install-tree`, the tree tier 3 installs, links against the pinned Debian sysroot. Each Arch recipe calls `make install` and `make install-terminfo` in its `package()` function.
- The Arch packages are published on the AUR, Arch's user repository, under the maintainer's account. `vtium-arch` holds one directory per package and a publish script that pushes the directory of each published package to that package's AUR repository, so the AUR always carries what those directories hold. The published packages are `vtium`, `vtium-git`, `vtium-terminfo`, `vtium-terminfo-git` and `vtium-fonts` (D8). `vtium-git`'s history is published as it is, and each recipe's `Maintainer:` line gives the maintainer's plain email address. Anyone may install them, at their own risk. The maintainer builds them on this machine with `makepkg` the same way.

### D2: what the packages build

- `vtium-git` builds the tip of GitHub's `main`. Only reviewed work whose CI passed reaches `main`, so the packaged vtium is never a branch in progress.
- A documented setting in `vtium-arch` points the build at another git source and branch instead, such as a local checkout (`git+file:///path/to/vtium`, with `#branch=integration`), through makepkg's source entry (PKGBUILD(5)). makepkg clones that source, so the build takes the branch's last commit and never a checkout's uncommitted changes. The setting is read from the environment of the `makepkg` run, and `vtium-arch`'s README names it.

### D5: updates

- The packaged vtium runs behind development on purpose. The maintainer rebuilds and upgrades it when they choose, and each upgrade exercises what a user's upgrade does: new files under a running console, a unit file changed under systemd, and the next start running the new build.
- An upgrade replaces the files and never restarts a running `vtium@ttyN`, because a restart hangs up every session on that VT. The package's install script restarts nothing, and Arch's systemd hook only reloads the unit files. A running vtium keeps the build it started with in memory, and the new build runs from that VT's next start: a reboot, a failure that its unit's `Restart=on-failure` starts again, or a restart the user asks for.
- To run the new build on purpose, the user logs out of the sessions on VT N and runs `systemctl restart vtium@ttyN.service` from another VT or over ssh; every session still on VT N ends. `journalctl -b -u vtium@ttyN.service | grep Revision` shows the build that VT runs, and `pacman -Q vtium-git` the build installed. The package's upgrade message names the restart, the sessions it ends, and the VTs whose `vtium@` is running.
- A running console keeps the helper it started with: vtium opens the helper's program once at start and starts every helper from that open file (ADR-1200 D15). An upgrade replaces `/usr/bin/vtium-vitrify` by renaming a new file into place, so the old console goes on starting the old helper, and the new helper runs from that VT's next start, with the new console.

### D7: `vtium console` gives VTs to vtium and takes them back

- `vtium console` is a subcommand of the vtium binary. It makes the changes to systemd's units that give one VT, or every VT, to the packaged vtium, `vtium@.service`, and the changes that give them back, so that the user types one command in place of the steps D3 once had them type by hand. Its verbs are `enable N`, `enable --all`, `disable N`, `disable --all` and `status`. The package's install script runs `enable --all`, and its removal script runs `disable --all` (D3). N is a VT's number from 1 to 63, or its name, `ttyN`. `disable` takes exactly one of N and `--all`; a bare `disable` is refused with the usage, so that a mistyped command never takes back every VT.

> Edited 2026-11-10: the maintainer decided that the package's scripts make and give back the claim (`basis`, 2026-11-10; D3). The first bullet did not name the scripts.

- It works on `vtium@.service` alone. vtium looks for a unit file, and for the template link `autovt@.service`, along systemd's unit search path in its order (systemd.unit(5)): `/etc/systemd/system`, `/run/systemd/system`, `/usr/local/lib/systemd/system`, `/usr/lib/systemd/system`, and `/lib/systemd/system`, a split-usr host's vendor directory, as on Debian. The first directory that has the file decides, as it does for systemd. When no directory has `vtium@.service`, or the first that has it masks it by a link to `/dev/null`, `enable` and `disable` change nothing, say that the vtium package installs the unit or name `systemctl unmask vtium@.service`, and exit with status 1, and `status` says the same on its first line and then shows the VTs as it always does. A masked template is refused before anything is written, because `systemctl enable vtium@ttyN.service` refuses it too (measured), after vtium would have written its records and the template link. The drop-in tree that `make install-tree` stages names its unit `kmsconvt@.service`, as the C reference did, and there `systemctl enable kmsconvt@.service` gives every VT to vtium (C notes). The development install's `vtium-dev@` stays `make vt-install`'s (D4).
- **Root.** `enable` and `disable` change files under `/etc/systemd/system` and `/var/lib/vtium`, which only root may write. When vtium's effective user is not root, they change nothing, say that the verb needs root, give the same command run as root, such as `sudo vtium console enable --all`, and exit with status 1. vtium never runs sudo itself. `status` reads only what any user may read, and any user may run it.
- **Without systemd.** vtium checks that the host was booted with systemd the way sd_booted(3) does: by whether `/run/systemd/system` is a directory. When it is not, as on a host whose PID 1 is sysvinit, OpenRC, runit, s6 or busybox init, with elogind or without it, every verb changes nothing, says that this host does not run systemd and that its init runs `vtium --vt=ttyN --no-switchvt` on a VT where it ran a getty (docs/systemd.md), and exits with status 1. This check comes before the root check, so a user is never told to use sudo for a command that cannot work.
- **It starts and stops nothing.** Starting vtium on a VT, or stopping it, ends every session on that VT, the session the user typed the command in included. So `enable` and `disable` change only which console systemd and logind start on a VT next time. For each VT they change, they print when that is, at the next boot or the next time logind starts a console there, and the command that makes the change now, with a warning that it ends every session on that VT: `systemctl start vtium@ttyN.service` after `enable`, `systemctl stop vtium@ttyN.service` after `disable`.
- **It masks nothing.** A mask is the administrator's own choice, so vtium never masks or unmasks a unit. `enable N` refuses a VT whose `vtium@ttyN` is masked, naming `systemctl unmask vtium@ttyN.service`, and every verb but `status` refuses a masked `vtium@.service` (the bullet before). A masked `getty@ttyN` is left as it is. A mask does not reach a unit that systemd loads through a link: with `vtium@tty2.service` masked and the template link naming `vtium@.service`, `autovt@tty2.service` still loads `vtium@.service` (measured with `systemd-analyze --root verify`). So `enable --all` treats a masked `vtium@ttyN` by where logind would start a console. On VT 1, where logind never starts one, on a VT above 6, and on a VT from 2 to 5 whose getty is enabled at boot and holds the VT, it passes the VT by, leaves its getty as it is, and names it. On a VT whose own `autovt@ttyN.service` links to `vtium@.service`, as `enable N` left it, it also passes the VT by and says that the mask does not keep vtium off it: that link still loads vtium (measured), and `vtium console disable N` takes the VT back. On VT 6, where logind starts `autovt@tty6.service` at every switch, and on a VT from 2 to 5 where no getty is enabled to hold it, it refuses while the VT has no link of its own, names the mask and `systemctl unmask vtium@ttyN.service`, and changes nothing.
- **vtium follows common convention, never takes a VT another program holds, and its failure never stops another program** (the maintainer, 2026-11-04, `considered`). vtium's integration does what systemd and the other init systems already do, on systems with systemd and without it, and breaks no new ground. With a display manager enabled, VT 1 stays the display manager's and the getty's, whatever VT the display manager uses now, and vtium takes other VTs through the init system's standard mechanism. `vtium console` never gives vtium a VT that the system's intended configuration gives to another program: a unit enabled at boot that claims the VT, and an enabled display manager, which claims VT 1 and any VT its own configuration names. On a system without systemd, `vtium console` changes nothing, and the init system's own getty and console entries decide which VTs are vtium's (docs/systemd.md). The VT's own getty, which `enable` is asked to replace, is not another program. What is running now, a graphical session, a greeter or another console, adds to the held VTs and never frees one, and nothing else frees one either: neither a display manager's configuration naming another VT nor a greeter running on another VT. When vtium fails on a VT, the getty that takes its place starts only when its start stops no other program: a getty whose start would stop a running, queued or enabled unit is not started, and the VT is left without a console, with the reason in the journal.
- **Other programs keep their VTs.** A display manager, the greeter and graphical sessions it starts, a kiosk, and another console each use a VT, now or from the next boot. vtium console leaves alone every VT another program holds, because a vtium started there would race the display server for the display card's DRM master, or stop the other program through vtium's `Conflicts=`. It judges which VTs are held from what is on the machine, in three parts.
  - *What running now adds.* vtium asks logind which sessions run, with `loginctl list-sessions --no-legend` and then `loginctl show-session ID... -p Name -p VTNr -p Service -p Type -p Class`, and takes the VT (`VTNr`) of each session whose type is `x11`, `wayland` or `mir`, or whose class is `greeter`. It asks loginctl, the interface systemd documents, and never reads logind's files under `/run/systemd/sessions`, which ADR-1400 rejected as an interface. When loginctl fails, `enable` changes nothing and says that it cannot tell which VTs graphics hold, `status` says the same on a line of its own, and `disable` runs as it always does, since it takes nothing. vtium also asks the running manager for every active unit on a VT, with `systemctl list-units --plain --no-legend --state=active '*@tty*.service'`, and a unit named `PREFIX@ttyN.service` there holds VT N now, unless it is one of the consoles this decision gives rules of their own: vtium, the development install, the getty and kmscon.
  - *What the intended configuration claims.* The units systemd starts at boot are the display manager, which is enabled by linking `/etc/systemd/system/display-manager.service` to its unit, and each service linked in a `*.wants` or `*.requires` directory of any unit directory, but those four consoles and a masked unit. vtium reads each unit as systemd does. systemd loads it by its name, so vtium reads the file of that name in the first unit directory that has one, which can be an administrator's copy in `/etc/systemd/system` rather than the file a link names (measured), and an instance with no file of its own reads its template's. Then it reads the unit's drop-ins, each `*.conf` file in these directories, each looked for in every unit directory in the search path's order: `NAME.d` for the unit's own name, then for its template, then for the display manager's alias `display-manager.service`; the prefix directory of each name up to a dash, such as `display-.service.d` (a name with more dashes has one such directory for each); and `service.d`, which applies to every service. A drop-in of one file name is read once, from the first of these directories that has it, so the unit's own name's directories win over the alias's, and the drop-ins are then read in file-name order (measured). A unit ties itself to a VT in three ways, with `%i` and `%I` read as the unit's instance: it is an instance on the VT, `PREFIX@ttyN.service`, which holds VT N; its `[Service]` section's `TTYPath=/dev/ttyN`, which holds VT N; and its `[Unit]` section's `Conflicts=getty@ttyN.service`, which holds VT N. A drop-in only adds to `Conflicts=`: an empty `Conflicts=` clears nothing, because systemd cannot reset a dependency to an empty list (systemd.unit(5); measured), so a getty the vendor's unit names stays named unless an administrator's copy of the unit replaces it. A masked `display-manager.service`, or a masked unit that it names, claims nothing.
  - *What a display manager's configuration adds.* vtium reads the display manager's own configuration files, and never runs them, for a VT its greeter starts on, as each display manager reads them in its own source. It knows three, by the name of the unit `display-manager.service` links to, with a trailing number dropped. SDDM 0.21 reads every file in `/usr/lib/sddm/sddm.conf.d`, then in `/etc/sddm.conf.d`, each in name order, then `/etc/sddm.conf`, a later value winning; on each line it drops everything from a `#` on and trims the rest, and it reads the section `[XDisplay]` as `[X11]` (`src/common/ConfigReader.cpp`). Its `[X11] MinimumVT=`, which SDDM before 0.20 read and sddm.conf(5) says SDDM 0.20 dropped, names the lowest VT its greeter takes, and vtium holds that VT. LightDM reads `lightdm/lightdm.conf.d/*.conf` under `/usr/share`, `/usr/local/share` and `/etc/xdg`, then `/etc/lightdm/lightdm.conf.d/*.conf`, then `/etc/lightdm/lightdm.conf` (`common/configuration.c`), and its first greeter takes `[LightDM] minimum-vt`, 7 when no file sets it (`src/lightdm.c`); it reads a value that is no number as 0 and takes 1 for any value below 1 (`src/vt.c`). greetd reads the file its `--config` names, or else `/etc/greetd/greetd.conf`, and `/etc/greetd/config.toml` when that is missing, skips a line that starts with `#`, and drops the quotes around a value (`greetd/src/config/mod.rs`, `inish/src/lib.rs`); its `[terminal] vt`, or a `--vt` on its command line, is a VT's number, or `current`, the VT shown when greetd starts, which is VT 1 at boot, or `next` or `none`, which name no VT. vtium reads both options from the `ExecStart=` of greetd's unit. A VT number outside 1 to 63, a value that names no VT, and a file vtium cannot read add nothing. vtium reads a unit file as systemd does (systemd.syntax(7)): a line that ends in a backslash goes on with the next one, a comment line among them left out, and `%%` stands for a percent sign.
  - *The judgment.* A VT is held when the system's intended configuration gives it to another program, or when something running now uses it. By common convention, VT 1 is the display manager's and its getty's whenever a display manager is enabled. A display manager is enabled when `/etc/systemd/system/display-manager.service` links to its unit, as most display managers' `[Install]` sections make it, or when a unit that starts at boot runs a display manager vtium knows by name: sddm, gdm, lightdm, greetd, ly, lemurs, lxdm, xdm, slim or emptty, the name read from the unit's name with any instance and trailing number dropped. ly ships `ly@.service` with `Alias=autovt@.service`, `WantedBy=multi-user.target` and `DefaultInstance=tty2`, and no `display-manager.service` alias, so enabled it is `ly@tty2` in `multi-user.target.wants`. That holds whatever the display manager's unit names, Debian's `lightdm.service` naming no getty at all, and whatever VT its greeter uses now, as SDDM's X11 greeter on VT 2 on the maintainer's laptop. A unit that names `getty@ttyN.service` in `Conflicts=` holds VT N, a unit with `TTYPath=/dev/ttyN` or an instance on VT N holds VT N, and the display manager's configuration adds the VT its greeter starts on. Nothing frees a VT: neither a configuration file naming another VT nor a greeter running on another VT. So VT 1 on a machine with a display manager stays the getty's, as systemd's preset leaves it, and vtium takes the other VTs.
  - `enable N` refuses N while anything holds it, naming what holds it and why: the session's user, service and type, such as "the graphical session of aaron (sddm, wayland) holds VT 7 now"; the other console's unit; or the unit enabled at boot and the signal it read, such as "the display manager sddm.service holds VT 1 at boot: a display manager is enabled, and by common convention VT 1 stays the display manager's and its getty's". `enable --all` passes by every VT anything holds: it neither enables vtium there nor takes a getty from it, and it names each VT it left alone, what holds it and why. `status` marks each held VT: the display manager as "display manager (sddm.service)" and another unit by its name in the column for boot, and "graphical session of aaron (sddm, wayland)" in the column for what runs now; under the table it gives a line for each VT a unit holds at boot, with the reason.
  - A VT from 2 to 5 that a display manager claims has no link of its own, so after `enable --all` the template link governs it. Once the greeter has left that VT and nothing holds it open, a switch to it makes logind start vtium there, beside the running display manager. That is no regression: under the getty's template link, logind would start the getty there, and the getty's start would stop the display manager through the `Conflicts=` by which it claims the VT.
- **A vtium failure stops no other program.** When vtium on VT N fails, its unit's `OnFailure=` starts `vtium-getty@ttyN.service`, which skips itself under a closed head-file policy (ADR-1401 D9) and otherwise runs `vtium console fallback ttyN`. That starts `getty@ttyN.service` so the VT has a login again, unless the start would stop another program. Starting a unit stops every unit it conflicts with in either direction: the units its own `Conflicts=` names, and the units whose `Conflicts=` names it, which systemd lists as its `ConflictedBy=`. vtium asks the running manager for both, with `systemctl show -p Conflicts -p ConflictedBy -- getty@ttyN.service`, and then for each unit's state, with `systemctl show -p Id -p ActiveState -p UnitFileState -p Job -- UNIT...`, since only the manager knows which units are loaded, running, or have a job queued. A unit that is active, activating or reloading, has a job queued, or whose unit file state is enabled, linked, an alias, indirect or generated, holds the getty back: then vtium starts nothing and writes to the journal that VT N is left without a console, which units the start would stop and their states, and how to start vtium again. vtium's own units on VT N, `vtium@ttyN` and `vtium-dev@ttyN`, hold nothing back, since the getty takes the VT in their place. When the manager cannot be asked, or answers for fewer units than it was asked about, vtium cannot tell what the start would stop, so it starts nothing, says so, and exits with status 1. Otherwise it starts the getty with `systemctl --no-block start getty@ttyN.service`, in systemd's default job mode, `replace`. That start stops vtium's own unit on the VT, a restart of it that `Restart=on-failure` has scheduled included, so the getty takes the VT, as tier 3's `heads-partly-open` checks. The job mode `fail` would leave that restart standing: on systemd 262 it left vtium and the getty running on the VT together (measured in tier 3). `fallback` starts nothing while a unit that conflicts with the getty has a job queued, so the start replaces no such job, except one queued in the moment between that check and the start. `fallback` needs root and systemd as `enable` does, takes exactly one VT, and runs no other verb's steps. Before this, the fallback unit ran `systemctl --no-block start getty@%i.service` itself; on the maintainer's laptop that start on VT 1 stopped SDDM through its `Conflicts=getty@tty1.service`, and the machine booted without a desktop.
- **The C reference's console.** The C reference's console ("kmscon" in this section) holds VT N when `kmsconvt@ttyN.service` is enabled or running, or when `/etc/systemd/system/autovt@ttyN.service` links to `kmsconvt@.service`. It holds the template link when `/etc/systemd/system/autovt@.service` links to `kmsconvt@.service`, and logind then starts it on every VT that has no link of its own. The template link can name one console, so `enable --all` refuses while kmscon holds it. A VT that kmscon holds on its own, through its own `autovt@ttyN.service` link, its want or a running unit, `enable --all` leaves to kmscon, getty and link included, and names it; `enable N` refuses it; `disable` never touches it. A user who keeps kmscon on one VT beside vtium on the others gives it that VT's own link by hand: `systemctl disable getty@ttyN.service` where that VT's getty is enabled at boot, then `ln -s /usr/lib/systemd/system/kmsconvt@.service /etc/systemd/system/autovt@ttyN.service` and `systemctl daemon-reload`. systemd then loads `kmsconvt@ttyN.service` for `autovt@ttyN.service` and `vtium@ttyM.service` for every other VT M (measured with `systemd-analyze --root verify`), and nothing starts kmscon at boot: logind starts it on the next switch to VT N while no console runs there. That keeps a second console off boot, for the same reason `enable --all` enables vtium at boot on VT 1 alone. `systemctl is-enabled kmsconvt@ttyN.service` reads `disabled` with such a link (measured), so vtium reads the link itself to see it. `systemctl enable --now kmsconvt@ttyN.service` makes the same link and also starts kmscon at boot and at once, beside vtium on VT 1. kmscon's own `systemctl enable kmsconvt@` fails on vtium's template link and still enables kmscon at boot on VT 1 (measured), so `crates/vtium/README.md` warns against it. Each refusal changes nothing and names the commands that free the VT: for one VT, `systemctl disable --now kmsconvt@ttyN.service`, which ends every session on it, and `rm /etc/systemd/system/autovt@ttyN.service`, which `disable` leaves (measured); for the template, `systemctl disable kmsconvt@.service`, which removes every link to `kmsconvt@.service` (measured). `enable N` on a VT that kmscon does not hold works while kmscon holds the template link, because VT N's own `autovt@ttyN.service` link wins over the template, as it did in D3's one-VT steps.
- **What `enable N` does.** systemd starts the units that `getty.target` wants at boot, and logind starts `autovt@ttyN.service` on a VT that nothing holds when the user switches to it. `enable N`:
  1. Refuses VT N, changing nothing, when kmscon holds it; when another program holds it ("Other programs keep their VTs" above); when the development install holds it (`vtium-dev@ttyN` enabled or running, or `autovt@ttyN.service` linking to `vtium-dev@.service`), naming `make vt-uninstall VT=N`; when `vtium@ttyN` is masked; and when `/etc/systemd/system/autovt@ttyN.service` exists and is anything but a link to `vtium@.service`, naming it, because `systemctl enable vtium@ttyN.service` then fails after it has already added vtium to `getty.target`'s wants (measured).
  2. Writes the record `/var/lib/vtium/console/ttyN` when no record for VT N exists yet, before it changes anything else. The record holds the path that `getty.target.wants/getty@ttyN.service` links to when the getty is enabled, and is empty when no getty is enabled there.
  3. Runs `systemctl enable vtium@ttyN.service` unless vtium is enabled there already. It links `getty.target.wants/vtium@ttyN.service` and `autovt@ttyN.service` to `vtium@.service`, so systemd starts vtium on VT N at boot and logind starts vtium there in place of the getty.
  4. Runs `systemctl disable getty@ttyN.service` when the getty is enabled. vtium is enabled before the getty is disabled, so a run cut short never leaves VT N with no console enabled.
  Each step that finds its work done skips it, so running `enable N` again finishes a run that was cut short, and on a VT already given to vtium it says so and changes nothing.
- **What `enable --all` does.** It gives vtium the template link, which logind follows on every VT that has no link of its own, VT 1, and the VTs whose gettys systemd starts at boot:
  1. Refuses, changing nothing, when kmscon holds the template link, when loginctl cannot say which sessions run, when `/etc/systemd/system/autovt@.service` exists and is not a link, when something on VT 6, logind's reserved VT, would meet vtium there (see "When logind starts a console" below), and when `vtium@ttyN` is masked on a VT the template link still reaches ("It masks nothing" above).
  2. Writes the record `/var/lib/vtium/console/autovt@.service`, which holds the path `autovt@.service` linked to, or is empty when there was no link, unless the template already links to `vtium@.service` or a record exists.
  3. Links `/etc/systemd/system/autovt@.service` to `vtium@.service`, by making the link under a temporary name in the same directory and renaming it into place. No systemctl verb can make this link: `systemctl enable vtium@.service` is refused before it links anything, as D3 chose.
  4. Does `enable N` for VT 1, unless another program, kmscon or the development install holds it or `vtium@tty1` is masked. logind never starts a console on VT 1 (below), so `getty.target`'s wants are the only thing that gives VT 1 a console at boot.
  5. For each VT from 2 to 6 that no other program holds and whose `getty@ttyN` is enabled, writes its record and runs `systemctl disable getty@ttyN.service`, and enables no `vtium@ttyN` there. A getty enabled there would hold the VT from boot, and with it gone logind starts vtium through the template link the first time the user switches to the VT. vtium is not enabled at boot on those VTs because each vtium started at boot opens the display card, and the first to open it keeps the card's DRM master while its VT is not shown, so a second one started at the same time cannot draw until vtium drops master after opening the card on a VT that is not shown. logind starts consoles by itself only on VTs 1 to 6 (`NAutoVTs=6`, logind.conf(5)'s default), so a getty enabled on a VT above 6 stays enabled, and `enable --all` names it and says that `vtium console enable N` gives that VT to vtium.
  6. Runs `systemctl daemon-reload`, so the manager reads the new template link.
  A VT that another program holds, that kmscon or the development install holds on its own, or whose `vtium@ttyN` is masked, keeps it, and `enable --all` names it. A VT that the development install holds keeps it, because its own `autovt@ttyN.service` link wins over the template, and `enable --all` names each such VT. So does a VT whose own `autovt@ttyN.service` links to another unit, such as a getty's alias that `systemctl enable getty@ttyN.service` made; `enable --all` names it and the link that holds it.
- **When logind starts a console.** logind starts `autovt@ttyN.service` from `manager_spawn_autovt` (systemd 262, `src/login/logind-core.c`), which `seat_active_vt_changed` (`src/login/logind-seat.c`) calls each time the VT on screen changes, and once when logind starts, for the VT then on screen. `manager_spawn_autovt` returns at once for a VT above `NAutoVTs=` (6 by default) that is not the reserved VT, `ReserveVT=` (6 by default). For any other VT but the reserved one, it first asks the kernel whether the VT is busy, by `VT_GETSTATE` on `/dev/tty1` (`vt_is_busy`), which says whether any process has the VT open, and starts nothing when it is. logind's own open of `/dev/tty1` for that question counts as a process having VT 1 open, so VT 1 always reads as busy, and logind never starts `autovt@tty1.service`; systemd's comment there says that tty1 needs an explicitly loaded getty or display manager. Only then does it ask systemd to start `autovt@ttyN.service`, with `StartUnit` in the job mode `fail`. The reserved VT is the exception: logind holds it open itself (`manager_reserve_vt` in `src/login/logind.c`) and starts `autovt@ttyN.service` there on every switch to it, busy or not.
  - So a graphical session or a running getty, which holds its VT open, is never joined by a console that logind starts on a switch to its VT, on VTs 1 to 5. A session started later on such a VT is safe from vtium on a switch, and the risk to it is a vtium enabled at boot on its VT, which `enable` refuses while the session runs. This machine shows it: its gettys on VTs 2 to 6 run from boot, its template link names `kmsconvt@.service`, and logind started the C reference's console on no VT this boot.
  - On VT 6, the reserved VT, logind starts `autovt@tty6.service` at every switch, even beside a session there. With the template link naming vtium and no link of VT 6's own, that start runs vtium on VT 6, and vtium's `Conflicts=` stops a getty, kmscon or the development install running there. So `enable --all` and `enable 6` refuse while a login session is on VT 6, which logind lists with VT 6 as its `VTNr`, such as a user logged in at the getty there, unless vtium already runs on VT 6. vtium sets `XDG_VTNR` in its session's environment, so logind lists a login inside vtium on VT 6 as a session on VT 6 too, and the switch's start of `vtium@tty6.service` then finds it active and stops nothing. On a VT already given to vtium, `enable 6` says so before it checks for a login. `enable --all` also refuses while another program holds VT 6, and, while VT 6 has no link of its own, while kmscon or the development install is enabled or running there and while `vtium@tty6` is masked; `enable 6` refuses kmscon and the development install on any VT it is asked for ("What `enable N` does"). Each refusal names what to free first and changes nothing. VT 6's own link, such as one to `kmsconvt@.service`, keeps the template from it, and then `enable --all` leaves VT 6 to that console. A getty waiting at its login prompt on VT 6 holds no session, so stopping it ends nothing: both verbs go ahead beside it, and each says that the next switch to VT 6 stops a getty there if one waits at its login prompt, which ends no session. While vtium already runs on VT 6, `enable 6` says neither that nor how to start vtium. vtium reads neither `NAutoVTs=` nor `ReserveVT=` from logind.conf(5), and takes their defaults, 6 and 6.
- **What `disable N` does.** It undoes `enable N` in the opposite order, so VT N always has a console enabled:
  1. When the record `/var/lib/vtium/console/ttyN` holds a path, links `getty.target.wants/getty@ttyN.service` to that path again, by a link under a temporary name renamed into place. That enables the getty exactly as `enable N` found it: linked to the same unit file, with no `autovt@ttyN.service` alias, which `systemctl enable getty@ttyN.service` would add (measured). `systemctl add-wants` would link to the first getty unit file on the search path, such as an override in `/etc/systemd/system`, which may not be the file the want linked to (measured). An empty record enables no getty. With no record at all, or one that holds neither, VT 1 alone gets `systemctl add-wants getty.target getty@tty1.service`: that is the state D3's earlier hand-typed steps left, and VT 1 has no login at boot without its getty.
  2. Runs `systemctl disable vtium@ttyN.service` while vtium is enabled there.
  3. Removes `/etc/systemd/system/autovt@ttyN.service` while it links to `vtium@.service`: `disable` leaves it (measured), and logind would go on starting vtium on VT N.
  4. Removes the record, and runs `systemctl daemon-reload` when it changed a link by hand.
  On a VT where vtium is not enabled, no `autovt@ttyN.service` links to `vtium@.service` and no record names the VT, `disable N` says so and changes nothing. While the template links to `vtium@.service` and no getty is enabled on VT N, logind still starts vtium on VT N after `disable N`. `disable N` has still undone everything `enable N` did, so vtium exits with status 0, and it says on standard output that logind still starts vtium there and names `vtium console disable --all`.

> Edited 2026-11-04: the maintainer decided that `disable N` exits 0 when it has undone what `enable N` did (`considered`, 2026-11-04). While the template linked to `vtium@.service`, `disable N` printed its note that logind still starts vtium on VT N on standard error and exited with status 1; it now prints the note on standard output and exits 0. The earlier text is in git at d20074b1.

- **What `disable --all` does.** It does `disable N` for each VT where `vtium@ttyN` is enabled, where `autovt@ttyN.service` links to `vtium@.service`, or where a record names the VT. Then, while `autovt@.service` links to `vtium@.service`, it links the template back to the path the record holds, or removes the link when the record is empty. With no record, as on a machine set up by D3's earlier hand-typed steps, it removes vtium's link and adds nothing when a directory later on the search path has a template link, such as Debian's `/lib/systemd/system/autovt@.service`, which is then in force again; with none, it links the template to `getty@.service`, the link systemd's preset makes from getty's own `Alias=autovt@.service`. It then removes the record and runs `systemctl daemon-reload`. A template link that names any other unit is left as it is, and so are the development install's VTs. `systemctl disable vtium@.service` cannot do this work: it fails on the template's `DefaultInstance=` as the template's enable does, and changes nothing (measured).
- **The records.** A machine may have gettys enabled on several VTs, as this machine has on VTs 1 to 6, and `systemctl preset getty@.service`, which D3's earlier hand-typed way back used, enables only `getty@tty1`. The records let `disable` give back exactly what `enable` took. They live in `/var/lib/vtium/console/`, one small text file each, in a directory that vtium creates owned by root with mode 0755. Each is written under a temporary name and renamed into place. A VT's record holds the getty's link target or nothing (`enable N`, step 2), and the template's record holds the template link's target or nothing (`enable --all`, step 2). A VT's record that holds anything but nothing or a path to `getty@.service`, and a template record that holds anything but nothing or a path to a unit file named `PREFIX@.service` other than `vtium@.service`, is taken as no record.
- **What `status` prints.** First, one line on what logind starts on a VT that has no link of its own, from the template link in force on the search path: vtium, a getty, kmscon, another unit, or nothing when there is no link. Then a table with a row for each VT from 1 to 6, the VTs logind starts consoles on by default, and for each VT up to 63 where a console is enabled, linked, running or recorded. Its columns are the VT, the console systemd starts there at boot (`getty.target`'s wants), the console logind starts when the user switches to it (VT N's own `autovt@ttyN.service` link, or else the template link), and the console running there now. The column for a switch shows `-` on VT 1, where logind never starts a console, and on each VT above 6 but the reserved VT. A column with nothing in it shows `-`. It exits with status 0, or 1 when it cannot read systemd's state.
- **How vtium reads and changes the state.** It reads the links under `/etc/systemd/system`, the template link along the search path and its records itself, and asks the running manager only which consoles run, with `systemctl list-units --state=active`. It changes the units through `systemctl enable`, `disable`, `add-wants` and `daemon-reload`, and changes by hand only the three links no systemctl verb makes or removes as they were: the template link, a VT's leftover `autovt@ttyN.service` link to `vtium@.service`, and a getty's want linked back to the unit file the record names.
- **Exit statuses.** 0 when the verb did what it was asked or found it done, 1 when it refused or a step failed, and 2 for words it cannot take, as `vtium blank` does. A step that fails stops the run: vtium names the step and prints systemctl's message, and running the same verb again finishes the change, while the opposite verb undoes what was done. A run of `enable --all`, `disable N` or `disable --all` that finds no link to change still runs `systemctl daemon-reload`, the last step of each, so a rerun finishes a run whose reload failed. vtium cannot tell from the disk whether the manager has read the links, and a reload starts and stops nothing, so it reloads rather than keep a record of the failure.

On Arch, `libglvnd` ships `libEGL.so.1` and `mesa` ships `libgbm.so.1` (measured). EGL also needs a driver for the card, which `mesa` gives for most cards and NVIDIA's own driver gives for its cards. `vtium` and `vtium-git` require both libraries. `vtium-minspec-gpu` and `vtium-minspec-gpu-git` list both as optional dependencies, so the package manager installs neither unless asked, and `vtium-minspec` and `vtium-minspec-git` name neither.
  - `logind` links libsystemd's sd-bus, which the build finds through pkg-config (`crates/vtium-platform/Cargo.toml`). On Arch that is `systemd-libs`, which the package already depends on for udev.
  - The image helper links no library beyond the C runtime, since its decoders are written in Rust (`crates/vtium-image-helper/Cargo.toml`). It needs its account, which pacman's `20-systemd-sysusers.hook` creates from the sysusers file when the package is installed.
  - For a later deb or rpm recipe, the same needs map to that distribution's packages, such as `libegl1`, `libgbm1` and `libsystemd0` on Debian. Each recipe checks the names when it is written.
- **Frits, and no fonts.** The console draws with its built-in fonts, unifont and unscii-8, when no font is installed. A frit (a font set file) names the fonts the glyph helper draws from, and the helper leaves out a font the machine lacks. No vtium package ships a font file.
  - The console packages install their frits into `/etc/vtium/fonts`, the one directory vtium reads frits from (`crates/vtium-config/src/frit.rs`), as files the package owns and that keep a user's edits across an upgrade (pacman's `backup=` list). Each is ready to choose with `vtium config` or vtium.conf's `font-name`, and a frit that nothing names changes nothing. `/etc/vtium/vtium.conf` stays the user's (D3).
  - `vtium` and `vtium-git` ship four frits: `desktop`, JetBrains Mono with Nerd Fonts' symbols and Noto Color Emoji over the built-in unifont, starting at 18 points (`tools/specimens/frits/desktop.vtfrit`); a Terminus frit, from the Terminus console font; and `minspec-16` and `minspec-8`, which add Nerd Fonts' symbols and color emoji over the built-in fonts (`crates/vtium-config/frits/`). The four minspec packages ship `minspec-16` and `minspec-8`.
  - `vtium-fonts` is a package of its own on each package manager, and it is published on the AUR (the maintainer, 2026-11-06). It is a curated set of fonts chosen to go with the frits vtium ships, and it grows as new frits are added: each new frit's fonts join its dependencies (the maintainer, 2026-11-06). It installs no font file and no frit, only its license, and depends on that distribution's packages for every font the shipped frits name. On Arch those are `ttf-jetbrains-mono`, `ttf-nerd-fonts-symbols-mono`, `noto-fonts-emoji` and `terminus-font`, all in the extra repository (measured). Each console package lists `vtium-fonts` as an optional dependency, so the fonts stay optional. The maintainer accepted the name (`considered`, 2026-11-04).

- **How a frit finds the system's fonts.** A frit names a font by family, `font:FAMILY`, and the glyph helper finds the file without fontconfig (`crates/vtium-config/src/sources.rs`):
  1. It first looks for a kbd console font of that name in the `consolefonts` directory under `/usr/share/kbd`, `/usr/share` and `/usr/lib/kbd`, comparing names with case and blanks ignored and kbd's suffixes and compressions dropped (`KBD_DIRS`, `find_family`). A console font stores no family name, so this step matches its file's name.
  2. Else it looks for an outline font file, `.ttf`, `.otf`, `.ttc` or `.otc`, under `/usr/share/fonts` and `/usr/local/share/fonts`, up to 8 directories deep (`FONT_DIRS`), whose family name is FAMILY with case and blanks ignored, as fontconfig compares families (the maintainer, 2026-11-04). The family name is one the font's own name table stores: a face matches when its typographic family (name ID 16) or its legacy family (name ID 1), in any language the table holds, is FAMILY. The glyph helper decides with one reader of a face's names and one test, both for the search and for the rasteriser's choice of the face it draws (`crates/vtium-config/src/names.rs`), so the rasteriser takes every face the search finds. A face such as JetBrains Mono ExtraBold stores "JetBrains Mono ExtraBold" in name ID 1 and "JetBrains Mono" in name ID 16, so `font:JetBrains Mono` finds it through the typographic family, and `font:JetBrains Mono ExtraBold` through the legacy one. Reading name tables costs a file open each, so the helper takes two passes. It first matches file names as it does today, a file whose name less its extension is the family, or the family followed by `Regular`, with case, blanks, `-` and `_` ignored, and reads that file's name table to confirm the family. Only when no file name matches does it open the other files' name tables, at most 4096 files in one search, and a search that reaches that cap fails with a message that names the cap and the family, even when it has found a face of the family in another style, whose file the message then names; this machine holds 953 outline font files under those directories (measured 2026-11-04). The cap counts files opened, apart from `FAMILY_ENTRIES_MAX`, which bounds the entries of one directory. Among the files named for the family, the file name decides, the plain name before the name with `Regular`, then the directory listed first, then the path that sorts first, and the style of the face does not. Among the other files, the helper takes the first with a face whose subfamily is `Regular` with case ignored, its typographic subfamily (name ID 17) or else its subfamily (name ID 2), then the directory listed first, then the path that sorts first, and else the first file of the family in that order, so the same file wins on every run. It reads a file only if, with its links resolved, it stays under those directories. `vtium config`'s `--font-dir` option names other directories in their place (`crates/vtium-config/src/cli.rs`).

  So one frit finds the same font on every distribution that installs it under `/usr/share/fonts`, whatever the distribution names the file, a variable font such as `JetBrainsMono[wght].ttf` included. On Arch the shipped frits' fonts are `/usr/share/fonts/TTF/JetBrainsMono-Regular.ttf`, `/usr/share/fonts/TTF/SymbolsNerdFontMono-Regular.ttf` and `/usr/share/fonts/noto/NotoColorEmoji.ttf` (measured with `pacman -Fl`). Only the Terminus frit names a console font, by the name the distribution's package gives it: on Arch `ter-v16n`, in `/usr/share/kbd/consolefonts/ter-v16n.psf.gz` (measured). Each distribution's recipe repository carries the Terminus frit with its own source name. A font installed outside those directories, as on NixOS, is not found.
- **The picture gallery tool.** `vtium` and `vtium-git` install `tools/gallery/gallery` as `/usr/bin/vtium-gallery`, a bash script that shows PNG pictures as a grid of thumbnails, each named under it, through the kitty graphics protocol (the maintainer, 2026-11-04). It needs bash and the base tools `stty`, `od`, `base64`, `tr`, `fold` and `sort`, and no image library, since the terminal scales each picture (the script's header). The four minspec packages do not ship it, since their console draws no pictures: `make install` stages it when `FEATURES` names `images`.
- **More than one display.** Every build drives every display the console can see: with no head file vtium shows one grid on all of them, and a head file, the sections of vtium.conf, gives each display a terminal of its own (ADR-1401, ADR-1403 D3). Every console package ships the head file's template as the sections of the example configuration, `/etc/vtium/vtium.conf.example` (D3), for a user to copy into `/etc/vtium/vtium.conf` and edit.

### D9: each release carries its dependencies' source

> Added 2026-11-06 by the maintainer's decision (the `considered` entry of that date).

vtium's repository references its outside crates through `Cargo.lock`, which pins each one and its checksum, and keeps no copy of their source. The Arch recipes fetch the crates with `cargo fetch --locked` and then build offline (D2). A package manager that builds with no network at all, as Debian's does, needs the crates' source beside vtium's. So each GitHub release carries it: when a release is published, a CI workflow checks out its tag, runs `cargo vendor --locked`, packs the vendored crates as `vtium-VERSION-vendor.tar.zst` with the `.cargo/config.toml` lines that point Cargo at them, and attaches the archive and its SHA-256 to the release. The repository itself stays free of vendored code, so a crate update stays a change to `Cargo.lock` alone. The workflow can also run by hand on any tag, branch or commit that has it, which builds the archive as a workflow artifact and attaches nothing, so it can be checked before a real release depends on it. A release runs the workflow from its own tagged commit, so the first release that carries the archive is the first whose tag contains the workflow.

## C notes: the C reference's packaging

- The C reference shipped two units, `scripts/systemd/kmsconvt@.service.in` and `scripts/systemd/kmscon.service.in` (kmscon b1f7a7c5), and its terminfo entry, `scripts/terminfo/kmscon.ti`. Its `kmsconvt@.service` started a getty directly on failure, with `OnFailure=getty@%i.service`, and enabled VT 1 when it was enabled with no VT named, through `DefaultInstance=tty1`.
- To give every VT to the C reference, its unit's opening comment told the user to run `systemctl enable kmsconvt@` (`scripts/systemd/kmsconvt@.service.in`, kmscon b1f7a7c5). On a machine with no template link yet, that template enable linked `autovt@.service` to the unit through its `Alias=autovt@.service`, so logind started the C reference's console on every VT it spawned, and its `DefaultInstance=tty1` enabled VT 1, which its `Conflicts=getty@%i.service` took from the getty at boot. On a machine where `autovt@.service` already linked to `getty@.service`, as on Arch by default, whose systemd package's install script runs `systemctl enable getty@.service` (`/var/lib/pacman/local/systemd-262.1-1/install`), the enable failed with "already exists and is a symlink to getty@.service", linked only `getty.target.wants/kmsconvt@tty1.service`, and left the template on the getty; only `systemctl enable --force kmsconvt@.service` replaced the template link (measured with systemd 262 on vtium's shipped `kmsconvt@.service`, whose `[Install]` section is the C reference's, and on Arch's kmscon 10.1.0 unit). Either way it left `getty@tty1`, and every other getty enabled at boot, enabled, and `DefaultInstance=tty1` enabled the C reference's console on VT 1 even where a display manager started there at boot, so the two raced for the display. The C reference documented no way back: that enable line in the unit's comment is the only place its tree names enabling or disabling the unit. The measured way back would have been `systemctl disable kmsconvt@`, which removes every link to the unit, the template link included, and so leaves `autovt@.service` linked to nothing until the getty's preset links it again.
- Arch's `kmscon` package installs those units under `/usr/lib/systemd/system` and splits the terminfo entry into its own package, `kmscon-terminfo`, on which `kmscon` depends. On this machine the entry is the one from release 10.1.0, which lacks features that the C reference's own entry at b1f7a7c5 lists.
- The C reference chose its optional parts at build time through meson features that each defaulted to `auto`: the GPU backend `video_drm3d`, the renderer `renderer_gltex`, the font backends, `images` and `sd_login` among them (`meson.options`, kmscon b1f7a7c5). It built most of them as loadable modules, so one package served every machine: Arch's `kmscon` 10.1.0 installed `mod-drm3d.so`, `mod-gltex.so`, `mod-freetype.so`, `mod-pango.so`, `mod-psf.so` and `mod-unifont.so` under `/usr/lib/kmscon`, and at start the C reference logged and skipped a module it could not open, such as one whose libraries were missing (`src/shl/module.c:53-57, 224-228`, kmscon b1f7a7c5). That package listed no EGL or GBM library among its dependencies, and listed fontconfig as optional (measured 2026-11-04).

## Where vtium departs from the C reference

- **No default VT for the packaged unit.** vtium's packaged unit refuses an enable that names no VT and links nothing (D3), where the C reference's unit took VT 1 (C notes), so it never starts by accident on a VT that a desktop or another console holds, nor on every VT logind spawns.

- **Other programs keep their VTs, and a failure stops none.** The C reference's `DefaultInstance=tty1` enabled its console on VT 1 beside a display manager there, and its `OnFailure=getty@%i.service` started a getty that stopped any display manager whose `Conflicts=` named it (C notes). `vtium console` refuses, and `enable --all` passes by, every VT another program holds now or claims at boot, judged from what is on the machine, and vtium's fallback starts no getty whose start would stop another program (D7).
- **A package for each build.** The C reference's one package carried its optional parts as modules it loaded at start (C notes). vtium builds its features into the console, so each package manager publishes a desktop build under vtium's name, and the minspec builds have recipes of their own (D8). The AUR carries no minspec package. The desktop build lists the GL libraries its GPU path loads among its dependencies.

> Edited 2026-11-06: the maintainer kept the minspec packages off the AUR (`considered`, 2026-11-06; D8). The departure read: "so each package manager publishes a desktop build under vtium's name and two minspec builds beside it (D8), and the desktop build lists the GL libraries its GPU path loads among its dependencies."
- **vtium on every VT is one command with an exact way back.** The C reference gave every VT to its console through the template enable, which left the enabled gettys enabled, failed where the template link already named the getty, and had no documented way back (C notes). `vtium console enable --all` (D7) disables the gettys it displaces and records what it changed, and `vtium console disable --all` puts back the template link and each getty as it found them.

## Consequences

### Positive

- The maintainer runs a packaged vtium every day, so the head file, the profiles, the upgrades and the units are tested in the way users meet them.
- Development keeps its own install and its review runs while the packaged vtium runs, and neither replaces the other's files or units.
- vtium takes no file or unit name of `kmscon`'s, so a machine that also runs `kmscon` keeps it usable on VTs of its own.
- The recipes call vtium's own targets, so vtium's tree says once which file goes where, and a new package manager adds a recipe and a repository, not a second account of vtium's layout.
- A user's sessions never end because of an upgrade.
- A VT, or every VT, goes to vtium and comes back with one command each (D7), and the way back gives back exactly the gettys and the template link that were there.
- A person who installs `vtium` on a desktop gets pictures, the GPU path, on by default from `v0.1.0-alpha.6` on, and a choice of fonts with no build variable to set, and the user of a small machine still gets the minspec console by building the `vtium` recipe with `VTIUM_FEATURES` (D8).
- The AUR carries no package that differs from `vtium` only in build options, and `vtium-arch`'s CI still builds every minspec recipe (D8).

### Neutral

- `packaging/` holds only submodules. A clone without `--recurse-submodules` has empty directories there, and no gate, CI job or build reads them.
- The recipes build with the host's toolchain and need a network connection only for the crates: `prepare()` runs `cargo fetch --locked`, and `build()` runs offline with `--frozen`.
- Each later version tag moves `vtium`'s recipe to that tag, and the publish script pushes it to the AUR.

## Alternatives Considered

- **Recipes in vtium's own tree,** under `packaging/` as plain files. Rejected by the maintainer: a recipe repository of its own can be published and versioned apart from vtium, and the submodule still ties each recipe to the code it builds.
- **A package that replaces `kmscon`'s,** providing and conflicting with `kmscon` and installing vtium's units under `kmscon`'s names. Rejected by the maintainer: `kmscon` is an independent product, and vtium is not coupled to it.
- **A local builder only, published later.** Replaced by the maintainer: the packages go on the AUR now, since the maintainer holds an account there and the names stay vtium's.
- **Checking a signature on `vtium-git`'s source.** Rejected: the tip of `main` carries GitHub's signature on its merge commit, which proves nothing about vtium's maintainer.
- **Signed commits.** Rejected: an agent's every commit would ask for the passphrase; the signed tag is what a builder checks.
- **Building the local checkout by default.** Rejected by the maintainer: `main` holds only reviewed work with green CI, and the setting in D2 reaches a local checkout when one is wanted.
- **One set of names for both installs,** with `make vt-install` replacing the package's files. Rejected: the maintainer wants the packaged vtium kept running while development goes on, and a unit in `/etc/systemd/system` overrides the packaged one on every VT.
- **Keeping the development binary's name `vtium` in a directory of its own,** such as `/usr/local/lib/vtium-dev/vtium`, so that `vtium blank` finds it without change. Not chosen: `ps`, `pgrep` and the journal then show two processes with one name, and telling them apart is the point of separate names.
- **Restarting vtium after an upgrade,** as some packages restart their daemons. Rejected: a restart hangs up every session on the VT, so the user chooses when.
- **The minspec build under vtium's name, with `VTIUM_FEATURES` for anything more,** as D2 had it. Replaced by the maintainer (2026-11-04): the AUR's `vtium` drew no pictures and never used the GPU, and a person installing it from an AUR helper sets no build variable.
- **The minspec packages on the AUR,** `vtium-minspec` and `vtium-minspec-gpu` with their `-git` twins, as D8 had them from 2026-11-04. Replaced by the maintainer (2026-11-06): they differ from `vtium` only in build options, and the maintainer does not want the AUR to carry such packages. Their recipes stay in `vtium-arch`, and its CI builds them (D8).
- **One package that loads its optional parts at start,** as the C reference's modules did. Not chosen: vtium's features are compiled into the console (`crates/vtium/Cargo.toml`), and the GPU path already loads its libraries at run time, so the only weight a minspec machine would save is the code, which a package of its own saves.
- **Bundling the frits' fonts in vtium's packages.** Rejected by the maintainer (2026-11-04): the fonts come from each distribution's own packages, which `vtium-fonts` names, and the frits find them where the distribution installs them (D8).
- **One recipe building every package of a channel.** Rejected by the maintainer (2026-11-04): everyone who installed either console would compile both (D8).
- **Enabling vtium on a VT from the package's install script.** Rejected: the VT to give vtium is the user's choice, and a VT given by mistake ends the session on it.
