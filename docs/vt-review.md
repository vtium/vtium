# The VT review

The operator judges vtium by eye on a VT of a real machine (#68). `make vt-accept`, `make vt-login`, `make vt-check` and `make vt-shell` borrow one VT: they stop the console unit there, run vtium with the acceptance pass, a login prompt, a guide or the operator's own shell as its only session, and start the units they stopped again when the session ends. The answers come back as a log. Nothing is installed and no system file changes. The review adds to the harness tiers ([architecture.md](architecture.md#how-it-is-judged)) and replaces none of them.

It is written for a host under systemd and logind whose VTs run `vtium-dev@ttyN`, `getty@ttyN`, the C reference's `kmsconvt@ttyN`, or the unit that `autovt@ttyN` names. The tools are in `tools/vt/` and carry over the C reference's `make vt-demo`, `vt-login` and `vt-check` and the lessons of their first runs.

## This machine's VTs

The maintainer's machine runs the packaged vtium and has no kmscon installed. `sudo vtium console enable --all` pointed `/etc/systemd/system/autovt@.service` at the packaged `vtium@.service` and disabled the gettys on VTs 2 to 6, so logind starts the packaged vtium on each of those VTs when it is switched to.

| VT | What runs there |
|---|---|
| 1 | sddm, the display manager, whose unit takes the VT with `Conflicts=getty@tty1.service` |
| 2, 3, 4 and 6 | the packaged vtium, `vtium@ttyN`, which logind starts when the VT is switched to |
| 5 | the development VT: `vtium-dev@tty5`, a build of this checkout, which `make vt-install VT=5` installed ([below](#installing-vtium-on-a-vt)) |
| 7 | the maintainer's Wayland session |

`vtium console status` prints this layout as it stands: for each VT, what systemd starts at boot, what logind starts when the VT is switched to, and what runs there now. VT 5 became the development VT through `sudo vtium console disable 5` and then `make vt-install VT=5`, which gave VT 5 a link of its own, `/etc/systemd/system/autovt@tty5.service`, to `vtium-dev@.service`, and a manifest, `/var/lib/vtium-dev-install/tty5`.

Every review run borrows VT 5, since every other VT a run could take is refused ([Which VT a run takes](#which-vt-a-run-takes)). After a merge lands on `integration`, the main session runs `make vt-install VT=5` from the integration worktree, which replaces the development build and restarts `vtium-dev@tty5`, so VT 5 runs the merged code between review runs.

## Who starts a run

The main session starts a run when a branch reaches a visual review point, without asking first, tells the operator which VT to switch to, and reads the answers when the run ends. The operator switches to the VT and works through it. Subagents never start a run: they verify in their worktrees through the tiers, with `make test-tools` and `DRY_RUN=1` for the tools themselves, and report. One build is on the VT at a time, from one place. When sudo needs a password, the run asks for it in the terminal the main session started it from, before the operator leaves for the VT.

## Running it

```sh
make vt-check GUIDE=start               # the guide tools/vt/checks/start.guide
make vt-check GUIDE=start GUIDE_STEPS=2 # only that step
make vt-accept                          # the acceptance pass, built with pictures: every page answered, the pass recorded
make vt-accept FEATURES=                # the same with the minspec build; the picture pages record skip
make vt-accept VT=4 DEMO_ARGS='--font-size=30 --mode=1366x768'
make vt-login                           # a login prompt, for the acceptance pass or anything else by hand
make vt-shell                           # your login shell, as you, with no login; exit it to end the run
make vt-accept DRY_RUN=1                # pick the VT and print every command; run none
make vt-shell VT_DEBUG=1                # log debug messages and copy the kernel's DRM state at each display change
make help                               # the targets
```

Each target builds the minspec binary (`make minspec`, `target/x86_64-unknown-linux-gnu/minspec/vtium`), picks a VT ([below](#which-vt-a-run-takes)), runs `sudo -v`, prints the VT to switch to and the key back, and blocks until the run ends:

```
================================================================
  Switch to VT 5 now: Ctrl-Alt-F5    (Ctrl-Alt-F7 returns to this desktop)
================================================================
```

When it ends, it prints a health check of vtium's log (its `panicked at` lines), the log's path (with `make vt-shell`, the transcript's too), the answers the run added and the path of the answers file. It exits non-zero when vtium failed, the run was cut short, or nothing was recorded.

### Which VT a run takes

Without `VT=N`, a run takes the development VT: a VT whose manifest `make vt-install` wrote under `/var/lib/vtium-dev-install`, and whose `vtium-dev@ttyN` is enabled. When there are several, it takes the lowest. `vt.sh` prints which VT it borrows before the banner. On a machine with no development VT, the run takes the first free VT of 5, 6, 4, 3 and 2, and `VT=N` names the VT in place of either. Both `vt.sh` and `run-vt.sh` refuse a VT:

- that is on screen, which is the VT the command was typed on;
- that a logind session is on, such as a login inside vtium-dev; the operator logs out there first;
- that the packaged vtium holds: `vtium@ttyN` runs or is enabled, or logind starts it when the VT is switched to, because `autovt@ttyN` names it, as `vtium console enable --all` arranges on every VT without a link of its own. That VT is the operator's everyday console, which a run would stop, and which a start limit or a failed restore would leave without a console. `sudo vtium console disable N`, followed by `sudo systemctl stop vtium@ttyN.service` when it runs, frees a VT that `vtium console enable N` gave the packaged vtium; a VT that `enable --all` gave it stays the packaged vtium's until `sudo vtium console disable --all`;
- that is logind's reserved VT, the VT that `ReserveVT=` in logind.conf(5) names, 6 by default. logind starts `autovt@ttyN` there at every switch to it, even while something holds the VT open, and that console would hang the VT up under the run's vtium. The run reads the setting with `systemd-analyze cat-config systemd/logind.conf`.

The development VT is borrowed, not refused: the run stops `vtium-dev@ttyN` and starts it again when it ends ([What a run does](#what-a-run-does)).

| Variable | What it does |
|---|---|
| `VTIUM_BIN=PATH` | the binary to run in place of the minspec build, which is then not built. It runs as root, so it is taken from make's command line or the Makefile, never from the environment, and `run-vt.sh` refuses a file owned by anyone but root or the invoking user, or writable by group or others. |
| `VT=N` | the VT, 2 to 12, in place of the development VT or a free VT ([Which VT a run takes](#which-vt-a-run-takes)). |
| `DEMO_ARGS='...'` | vtium's options, split into words as `xargs` splits them: quotes and backslashes honoured, nothing expanded or run. Each option is one word, `--name=value` or `--name` / `--no-name`. |
| `GUIDE=NAME`, `GUIDE_STEPS='2 3'` | `make vt-check`'s guide, a name in `tools/vt/checks` or a path, and the steps to run. The guide and the steps are checked before sudo; without `GUIDE` the target fails before the build, naming the guides. |
| `DRY_RUN=1` | picks the VT and prints the command, then runs `run-vt.sh --dry-run` without sudo: it asks what it would ask (the VT on screen, the sessions, the active units) and prints each command that would change anything. |
| `VT_DEBUG=1` | runs vtium with `--debug`, so its log holds its debug messages too, and copies the kernel's DRM state into a directory beside the log, named like the log with `.drm` in place of `.log`. Each time vtium logs that a display came or went, `run-vt.sh` copies `/sys/kernel/debug/dri/<N>/state` of every card as `NNN-came-<N>.state` or `NNN-went-<N>.state`; each time a display's first flip after its modeset is done, which vtium logs at debug once the card scans the new mode out, as `NNN-modeset-<N>.state`; and once more as `end-<N>.state` after vtium stops and before the console unit starts again. A line in vtium's log names each copy, so the log shows which state followed which line. The copies are written as the invoking user. When something vtium started still holds its output 5 s after vtium stops, the log ends there, so the run never waits on it. |

The variables reach `tools/vt/vt.sh` through the environment, never as recipe text. The allowlist is written for the command line #21 gives vtium, the C reference's; vtium parses no arguments yet. `DEMO_ARGS` takes the options the C reference's review took: display, font, palette, text and input options, `--render-timer`, `--image-storage-limit` (`auto` or up to 4G) and `--sync-timeout`, vtium's on-screen display options, `--osd`, `--osd-timeout` and `--focus-mark`, and `--display-buffers` (`1`, `2` or `3`, how many buffers each display draws into, ADR-1401 D2), each named in full in lower-case letters and dashes. `run-vt.sh` refuses the rest: the VT, seat and session options, `--login`, `--configdir`, `--oneshot`, the grabs, the options that name files, and any value in a word of its own, which vtium would take as the option's value or move into the login command that runs as root.

By hand: `sudo tools/vt/run-vt.sh --bin=target/x86_64-unknown-linux-gnu/minspec/vtium [--debug=DIR] [--login | --guide=FILE [--steps=LIST] | --shell [--transcript=FILE]] [N] [-- vtium-option...]`, and `tools/vt/run-vt.sh --bin=... --dry-run 5` without root.

## What a run does

1. `vt.sh` picks the VT and refuses the ones [above](#which-vt-a-run-takes), reading the VT on screen from `/sys/class/tty/tty0/active` and the sessions from `loginctl`, checks a guide with `guide.sh --check`, creates `/tmp/vtium-vt` (mode 0700) for its log, refusing it when it is a symlink, another user's or open to anyone else, and runs `sudo -v`.
2. `sudo tools/vt/run-vt.sh` takes the lock `/run/vtium-vt.lock` for the whole run, so a second run is refused while one is going: one build on a VT at a time. It checks the VT again: it refuses the VT on screen, any VT a logind session is on, the desktop's included, the packaged vtium's VT and logind's reserved VT, and refuses when `loginctl` cannot list the sessions or read one still listed.
3. It records which of `vtium-dev@ttyN`, `getty@ttyN`, `kmsconvt@ttyN` and `autovt@ttyN` are active, and stops them. `autovt@ttyN` is another name for the unit logind started there, which is `vtium-dev@ttyN` on the development VT, so the run records and stops that unit once, under its own name. A trap on exit, Ctrl-C, SIGTERM and SIGHUP stops vtium with SIGTERM (SIGKILL after 5 seconds) and starts those units again, and only those, so the VT comes back as the run found it after a normal end, an interrupt or a crash: vtium-dev when vtium-dev ran, a getty when a getty ran, as it does after vtium-dev failed and its fallback started one, and nothing when nothing ran. While it restores it ignores a second signal and a closed terminal, and no failed write cuts it short. A failed restart exits 1 and names the command that restores the unit.
4. From the moment its units have stopped until it starts them again, `run-vt.sh` holds `/dev/ttyN` open. logind starts `autovt@ttyN` when a VT is switched to only while nothing holds that VT open, which it asks the kernel with `VT_GETSTATE`, and on the development VT that unit is `vtium-dev@ttyN`, through the VT's own link. vtium holds the VT while it runs, and the hold covers the moments before vtium opens it and after vtium ends, so a switch to the VT at any point of the run starts nothing there. The run lets go of the VT before it starts the units again, because a console unit's start hangs the VT up and may hand it back to the kernel (`TTYVHangup=`, `TTYVTDisallocate=`). vtium and its session do not inherit the hold.
5. It runs vtium with `--vt=ttyN --no-switchvt --configdir tools/vt/config --oneshot`, the options from `DEMO_ARGS`, and the session after `--login --`. The acceptance pass, the guide and the shell run as the invoking user through `setpriv`, with a cleared environment that gets back only `VTIUM_HEAD` and `VTIUM_CONSOLE`, carried across as words vtium fills in, never as root: a user whose password entry has uid 0 is refused, whatever its name. `tools/vt/config` keeps the system's config out of the run.
6. With `--login` the session is `/bin/login -p`, and vtium runs without `--oneshot`. The first logout ends the run: once a session on the VT has been open, none open there means its user logged out. Ctrl-C also ends it, the login with it. vtium ending on its own is a failure. A poll whose `loginctl` fails changes nothing; ten in a row get a warning.

No tool switches a VT: the operator does, with Ctrl-Alt-FN. Before vtium starts, the run prints the command that restores the VT by hand, naming the units it stopped, such as `manual restore: sudo systemctl start vtium-dev@tty5.service` on the development VT, and a failed restart names it again.

## Your shell

`make vt-shell` runs the operator's login shell as vtium's session, for anything by hand: the session is the operator's own, with no acceptance pass, guide or login prompt. Exiting the shell ends vtium, the console unit comes back and `make` returns. Ctrl-C in the terminal `make` runs in ends it too, as a normal end.

- The user is the one who ran `make` (sudo's `SUDO_USER`). Their entry in the password database (`getent passwd`) names the uid, gid, home directory and shell. The shell must be listed in `/etc/shells`, be an executable file, and have a path of letters, digits and `/._+-`. The home directory must exist, be a directory and be the user's.
- It runs through `setpriv` as that user, with no inheritable capabilities, as a login shell (`-l`) in the home directory. Its environment is the one `setpriv --reset-env` gives (`HOME`, `SHELL`, `USER`, `LOGNAME`, `PATH` and `TERM`), plus `LANG` and `LC_*` from `/etc/locale.conf`. When `/run/user/UID` is a directory of the user's alone (mode 0700, not a symlink), it also gets `XDG_RUNTIME_DIR`, and `DBUS_SESSION_BUS_ADDRESS` when `bus` there is a socket: the rights the desktop session already gives the user, such as pipewire and `systemctl --user`. `DISPLAY` and `WAYLAND_DISPLAY` are not passed. There is no PAM and no logind session of its own.
- Ctrl-C and Ctrl-\ reach what the shell runs: vtium starts in the background, with SIGINT and SIGQUIT ignored, and its pty starts the session with every signal at its default. The acceptance pass and the guide get the same.
- A job left running in the background when the shell exits keeps running after the run: no logind scope reaps it.
- `script -q -f` (util-linux) records the session into a transcript: what the screen was sent, so a password typed without echo is not in it. vtium has no option that copies its pty's output to a file, and `script` runs as the user, so the transcript is written with the user's rights. `-f` writes each chunk at once, so a crash keeps what came before it.
- vtium's log and the transcript go to `/tmp/vtium-vt` (mode 0700), each under a new name, the transcript with mode 0600, and the end of the run prints both paths:

```
vtium log: /tmp/vtium-vt/vt-20261027T151200-tty5-a1B2c3.log
transcript: /tmp/vtium-vt/vt-20261027T151200-tty5-a1B2c3.transcript
```

## Guides

`make vt-check` runs `tools/vt/checks/guide.sh` as vtium's session. Each step is one screen: the command it runs, what to do and what to expect. Enter runs the step's command, or starts its probe or shell; q stops a probe and `exit` ends a shell, and the operator answers y, n or s, with a note. At a step's first prompt, s skips the step and q ends the checks. After the last step vtium exits and the console comes back.

The steps' commands and shells run with the system's locale: when the session has no `LANG`, `guide.sh` takes `LANG` and `LC_*` from `/etc/locale.conf`, by the rule `make vt-shell` uses, so a program such as tmux or vim draws UTF-8. A console that the open chord, Ctrl+Super+Enter, adds to the head runs the head's command again, which is the guide. The guide runs only in the head's first console, so one run asks each step once and keeps one set of answers: in a console whose `VTIUM_CONSOLE` is past 1, `guide.sh` prints which console it is and runs a shell with the prompt `console-N$ `, which `exit` ends.

The answers, and each line a probe prints, are appended to `/tmp/vtium-vt/vt-check.log` under a header naming the guide, the time, the tty and the steps. `guide.sh` refuses that directory before anything is asked when it is a symlink, another user's or open to anyone else.

A guide is `tools/vt/checks/NAME.guide`, lines of `key: text`; blank lines and lines starting with `#` are skipped. Its opening comment says what it checks and the command that runs it.

| Key | What it holds |
|---|---|
| `title:` | once, before the first step: the first screen's heading and the log's header |
| `intro:` | a line for the first screen, before the first step |
| `step:` | starts a step, with its title |
| `run:` | the step's command, one line, shown under `Run:`. Enter runs it on the guide's terminal, vtium's VT, through `bash --noprofile --norc -c`, echoed after the prompt `vtium-check$ ` as a shell would show it, and the step asks once it ends; a status other than 0 is shown and logged. A key pressed while it runs is neither echoed onto the picture nor kept, so it never answers the step. Ctrl-C stops the command, and Ctrl-\ the program it runs at that moment, as at a prompt; the checks go on, and the step asks. |
| `probe:` | the step's mode: `shell`, an interactive shell with the prompt `vtium-check$ `, or a mode of `checks/probe.py` (`probe.py --list`), which sets a terminal mode and prints each sequence the terminal sends, timed. A step has a `run:` or a `probe:`, not both, and one without either asks once Enter is pressed. |
| `do:`, `expect:` | a line shown as typed under `Do:` or `Expect:`; each step needs an `expect:` line, and a `do:` or `run:` line |

A step that judges a picture runs the command that draws it, so the picture is on screen while the operator answers, and one step judges each picture. `do:` holds what only the operator can do: switch VTs, keep still, look. A step keeps the `shell` probe when typing the command is what it checks.

`{vt}` and `{desktop}` in the text are the run's VT and the desktop's. `guide.sh --check FILE` checks a guide without a terminal and lists its steps. `start.guide` checks that vtium starts and that a shell runs and echoes at its prompt; #21 adds the steps for what it wires in. `blank.guide` checks that `setterm --blank` times the DPMS blank and that a program's `CSI 13 ]` wakes the displays (#79). `vt.guide` checks the switch away and back, and that keys reach vtium and not the kernel console (#19). `wave-a.guide` checks what Wave A changed on screen: the blink styles, X11 color names and a program waking the blank. `token.guide` checks frames drawn straight into the display's buffer (ADR-1401 D2): text appearing a letter at a time, scrolling, a full-screen redraw and clear, the scrollback, the cursor, a VT switch while lines arrive, the displays going dark and waking, and a display unplugged and plugged back, each with no tearing, missing line or old content. `daily.guide` is the daily-driver soak, run with `DEMO_ARGS='--bell'`: your own login shell, an editor, a pager, top or htop, tmux, a long `cat`, 256 colors and truecolor, Unicode and wide characters, copy and paste with the mouse, the wheel, an OSC 8 link with Ctrl's overlay and Ctrl+click, OSC 133 prompt jumps, the bell, zoom, suspend and resume, and last whether you would leave vtium running on a VT. It runs with no login, which `make vt-login` checks. `chords.guide`, run with `DEMO_ARGS='--osd=full'` so the top line names the console shown, checks the console chords under the open policy (ADR-1401 D1, D5): Ctrl+Super+Enter opens a console just after the one shown, Ctrl+Super+Backspace closes the one shown and does nothing on the last, a new console never takes an id given before in the run, a head stops at its cap of 4, and Ctrl shows a link's address only while it is held, across a console chord too. `restart.guide` checks that vtium's unit starts vtium again after a failure (ADR-1401 D9, [systemd.md](systemd.md)): under the open policy one SIGKILL hands the VT to the getty fallback, and under a closed policy vtium comes back, and past systemd's start limit of 5 starts in 10 s the VT is left with no login, until `systemctl reset-failed` and a start bring vtium back.

`restart.guide` is the one guide that never runs as vtium's session, since its steps kill vtium. The maintainer runs it by hand in a desktop terminal, from the checkout's top directory, as `GUIDE_VT=N GUIDE_DESKTOP=D tools/vt/checks/guide.sh tools/vt/checks/restart.guide`, where N is a spare VT that is not on screen and has no login, and D is the desktop's VT. Its first step checks that N is spare and that the terminal is not inside vtium. Its second runs `make vt-install VT=N` ([below](#installing-vtium-on-a-vt)) and checks that the unit has `Restart=on-failure`, and its last runs `make vt-uninstall VT=N`, which the maintainer skips to keep vtium on that VT. Every kill goes through `systemctl kill --kill-whom=main` to the unit of VT N, so it reaches that one vtium, where `pkill -x vtium` would also kill a `make vt-check` run. The closed-policy steps install `tools/vt/checks/restart-closed.conf`, the shipped rules under `policy = closed` with the head not isolated, as `/etc/vtium/heads.conf`, after `vtium check-config` passes it and only when no head file is installed; the recovery step removes it only when it is that file, and removes `/etc/vtium` only when the install step created it. The maintainer skips those four steps to leave `/etc/vtium` untouched. A run that stops between the install step and the recovery step leaves the closed head file in place, where every vtium on the machine reads it at its next start; remove it by hand with `sudo rm /etc/vtium/heads.conf`, which the install step's text also gives.

The C reference's first guided run left lessons the guides keep:

- A guide names the Super (Windows) key in full: "Logo" was misread. `guide.sh --check` refuses a guide that says Logo.
- Shift+PgUp is the terminal's own scrollback key and never reaches a probe.
- Turning a monitor off and on is an unplug, which gives FOCUS OUT and then FOCUS IN, not a DPMS blank. A DPMS step needs the terminal's own blank, from `--dpms-timeout`.
- A probe's times are the times it read the bytes, so a probe reads while it waits.

## Installing vtium on a VT

vtium is installed on this machine in two ways, under separate names, so that both can run at once, each on its own VT. The packaged vtium comes from one of two Arch packages, whose recipes are in packaging/arch: `vtium`, the release, built from its signed tag, and `vtium-git`, built from the tip of main. The two conflict, so a machine has one of them, and this machine has `vtium`, at 0.1.0-alpha.1. Either package owns `/usr/bin/vtium`, `/usr/bin/vtium-config`, `vtium@.service` and `vtium-getty@.service`, and, built with images, `/usr/bin/vtium-image` and `/usr/lib/sysusers.d/vtium-image.conf`; the maintainer installs it with pacman and gives it VTs with `sudo vtium console enable` (ADR-1500 D7). The development install comes from this checkout through `make vt-install`, which owns `/usr/local/bin/vtium-dev`, `/usr/local/bin/vtium-dev-config`, `vtium-dev@.service` and `vtium-dev-getty@.service`, and, for a console with pictures, `/usr/local/bin/vtium-dev-image` and `/etc/sysusers.d/vtium-dev-image.conf`. Neither touches the other's files. The packaged vtium lags development on purpose: it tests how vtium is deployed and updated, and the development install tests the work in progress.

`make vt-install VT=N` makes a development build of vtium the console of VT N of this machine, in place of its getty, and it stays there across reboots until `make vt-uninstall VT=N`. That VT becomes the development VT, which a review run borrows for one session: the run stops vtium-dev there and starts it again when it ends ([Which VT a run takes](#which-vt-a-run-takes)). Run both as yourself, never as root or under sudo: each refuses root before it builds anything, and asks sudo for each step that needs root, so sudo asks for the password in the terminal they run in.

```sh
make vt-install VT=5 DRY_RUN=1   # print the units it would write and every command; run none
make vt-install VT=5             # install the development build on VT 5, then Ctrl-Alt-F5 shows it
make vt-install VT=5 FEATURES=images   # a console with pictures, with its image helper
make vt-install VT=5             # again, after a merge: the binaries are replaced and vtium-dev on VT 5 restarts
make vt-uninstall VT=5 DRY_RUN=1 # print what uninstall would do
make vt-uninstall VT=5           # VT 5 back as it was
```

vtium starts its glyph helper, `vtium-config`, at a path fixed when the binary is built (`VTIUM_FONT_HELPER`, read in `crates/vtium/src/helper.rs`, `/usr/bin/vtium-config` when unset). So `make vt-install` builds its own console, `make vt-dev-console`, which is the minspec build made to start the helper at `/usr/local/bin/vtium-dev-config`, in the target directory `target/vt-dev` so that it never replaces the minspec build the review runs use. It builds the helper with `make config-release`. `FEATURES='...'` builds the console with those features. vtium starts its image helper, `vtium-image`, the same way, at a path fixed when the binary is built (`VTIUM_IMAGE`, read in `crates/vtium/src/head/images.rs` and `crates/vtium-platform/src/image_helper/start.rs`, `/usr/bin/vtium-image` when unset), and only a console built with images starts it. With `images` in `FEATURES`, `make vt-dev-console` builds the console to start it at `/usr/local/bin/vtium-dev-image`, and checks that the binary names that path, and `make vt-install` builds the helper with `make image-release`. `VTIUM_BIN=PATH`, `VTIUM_CONFIG_BIN=PATH` and `VTIUM_IMAGE_BIN=PATH` on make's command line install another console, glyph helper and image helper as they are, and `make vt-install` builds none of them. It builds its own image helper only with `images` in `FEATURES`, so a console with pictures named with `VTIUM_BIN` needs `FEATURES=images` beside it, or the image helper named with `VTIUM_IMAGE_BIN`; without either, install copies whatever `target/x86_64-unknown-linux-gnu/release/vtium-image` an earlier build left there, and refuses when there is none.

`tools/vt/vt-install.sh` does the work. Install refuses VT 1, a VT outside 2 to 12, the VT on screen and a VT a logind session is on, by the check `run-vt.sh` uses, a VT where the C reference's `kmsconvt@ttyN` runs, and a VT where the packaged `vtium@ttyN` runs or is enabled. It refuses a console that does not name `/usr/local/bin/vtium-dev-config`, since that console would start the packaged helper, or none, and a console or helper that someone other than root or the user could have written. Install reads from the console itself whether it has pictures. Every build names the image helper path it was built with, through the `image-helper` key's default, and `make vt-dev-console` names `/usr/local/bin/vtium-dev-image` exactly when it builds with images, so a console that names that path has pictures and gets the image helper. Install refuses a console built with images that names another path, since it would start the packaged helper, another build's, or none. It tells such a build by a line only a build with images carries, the message vtium logs when it cannot open its image helper, and the tool tests check that the line is still in code built only with images. One run of install or uninstall goes at a time. Each run takes an flock (a lock on an open file) on `/var/lib/vtium-dev-install` before it reads what is installed, and holds it until it ends, and a second run refuses while the first holds it. A first install, which finds no such directory, makes it and takes the lock before it writes anything into it, and refuses when another run has written there since it started. It then:

1. Generates two units from the shipped ones in `crates/vtium/install/` with `tools/vt/units.sh`, the one script that makes the units for both installs, so the units have one source. `vtium-dev@.service` is the shipped `vtium@.service` with these changes: its name; an opening comment of its own; `ExecStart=` running `/usr/local/bin/vtium-dev` in place of `/usr/bin/vtium`; `OnFailure=` naming `vtium-dev-getty@.service`; `Conflicts=` and `After=` lines naming `vtium@%i.service` and `kmsconvt@%i.service`, so that starting it on a VT first stops the packaged vtium or the C reference's console there, as it stops the getty; and `DefaultInstance=name-a-VT/vtium-dev@ttyN`, which names no VT, so that `systemctl enable vtium-dev@.service` with no VT named fails and links nothing. `vtium-dev-getty@.service` is the shipped `vtium-getty@.service` under its new name. Every other line is the shipped unit's, so `Restart=` and its kin come through as the shipped unit has them, and so does `Alias=autovt@.service`. logind starts `autovt@ttyN` on a VT that nothing holds: when the VT is switched to, at boot before vtium starts, in the moment before a restart, or after a failure. The template link `/etc/systemd/system/autovt@.service` names the unit that `autovt@ttyN` starts on every VT without a link of its own: on this machine the packaged `vtium@.service`, which `vtium console enable --all` linked, and on another machine a getty or the C reference's `kmsconvt@.service`. Enabling `vtium-dev@ttyN` makes `/etc/systemd/system/autovt@ttyN.service`, a link to `vtium-dev@.service` for that VT alone, so logind starts vtium-dev there and never the console the template names. vt-install leaves the template link alone, and never uses the names `kmsconvt@` and `kmsconvt-getty@`, which belong to the C reference's package. Install fails before it changes anything when the shipped unit no longer has the lines it changes.
2. Refuses when `/usr/local/bin/vtium-dev`, `/usr/local/bin/vtium-dev-config`, either unit file, or, for a console with pictures, `/usr/local/bin/vtium-dev-image` or `/etc/sysusers.d/vtium-dev-image.conf` is there already and is not the file vt-install wrote, by the checksum in its record, `/var/lib/vtium-dev-install/files`: a file vt-install never wrote is someone else's, and one that changed since is someone's edit, and it never replaces either. It refuses `/etc/systemd/system/autovt@ttyN.service` there already unless an earlier install on this VT made it.
3. Writes the manifest `/var/lib/vtium-dev-install/ttyN` first, so that a run cut short can still be undone. The manifest records whether `getty@ttyN` was enabled and running before. A second install on the same VT keeps the first record.
4. Copies the helper to `/usr/local/bin/vtium-dev-config`, for a console with pictures the image helper to `/usr/local/bin/vtium-dev-image` and its sysusers file to `/etc/sysusers.d/vtium-dev-image.conf`, the binary to `/usr/local/bin/vtium-dev` and the units to `/etc/systemd/system`, all owned by root, and keeps the checksum of each in `/var/lib/vtium-dev-install/files`, which every VT that holds vtium-dev shares as it shares the files. Install writes each file, the manifest and the record included, to a temporary name in the same directory, `.NAME.vt-install-new`, and then renames it into place with `mv -fT`. It runs `sync` on each temporary file before the rename, so a power cut just after the rename cannot leave the path empty, and it runs `sync` on `/var/lib/vtium-dev-install` after the manifest's rename, so the manifest is on the disk before anything in `/usr/local` or `/etc` changes. A rename replaces the file whole, so each path holds either the old file or the whole new one, never part of a file, even when a copy fails halfway on a full disk. A copy that fails removes its part-written temporary file. Only vt-install uses those names, and systemd passes over a file whose name starts with a dot when it reads a unit directory. The record is written before the copies, holding each file's checksum from before and after, so a copy that fails leaves every file in a state the record knows: `make vt-uninstall VT=N` removes the run, and a second `make vt-install VT=N` finishes it. Once the copies are done the record holds only the new checksums. For a console with pictures, install then runs `systemd-sysusers /etc/sysusers.d/vtium-dev-image.conf`, which creates the `vtium-image` account that the image helper runs as at the login prompt (ADR-1101 D2); without the account the helper runs as nobody. The sysusers file is the shipped `crates/vtium/install/vtium-image.conf` under an opening comment of its own, and its name is the development install's own, so it never masks the file a package installs as `/usr/lib/sysusers.d/vtium-image.conf`. Install then runs `systemctl daemon-reload`, enables `vtium-dev@ttyN` and restarts it, which starts it the first time, and disables `getty@ttyN`. vtium starts before the getty is touched: its `Conflicts=getty@%i.service` stops the getty, and its `After=getty@%i.service` makes that stop finish before vtium starts, since `Conflicts=` alone orders nothing and the getty's hangup of the VT at its stop would otherwise race vtium's start. The VT always has one of them. When any of these steps fails, install says what to do next: nothing, when it failed before the manifest was written; `make vt-uninstall VT=N` to undo the run, after it; and on a second install over an earlier one, that `make vt-uninstall VT=N` removes the whole install on VT N, the earlier one too, while `make vt-install VT=N` tries again.

An install made before the tool was renamed vtium-config (ADR-1201 D12) left its helper at `/usr/local/bin/vtium-dev-vitrify`. A later install removes that file once the new helper is in place, and uninstall removes it with the other files, each only while the file is still the one the record names. vt-install keeps and names such a file when it changed since, and leaves alone one its record does not name.

Every VT that holds vtium-dev runs the one console, so an install of a console without pictures removes the image helper and the sysusers file an earlier install wrote, once the new console is in place, each only while it is still the file the record names. vt-install keeps and names such a file when it changed since. It leaves the `vtium-image` account.

A second install replaces the binaries that every VT holding vtium-dev shares, but restarts only its own VT's `vtium-dev@ttyN`. vtium-dev on another installed VT keeps running the build it started with, from memory, until that VT's vtium-dev restarts, at a failure, a reboot or its own `make vt-install VT=N`.

Uninstall reads the manifest and undoes each step: it stops and disables `vtium-dev@ttyN`, removes the link `autovt@ttyN.service` that `disable` leaves while it still points at `vtium-dev@.service`, clears a failed state of it or its fallback, adds `getty@ttyN` back to `getty.target`'s wants with `systemctl add-wants` where the manifest says it was enabled, which makes no alias `autovt@ttyN` of the getty's own as `systemctl enable` would, starts it again where it was running, and removes the manifest. It also removes any file left at one of vt-install's temporary names, which a run killed in the middle of a copy leaves behind. It removes the binaries, the image helper and its sysusers file, the two units and the record only when no other VT's manifest is left, so vtium-dev installed on two VTs keeps its files until both are uninstalled. Even then it removes a file only while its checksum still matches the record, and it names each file it keeps because it changed. It then removes `/var/lib/vtium-dev-install` once nothing is left in it. It leaves the `vtium-image` account, because `systemd-sysusers` never removes an account; `sudo userdel vtium-image` removes it when no package's sysusers file names it. On a VT that has no manifest, uninstall removes the files at the temporary names and the empty `/var/lib/vtium-dev-install` that a first install cut short before its manifest was in place leaves, and refuses when it finds neither. It refuses a VT with a logind session on it, such as a login in the installed vtium; log out there first.

A review run borrows the development VT and never takes a VT the packaged vtium holds ([Which VT a run takes](#which-vt-a-run-takes)). A review run starts the helper built with the vtium it runs, never the packaged one or the development install's. `make vt-check` and the other review targets build `make config-release` with the console, and `run-vt.sh --helper=PATH` copies it, owned by root and mode 0755, into `/run/vtium-vt/`, a directory only root can write, and runs vtium with `--font-helper` naming the copy. vtium names itself `TERM=xterm-vtium`, so the run also compiles the checkout's `crates/vtium/install/xterm-vtium.ti` into `/run/vtium-vt/terminfo`, and the demo, the guide and the shell get `TERMINFO` naming it, so they read the entry the package ships. The run does not pass that variable to `/bin/login`'s session, so `make vt-login` uses the system's `xterm-vtium` entry when the package has installed one, and runs vtium with `--term=kmscon` when none is installed, and says so. The run removes `/run/vtium-vt/` when it ends. No guide reads frits from anywhere but `/etc/vtium/fonts`, so a run passes no `--font-frits`.

The installed vtium runs with the system's configuration, not the review's: it reads `/etc/vtium/vtium.conf`, `/etc/vtium/heads.conf` and the frits (font set files) in `/etc/vtium/fonts`, and so does the packaged vtium. Neither target writes, moves or removes any of these files, so a setting there applies to both installed vtiums.

If uninstall cannot run, VT N goes back by hand. These undo what install did on VT N alone:

```sh
sudo systemctl disable --now vtium-dev@ttyN.service
sudo rm /etc/systemd/system/autovt@ttyN.service           # the alias enable made, which disable leaves
sudo systemctl add-wants getty.target getty@ttyN.service   # only where getty@ttyN was enabled before
sudo systemctl start getty@ttyN.service
sudo rm /var/lib/vtium-dev-install/ttyN                    # VT N's manifest, and no other VT's
sudo systemctl daemon-reload
```

The binaries, the image helper's sysusers file and the units are shared by every VT that holds vtium-dev. When `ls /var/lib/vtium-dev-install` shows no other `tty` manifest, they go too: `sudo sha256sum -c /var/lib/vtium-dev-install/files` says `OK` for each file that is still the one install wrote. Remove those with `sudo rm`, keep any that fail the check, since someone changed them, and then remove the record with `sudo rm -r /var/lib/vtium-dev-install`.

### What the package ships

`make install DESTDIR=DIR PREFIX=/usr PKGNAME=NAME` stages under DIR exactly what the `vtium` package ships, and `make install-terminfo DESTDIR=DIR PREFIX=/usr` what the `vtium-terminfo` package ships, so that a package's build can be one call each (ADR-1500 D1, D3). The AUR recipes in packaging/arch call these targets, which main has. Both need DESTDIR named, not empty and not `/`, so neither installs onto this machine, where a `vtium@.service` in `/usr/local/lib/systemd/system` would take the place of the packaged one. `make install` builds with the host's toolchain, as a distribution's package build does, in the target directory `target/install`, and `CARGO_BUILD_FLAGS='--frozen'` passes a flag to each cargo call. They stage:

| File | Target | What it is |
|---|---|---|
| `PREFIX/bin/vtium` | install | the console, built with the minspec profile and `FEATURES`, which starts its helper at `PREFIX/bin/vtium-config` |
| `PREFIX/bin/vtium-config` | install | the font and settings tool, which `vtium config` runs and which is also the glyph helper |
| `PREFIX/lib/systemd/system/vtium@.service`, `vtium-getty@.service` | install | the VT unit and its getty fallback, made by `tools/vt/units.sh`: `ExecStart=` runs `PREFIX/bin/vtium`, `Conflicts=` and `After=` name `kmsconvt@%i.service`, and `DefaultInstance=name-a-VT/vtium@ttyN` names no VT, so `systemctl enable vtium@.service` with no VT named fails and links nothing on any machine (below) |
| `/etc/vtium/vtium.conf.example` | install | the example configuration, which stays in `/etc` whatever `PREFIX` is, because vtium reads its configuration from `/etc/vtium` alone |
| `PREFIX/share/doc/vtium/examples/` | install | the example udev rules and hwdb fragment, which are documentation and never active (ADR-1401 D4) |
| `PREFIX/share/licenses/PKGNAME/LICENSE` | both | the license, under the package's name: `vtium` by default for `install`, `vtium-terminfo` for `install-terminfo` |
| `PREFIX/share/terminfo/x/xterm-vtium` | install-terminfo | vtium's terminfo entry, compiled with `tic -x` from `crates/vtium/install/xterm-vtium.ti`; the target stops when that file is missing |

The refused `DefaultInstance=` is there because of what `systemctl enable` does with a template and no VT (measured with systemd 262; systemd 254's `src/shared/install.c` does the same). It links each `Alias=` before it checks `WantedBy=`, so with no `DefaultInstance=` it first links `/etc/systemd/system/autovt@.service` to `vtium@.service`, on a machine where that link does not exist yet, and only then refuses the template; logind would then start vtium on every VT it spawns. With the shipped `DefaultInstance=tty1` it would enable VT 1. With a value that names no instance, `systemctl` stops before it links anything, and it ignores `DefaultInstance=` when it enables an instance, so `systemctl enable vtium@tty3.service` links `getty.target.wants/vtium@tty3.service` and `autovt@tty3.service` as before. The cost is that `systemctl list-unit-files` shows `vtium@.service` as `bad` and `systemctl is-enabled vtium@.service` fails; each `vtium@ttyN` reads as enabled or disabled as usual. A machine that runs no kmscon console on purpose gives every VT to the packaged vtium with `sudo vtium console enable --all` (ADR-1500 D7), which points `autovt@.service` at `vtium@.service`; `make vt-install` never does this for the development install. `make vt-uninstall` names a template link `autovt@.service` that points at `vtium-dev@.service`, which no command of vtium's makes.

Neither ships a file that the C reference's packages own: not `/etc/kmscon/kmscon.conf.example`, not the `kmscon` unit files, and no terminfo entry named `kmscon`, which a distribution's `kmscon-terminfo` package holds. `make install-tree`, which tier 3 installs in its guest, stages the same `vtium@` and `vtium-getty@` units and the same `/etc/vtium/vtium.conf.example` as the package. It differs in two ways: it links against the pinned Debian sysroot, and beside `xterm-vtium`, which the `vtium-terminfo` package ships, it installs the terminfo entry named `kmscon`.

## The acceptance pass

The acceptance pass (ADR-1501) is one pass through every page in `tools/vt/sections/`, answered on the VT with single keys. `make vt-accept` builds the console with pictures unless `FEATURES` is named on make's command line, and gives vtium the image helper built with it, `vtium-image`, which `run-vt.sh` copies into `/run/vtium-vt/` beside the glyph helper and names with `--image-helper`, so the pages whose pictures the helper decodes show them. `tools/vt/accept.sh` shows a title page that names the build and lists the pages, then each page in file name order, then a summary. Below each page a footer gives the page's guidance, its `# look-for:` and `# wrong-looks-like:` lines, and one key answers it: y looks right, n looks wrong, u unsure, s skip; c types a comment first, r draws the page again, b goes back a page and q quits. A page the build cannot show, such as a pictures page under a build without pictures, says why and is recorded as skip. Before each page the walk puts back what the page before it changed: the pen, reverse video, the cursor's shape, the palette, the scroll region and kitty pictures.

Each answer rewrites the pass's record, a markdown file named after the pass in `~/.local/state/vtium/acceptance/` (`$XDG_STATE_HOME/vtium/acceptance`, or `ACCEPT_DIR`): the build's label, VT, binary and features, the hardware it ran on (the machine's model, the kernel, each GPU or display controller with its driver, each connected display's connector, preferred mode and EDID make and model, and the text area vtium reports), the fonts, the terminal, its DA1 answer, and each page's answer and comment. The record says it is evidence about that hardware only. A pass quit part way is offered for resuming at its first unanswered page by the next run of the same build. When a review run ends, `vt.sh` prints the pass the run wrote. `tools/vt/feedback.sh` prints a pass (the newest by default), lists them with `--list`, and compares two with `--compare A B`, by id or by a record's path, printing each page whose answer changed, warning first when the two ran on different hardware, and exiting 1 when one went from yes to no. One pass on the build of each batch that goes from `stage` to main is committed as `docs/acceptance/<YYYY-MM-DD>-<git describe>.md`. The acceptance pass runs in any terminal: `ACCEPT_LABEL='foot 1.21' tools/vt/accept.sh` there records a pass of its own label. `ACCEPT_NOPAGE=1 tools/vt/accept.sh sgr` draws a page and its guidance without waiting for keys.

The language pages show one sentence in thirteen scripts under every style, and each is walked twice, once in each of the acceptance pass's font sets in `tools/vt/sections/frits/`: an outline set and a bitmap set. The walk switches the console to each with OSC 50, which vtium takes only for a frit in its frits directory, so `run-vt.sh` copies the system's frits and the acceptance pass's into `/run/vtium-vt/frits` and runs vtium with `--font-frits` naming it. The copy runs as root and everyone may read it, so `run-vt.sh` refuses a frit that is a symlink, that has a second hard link, that belongs to someone other than root or the user, or that group or others may write: any of those could name a file the user may not read. The pass record names each font file with its SHA-256 and package, and the comparison lists the font files that differ between two passes.

A page is one file, `tools/vt/sections/NN-name.sh`: deterministic output, at most 17 rows of 80 columns so it fits 80x25 with its header and footer, and both guidance fields in terms a person can check by eye. ADR-1501 lists the pages and what each shows. A change that adds something visible adds its page.

## Testing the tools

`make test-tools`, part of CI, runs `tools/vt/tests/test_vt.py`, `tools/vt/tests/test_accept.py` and shellcheck. `test_accept.py` drives the acceptance pass through stand-in pages on a pseudo-terminal and checks the pass record, the resume and the comparison, and checks each real page's guidance and size and what the picture pages send to a terminal with and without pictures. The tests run every path without a VT, sudo or logind: `VTIUM_VT_STANDINS` names a directory of stand-ins for `systemctl`, `loginctl`, `setpriv`, `getent`, `systemd-analyze`, `sudo`, the VT's `/dev/ttyN`, `/etc/shells`, `/etc/locale.conf`, `/run/user` and the VT on screen, run from there by full path, and a stand-in vtium that exits, crashes, waits for a signal or runs its session. They check that a VT a session is on is refused, that the shell is the one the password database names and `/etc/shells` lists, that a home directory not the user's and a session as uid 0 are refused, that the shell gets the locale and the user's runtime directory and bus only when they are the user's, that the console unit is restored after a crash, Ctrl-C, SIGTERM and SIGHUP, that a guide failing `--check` stops before sudo, that a `run:` step shows its command, runs it on the guide's terminal and drops a key pressed meanwhile, that a console after the head's first runs a shell in place of the guide, that `vt-install.sh` generates the units from the shipped ones with only their names, `ExecStart=`'s path and the fallback's name changed, refuses VT 1, the VT on screen, a VT with a session, a VT the C reference's console or the packaged vtium holds, a console that would start another helper and a file it did not write, records and restores the getty's state, keeps files another VT still holds, and runs nothing in a dry run, that the review runs take the development VT, stop and start again only the units they found running there, hold the VT open from the stop to the restart, and pass over a VT the packaged vtium holds and logind's reserved VT, that `make install` stages the package's files and none that the C reference's packages own, with the console starting its helper where the package puts it, that a guide's steps get `LANG` and `LC_*` from a locale file (`GUIDE_LOCALE_CONF` stands in for `/etc/locale.conf`) only when no `LANG` is set and only as locale names, that the answers log refuses a symlinked or foreign directory, that no tool reaches `chvt` or `fgconsole`, and they run `start.guide`, the demo and a stand-in shell end to end through `make`. As root, `make vt-install` under `VTIUM_VT_STANDINS` needs the binary and the helper named with `VTIUM_BIN=PATH` and `VTIUM_CONFIG_BIN=PATH`, so that no build runs as root, and `vt-install.sh` refuses the stand-ins' directory and its `sudo`, `systemctl` and `loginctl` stand-ins unless each belongs to root or to the user who ran sudo and none is writable by group or others. As root, `run-vt.sh` refuses `VTIUM_VT_STANDINS`, and `vt.sh` honours it and `VTIUM_VT_DIR` only together, so a stale export cannot choose what runs as root or where the answers are read.

## Departures from the C reference's review

- vtium is one binary with no modules, so `run-vt.sh` runs it directly; the C reference bind-mounted its staged modules in a private mount namespace.
- The binary is a variable, checked for its owner and mode before it runs as root; the C reference ran the package it staged itself.
- A dry run asks the real read-only questions (the VT on screen, the sessions, the active units); the C reference's assumed them.
- `run-vt.sh` holds the VT open from the moment its units have stopped until it starts them again. The C reference's review held nothing, so a switch to the VT before its console opened the VT, or after the console ended, let logind start the VT's own console there.
- A run refuses logind's reserved VT, where logind starts a console at every switch even while the VT is held open. The C reference's review took VT 6, the default reserved VT, when 5 was busy.
- The acceptance pass refuses to record into a symlinked or foreign directory, as the guide's log and the run log do. ADR-1501 lists its other departures from the C reference's demo.
- The health check counts Rust panics; the C reference's counted its own freeze signature.
- Guides gain the `shell` step and the `run:` line. The acceptance pass has no review kits: one pass covers every page.
