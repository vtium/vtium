# The sections of vtium.conf

vtium's configuration file, `/etc/vtium/vtium.conf`, holds vtium's settings at its top and, below them, sections that declare vtium's heads, the look each head draws with, and the ordered rules that place each display and each input in a head. This page is the reference for those sections: the terms they use, their syntax and match keys, the routes by which one keyboard can reach another person's session, and what vtium does with sections it cannot fully use. [Configure vtium](configure.md) describes the whole file and how to change it, [heads.md](heads.md) gives complete sections for each common setup, and [Heads](concepts/heads.md#two-policies-open-and-closed) explains the two policies, open and closed.

## Terms

- **Head**: a terminal for one or more displays, with its own grid, its own look and its own consoles. A head with several displays shows one grid on all of them, sized for the smallest and drawn larger on the bigger ones.
- **Console**: one session of a head, with its own login, screen and scrollback; a head shows one of its consoles at a time. A head's consoles live inside the one VT vtium runs on, apart from the kernel's virtual consoles, the VTs.
- **Look**: what a head draws with, one `[look NAME]` section: its [frit](concepts/fonts.md#the-frit), vtium's font set file `/etc/vtium/fonts/NAME.vtfrit`, named by `font-name`, its size and its other font settings. A head names its look with `look = NAME`. `default`, the value when a head names none, is the `[look default]` section where the file has one, else the settings above the first section.
- **Display**: a monitor or panel, one connector of a graphics card. A head is lit when at least one of its displays is on. The **boot display** is the display lit at start, else the first connected display on the boot graphics card, else the first connected display on any card.
- **Builtin**: the configuration vtium runs when vtium.conf has no section, and in place of sections it cannot use: one head on every display, with every keyboard, pointer and key device roaming. It is compiled in, and [default.conf](heads/default.conf) writes it out. vtium never writes vtium.conf; vtium-config writes it only when you install a draft ([Configure vtium](configure.md#change-it-with-vtium-config)).
- **Policy**, `open` or `closed`: what the sections give anything they do not mention. Open lets an input no rule places roam, and isolates a head only where it says so; closed ignores such an input, and isolates every head that does not say otherwise. Under both, a display no rule names is off.
- **Isolated**: a head with `isolated = yes`. Its keyboards' VT keys reach its session as keys and never switch the VT, the rescue key never takes its keyboards away, and it is never the active head, so no roaming keyboard reaches it.
- **Roaming keyboard**: a keyboard, or mouse, that no head owns. It types into the active head.
- **The active head**: the one head roaming keyboards type into, never an isolated head. At start it is the head showing the boot display, if that head is not isolated; otherwise it is the first head in the file that has a lit display and is not isolated. It moves only by the roaming chord or the anti-lockout guard; while there is none, the first head that can be the active head becomes it as soon as it lights. It stays where it is when its display goes, so roaming keyboards can type into an unlit head. The on-screen display marks it for a few seconds after it moves.
- **On-screen display (OSD)**: vtium's own status at the top of each head, drawn outside the session's output. vtium.conf's `osd` chooses what it draws: with `minimal`, the default, a dot in the top-right cell, filled on the active head and hollow on the others; with `full`, a line such as `● desk · console 2 of 3`, the head's name and which of its consoles it shows; with `off`, nothing. It shows on each head with a lit display when the active head moves, and under `full` also on a head that switches to another console, opens or closes one, or gets its display back. It stays for `osd-timeout` seconds, 3 by default, or for good with `never` ([config.md](config.md)). A notice of a problem, such as an invalid file, shows whatever `osd` says.
- **The head a keyboard asks**: the head under whose rights a keyboard's keys act. A keyboard a rule gives a head asks that head; a roaming keyboard asks the active head, so its VT keys switch the VT; and with no active head a roaming keyboard asks none and delivers nothing, the VT keys included.
- **The roaming chord**: the keys that make the next or previous lit head the active head, today `Ctrl-Super-Up` and `Ctrl-Super-Down`. Only roaming keyboards can use it.
- **Console chords**: the keys that act on a head's consoles, on the head the keyboard asks. `Ctrl-Super-Right` shows the next console and `Ctrl-Super-Left` the previous. Under the open policy, `Ctrl-Super-Return` opens a new console just after the one shown and shows it, and `Ctrl-Super-Backspace` closes the console shown, whose programs get a hang-up, and shows the one after it; on a head's last console it does nothing. At the caps on consoles (below) nothing opens, and the top of the head says so for a few seconds, as in `No more consoles: desk has 4, its most.` Under the closed policy a head keeps the consoles it started with: vtium takes both keys and does nothing with them, so neither reaches the session as Return or Backspace.
- **The rescue key**: `Ctrl-Alt-F<n>` for the VT you're already on. vtium runs on the VT of its unit, `vtium@ttyN` ([systemd.md](systemd.md)), so on VT 2 the rescue key is `Ctrl-Alt-F2`. Under the open policy it makes the keyboard that pressed it roam for the rest of the boot. A press that moves nothing, under the closed policy or on an isolated head, is swallowed and never reaches the session.
- **The anti-lockout guard**: under the open policy, while no keyboard reaches a lit head, every keyboard roams, with a notice, until one does.
- **The display guard**: when the rules light no display at all, vtium lights the boot display anyway. Under open it shows the first head there. Under closed it shows only a notice there, and only for a file with heads.

## Reading the sections

The sections need two keys among vtium's settings above the first section, in any order: `version = 1` and, optionally, `policy`. Everything from the first section heading on is the sections, so a setting written below a heading belongs to that section. Each `[look NAME]` section declares a look, and takes the font keys of the top level under the same names: `font-name`, which names the look's frit, `font-engine`, `font-size`, `font-hinting`, `font-line-spacing`, `display-depth`, `display-dpi`, `cell`, the cell in pixels as `WIDTHxHEIGHT`, and `vtlook`. Within one look, `font-size` wins over `cell`. Each `[head NAME]` section declares a head; a head's keys are `look`, `consoles`, `login`, `when-display-lost` and `isolated`. Under `[rules]`, each line is `display MATCH -> TARGET` or `input MATCH -> TARGET`; each display and each input walks the rules from the top on its own, and the first that matches places it in a head, roaming (`roaming`), ignored (`ignore`) or off (`off`). There is no other section. A key set in a head's section wins over the same key in its look, and a look's over the top level. A section's key always takes `key = value`; the switches, a key alone or `no-` and the key, belong to the top level. `#` starts a comment at the start of a line or after whitespace, so the comments after values in the files below are comments; a `#` inside a word, as in `cmd --x#1`, is part of the value, and `\#` gives a literal `#` after whitespace.

[heads/reference.conf](heads/reference.conf) is the annotated reference to every option of the sections: it runs builtin as it stands, explains each key, match key and target in a comment, and gives the alternatives as examples ready to uncomment.

An input sent to `ignore` delivers nothing. Under closed vtium never opens it; under open vtium opens a keyboard only to watch for the rescue key, and opens no other ignored input. A display sent to `off` has its connector set off, so it shows nothing.

A head's `when-display-lost` says what its sessions do when its last display goes: `keep`, the default, runs them on unseen and brings them back with a display the head's rules match; `hangup` hangs them up at once; and `hangup DURATION`, such as `hangup 30s`, with an `s`, `m` or `h` suffix or plain seconds, brings them back if a display returns within the time and hangs them up after it. After a hang-up, a display returning starts the head's consoles afresh, each at its login.

A match is `*`, every display or every input, or one or more `key:value` tokens, every one of which must hold. Keys that need udev's database match nothing on a system with no udev daemon, and `check-config` notes each rule that uses one.

| Key | Matches | Needs udev's database |
|---|---|---|
| `path:` | a USB port, by udev's `ID_PATH` up to the port | yes |
| `serial:` | one unit wherever it is plugged, `VENDOR:PRODUCT:SERIAL` | yes |
| `bluetooth:` | one Bluetooth device, by its address | no |
| `id:` | every unit of a model, `VENDOR:PRODUCT` | no |
| `name:` | a device by the name it reports, a glob | no |
| `class:` | a kind of input: `keyboard`, `key`, `mouse`, `touchpad`, `touchscreen`, `trackball`, `pointingstick`, `tablet`, `tablet-pad`, `joystick`, `accelerometer`, `switch` | no: vtium derives the class itself where no udev daemon runs |
| `edid:` | one monitor, `MAKER:PRODUCT:SERIAL` from its EDID | no |
| `connector:` | a port of a graphics card, `CARD/CONNECTOR` (`pci-0000:03:00.0/DP-1`), globs allowed | yes |
| `connector-path:` | one port of a DisplayPort multi-stream hub, by the connector's `PATH` (`mst:...`), globs allowed; the `PATH` survives a replug or a resume, but its first number can change across a kernel or firmware update | no |
| `card:` | every output of a graphics card, by its `ID_PATH`, a glob | yes |
| `udev:` | any udev property of an input, `NAME=VALUE`, a glob on the value | yes |

A rule names a device most strongly by its USB port (`path:`), its unit (`serial:`) or its monitor (`edid:`), and only for convenience by its model (`id:`) or its name (`name:`). A `path:` value matches exactly or as a prefix that ends at a port: `...usb-0:3.1` takes every interface of the device in port 3.1 (`...usb-0:3.1:1.0`) and every device on a hub plugged into it (`...usb-0:3.1.2:1.0`), and never port 3.10. `serial:` binds the unit wherever it is plugged. Two monitors with the same EDID, such as two of one model that report serial 0, both match one `edid:` rule and show the same head; tell them apart with `connector:`, or with `card:` where they hang off different graphics cards. `vtium config flow --json` lists the values for every device present. To find them by hand:

- `path:` is udev's `ID_PATH` up to the port: `udevadm info -q property -n /dev/input/event5 | grep ID_PATH=` prints `ID_PATH=pci-0000:15:00.0-usb-0:3.3:1.0`, and the rule takes `path:pci-0000:15:00.0-usb-0:3.3`. `ls -l /dev/input/by-path/` maps the ports to event nodes.
- `edid:` is `MAKER:PRODUCT:SERIAL` from the monitor's EDID, which `/sys/class/drm/card*-*/edid` holds; a decoder such as `edid-decode /sys/class/drm/card1-DP-8/edid` prints the manufacturer, the product code and the serial.

A wrong value is no error: a `path:` of an empty port or an `edid:` of another monitor matches nothing, the device walks on to the next rule and then to the file's policy ([the two policies](concepts/heads.md#two-policies-open-and-closed)), and `check-config` notes that the rule matches no device present. A misspelt key, such as `pth:` for `path:`, is an error that drops the rule: the file is partly broken, the console shows `vtium.conf has errors: running the parts without errors.`, and `check-config` exits 1. Either way the device goes where the rule did not send it: in an open file a keyboard roams, and in a closed one it is ignored. A partly broken open file also runs every head as not isolated ([Invalid files](#invalid-files)).

vtium reads vtium.conf only when root owns it and neither its group nor others can write it: the owner must be root, the group may be any group, and a group-writable file fails even when its group is root. `/etc/vtium` and each directory above it pass the same check. vtium-config installs a file that passes ([When vtium-config asks for sudo](configure.md#when-vtium-config-asks-for-sudo)). By hand, install a file with `install -o root -g root -m 0644 vtium.conf /etc/vtium/vtium.conf`, after `install -d -o root -g root -m 0755 /etc/vtium` where the directory is missing.

`vtium check-config FILE` checks a candidate before it is installed, and reports its owner and mode as a note, since installing it makes it root's; with no FILE it checks the installed file, its ownership included. It exits 1 on an error or a warning about the file itself: a line it cannot parse, a missing or unknown `version`, an unknown key, match key or value, a key, a head or a `[rules]` given twice, a target of the wrong kind, a rule naming no head, a rule an earlier one shadows, a look naming a missing frit, a head naming a look the file does not declare, a `consoles` value past its cap, and an installed file that fails the ownership check. A head no rule names is a note, and so is everything that depends on the devices present, with exit status 0: a rule matching none of them, a head that only one keyboard reaches, what the policy did with the devices no rule names, and every right a file takes away.

Each head's consoles run its `login` command, else the `login` at vtium.conf's top level, as root; a kiosk program drops its privileges itself, or is started through a tool that does. vtium never reads `kmscon`'s own file, `/etc/kmscon/kmscon.conf`. A head starts with the consoles its `consoles` gives it, 1 when unset, at most 4 a head and 8 for all heads together; vtium.conf's `head-consoles-max` and `consoles-max` raise these, to at most 50. The same caps bound the consoles the open chord adds later. A value past the head's cap gives the cap, with a warning, and where the heads ask for more than the total, each keeps its first console and the rest are given in the file's order. A file declares at most 16 heads, a limit no setting raises.

The programs in a console can tell which console they run in. When a console's session starts, vtium sets two variables in its environment: `VTIUM_HEAD`, the head's name, and `VTIUM_CONSOLE`, the console's id. A head gives its consoles ids from 1 in the order it opens them at its start, a console the open chord adds takes the next id the head has not given, and no id is given twice before vtium restarts. A console keeps its id when its session starts again, after its program exits or after a hang-up. Under the closed policy a head's consoles never open or close while it runs, so the id is also the console's place among them, which the on-screen display's full line shows: the console whose id is 2 reads `console 2 of 3`. Under the open policy the two part once a console opens or closes: with consoles 1, 2 and 3, closing console 2 and opening one from console 1 gives a console 4, which reads `console 2 of 3`. The variables are fixed when the session starts, so they cannot say which console the head shows now. They reach the shell only through a login command that keeps the environment it is given. vtium's default command, `/bin/login -p`, keeps them, so the shipped `vtium@.service` and a vtium.conf with no `login` give them to the shell. With vtium.conf's `reset-env` off, vtium runs `/bin/login` without `-p`, which clears the environment, and so do a getty's login and any `login` command of a head that clears it. Such a command can still take them as words: vtium replaces a word of the command that is exactly `$VTIUM_HEAD` or `$VTIUM_CONSOLE` with its value. A program that wants to know that turns on focus reporting (`printf '\033[?1004h'`): while a keyboard types into the head, vtium sends it a focus-in when the head shows its console and a focus-out when the head switches to another.

## Which input can reach whose session

Each route by which one keyboard can disturb another person's session has a switch of its own, and acts under the head the keyboard asks ([Terms](#terms)). In an open file a route the file says nothing about is open, as on today's console; in a closed file it is closed until the file opens it.

| Route | Disturbs | Governed by |
|---|---|---|
| The VT keys, `Ctrl-Alt-F<n>` and `XF86Switch_VT_<n>` | every display, which leaves for another VT | the `isolated` of the head the keyboard asks; a roaming keyboard with no active head asks none |
| The console chords | the console the head shows | the head's `consoles`, a fixed count the chords switch among: with 1 there is nothing to switch |
| The roaming chord | where the roaming keyboards type | taken only from roaming keyboards |
| The rescue key | takes a keyboard off its head, or makes an ignored one roam | the policy, on under open and off under closed, and under open the head's `isolated` |
| The anti-lockout guard | makes every keyboard roam | the policy: on under open, off under closed |
| Unclaimed keyboards | type into the active head | the policy: under open they roam unless a rule such as `input * -> ignore` closes them, and under closed they are ignored |
| Arrival by roaming | the active head | the head's `isolated`: an isolated head is never the active head |

## Invalid files

vtium never fixes, renames or replaces the file, and resolves it in three steps. An error in a section never drops a setting above the first section, and a mistake above it never drops a section: above the first section vtium reads its settings the forgiving way [config.md](config.md) describes, reporting an unknown key or a bad value and going on.

1. **Trust.** A file that fails the ownership check above, or that vtium cannot open, is never read: builtin runs, with every setting at its default, and the console shows `vtium.conf not used: running the built-in configuration.` A closed file left writable, or deleted, therefore opens the machine at the next boot or restart of vtium.
2. **The policy.** vtium reads `policy` from the settings above the first section. A line above the first section that begins with `policy`, in any mix of upper and lower case, is a policy line. When vtium cannot read a policy line, the file is closed and broken: nothing of it runs, no keyboard delivers anything, and the panic screen shows that line's error first. vtium cannot read a policy line that holds a byte that is not UTF-8 or a control character, that runs past 8192 bytes, that the 65536-byte bound cuts, or that says anything but `policy = open` or `policy = closed`, such as `Policy = closed`, `policy = opne` or `policy` alone. vtium judges a line the 65536-byte bound cuts by the bytes before the bound, so it is a policy line only when all six letters of `policy` come before the bound. A line such as `policies = open` does not begin with `policy`, so it is no policy line: vtium reads it as one of its own settings, warns that it is an unknown key, and ignores it. A line that shows as a policy line but begins with a character that does not show on screen, such as a no-break space or a zero-width space, is no policy line either: vtium warns that it is an unknown key, and the warning shows that character escaped. When every policy line is readable, a `policy = closed` line wins over any other. A second readable `policy` line is an error that drops that line alone, and so is a `policy` line inside a section.
3. **The rest.** An error inside a head's section drops that head; an error inside a look's section drops that look, and a head that names it draws with the default look; a bad rule drops that rule alone; a missing or unknown `version`, or an error that leaves the structure of the sections untrustworthy, drops every section and keeps the policy. If a head survives, vtium runs what survives and shows `vtium.conf has errors: running the parts without errors.` In an open file vtium then adds builtin's input rules after the surviving rules, so a keyboard, pointer or key device that no surviving rule places roams and every other input is ignored, and it runs every surviving head as not isolated, so the rescue key and the active head always have somewhere to land. A closed file keeps its heads' isolation as written. If nothing survives, an open file runs builtin with `vtium.conf not used: running the built-in configuration.`, and a closed file shows the panic screen.

The panic screen means vtium has started correctly and can serve nothing. The boot display shows `vtium.conf has errors and counts as closed: all input is off.`, a sentence saying that the file's errors leave no head that can run, the first three errors with their lines, `More errors: N` when there are more, and the console line's next step. The screen stays for as long as vtium runs. `check-config` rebuilds the full report from the file itself, run over ssh or from a live USB with the disk mounted.

That failure is final by design. vtium keeps no copy and no last-known-good of the file, so a closed file is checked before it is relied on: with `vtium check-config FILE` or `vtium config check FILE`. A trial that applies a candidate and reverts it unless you confirm it is not built yet. See [the issue that tracks it](https://github.com/vtium/vtium/issues/367).
