# systemd, logind and PID 1

vtium runs without systemd: launched by its unit, an init script or by hand (ADR-1400). This page lists every place vtium touches systemd, logind or the conventions of a systemd PID 1, and what it does on a host without them. A touchpoint not listed here is a defect in this page.

"Without systemd" is a host whose PID 1 is another init (sysvinit, OpenRC, runit, s6, busybox) with no logind. "elogind" is such a host running elogind, the standalone logind, which owns `org.freedesktop.login1` on the system bus and ships libelogind in place of libsystemd; vtium's `logind` feature links whichever of the two pkg-config finds, libsystemd first.

Where systemd runs vtium through its units, vtium supports systemd 254 and newer (ADR-1401 D9). vtium also runs with no systemd at all. This page's column for a host without systemd describes how, and tier 3's variants without systemd (`make tier3-nosystemd`) test it. On systemd 239 to 253, which vtium does not support, the unit's `OnFailure=` starts the getty fallback only once vtium's unit stops restarting. So under an open policy in vtium.conf a failure that repeats more slowly than 5 starts in 10 s never trips the start limit and never brings a getty: on a machine with no display, vtium waits `display-wait`, exits with status 1 and is restarted, over and over, and no login prompt ever comes. Tier 3 refuses a guest whose systemd is older than 254.

## Giving vtium a VT without systemd

Without systemd, `vtium console` changes nothing and says so, and the VTs that are not vtium's are the ones your init system's configuration gives to a getty, another console or a display manager. You give vtium a VT the way your init system already runs a getty there: replace the getty's entry for that VT with one that runs `vtium --vt=ttyN --no-switchvt`, and let the init system restart it when it exits. vtium adds no fallback of its own there: when vtium keeps failing, the init system's own respawn limit applies, and you log in on another VT. By the usual layout, VTs 1 to 6 hold consoles and a display manager runs on a VT of its own, usually 7. Keep a getty on VT 1, so that a login is there if vtium cannot start, and give vtium VTs from 2 to 6. Each entry starts vtium at boot; two that start at once race for DRM master, and one loses (vtium/vtium#139).

With sysvinit, change the VT's line in `/etc/inittab`, then run `telinit q` so that init reads the file again. Debian's line for VT 2 becomes:

```
2:23:respawn:/usr/bin/vtium --vt=tty2 --no-switchvt
```

init starts vtium at the runlevel's start and starts it again each time it exits. Tier 3's guest without systemd runs vtium this way (`sysvinit-640x480`), through a wrapper that only sends vtium's log to the serial port.

With OpenRC, each VT's getty is a service linked to `/etc/init.d/agetty`, such as `agetty.tty2`. Write `/etc/init.d/vtium` in the same shape:

```sh
#!/sbin/openrc-run
description="vtium on ${RC_SVCNAME#*.}"
supervisor=supervise-daemon
command=/usr/bin/vtium
command_args="--vt=${RC_SVCNAME#*.} --no-switchvt"
```

Make it executable, link it for the VT, and swap the services in the default runlevel:

```
# ln -s vtium /etc/init.d/vtium.tty2
# rc-update del agetty.tty2 default
# rc-update add vtium.tty2 default
```

`supervise-daemon` starts vtium again when it exits. On a system whose OpenRC runs under sysvinit's init, the gettys are in `/etc/inittab` instead, and the sysvinit steps apply. Alpine runs OpenRC under busybox init, whose `/etc/inittab` line for VT 2 reads `tty2::respawn:/sbin/getty 38400 tty2`: replace it with `tty2::respawn:/usr/bin/vtium --vt=tty2 --no-switchvt`, and run `kill -HUP 1`, since busybox has no `telinit q`, to make init read the file again.

With runit, as on Void Linux, each VT's getty is a service directory such as `/etc/sv/agetty-tty2`, enabled by a link in `/var/service`. Make `/etc/sv/vtium-tty2/run`, executable:

```sh
#!/bin/sh
exec /usr/bin/vtium --vt=tty2 --no-switchvt
```

and swap the links:

```
# rm /var/service/agetty-tty2
# ln -s /etc/sv/vtium-tty2 /var/service/
```

`runsv` starts vtium again when it exits. vtium's tests run the sysvinit way only; the OpenRC and runit steps follow those systems' own getty services and are untested by vtium.

## What vtium never does

- It reads none of logind's state files under `/run/systemd`; ADR-1400 rejected them as an interface. When vtium runs as the console, it never asks what PID 1 is; it reads only which signals PID 1 catches. The subcommand `vtium console` checks whether the host was booted with systemd, by whether `/run/systemd/system` is a directory, as sd_booted(3) does, and then asks the running manager which consoles run, with `systemctl list-units`, and logind which graphical sessions run, with `loginctl`.
- It links no libsystemd or libelogind in the minspec build: `ldd` on it lists neither (ADR-1400's observable).
- It sends PID 1 no other signal, and calls `reboot(2)` only for `grab-reboot` at a non-zero `kernel.ctrl-alt-del`.

## Where it is tested

Tier 3 runs two guests (`tools/tier3/README.md`). The Arch Linux guest runs systemd and logind; its power variants prove the reboot paths, power-off, and suspend through logind and through `/sys/power/state`. The guest without systemd, Debian with sysvinit as PID 1 and no logind (`make tier3-nosystemd`), proves this page's column for a host without systemd: vtium started by an inittab line and drawing, with the udev daemon and without it, the reboot through the inittab's `ctrlaltdel` entry and the kernel's own, and the power-off through sysvinit. Each row it proves names its variant or case. The closed marker is tested against a stand-in directory by the tests in `crates/vtium/src/getty.rs`, and on the Arch guest by tier 3's heads variants: in `heads-closed-broken`, under a closed policy, the `getty-fallback` check fails vtium by a kill, a crash and a hangup, and after each the fallback unit skips itself, no getty runs on the VT, and the unit's `Restart=` line starts vtium again; the `start-limit` check kills each vtium the unit starts until the unit stops restarting, and past the limit the unit stays failed with `start-limit-hit` and no getty runs. Under an open policy the getty starts, and its start stops vtium's unit (`heads-partly-open`, which runs both checks as the open control, and `heads-open-nodisplay` after no display came within `display-wait`). Untested still: busybox init, runit and s6, an init that ignores `SIGRTMIN+4` (vtium/vtium#140), and elogind (vtium/vtium#100). Tier 3's `heads-survive` restarts vtium's unit and then kills vtium under a closed policy, and after each the same logged-in shell leads its session on the same pty at the same size and answers a line typed on the console's keyboard. The store's datagrams are tested against a stand-in for the notification socket that checks what systemd 262 checks (`crates/vtium/src/survive/tests.rs`); the holder is tested by unit tests alone, since no tier runs it on a host without systemd yet. The unit tests stand in for PID 1, logind and the kernel (`crates/vtium/src/power.rs`, `crates/vtium/tests/power_keys.rs`). `vtium console` is tested against a scratch root and a stand-in systemctl that does what systemd 262's `systemctl --root` was measured doing (`crates/vtium/src/console/tests.rs`); no tier runs it against a running systemd yet.
