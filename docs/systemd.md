# systemd, logind and PID 1

vtium runs without systemd: launched by its unit, an init script or by hand (ADR-1400). This page lists every place vtium touches systemd, logind or the conventions of a systemd PID 1, and what it does on a host without them. A touchpoint not listed here is a defect in this page.

"Without systemd" is a host whose PID 1 is another init (sysvinit, OpenRC, runit, s6, busybox) with no logind. "elogind" is such a host running elogind, the standalone logind, which owns `org.freedesktop.login1` on the system bus and ships libelogind in place of libsystemd; vtium's `logind` feature links whichever of the two pkg-config finds, libsystemd first.

Where systemd runs vtium through its units, vtium supports systemd 254 and newer (ADR-1401 D9). vtium also runs with no systemd at all. This page's column for a host without systemd describes how, and tier 3's variants without systemd (`make tier3-nosystemd`) test it. On systemd 239 to 253, which vtium does not support, the unit's `OnFailure=` starts the getty fallback only once vtium's unit stops restarting. So under an open head-file policy a failure that repeats more slowly than 5 starts in 10 s never trips the start limit and never brings a getty: on a machine with no display, vtium waits `display-wait`, exits with status 1 and is restarted, over and over, and no login prompt ever comes. Tier 3 refuses a guest whose systemd is older than 254.

Under a closed head-file policy a getty's login would take any keyboard (ADR-1401 D9), so vtium writes the empty file `/run/vtium/ttyN.closed` once it has read the policy, before it opens its loop or its VT, creating `/run/vtium` where it is missing, and the fallback unit's `ConditionPathExists=!/run/vtium/%i.closed` skips the getty while the file exists. The VT's run directory, `/run/vtium/ttyN/`, will be the unit's `RuntimeDirectory=vtium/%i` (the run state's row below); systemd removes only that innermost directory when vtium stops, so the marker sits one level up. vtium removes the file when it starts under an open policy, and `/run` is cleared at every boot. A failure before vtium has read the head file, such as a command line it cannot start with, writes no marker, so the getty starts unless an earlier closed run of this boot left one. The marker governs the fallback alone. A `getty@ttyN` enabled on vtium's VT, as systemd's default preset enables `getty@tty1`, is wanted by `getty.target` beside vtium's unit. When both start in one transaction, as at boot, systemd starts vtium's unit, the one that declares `Conflicts=`, and stops the getty (systemd.unit(5)). The enabled getty still takes the VT in two cases: on a VT where logind starts vtium only when the VT is switched to, the getty starts at boot first and logind then starts nothing there; and a `systemctl start getty@ttyN.service` while vtium runs, by hand or from a unit that pulls the getty in, stops vtium and starts the getty. So a closed machine disables it (`systemctl disable getty@ttyN.service`). Once vtium has ended, the kernel takes `Ctrl-Alt-F<n>` again, so a getty on another VT is one key away, and a kiosk also masks the gettys enabled on the other VTs. It also sets logind's `NAutoVTs=0` and `ReserveVT=0` (logind.conf(5)), which otherwise start `autovt@ttyN` on a VT as it is switched to and keep one ready on VT 6; with vtium's unit enabled, `autovt@ttyN` is another vtium, which starts a login of its own on that VT. The unit has `Restart=on-failure` with systemd's defaults and no `RestartSec=` or `StartLimit*` of its own, so systemd starts vtium again 100 ms after each failure and allows 5 starts in a 10 s window that opens at the first start it counts (`DefaultStartLimitIntervalSec=` and `DefaultStartLimitBurst=` in systemd-system.conf(5), which a host may change). A SIGKILL, a panic and an exit with status 1 are failures; an exit with status 0, which vtium makes on SIGTERM and SIGINT, and an end by SIGHUP, SIGINT, SIGTERM or SIGPIPE, which systemd counts as clean, start nothing (ADR-1401 D9). Under a closed policy a one-off failure therefore brings vtium back on its VT while the marker keeps the getty away. A fault that recurs faster than 5 starts in 10 s trips the limit and leaves the unit failed with the result `start-limit-hit`, the fallback skips the getty, and the VT has no login: the operator runs `systemctl reset-failed kmsconvt@ttyN` and then starts the unit, over ssh or a serial getty, or restarts the machine; where logind starts vtium as `autovt@ttyN`, switching away from its VT and back also starts vtium again once the 10 s have passed. A fault that recurs more slowly never trips the limit, and vtium keeps restarting, hanging up every session each time. Under an open policy, on systemd 254 and later, each failure still starts `OnFailure=`, since the default `RestartMode=normal` passes through the failed state, so the fallback starts the getty; because vtium's unit conflicts with `getty@%i.service`, the getty wins whether it starts before the restart, which it cancels, or after it, when it stops the vtium that came back 100 ms after the failure. systemd 239 to 253 are unsupported (above) | vtium exits 1 the same, and writes and removes the marker the same, though nothing reads it; whether a getty follows is the init's respawn line or the script's | As without systemd | none |

## What vtium never does

- It reads none of logind's state files under `/run/systemd`; ADR-1400 rejected them as an interface. What PID 1 is, it never asks; it reads only which signals PID 1 catches.
- It links no libsystemd or libelogind in the minspec build: `ldd` on it lists neither (ADR-1400's observable).
- It sends PID 1 no other signal, and calls `reboot(2)` only for `grab-reboot` at a non-zero `kernel.ctrl-alt-del`.

## Where it is tested

Tier 3 runs two guests (`tools/tier3/README.md`). The Arch Linux guest runs systemd and logind; its power variants prove the reboot paths, power-off, and suspend through logind and through `/sys/power/state`. The guest without systemd, Debian with sysvinit as PID 1 and no logind (`make tier3-nosystemd`), proves this page's column for a host without systemd: vtium started by an inittab line and drawing, with the udev daemon and without it, the reboot through the inittab's `ctrlaltdel` entry and the kernel's own, and the power-off through sysvinit. Each row it proves names its variant or case. The closed marker is tested against a stand-in directory by the tests in `crates/vtium/src/getty.rs`, and on the Arch guest by tier 3's head-file variants: in `heads-closed-broken`, under a closed policy, the `getty-fallback` check fails vtium by a kill, a crash and a hangup, and after each the fallback unit skips itself, no getty runs on the VT, and the unit's `Restart=` line starts vtium again; the `start-limit` check kills each vtium the unit starts until the unit stops restarting, and past the limit the unit stays failed with `start-limit-hit` and no getty runs. Under an open policy the getty starts, and its start stops vtium's unit (`heads-partly-open`, which runs both checks as the open control, and `heads-open-nodisplay` after no display came within `display-wait`). Untested still: busybox init, runit and s6, an init that ignores `SIGRTMIN+4` (vtium/vtium#140), and elogind (vtium/vtium#100). The unit tests stand in for PID 1, logind and the kernel (`crates/vtium/src/power.rs`, `crates/vtium/tests/power_keys.rs`).
