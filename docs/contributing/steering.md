# Steering the work

This page holds what only the steering session does. The session takes a batch from `integration` to main, gathers the maintainer's verdict, runs the code review, cuts a release and keeps the scope ledger. [AGENTS.md](https://github.com/vtium/vtium/blob/main/AGENTS.md#the-working-loop) holds steps 1 to 6 of the working loop, and this page goes on from step 7. AGENTS.md also defines the roles, the branches `integration` and `stage`, and the [verification levels](https://github.com/vtium/vtium/blob/main/AGENTS.md#the-verification-levels) V0 to V4.

## From stage to release

7. **At a merge point,** the steering session picks a commit of `integration` that passed the full gates on the merged tree. The steering session runs `make stage-check COMMIT=<commit>` first, which fetches main from GitHub and fails unless the commit descends from main. When the previous stage PR merged, main gained a merge commit that `integration` does not have. The check then fails until the steering session merges `origin/main` into `integration` and runs the full gates on the merged tree. Once the check passes, the steering session moves `stage` to the commit with `git push origin <commit>:stage`. The stage PR's body says `Closes #N` for each issue that `make conformance-issues` lists to close, so GitHub closes each issue when main gets its rows. Nobody closes such an issue by hand before then, because main's rows still wait on it and main's check would fail. `stage` only ever moves forward to a later commit of `integration`, and nobody commits on `stage`. The steering session then opens one PR from `stage` to main, so the maintainer reads a diff that does not move, with the batch's ADR notes and goldens in it, while `integration` keeps taking new work. A fix that the maintainer's review asks for lands on `integration` and reaches main with the next batch, or the steering session moves `stage` forward to that fix, which starts the PR's CI again. The steering session waits for that PR's CI. The PR merges only after each card in the batch has had its code review and its fix round (step 9). A PR merges only once every CI job has passed, `arm-native` included. vtium has to keep working on platforms other than the x86 machines it is written on, and `arm-native` runs on ARM hardware like the hardware vtium's smallest build is most likely to run on. A PR merges with a regular merge commit, never a squash or a rebase. A release is tagged on main.
8. **The maintainer judges each new capability of the batch** (V3). The steering session puts each new capability on a VT tour page or a picture page. The maintainer's verdicts are the fix list. Each accepted capability keeps scenario tests that go on checking it.
9. **After the verdict, one full code review reads the wave's code** (`git diff <merge>^1 <merge>`, where `<merge>` is the commit that merged the wave's candidate into `integration`). Fresh reviewers, which did not write the wave's cards, check its code paths, the places where one card's code meets another's, its implementation, its safety and security, and its performance. A large wave's review is split across reviewers by crate and is still one round. The reviewers run the tests of what the wave touched and plant the defects that its cards claim to catch. Every finding is fixed in one fix round, wording included, by freshly briefed agents, and the steering session checks that round by planting the defects again. A second round goes to the maintainer's eyes. A finding is fixed in the change that found it when the change caused the finding or when the finding sits in code the change touches or depends on, under the area's ADRs and conventions. Filing an issue does not fix a finding. Declining a finding needs evidence that the finding is wrong, and deferring one needs the maintainer's explicit OK for that finding. Each fix round lands on `integration` with `git merge --no-ff`, and the steering session runs the gates that the fix round's files reach before it pushes.
10. **Before a release, V4 runs on the release candidate**, the `stage` commit whose PR goes to main and is then tagged, and the maintainer's V3 look covers the build on this machine. A defect either finds is fixed on `integration` and moves `stage` forward, and the defect is rechecked at its own level. The tag and the published packages wait for V4, for V3 and for the maintainer's word. Before the tag, a commit of its own moves the workspace's version in `Cargo.toml` to the release's version, with `Cargo.lock` and the fuzz lockfiles, and merges to main. The tag goes on main's merge of that commit, so the released binary reports the release's version. After the version bump, and again after the release-notes row gains its date, run `make man` and commit the man pages: each page's title line carries the version and that row's date, and `make man-check` fails until they match. The 0.1.0-alpha.9 tag first went out without the bump, and its binary reported 0.1.0-alpha.8 until the tag was made again. A release is published from a draft, because GitHub's immutable releases lock a release's files and tag once it is published. Once the signed tag is pushed, write the release notes with `make release-notes VERSION=<version>`. Save the draft with `gh release create v<version> --draft --verify-tag --title "VTium <version>" --notes-file target/release-notes/<version>.md`, adding `--prerelease` for a pre-release. Then run `gh workflow run release-vendor.yml --ref v<version> -f draft=true`. The run fails unless the tag is an annotated tag whose signature GitHub verifies, and the tag still names the commit the run started on. It packs the release files from that commit, attests them, and attaches them to the draft. Then it checks that the draft carries exactly the files `SHA256SUMS` lists, each matching its SHA-256 and attested by this workflow from the tag. If the run fails, start it again with the same command: it replaces the files it attached, and a second run on the same tag waits for the first. Look over the draft's files and notes, then publish the draft. Publishing starts the workflow's published job, which runs the same checks again on the published release. If the published job fails while immutable releases are off, turn the release back into a draft with `gh release edit v<version> --draft=true`, run the draft run again, and publish the release again. Once immutable releases are on, the release's files and tag are locked, so the fix is a new release with a new version. Once the release is published, start vtium-arch's watcher with `gh workflow run update.yml -R vtium/vtium-arch`, which opens the pull request that moves the Arch recipes to the new tag.

A small change to pages for readers only skips this loop. It changes files under `docs/` and nothing that a gate builds or runs, such as adding an image or fixing a sentence. The steering session makes it on a branch cut from main, runs `docs/scripts/prose --check`, `docs/scripts/claims`, `docs/scripts/fork-refs` and `make docs`, and pushes the branch straight to main once they pass. Then the steering session merges main into `integration`. The maintainer decided this on 2026-11-16, after a one-commit docs change went through `stage` and its PR.

## Scope on the way to a release

Work meets reality as it is built, and the loop takes in what that finds without letting the release's scope keep growing. The maintainer set this on 2026-11-20. Each thing that comes up during a wave goes to one place:

| What came up | Where it goes |
|---|---|
| A finding the card caused, or one in code the card touches or runs through | Fixed in the card, as step 9 of [From stage to release](#from-stage-to-release) says. |
| A bug in vtium, a false statement in a page included | The next wave, without asking. |
| A new feature or idea | An issue with the label `after-0.1.0`. It moves into the plan only when the maintainer pulls it in, with one line on the issue saying why. |
| Something that changes a card's scope or a phase of the plan | A question for the maintainer before anyone builds it. |

The scope of 0.1.0 is the list of open issues on the tracker, vtium/vtium#47, as of 2026-11-20. An issue filed after that starts as `after-0.1.0`. The first beta is a soft beta with no feature freeze. The plan still takes in what the maintainer pulls in, and ADR-1510 D1 says how a format may change during the beta.

Before each stage PR, the steering session checks that the README, the docs index and the showcase say what the wave added. The stage PR's body ends with a scope ledger: each item that came up during the wave, and where it went.

## The VT review

The steering session runs each VT review that [tools/AGENTS.md](https://github.com/vtium/vtium/blob/main/tools/AGENTS.md#the-vt-review) describes:

- The steering session starts the run with `make vt-check GUIDE=...` without asking first, and tells the maintainer which VT to switch to.
- The maintainer switches to that VT (Ctrl-Alt-F<n>), follows each step of the guide, and answers y, n or skip, with a note. Sudo asks for its password in the terminal where the run started.
- When the run ends, the steering session reads the answers from the log.
- The steering session refreshes the development VT after each merge to `integration`, and a delegated agent never does. The steering session cannot type a password, so sudo's credentials must already be cached in its terminal. When they are not, the steering session asks the maintainer to run `sudo -v` there first.

## The signed release tag

A release tag is signed with the maintainer's PGP key, not the SSH key. The Arch recipes in vtium/vtium-arch check each release tag with makepkg, and makepkg accepts only a PGP signature by a key in the recipe's `keys/pgp/` folder. Create the tag with `git -c gpg.format=openpgp tag -a -s -u BA464FC9847A832A -m "VTium <version>" v<version> <commit>`, and check it with `git -c gpg.format=openpgp tag -v v<version>` before you push it. The PGP key asks for its passphrase through gpg's pinentry, so the maintainer runs the command when the steering session cannot. The 0.1.0-alpha.8 tag was first signed with the SSH key, and the Arch recipes' checks failed until the maintainer signed it again with the PGP key.
