# The suite

vtium is one console and a few programs and files around it. The table lists each, who runs it, and whether it is built or proposed. vtium-config is the configuration tool. A user runs it as `vtium config`, which hands its words to vtium-config. The last column links the GitHub issue that tracks each piece, or the page that describes it.

| Piece | What it is | Run by | State | See |
|---|---|---|---|---|
| `vtium` | The console: one process per VT, which owns that VT, its display and its input devices, and runs the session | root, started by init or logind | built | [the issue that wires the vtium binary](https://github.com/vtium/vtium/issues/21) |
| `vtium blank`, `vtium wake` | Blank or wake a VT's displays from outside its session, by signalling the vtium on that VT | root, or the user vtium runs as | built | [the issue that blanks and wakes from outside the session](https://github.com/vtium/vtium/issues/116) |
| `vtium check-config` | Checks vtium.conf, or a file named in its place, as the console would read it at its start, and prints each problem with its line number; it changes nothing | any user | built | [config.md](../config.md) |
| `vtium console enable`, `disable`, `status`, `fallback` | Chooses which VTs run vtium from their next start, in direct mode or seat mode, recommends a mode when none is given, shows what runs on each VT, and starts a login prompt on a VT where vtium failed | root; any user for `status` | built | [Install VTium](../install.md#giving-vtium-a-vt), [Reading vtium console status](../troubleshooting.md#reading-vtium-console-status) |
| `vtium config preview` | Draws a sample of each font it names as the helper would draw it, as a picture in a terminal that shows kitty graphics and as a line of text in one that does not, and writes nothing | the user | built | [the preview issue](https://github.com/vtium/vtium/issues/120) |
| `vtium config tui`, `flow`, `install` and the other flow commands | Edit the user's draft of vtium.conf, draw it as a flow from the displays to the input devices, and install it as `/etc/vtium/vtium.conf` ([Configure vtium](../configure.md)) | the user, with sudo once for each install | built | [the configuration flow issue](https://github.com/vtium/vtium/issues/299) |
| `vtium config new-frit` | Makes a frit of the fonts it names, in order, or installs a frit written from the template it prints; alone at a terminal it opens vtium config's full-screen tool at its new-frit view | the user, with sudo once to install | built | |
| `vtium-config serve` | The helper: generates a frit's glyphs at run time in a sandbox, started on the console's first need and gone when idle | the console, never as root | built: PSF and kbd sources, and outline and color fonts | [the issue that renders glyphs in the font helper](https://github.com/vtium/vtium/issues/145), [the outline fonts issue](https://github.com/vtium/vtium/issues/23) |
| `vtium config fonts`, `check`, `remove-frit` | List every frit and built-in font with the font files each is missing, check a frit or a vtium.conf, and remove a frit that vtium.conf does not use | the user, with sudo once to remove a frit | built | [the vtium config tracker](https://github.com/vtium/vtium/issues/3) |
| `vtium config report` | Collects what a bug report needs into one document: the vtium builds and their features, the kernel, the state of each vtium console, the displays, the configuration and each console's log; it changes nothing | the user, or root to include the kernel's display state and the whole journal | built | [Collecting a report](../troubleshooting.md#collecting-a-report-and-filing-an-issue) |
| `vtium config use-frit` | Switches the running console among the frits and the built-in fonts | the user, in the session | built | [the issue that loads the configured font set](https://github.com/vtium/vtium/issues/126) |
| `vtium-image`, the image helper | Reads the files and shared memory that a program names for an image, and decodes PNG, JPEG, GIF and zlib for the console, in a sandbox; it is part of a vtium built with the `images` feature | the console starts it as the user who is logged in; when root logs in, it runs with root's user id, and vtium removes every capability first | built | [the issue for the image helper and its sandbox](https://github.com/vtium/vtium/issues/31) |
| `vtium-clipboard`, also `vticlip` | Copies to the console's selection from a script or a pipe | the user, in the session | proposed; copy decided, paste open | [the vtium-clipboard issue](https://github.com/vtium/vtium/issues/113) |
| The frits | Small text files that name a font's sources, which the helper draws from | written by root | built | [the vtium config tracker](https://github.com/vtium/vtium/issues/3), [the issue that renders glyphs in the font helper](https://github.com/vtium/vtium/issues/145) |
| The built-in fonts | Unifont, and Unscii-8 for small cells, compiled into vtium: the first frame's font and the fallback for each character a frit lacks | inside `vtium` | built: Unscii-8 for cells under 16 pixels and unifont from 16 | [the vtium config tracker](https://github.com/vtium/vtium/issues/3), [the per-character fallback issue](https://github.com/vtium/vtium/issues/141) |
| The configuration | One file, `/etc/vtium/vtium.conf`, and the command line: the settings at the file's top, and below them the sections that declare the heads, their looks and the ordered rules that place each display and input; vtium runs its compiled-in heads and rules when the file has no section and never writes the file | written by root, or installed from a user's draft by `vtium config install`, read by `vtium` | built | [config.md](../config.md), [the heads issue](https://github.com/vtium/vtium/issues/156), [the configuration flow issue](https://github.com/vtium/vtium/issues/299) |
| The unit | systemd's service for vtium on a VT, in getty's place | started by logind | built | [systemd.md](../systemd.md) |
| The terminfo entry | Tells programs in the session what vtium can do | read by the session's programs | built | [crates/vtium](https://github.com/vtium/vtium/blob/main/crates/vtium/README.md), [the issue that wires the vtium binary](https://github.com/vtium/vtium/issues/21) |

vtium is the only piece needed to use the console. vtium-config, vtium-image and vtium-clipboard are separate binaries. So the font decoders, the rasteriser, the image decoders and the configuration tool stay out of the console's binary, and none of them counts against the minspec build's budget.

## What runs as root, and what as the user

The figure shows the suite in two bands, what runs as root above and what runs as the user who logged in below. The session reaches the console only through the pty, the kernel's pair of devices that lets one program act as the terminal of another; vtium config reaches root's side once for each install, through `sudo vtium-config apply`, to install vtium.conf and frits. vtium-clipboard is drawn dashed, as proposed.

![Two bands. Above, running as root: the kernel's devices (the VT, the display, keyboards and pointers) joined to vtium, the console; vtium-config apply, under sudo, writing vtium.conf and frits into /etc/vtium, which vtium reads. Between the bands, the pty, joined to vtium by bytes both ways. Below, running as the user who logged in: vtium config use-frit, vtium-clipboard, and shell and programs, each joined to the pty; and vtium config preview, vtium config set KEY VALUE with the draft's other commands, and vtium config new-frit with its templates, the last two of which hand vtium.conf or a frit to vtium-config apply, under sudo once for each install. vtium-clipboard alone is drawn dashed, as proposed; every other piece is drawn solid, as built.](../figures/concepts-pieces.svg)

The console runs as root for its whole life. Root lets it open the VT, take the display, read the keyboards and pointers directly, and start the system's login program, which authenticates the user and starts their shell with the user's rights. The image helper decodes pictures. vtium starts it as the user who is logged in on the console. When root logs in, the image helper runs with root's user id, but vtium removes every capability first. When vtium cannot find the logged-in user, the image helper never falls back to root.

A program in the session reaches vtium only through the bytes it writes to its terminal. vtium's replies to those bytes are built from its own state and never echo what a program sent, so text a program prints cannot type into another program reading the replies ([architecture.md](../architecture.md#determinism), "No reflection").

Only root writes frits, so the configuration and OSC 50 name only fonts root chose. Everything before that runs as the user: previews, choosing fonts for a new frit, and the template. The helper that draws a frit's glyphs never runs as root, and the console trusts its glyphs only to be well-formed. Switching among frits and copying to the clipboard run in the session and speak to vtium through the terminal like any other program.
